# 第 28 课：模块综合——把批次拆成一份能重复构建的工程

这一课不教新语法。它教的是怎么把上一课那些零件**装成一个工程**：主程序管流程和计数，过账和报告各拆成独立子程序，三边的接口全部来自 Copybook，再配一个 `build.sh` 把语法检查、分别编译、链接、运行和清理固定成四个动作。做到的效果就一句话：谁都不用记编译顺序，改了共享声明就整体重编。

## 业务现场

周四下午四点，组长走过来：清算那边要往账户记录里加个字段，今晚就要上，下游报告等着用。

你打开工程一看，记录定义不在主程序里，在一个 `.CPY` 文件里——心里一松，"改一处就行"。

可这份声明不止你一个人在用。主程序用它，过账模块用它，报告模块也用它。你要是图快，只把主程序重新编译一遍，链接的时候把上次留下的 `post_transaction_28.o`、`report_account_28.o` 又拼了上去，那两个老目标文件里，余额还在**老的字节偏移**上。链接器不会拦你，它只管名字和调用形状对不对，不管"两边对同一块内存的理解是不是同一份"。程序照样跑，退出码照样 `0`，账已经错了。

这一课要治的就是这种病。它最难缠的地方是**不报错**：没有编译错误，没有文件状态码，账户报告上的数字看起来还挺正常。等有人发现余额对不上，你手里只剩一个可执行文件——它是拿哪几个目标文件、按什么顺序拼出来的？没人记编译顺序，这个问题当晚就答不上来。

（教学演示：这里的角色、时间、金额都是把问题说清楚用的，不是哪家真实机构的真实数据。）

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 人话版：把一个"什么都干"的大程序切成三块——主程序管流程和计数，过账子程序管业务规则，报告子程序只管把结果读出来显示；三块之间不再靠"我们商量好按这个顺序传参"，而是把字段声明写进 Copybook，大家 `COPY` 同一份。再给这个工程配一个入口脚本，把编译和运行固定成四个命令。术语上，这就是"主程序 + 被调用子程序 + 共享 Copybook"的模块化工程；编译上则是每个模块各出一个目标文件，只让主程序带 `-x` 生成可执行文件。

**它在业务里解决什么问题。**

- **接口只有一份定义。** 字段宽度和顺序改一处，三个模块看的是同一份声明。真正省下的不是打字时间，而是"改完忘了通知谁"这类事故。
- **顺序写进脚本，不靠记性。** 新同事、半夜被叫起来的值班的人、三个月后的你自己，跑的都是同一条命令。有一条固定入口，才有"这次跑的和上次跑的是同一套东西"这句话。
- **职责划得清。** 余额只有过账模块能改，计数只有主程序能改，报告模块只读。出事时先看"谁负责哪块"，比在几百行里翻要快得多。

**什么时候不该这么拆、拆错会怎样。**

- 逻辑还没定型就急着拆模块，等于把还在变的规则冻进接口，之后每动一次都得全量重编，反而更慢。第 01–22 课的单文件程序，就是不拆的正确样子。
- 别指望编译器替你兜底。同名的字段、参数个数这类明显不一致有可能在编译或链接时报出来；但**宽度变了、只重编了一个模块**这种事，`cobc` 不检查，它只会算错——所以真正的护栏是"唯一接口定义 + 每次都全量重编"。
- 把 `build.sh` 当成"生产构建系统"是误会。它不锁编译器版本，不记 ABI，不产生产物版本号，也不做增量构建或依赖图推导。上生产要另外补（见文末"这份代码进了生产会怎样"）。

## 为什么现在学

`CALL` 你在第 24 课学过，`USING` 的参数方向在第 25 课，共享声明在第 23 课，业务拒绝和系统故障要分开报在第 26 课，批次要留日志在第 27 课。这些你都会了。

那这一课还缺什么？缺的不是语法，是**把它们组织起来的那套秩序**。第 23–27 课里，Copybook、子程序、日志都在单文件程序或最小脚本里演示，你怎么编都行，编错了当场就报。真实工程不给你这种待遇：

- 模块有三个甚至更多，"先编哪个、后编哪个"必须写下来；
- 接口是共享的，改一处会影响所有消费者，"改了要不要全量重编"必须有一个不用问就懂的答案；
- 跑之前要过一遍语法检查，跑完要能把产物一次清干净——否则目录里堆的全是上次的半成品，下次谁也不敢确定跑的是哪一份。

你可能会想，这不过是写个 shell 脚本而已。对，但它承载的是一条纪律：**一个固定入口，一份接口定义，一条可重复的构建路径。**

## 本课完成后的能力与边界

学完本课后，你可以：

- 把共享记录与状态放进 Copybook，供主程序和子程序以同一份声明编译。
- 把批次控制、过账规则与报告拆成三个程序单元，并说明各自拥有什么状态。
- 用 `CALL ... USING BY REFERENCE` 传递可更新记录，说明状态字段由谁写入、计数由谁维护。
- 用 `build.sh check|build|run|clean` 完成语法检查、模块编译、链接、运行与清理。
- 用 `expected-output.txt` 与 `expected-batch.log` 逐行核对标准输出与日志。

边界：样例交易固定写在主程序里，不读外部输入文件；构建脚本是本地单机脚本，不固定编译器版本、ABI 或产物版本。文件输入见第 15–22 课，日志与错误分类见第 26、27 课，数据库批次见第 29–32 课。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端 + `bash`；`build.sh` 需要 PATH 里有 `cobc`（可用 `COBC` 环境变量指定其他编译器命令）。
- 构建目录默认是课内 `build/`（可用 `BUILD_DIR` 覆盖）；`build/` 已被仓库忽略，`./build.sh clean` 即可清除。程序在构建目录里运行，`batch.log` 与目标文件都落在那里。

## 这个工程长什么样

| 文件 | 职责 |
|---|---|
| [`lesson.cob`](./lesson.cob) | 主程序：开日志、初始化账户、准备五笔样例交易、`CALL` 过账模块、汇总状态并写日志 |
| [`post_transaction_28.cob`](./post_transaction_28.cob) | 过账模块 `POST-TRANSACTION28`：按账户号与类型校验，成功时更新调用方余额，用状态字段返回结果 |
| [`report_account_28.cob`](./report_account_28.cob) | 报告模块 `REPORT-ACCOUNT28`：读取最终账户与批次计数并显示 |
| `copybooks/ACCOUNT-REC.CPY` | 账户记录：账户号 `X(10)`、客户号 `X(8)`、余额 `9(7)V99`（共 27 字节） |
| `copybooks/TRANSACTION-REC.CPY` | 交易记录：账户号 `X(10)`、类型 `X`、金额 `9(7)V99`（共 20 字节） |
| `copybooks/POST-STATUS.CPY` | 过账结果状态 `X(12)`：`POSTED`、`INSUFFICIENT`、`BAD_TYPE`、`NO_ACCOUNT` |
| `copybooks/BATCH-COUNTS.CPY` | 批次计数：`POSTED-COUNT`、`REJECTED-COUNT`（各 `9(3)`） |
| [`build.sh`](./build.sh) | 构建与运行入口（`check` / `build` / `run` / `clean`） |

接口全在 `copybooks/` 里，三个程序各 `COPY` 自己需要的那几份。为什么拆成四个而不是堆成一个大 Copybook？因为每份只描述**一个**接口的形状：账户记录、交易记录、过账状态、批次计数。谁需要哪份就 `COPY` 哪份，改动的影响面一眼能数出来。

- 账户记录宽 27 字节 = `X(10)` + `X(8)` + `9(7)V99`；主程序、过账模块、报告模块都用它。
- 交易记录宽 20 字节 = `X(10)` + `X(1)` + `9(7)V99`；主程序与过账模块用。
- 状态 `X(12)` 刚好放得下最长的 `INSUFFICIENT`；主程序与过账模块用。
- 计数是两个 `9(3)`，所以显示成 `002`、`003`；主程序与报告模块用。

`9(7)V99` 里的 `V` 是**隐含小数点**，不占字节，所以 27 和 20 这两个宽度里都只算九位数字。金额一律以这种十进制字段的契约传递，不掺 `BINARY-LONG` 之类的平台二进制布局——"余额"在每个模块眼里永远是同一串十进制字符。

## `build.sh` 的四个动作

```sh
./build.sh check    # 组合语法检查，不生成任何产物
./build.sh build    # 编译两个子程序为 .o，再链接出 build/lesson_28
./build.sh run      # 构建后在 build/ 里运行，输出与 batch.log 都落在 build/
echo $?             # 查看退出码
./build.sh clean    # 删除 build/（可执行文件、目标文件与日志）
```

一条条说清楚：

- **`check`** 调 `cobc -I copybooks -fsyntax-only`，把三个源文件一起过一遍语法。它不产出任何文件，只回答"能不能解析"。
- **`build`** 先做一遍 `check`，然后分别把两个子程序编成 `.o`，最后用 `-x` 把主程序和两个 `.o` 链成 `build/lesson_28`。
- **`run`** 先 `build`，再切进 `build/` 里跑可执行文件。`batch.log` 用的是相对文件名，所以落在**运行时的当前目录**，即 `build/`。
- **`clean`** 就是 `rm -rf build`，可执行文件、两个 `.o`、日志一次清干净。

几个不写出来就会踩的地方：

- `build` 每次都从头编三个源文件。这才是这道护栏的价值所在——只要你走脚本，就不会出现"新主程序 + 昨天老 `.o`"这种拼装。
- 写错动作名（比如 `./build.sh unknown`），脚本打印用法并返回 `64`。
- `cobc` 不在 PATH 里，或者 `COBC` 指了一个不存在的命令，返回 `127`。

## 五笔交易怎么走完一遍

账户起始余额 `1000.00`，五笔样例依次为：存款 `125.50`、取款 `25.25`、超余额取款 `2000.00`、未知类型 `X`、不存在账户 `A000000099` 的存款。只有前两笔成功：

| 序 | 类型 | 金额 | 结果状态 | 原因 |
|---:|---|---:|---|---|
| 1 | `D` | 125.50 | `POSTED` | 存款成功 |
| 2 | `C` | 25.25 | `POSTED` | 余额足够 |
| 3 | `C` | 2000.00 | `INSUFFICIENT` | 超过当前余额，余额不变 |
| 4 | `X` | 1.00 | `BAD_TYPE` | 类型不在 `D`/`C` 之内 |
| 5 | `D` | 1.00 | `NO_ACCOUNT` | 账户号与主记录不匹配 |

计数不变量：`記帳 + 拒否 = 5`，本课为 `2 + 3 = 5`。余额也能手算：`1000.00 + 125.50 − 25.25 = 1100.25`。

再说一遍这三个拒绝码的**性质**，因为它们特别容易被当成"程序坏了"：`INSUFFICIENT`、`BAD_TYPE`、`NO_ACCOUNT` 都是**业务结果**，不是构建或文件系统故障。超额取款返回 `INSUFFICIENT` 且不动余额，未知类型返回 `BAD_TYPE`，账户号对不上返回 `NO_ACCOUNT`——批次照常收尾，退出码仍是 `0`。

## 源码阅读路径

按"数据怎么流、状态谁改"的顺序读，比从上往下逐行看快得多：

1. `0000-MAIN`（[`lesson.cob`](./lesson.cob#L31) 第 31–53 行）：先开日志。只有日志打开成功、且没出 I/O 故障，才 `INITIALIZE` 账户与计数、跑五笔交易；跑完 `CALL "REPORT-ACCOUNT28"`；最后写 `BATCH_END`、关日志。`WS-IO-ERROR` 或 `WS-UNKNOWN-STATUS` 为 `Y` 时，把 `RETURN-CODE` 设成 `1`。
2. `1000-INITIALIZE-BATCH`（第 54–58 行）：账户 `A000000001`、客户 `C0001001`、余额 `1000.00`。这是本课唯一的"数据来源"——样例都写死在这里和 1100–1500 那五个装填段落里。
3. `2000-CALL-POSTER`（第 84–98 行）：每笔交易的公共出口。注意它先把 `WS-POST-STATUS` 清成空格——不清的话，上一笔的状态会残留在 `X(12)` 里。然后 `CALL "POST-TRANSACTION28" USING BY REFERENCE` 三样东西：账户记录、交易记录、状态。
4. `2100-REPORT-RESULT`（第 99–114 行）：`EVALUATE` 按状态分流计数，`POSTED` 加 `記帳`，三个拒绝码加 `拒否`，`WHEN OTHER` 记未知状态并让退出码非零。显示时用 `FUNCTION TRIM(... TRAILING)` 去掉 `X(12)` 的尾部空格——不然你看到的会是 `POSTED` 后面拖一串空白。
5. [`post_transaction_28.cob`](./post_transaction_28.cob#L15)（第 15–38 行）：先比账户号，不等就是 `NO_ACCOUNT`；相等再看类型，`D` 加余额、`C` 走余额检查、其它 `BAD_TYPE`。**余额只有这里能改**，计数和日志它碰都不碰。
6. [`report_account_28.cob`](./report_account_28.cob#L13)（第 13–20 行）：只读账户和计数，显示两行。这就是"只读消费者"该有的样子。
7. `1050-RUN-TRANSACTIONS`（第 115–128 行）：五笔依次跑，每笔之前先看 `WS-IO-ERROR`——日志写失败就停手，后面的交易不再过账。

## 运行与观察

**输入：** 无外部输入。五笔样例在主程序里固定写出。

**命令及作用：** 就是上一节的四个动作，这里只重复两条容易忽略的——`check` 不产生任何产物，`run` 会先重新构建再运行。

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `./build.sh check` 退出码 | `0`，无诊断 |
| `./build.sh build` 退出码 | `0`，无编译警告 |
| `./build.sh run` 退出码 | `0` |
| 标准输出 | 12 行，与 [`expected-output.txt`](./expected-output.txt) 逐行一致 |
| `build/batch.log` | 7 行，与 [`expected-batch.log`](./expected-batch.log) 逐行一致 |
| 生成文件 | `build/lesson_28`、两个 `.o`、`build/batch.log` |

```text
呼出=過帳 口座=A000000001 TYPE=D 金額=0000125.50
呼出=戻り 状態=POSTED
呼出=過帳 口座=A000000001 TYPE=C 金額=0000025.25
呼出=戻り 状態=POSTED
呼出=過帳 口座=A000000001 TYPE=C 金額=0002000.00
呼出=戻り 状態=INSUFFICIENT
呼出=過帳 口座=A000000001 TYPE=X 金額=0000001.00
呼出=戻り 状態=BAD_TYPE
呼出=過帳 口座=A000000099 TYPE=D 金額=0000001.00
呼出=戻り 状態=NO_ACCOUNT
口座=A000000001 CUSTOMER=C0001001 BALANCE=0001100.25
集計 記帳=002 拒否=003
```

**输出对照（实际标签 → 含义）：** `呼出=過帳` = 发出过账调用（`口座` 账户号、`TYPE` 类型、`金額` 金额）；`呼出=戻り 状態` = 调用返回状态；`口座`/`CUSTOMER`/`BALANCE` = 最终账户报告；`集計 記帳=.. 拒否=..` = 过账/拒绝计数汇总。

**`build/batch.log`：**

```text
EVENT=BATCH_START ID=TRAINING-001
EVENT=TRANSACTION NO=001 ACCOUNT=A000000001 TYPE=D STATUS=POSTED
EVENT=TRANSACTION NO=002 ACCOUNT=A000000001 TYPE=C STATUS=POSTED
EVENT=TRANSACTION NO=003 ACCOUNT=A000000001 TYPE=C STATUS=INSUFFICIENT
EVENT=TRANSACTION NO=004 ACCOUNT=A000000001 TYPE=X STATUS=BAD_TYPE
EVENT=TRANSACTION NO=005 ACCOUNT=A000000099 TYPE=D STATUS=NO_ACCOUNT
EVENT=BATCH_END POSTED=002 REJECTED=003 IO_ERROR=N
```

标准输出和日志各数一遍：屏幕上 5 笔 × 2 行 + 账户报告 1 行 + 计数 1 行 = 12 行；日志是 `BATCH_START` + 5 条交易 + `BATCH_END` = 7 行。日志里 `NO=003` 那条的状态和屏幕上第四行 `呼出=戻り` 的 `INSUFFICIENT` 必须一致——两边对不上，说明计数或日志不是从同一个状态值来的，那就是 bug。

| 场景 | 从何种干净状态开始 | 预期 | 实际命令与观察 | 结论 |
|---|---|---|---|---|
| 正常路径 | `./build.sh clean` 后没有 `build/` | 三步退出码均 `0`；stdout 12 行；日志 7 行 | `./build.sh check`、`build`、`run`，再 `diff` 两个 expected 文件 | 均无差异，吻合 |
| 参数错误 | 无 | 返回 `64` 并打印用法 | `./build.sh unknown` | 吻合 |
| 编译器命令缺失 | 无 | 返回 `127` | `COBC=no-such-cobc-xyz ./build.sh check` | 吻合 |
| 日志打不开 | 在 `build/` 里把 `batch.log` 建成目录再运行 | 退出码 `1`，不调用过账模块 | 标准输出只有一行 `エラー=ログOPEN 状態=37` | 吻合 |
| 练习一 | 原始源码，`1300-POST-OVERDRAFT` 的 `2000.00` 改成 `1000.00` | 余额 `0000100.25`，`記帳=003 拒否=002` | `./build.sh run`，并看日志里 `NO=003` 变为 `POSTED` | 吻合 |
| 练习二 | 原始源码，`1400-POST-UNKNOWN-TYPE` 的 `"X"` 改成 `"D"` | 余额 `0001101.25`，`記帳=003 拒否=002` | `./build.sh run`，并看日志 `NO=004 ... TYPE=D STATUS=POSTED` | 吻合 |

**未验证项（照旧写明，不作为结论）：**

- **标准错误上那行 `Warning: program compiled against libxml 212 using older 209`。** 这是运行环境的链接库版本警告，不是本程序的业务输出。为什么没验证：产生它的组件还没定位，本课核对结果也用不到它；真正的输出在标准输出，退出码 `0`。
- **日志 WRITE / CLOSE 失败的行为只有源码依据，没有跑出来过。** 要稳定注入"日志写到一半失败"需要构造一个能接受 `OPEN` 但拒绝 `WRITE` 的目标，本课没有这样的夹具，所以只能按代码说明。
- **过账模块返回未知状态的分支在样例里不可达。** 状态只由子程序写四个字面量之一，没有外部输入能制造第五种，所以"未知状态记为拒绝并令退出码非零"这段同样只是源码依据。
- **"改了 Copybook 只重编主程序会算错账"是风险说明，不是本课的实测结果。** 本课脚本每次全量重编，没有做"故意保留旧 `.o` 再手编主程序"的对照实验；这条留作生产事故的教训来理解。

## 构建错误与日志错误

- 日志无法打开时，主程序报告 `エラー=ログOPEN 状態=37`，退出码 `1`，**不会调用过账子程序**（已实测）。
- 日志 WRITE 或 CLOSE 失败时，代码同样设置系统错误并返回 `1`（按代码，未注入）。
- `BATCH_END` 在关闭日志**之前**写出，所以若日志 CLOSE 随后失败，最后一条日志仍可能写着 `IO_ERROR=N`；此时以标准输出与退出码为准（按代码）。
- 日志自身的 OPEN 失败写不进日志，只能靠标准输出和退出码报告——这是日志系统的固有边界，不是实现缺陷（已实测）。
- 过账模块返回未知状态时，主程序记为拒绝并令退出码非零（按代码，样例中不可达）。

## 修改练习

两项都从原始源码开始，用 `./build.sh run` 重跑，让子程序重新编译并重新链接：

1. 把 `1300-POST-OVERDRAFT` 的金额从 `2000.00` 改为 `1000.00`：这笔取款会成功，余额变成 `0000100.25`，计数变成 `記帳=003 拒否=002`，日志里 `NO=003` 的状态从 `INSUFFICIENT` 变成 `POSTED`。
2. 把 `1400-POST-UNKNOWN-TYPE` 的类型从 `"X"` 改为 `"D"`：未知类型拒绝变成有效存款，余额变成 `0001101.25`，计数同样是 `記帳=003 拒否=002`，日志里 `NO=004` 那条的类型与状态变为 `TYPE=D STATUS=POSTED`。

两项都改了源码、跑了脚本，所以正好能自己体会一次"全量重编"的作用：要是漏了这一步，你改的源码和跑的可执行文件就对不上了。完整题目与预期见 [`exercise.md`](./exercise.md)，参考答案见 [`answer.md`](./answer.md)。

## 举一反三练习

把样例交易改为文件输入，并把"读取 / EOF / 坏记录分类"放进一个独立模块；保持账户、交易与状态 Copybook 是唯一接口定义。说明 Copybook 改动后如何保证所有受影响的模块都被重新编译和链接。不要把业务拒绝伪装成编译失败，也不要重复定义 Copybook 里已有的记录布局。题目见 [`exercise.md`](./exercise.md)，本题不提供答案。

## 走一遍真实流程

把这一课放进一整条夜间链路，它站在"零件"和"项目"中间：

1. **上游是文件批次。** 交易数据怎么从文件里读进来、怎么处理 EOF 和坏记录，是第 [15](../15_sequential-file-read/README.md) 到 [22](../22_file-processing-practice/README.md) 课的事。本课的样例还在程序里写死，把它换成文件输入正是上面的举一反三题。
2. **本课交付的是一个工程，不是一段逻辑。** 产物有三样：能编译的三个模块、一份共享接口定义、一条固定的构建命令。下一课（[第 29 课](../29_embedded-sql/README.md)）要在 `lesson.cob` 这个位置接入数据库快照，它依赖的正是这里定下来的模块边界和 Copybook 契约。
3. **日志交给值班和对账。** `batch.log` 的格式与事件分类是[第 27 课](../27_logging/README.md)定的；本课把每笔交易的状态和批次计数写进同一份契约，第二天有人拿它跟上游报的笔数对账。
4. **接口的账要一直记着。** 主程序和两个子程序之间的参数顺序、方向、状态取值，是第 [23](../23_copybooks/README.md)–[25](../25_using-parameters/README.md) 课一步步做出来的。本课把它们装进工程之后，任何一次接口改动都要重跑 `check` 和 `build`，而不是"改完源码 git 一提交就完了"。
5. **再往后**，[第 29–31 课](../29_embedded-sql/README.md)把真 SQL、游标和文件/数据库同步接进来，[第 32 课](../32_bank-reconciliation-project/README.md)把整条链收成一个完整项目。

一句话：这一课不是加功能，是给前面所有零件定下**从哪里进来、怎么拼、怎么重来**。

## 这份代码进了生产会怎样

- **谁调度它**：夜间调度器只认构建产物的路径和退出码，不看你的屏幕。`build.sh` 是给人和 CI 用的——调度器跑的是它编出来的 `lesson_28`。
- **谁看它的输出和日志**：值班先看退出码，再看 `batch.log` 末尾那行 `EVENT=BATCH_END POSTED=.. REJECTED=.. IO_ERROR=..`。记住 `IO_ERROR=N` 不等于一切正常，上面"日志错误"里那条 CLOSE 失败就是反例。
- **出事谁被叫起来**：退出码非 `0` 的时候。第一件事是分清"业务拒绝"（记为拒否、退出码仍 `0`）和"系统故障"（日志开不了、写失败、出现未知状态码）——这两类混在一起，半夜就会为一个客户余额不足把人叫起来。
- **下一个系统怎么接**：本课没有输出文件，结果只在屏幕和日志里。真实链路要把过账结果写出去（[第 16 课](../16_file-writing/README.md)、[第 22 课](../22_file-processing-practice/README.md)）或写进数据库（[第 29 课](../29_embedded-sql/README.md)起）。
- **第一个月最容易出的事故**：就是开头那段——改了共享声明只重编主程序，于是老 `.o` 还在用老布局，账悄悄错掉。第二类是把"本地能编过"当成"这套构建能上生产"。
- **它还没做的事**：产物没有版本号，不锁编译器版本与选项，不含增量构建和依赖图；日志没有时间戳和唯一运行标识；没有重跑幂等；样例交易写死在程序里。

生产构建还要另外约定：固定编译器版本和编译选项、维护模块清单、给产物打版本和发布路径、在 CI 里跑同一套 `check`/`build`。本课只演示"本地可重复构建"这一件事，其余一项都没实现。数据库批次的构建与工具链见第 29–32 课。
