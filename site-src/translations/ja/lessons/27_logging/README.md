# 第 27 課：ログシステム——夜に何が起きたか、朝まで残るファイルに書く

夜間バッチの画面出力は翌日には残りません。本課では第 26 課の検証処理に独立した `batch.log` を加えます。バッチ開始、レコードの読み込み、業務拒否、システム障害、バッチ終了を、固定された `KEY=VALUE` 形式で 1 行ずつ記録します。翌日、当直担当者はこのファイルだけを見て「最後まで走ったか、どのレコードで問題が起きたか、再実行すべきか」に答えられます。

## 業務の現場

水曜日の午前 2 時 40 分、当直用の携帯電話が鳴ります。夜間の日次検証ジョブは終了コード `1` で終わりました。しかし画面はもうありません。ジョブとともに端末ウィンドウが閉じ、前夜に表示された行は朝には一つも残っていません。

最初に必要なのは「コードのどこが悪いか」ではなく、もっと実務的な 3 つの問いです。**バッチは最後まで終わったか。どのレコードに問題があったか。再実行する価値があるか。** プログラムが画面に表示するだけなら、入力全体をもう一度渡して画面を見ながら再実行するしかありません。しかし再実行は前の結果ファイルを上書きします。つまり、自分で現場の証拠を消すことになります。午前 3 時にこうして判断すれば、間違えるのはほぼ避けられません。

だから実際のジョブは、画面とは別に**独立したログファイル**を開きます。ログは、バッチが始まったこと（`BATCH_START`）、何番目のレコードを読んだか（`RECORD_READ NO=004 ACCOUNT=A00004`）、どのレコードが業務上拒否され、その理由は何か（`BUSINESS_REJECT ... REASON=BAD_AMOUNT`）、システム障害があったか（`SYSTEM_ERROR`）、受理・拒否件数はいくつか（`BATCH_END INPUT=005 ACCEPTED=002 REJECTED=003`）に答える必要があります。当直担当者はコードを読むのではなく、この数行を見ます。

ここでもう一つ、少し扱いにくい点を明確にしておきます。ログ自体もファイルなので、開き、書き、閉じる必要があります。**ログが壊れたら、自分自身のファイルにその障害を記録できません。** 循環論法のようですが、これは現実です。下の「ログ形式とライフサイクル」で、この境界がどこにあるかを具体的に見ます。

（教育用のシナリオです。機関、時刻、件数は問題を説明するためのもので、実在する機関の実データではありません。）

## なぜ今これを学ぶか

第 26 課では「業務拒否」と「システム障害」を区別できるようになりました。不正レコードは `rejected.txt` に振り分け、本当の I/O 障害が起きたら処理を止めてゼロ以外のコードを返します。分類は正しくなりましたが、その痕跡が残るのは画面と 2 つの結果ファイルだけです。

それだけでは知りたいことに答えきれません。`rejected.txt` にあるのは口座番号と理由（`A00002|BAD_AMOUNT`）だけで、**レコード番号がありません**。入力の何行目か分かりません。2 つの結果ファイルには**バッチの開始・終了境界がありません**。今回の実行が正常に終わったのか、途中で止まったのか分かりません。システム障害については記録が 1 文字も残りません。画面はさらに短命で、夜を越せません。

「出力をファイルにリダイレクトしてログにすればよいのでは」と思うかもしれません。文字は残せますが、残るのは人が読む文章です。たとえば `拒否口座=A00002 REASON=BAD_AMOUNT`。項目の区切りは空白で、レコード番号もありません。ログにはもう一つ、**機械が読む**用途があります。スケジューラーや当直用スクリプトは、文章のどこに数字があるか正規表現で推測せず、`REJECTED=003` を直接取り出せる必要があります。そのため形式を先に決めます。1 行に 1 イベント、`KEY=VALUE`、フィールド順は固定です。

もう一つ、覚えておくべき違いがあります。結果ファイルは**納品物**、ログは**処理記録**です。`accepted.txt` は後続の計上処理へ渡すもの、`batch.log` は人やスケジューラーが調べるために残すものです。互いの代わりにはなりません。

## この知識項目とは何か、何を解決するか

**この知識項目とは何か。** プログラムに「記録する」経路を一つ加えます。バッチの開始、レコードの読み込み、業務拒否、システム障害、バッチの終了を、独立した**別ファイル**へ固定 `KEY=VALUE` 形式で 1 行ずつ書き込みます。使うものはこれまでと同じ `SELECT` + `OPEN OUTPUT` + `WRITE` です。ただし、今回は業務データではなく「夜に何が起きたか」を書きます。

**業務上、何を解決するか。** メモリや画面にあった事実を、機械も読める形でディスクに残します。具体的には、最後まで走ったか（`BATCH_END` の入力・受理・拒否件数）、どのレコードに問題があったか（`NO=` レコード番号 + `ACCOUNT=` 口座番号 + `REASON=` 理由）、再実行すべきか（`SYSTEM_ERROR` フラグ）を確認できます。

ここで知っておくべき副作用があります。**ログもファイルです。** 独自の OPEN/WRITE/CLOSE 状態があり、開けない、書けない、閉じられないことがあります。ログは**自分の障害を自分の中に記録できません**。その 3 種の障害は画面と終了コードだけに記録されます。これは説明不足ではなく、ログシステム固有の境界です。どの時点で起きるかは下の「ログ形式とライフサイクル」を参照してください。

**いつ使わないか、誤用するとどうなるか。** ログの業務上の誤用は、構文間違いより高くつきます。

- **ログを結果ファイルとして扱う。** 後続処理に必要なのは `accepted.txt` の受理明細であり、ログは納品物ではありません。逆にログの内容を業務データの照合に使うと、「処理」と「成果物」を混同します。
- **本番ログの機能まで備わっていると思い込む。** バッチ ID は `TRAINING-001` の固定値で、時刻や実行 ID はなく、マスキング、保存期間、アクセス制御もありません。2 日分のログを並べても、ファイルだけではどの実行か分かりません。説明責任の証拠として使うなら、まずこれらを追加する必要があります。
- **`BATCH_END` があれば問題ないと思い込む。** `BATCH_END` はログを閉じる**前**に書かれます。そこに記録があるからといって、ログが正常に閉じたことや、ログと結果ファイルが原子的に納品されたことは証明されません。再実行時の `OPEN OUTPUT` は、前回の記録全体を上書きします。

## 本課修了時の能力と限界

本課を修了すると、次のことができます。

- バッチ開始、レコード読み込み、業務拒否、システム障害、バッチ終了を独立したログファイルに書く。
- レコード番号、口座番号、拒否理由を使って入力レコードを特定する。
- 業務イベントとファイル I/O 障害をそれぞれ `BUSINESS_REJECT` と `SYSTEM_ERROR` として記録する。
- ログ自身の OPEN/WRITE/CLOSE 状態を確認し、なぜログに自分の障害を記録できないか説明する。
- ログ末尾の件数を標準出力と結果ファイルに照合し、バッチが完全に終了したか判断する。

限界：ログは教育用の固定 `KEY=VALUE` 形式で、バッチ ID も `TRAINING-001` 固定です。タイムスタンプ、実行 ID、環境、入力署名、担当者の情報はなく、マスキング、保存期間、アクセス制御もありません。ログと結果ファイルの間に**原子的な引き渡し**の保証はなく、再実行も実装しません。

## 実行環境

- GnuCOBOL 3.2.0、デフォルト方言（`-std=cobol85` は付けない）。ソースは固定形式です。
- Linux 端末。データベースや追加ツールは不要です。
- `SELECT` は相対ファイル名を使います。プログラムはカレントディレクトリで 4 ファイルを読み書きします。`transactions.txt` を読み、`accepted.txt`、`rejected.txt`、`batch.log` を書きます。
- 3 つの出力はすべて `OPEN OUTPUT` で開くため、実行ごとに同名の既存ファイルを上書きします。本課では入力を `build/` にコピーしてそこで実行し、出力もそこへ置きます。`build/` はリポジトリで無視されているので、最後に `rm -rf build` でまとめて削除できます。

## ログ形式とライフサイクル

ログは行ごとの `KEY=VALUE` テキストで、1 行に 1 イベントです。正常な実行では次の順で記録します。

| イベント | 記録するタイミング | 主な項目 |
|---|---|---|
| `EVENT=BATCH_START` | ログを正常に開いた後、業務ファイルを開く前 | `ID=TRAINING-001` |
| `EVENT=RECORD_READ` | 入力レコードの読み込み成功後 | `NO=` は `001` から始まるレコード番号、`ACCOUNT=` は口座番号 |
| `EVENT=RECORD_ACCEPTED` | 受理レコードの WRITE 成功後 | `NO=`、`ACCOUNT=` |
| `EVENT=BUSINESS_REJECT` | 拒否レコードの WRITE 成功後 | `NO=`、`ACCOUNT=`、`REASON=` |
| `EVENT=SYSTEM_ERROR` | 入力または業務出力のファイル操作失敗時（ログに書ける場合） | `OP=`、`STATUS=` |
| `EVENT=BATCH_END` | データファイルを閉じた後、ログを閉じる前 | `INPUT=`、`ACCEPTED=`、`REJECTED=`、`SYSTEM_ERROR=` |

順序設計で覚えておく点があります。**業務入力を読む前にログを開きます。** ログを開けなければバッチは始まりません。これなら「業務データは変更されたのにログには記録されていない」という状況を避けられます。

各行は `STRING ... DELIMITED BY SIZE` で組み立てます。前の長いイベントの末尾が残らないよう、組み立て前に `WS-LOG-MESSAGE` を空にします（`WS-LOG-MESSAGE` は `PIC X(100)` で、本課の最長イベント 66 文字を格納できます）。

**ログに自分の障害を記録できない**箇所は 3 つです。

- **OPEN 失敗：** 最初の行さえ書けないので、標準出力と終了コードで報告するしかありません。本課では `batch.log` をディレクトリにしてこの経路を実測しました（下の失敗経路を参照）。
- **WRITE 失敗：** 後続処理を止め、ログへの追記を再試行しません。標準出力と終了コードで報告するしかありません。**本課ではこの経路を注入していません。** 動作はソースコード上の根拠だけです（「証拠の出典と検証範囲」を参照）。
- **CLOSE 失敗：** `BATCH_END` の後に発生し、標準出力とプロセス状態でしか報告できません。こちらも**注入していません**。

## 業務イベントとシステムイベント

| 種別 | 典型例 | 結果ファイル | ログイベント | 終了コード |
|---|---|---|---|---|
| 業務拒否 | 幅不正（`BAD_WIDTH`）、金額が数字でない（`BAD_AMOUNT`）、金額 0（`ZERO_AMOUNT`） | `rejected.txt` へ書く | `BUSINESS_REJECT` | `0` |
| システム障害 | 入力・出力・ログの OPEN、READ、WRITE、CLOSE 失敗 | 完全性は保証されない | `SYSTEM_ERROR`（ログに書ける場合） | `1` |

業務拒否は「処理完了」の結果です。バッチは通常どおり終了し、`0` を返します。システム障害は後続の読み込みを止めて `1` を返します。ファイルイベントを成功件数に数えるのは、対応する WRITE 状態が `00` のときだけです。これにより、ログの `ACCEPTED`/`REJECTED` 件数が結果ファイルの実際の行数と一致します。

## 件数の不変条件と照合できる結果

| 不変条件 | 本課での値 | 意味 |
|---|---|---|
| `INPUT = ACCEPTED + REJECTED` | `005 = 002 + 003` | 読み込んだレコードすべてに行き先が 1 つある |
| `ACCEPTED` = `accepted.txt` の行数 | `002` = 2 行 | ログの件数が実際の出力と一致 |
| `REJECTED` = `rejected.txt` の行数 | `003` = 3 行 | 拒否についても同じ |

標準出力、ログ、結果ファイルの 3 つが一致して初めて、処理全体に矛盾がないと判断できます。

## 実行と観察

**入力：** 本課ディレクトリの `transactions.txt`（口座番号|セント単位の金額を 1 行に 1 件、計 5 行）。`build/` にコピーしてそこでプログラムを実行し、3 ファイルを書き出します。

```sh
(cd build && ./lesson_27)                        # 在 build/ 里运行，输出落在那里

diff build/batch.log expected-batch.log          # 与预期日志逐行比对

```

**出力ラベルの対訳（実際のラベル → 意味）：** `受理口座` は受理した口座、`拒否口座` は拒否した口座で、`REASON=` は理由（`BAD_WIDTH`/`BAD_AMOUNT`/`ZERO_AMOUNT`）です。`集計 入力/受理/拒否` は入力・受理・拒否の件数、`システムエラー` はシステム障害フラグ（`N` はなし、`Y` はあり）です。ログのイベント名と項目名は英語のインターフェース識別子です。`EVENT=BATCH_START`/`RECORD_READ`/`RECORD_ACCEPTED`/`BUSINESS_REJECT`/`SYSTEM_ERROR`/`BATCH_END`、および `ID`/`NO`/`ACCOUNT`/`REASON`/`OP`/`STATUS`/`INPUT`/`ACCEPTED`/`REJECTED`/`SYSTEM_ERROR` の意味は上のイベント表を参照してください。

**失敗経路（どちらも実測済み）：**

- **入力ファイル欠落：** `build/` から `transactions.txt` を削除して実行します。標準出力は `エラー=OPEN_INPUT STATUS=35` から始まり、`集計` はすべて `000`、`システムエラー=Y`、終了コードは `1` です。ログには `BATCH_START`、`SYSTEM_ERROR OP=OPEN_INPUT STATUS=35`、`BATCH_END ... SYSTEM_ERROR=Y` の 3 行が残ります。入力を一度も正常に開けなかったので `INPUT=000` です。`BATCH_END` の `SYSTEM_ERROR=Y` が「レコードがない」を「空バッチが成功した」と誤読するのを防ぎます。
- **ログを開けない：** `build/` の `batch.log` をディレクトリにして実行します。標準出力は `エラー=ログOPEN 状態=37` / `集計 入力=000 受理=000 拒否=000` / `システムエラー=Y`、終了コードは `1` です。業務ファイルは**一度も開きません**。ログを開始できなければ、その夜の処理は始まりません。

**証拠の出典と検証範囲：** 上記 3 経路はすべて、このワークスペースで GnuCOBOL 3.2.0 を使って実行済みです。実行ファイルと 3 つの出力は `build/` 作業ディレクトリに置き、課のディレクトリにはソースとフィクスチャだけを残しました。

| シナリオ | クリーンな開始状態 | 期待値と実測 |
|---|---|---|
| 正常経路 | 空の `build/` に `transactions.txt` をコピー | 構文検査/コンパイル終了コード `0`、標準出力 7 行、終了コード `0`、`accepted.txt` 2 行・`rejected.txt` 3 行・`batch.log` 12 行。`diff batch.log expected-batch.log` に差分なし。一致 |
| 入力欠落 | `build/` に `transactions.txt` を置かない（以前の結果ファイルは先に削除） | 終了コード `1`、標準出力 3 行（エラー・すべて `000` の集計・`システムエラー=Y`）。ログはちょうど 3 行：`BATCH_START`、`SYSTEM_ERROR OP=OPEN_INPUT STATUS=35`、`BATCH_END ... SYSTEM_ERROR=Y`。一致 |
| ログを開けない | 入力コピーを置いたまま、`build/` の `batch.log` をディレクトリにする | 終了コード `1`。標準出力に `エラー=ログOPEN 状態=37`、全 `000` の集計、`システムエラー=Y`。`accepted.txt`/`rejected.txt` は作成されない。一致 |

**未検証の項目（結論として扱わないこと）：**

- **ログの WRITE/CLOSE 失敗は注入していません。** `WRITE`/`CLOSE` に `00` 以外を返させるには、下層の書き込み操作を失敗させる必要があります。本課には安定した注入手段がなく、実測していません。そのため「WRITE 失敗 → 状態を表示 → 後続レコードを停止 → 1 を返す」と「CLOSE 失敗 → 状態を表示 → エラーフラグを設定 → 1 を返す」は、現状ではソースコードだけが根拠です。
- **`FILE STATUS = "00"` はデータがディスクに書き込まれたことを意味しません。** 本課のコードにはフラッシュ処理がなく、`00` が示すのは書き込み呼び出しが受け付けられたことだけです。これはソースからの推論で、ここでは個別に実験していません。この種のバッファリング境界の実測記録は第 16 課にあります。
- ログの OPEN 失敗は実測済みです（上の「ログを開けない」）。本課で発生させられる READ 関連の障害は入力を開けないことだけで、読み込み途中の障害も注入していません。

**実際に観察した環境上の詳細：** このワークスペースで実行ファイルを動かすと、標準エラーに `Warning: program compiled against libxml 212 using older 209` と表示されます。実行環境のリンクライブラリの版違いによる警告で、業務出力ではありません。発生元のコンポーネントはまだ特定されていません。

## 変更練習

リポジトリ内のフィクスチャを変更せず、`build/` 作業ディレクトリで 2 つの課題を行います。まず `build/` を空の状態から準備します（`mkdir -p build`、コンパイル、`cp transactions.txt build/`）。

1. 入力の `A00002|00X50` を `A00002|00150` に変更します。レコードが業務拒否から受理に変わること、ログイベントが `BUSINESS_REJECT` から `RECORD_ACCEPTED` に変わること、`BATCH_END` の件数が変わることを確認します。
2. `build/transactions.txt` を削除して実行します。終了コード、標準出力のエラー行、`build/batch.log` 内のバッチ開始・システム障害・バッチ終了イベントの順序を記録します。

終わる前に件数の不変条件を確認します（`INPUT = ACCEPTED + REJECTED`、また 2 つの件数がそれぞれ結果ファイルの行数と一致すること）。問題と期待結果は [`exercise.md`](./exercise.md)、参考解答は [`answer.md`](./answer.md) を参照してください。

## 応用練習

「口座番号の重複」を業務拒否ルールとして追加し、最初のレコード番号と重複したレコード番号をログに両方記録します。さらに、実行ごとに一意なバッチ ID を使う複数バッチ入力方式を設計し、`BATCH_END` があってもすべての出力が原子的に納品された証明にはならないことを説明してください。顧客のプライバシー情報を丸ごとログに書かず、失敗したバッチの終了状態を省略しないこと。問題は [`exercise.md`](./exercise.md)、解答はありません。

## 実際の処理をたどる

夜間処理全体の中で、本課のログは「検証」と「納品」の間に位置します。

1. **上流は第 26 課です。** 検証プログラムは取引を 1 件ずつ読み、不正レコードを `rejected.txt` へ振り分け、本当の I/O 障害で停止してゼロ以外の終了コードを返します。業務拒否とシステム障害はすでに区別しますが、夜を越して残る記録はありません。本課はそのための「日記」を用意します。
2. **本課の工程。** 検証結果は従来どおり 2 つの結果ファイルへ出しつつ、同じ実行の各イベントを `batch.log` に固定形式で書きます。別のプログラムはありません。同じバッチでログも書き、追加されるのは `OPEN OUTPUT` 1 回と複数回の `WRITE` です。
3. **夜中に誰が見るか。** スケジューラーが認識するのは終了コードだけです。呼び出された当直担当者は終了コードを確認し、次に `batch.log` を読みます。最終行は `BATCH_END` か、件数は合うか、`SYSTEM_ERROR` はあるか。画面出力はもう消えており、ログだけが現場の記録です。
4. **日中に誰が見るか。** 照合担当者は `BATCH_END` の `INPUT=005` と上流ファイルの行数を照合します。確認担当者は `NO=` のレコード番号を使い、入力ファイルから不正データを探します（ここでレコード番号が役立ちます。口座番号だけでは入力の「何行目」か分かりません）。
5. **次は第 28 課です。** 検証、ログ、結果報告を、複数プログラムと Copybook による再現可能なプロジェクトにまとめます。ログを `expected-batch.log` と 1 行ずつ照合する点は同じです。その後の第 31・32 課では「バッチ + 件数 + 障害の記録」という考え方をファイルと SQLite の照合に広げ、データベース接続や同期結果のイベントもログに加えます。

一言で言えば、本課はこの処理チェーンで**「処理の経過」を書き残す唯一の場所**です。結果ファイルは出力の内容を証明し、完了したか、どこで止まったかを証明するのはログだけです。

## このコードが本番で使われたら

- **誰がスケジュールするか：** 上流の取引ファイルが準備された後に起動する夜間バッチスケジューラーです。実行ファイルのパスと終了コードだけを見て、画面もログも読みません。
- **誰がログを見るか：** 呼び出された当直担当者です。まず終了コードを確認し、次に `BATCH_END` と `SYSTEM_ERROR` を見ます。ログが分かりやすいかどうかで、その人が何時間起きているかが変わります。
- **障害時に誰が呼び出されるか：** 終了コードがゼロ以外なら必ず誰かが呼び出されます。終了コードが `0` でも上流件数と合わなければ、翌日に照合担当者が確認します。警報がない後者のほうが厄介です。
- **次のシステムへの受け渡し：** ログを後続プログラムが使うことはあまりありません。ログは人とスケジューラーのためのものです。業務の成果物は `accepted.txt`/`rejected.txt` のままで、後続課のモジュール化プロジェクトや総合課題へ渡します。
- **最初の 1 か月に起きやすい事故：** ログを不変の証拠だと思い込むことです。`batch.log` は `OPEN OUTPUT` で作り直すため、再実行すると前回の記録が消えます。本課には実行 ID もタイムスタンプもなく、別の日の実行も、同じ日の 2 回の実行も見た目が同じです。午前中の実行ログを午後の結果ファイルと比べて、件数が合わないことになります。騒ぎにはなりませんが、時間を取られます。
- **まだ実装していないこと：** 一意な実行 ID、タイムスタンプ、ログ保存期間とアクセス制御、マスキング、再実行、ログと結果ファイルの納品順や中断後の復旧ルールです。本課にはどれもありません。本番の監査証跡として使うなら、先に補う必要があります。
