# 第 03 课：MOVE 与 COMPUTE——金额运算中的截断与舍入

## 业务现场

结息日晚上，计息批次要在早上 8 点前把十二万笔存款的当期利息算完写完；柜面 9 点开门，客户在 App 上刷一眼余额，得是对的数字。

这笔账里每一笔利息都是“余额 × 利率”算出来的，结果几乎都会拖一长串小数，可余额只记到分。于是每笔都要当场决定：多出来的小数位，是直接抹掉，还是按规则进上去。抹掉叫截断，进上去叫舍入。

演示样例里这笔利息的精确值是 `15.0650`，抹掉得 `15.06`，进上去得 `15.07`。你可能会想，一分钱而已。但这批有十二万笔，如果每笔都朝同一边偏，攒起来就不是小数；更麻烦的是期末余额就是拿这个利息加上去的，这一分钱的差会原样带进余额里。

真正半夜把人叫起来的是第二天早上的对账。核心系统用自己的口径重算一遍，两边余额对不上——哪怕只差一分，对账岗也不能“差不多得了”，整批挂住，人工逐笔去找那一分钱落在哪儿。所以“结果用哪个字段装、这个字段保留几位小数”不是数学练习，是这批账能不能按时出去的关键。（场景是教学示意，金额和批次日是为了说清问题挑的，不是某家机构的真实数据。）

## 为什么现在学

第 02 课你已经能给余额、利率写出 `PIC`，字段宽度和精度都摆在源码里了。但那节课的字段只被 `DISPLAY` 打印过一次初值，从头到尾谁也没动过它们——真正的账不是打印出来的，是算出来的。

现在卡住你的是三件小事：怎样把一个值搬到另一个字段；怎样写出含加减乘的金额表达式；结果的小数位比接收字段多时，多出来的位是丢掉还是进位。最后一条直接决定期末余额写几，也是银行对账里最容易翻车的地方。

你也许想：搬个值、做次乘法，别的语言里不就是 `a = b` 和 `a = b * c` 吗？坑就在这儿。在 Java 或 Python 里，把 `BigDecimal` 赋给另一个变量，数值是不会变的；COBOL 的接收字段却带着明确的十进制尺度，搬过去的那一刻就按目标字段重新定型了。也就是说，**“搬一次值”本身就可能改变金额，而程序一声不吭。** 你要是不显式写下规则，它也不会替你问“这笔业务到底该截还是该舍”。

这一课也只走到这里：只用顺序执行的赋值和算术语句，不引入条件（第 04 课）和循环（第 06 课），先把“接收字段的尺度决定结果”这一条看死，后面往金额链上加判断、加循环时才不会带着错的底子。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 你多了两种能力。`MOVE` 把一个值搬进另一个字段，目标字段的 `PIC` 决定它搬过去长成什么样；`COMPUTE` 先把右边那一串加减乘算出来，再塞进左边的接收字段，尺度还是接收字段说了算。术语层面新增的就两条：接收字段的尺度决定小数位，`ROUNDED` 决定多出来的小数位怎么处理。

**它在业务里解决什么问题。** 它让余额、利息、手续费这类金额链能写成程序，而不是靠人拿计算器一笔笔敲；更关键的是，它把“保留几位、怎么进位”这条业务规则留在代码里，可以被复核、可以被修改。业务改一次初值，结果自动跟着重算，规则不会从代码里消失。

**什么时候不该用它、用错会怎样。** 金额的取舍规则不能拿“默认行为”顶班。不写 `ROUNDED` 就是截断，那只是本工具链的默认，不代表所有业务都这么记账；选错一天，批次就可能和会计口径差一分钱。另外，接收字段的整数位装不下时程序不会报警（下面有一份实测），所以金额字段的容量得照业务上限留，不能照着眼前这笔钱的位数凑。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `MOVE` 把值搬到另一个数值字段，并说明接收字段的小数位如何决定去留（本例 `15.0650` → `15.06`）。
- 用 `COMPUTE` 写出含加减乘的金额表达式，并在标准输出中逐项核对每一步中间值。
- 区分“截断”（不写 `ROUNDED`）与“按接收字段舍入”（写 `ROUNDED`），解释同一笔利息为什么会得到 `15.06` 和 `15.07`。
- 说明两种规则会让期末余额相差 `0.01`，并指出必须由业务/会计规则选定其中的一种。
- 说出金额字段位数不足时会发生什么，以及为什么本课样例不会触发这个边界。

边界：本课不引入 `IF` / `EVALUATE`（第 04、05 课）、循环（第 06 课）、段落（第 07 课）、文件输入（第 15 课）和错误处理语句（第 26 课）。所有余额和利率都是程序内演示常量，不是真实账户数据，也不代表任何银行计息方案；程序没有实现溢出检查。

## 知识点拆开看

### MOVE：搬过去的不是“同一个数”，而是按目标字段重新定型的值

`MOVE source TO target` 把 `source` 的值复制给 `target`，不改 `source`，也不做任何运算。可目标字段自带 `PIC` 尺度：`WS-INTEREST-RAW` 是 `9(5)V9999`（四位小数），`WS-INTEREST-MOVE` 是 `9(5)V99`（两位小数），用它俩做 `MOVE` 时多出的两位小数被丢掉，得到 `15.06`，而源字段还是 `15.0650`。

从 Java 或 Python 过来的人最容易在这儿想当然：把一个 `BigDecimal` 赋给另一个变量，数值通常不变；COBOL 的接收字段有明确的十进制尺度，搬移时按那份描述转换，所以“搬一次值”本身就可能改变金额。生产代码因此要把搬移前后的字段尺度和业务单位写清楚，不能指望读者从代码里猜。

### COMPUTE：先算右边，再按左边接收字段的尺度存进去

`COMPUTE target = expression` 先按右侧表达式求值，再把结果存进左侧数据项，接收字段的 `PIC` 同样决定保留几位小数。本例先算交易后余额：

```cobol
COMPUTE WS-PRE-INTEREST-BALANCE =
    WS-OPENING-BALANCE + WS-DEPOSIT
        - WS-WITHDRAWAL - WS-SERVICE-FEE
```

再算利息 `WS-PRE-INTEREST-BALANCE * WS-PERIOD-RATE`，把中间值写进四位小数的 `WS-INTEREST-RAW`。所有输入、中间值和接收字段都用明确的十进制 `PIC` 声明，所以每一步都能在源码里核对，不依赖浮点近似。

还有一点别偷懒：这些值必须由字段算出来，而不是写死在 `DISPLAY` 的字面量里。写死只能复述一次结果，初值一改就得手工重算，业务规则也从源码里消失了；用 `COMPUTE` 则规则留在代码里，改初值就自动得到新结果（本课练习正是这样做的）。

### 截断还是舍入：同一笔利息，两条业务规则

GnuCOBOL 中，接收字段小数位不足时，**不写** `ROUNDED` 等同于 `ROUNDED MODE IS TRUNCATION`（截断；本课金额非负，即丢弃多余小数位）；**写** `ROUNDED` 而不写模式时等同于 `NEAREST-AWAY-FROM-ZERO`（就近舍入，遇到正好一半时远离零）。本例利息的精确值是 `15.0650`：

| 写法 | 结果 | 说明 |
|---|---|---|
| `MOVE WS-INTEREST-RAW TO WS-INTEREST-MOVE` | `15.06` | 接收字段两位小数，丢掉第 3、4 位 |
| `COMPUTE WS-INTEREST-TRUNC = WS-INTEREST-RAW` | `15.06` | 不写 `ROUNDED`，同一截断规则 |
| `COMPUTE WS-INTEREST-ROUNDED ROUNDED = WS-INTEREST-RAW` | `15.07` | 第 3 位是 `5`，就近舍入进位 |

`ROUNDED` 写在接收字段之后、等号之前：

```cobol
COMPUTE WS-INTEREST-ROUNDED ROUNDED = WS-INTEREST-RAW
```

选哪一种不是编程偏好，而是业务和会计口径：截断值与舍入值会让期末余额相差 `0.01`，币种、产品和利息计提方式不同，规则也可能不同。所以别把 GnuCOBOL 的默认模式当成所有业务通用的规则，那是要跟账务和产品的人对过的。

### 装不下的时候，程序不会喊一声

小数位会丢，整数位也一样会丢。用一段独立探针在本机观察（探针不属于 [`lesson.cob`](./lesson.cob)，只用本课已学的 `PIC`、`COMPUTE`、`DISPLAY`）：

```sh
mkdir -p /tmp/l03probe && cd /tmp/l03probe
cat > probe.cob <<'EOF'
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PROBE03.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 WS-BAL PIC 9(7)V99 VALUE 1234567.89.
       01 WS-RATE PIC 9(1)V9(4) VALUE 0.9000.
       01 WS-INT PIC 9(5)V99 VALUE 55.55.
       PROCEDURE DIVISION.
           COMPUTE WS-INT = WS-BAL * WS-RATE.
           DISPLAY "利息=" WS-INT.
           STOP RUN.
EOF
cobc -x -o probe probe.cob && ./probe
```

`1234567.89 × 0.9000 = 1111111.101`，收进 `PIC 9(5)V99` 后实际打印 `利息=11111.10`，进程退出码为 `0`：高位数字被静默丢弃，程序既不中止也不报错。“算错了”本身不会变成错误信号，所以金额字段的容量、溢出判断和上报方式必须由程序显式规定。`ON SIZE ERROR` 能捕获这类条件，但它属于错误处理内容，本课未使用，留到第 26 课。

## 源码阅读路径

### 数据声明

| 字段 | PIC / 初值 | 用途与尺度 |
|---|---|---|
| `WS-OPENING-BALANCE` | `9(7)V99` / `1000.00` | 期初余额，元，两位小数 |
| `WS-DEPOSIT` | `9(7)V99` / `250.55` | 本期入账 |
| `WS-WITHDRAWAL` | `9(7)V99` / `40.10` | 本期支取 |
| `WS-SERVICE-FEE` | `9(5)V99` / `5.25` | 服务费；整数位 5 位，容量小于余额字段 |
| `WS-PERIOD-RATE` | `9(1)V9(4)` / `0.0125` | 演示利率 1.25%，四位小数；无日计数规则 |
| `WS-PRE-INTEREST-BALANCE` | `9(7)V99` / `ZERO` | 交易后、计息前余额 |
| `WS-INTEREST-RAW` | `9(5)V9999` / `ZERO` | 利息中间值，故意保留四位小数 |
| `WS-INTEREST-MOVE` | `9(5)V99` / `ZERO` | `MOVE` 后的两位小数结果 |
| `WS-INTEREST-TRUNC` | `9(5)V99` / `ZERO` | 不写 `ROUNDED` 的计算结果 |
| `WS-INTEREST-ROUNDED` | `9(5)V99` / `ZERO` | 写 `ROUNDED` 的计算结果 |
| `WS-CLOSING-BALANCE` | `9(7)V99` / `ZERO` | 按本课记账规则（入账舍入利息）的期末余额 |

### 执行顺序与状态变化

1. 第一个 `COMPUTE`：`1000.00 + 250.55 − 40.10 − 5.25`，把 `1205.20` 写入 `WS-PRE-INTEREST-BALANCE`。
2. 第二个 `COMPUTE`：`1205.20 × 0.0125 = 15.065`，接收字段是 `9(5)V9999`，输出为 `15.0650`。
3. `MOVE WS-INTEREST-RAW TO WS-INTEREST-MOVE`：接收字段只有两位小数，未舍入，得 `15.06`；`WS-INTEREST-RAW` 仍为 `15.0650`。
4. `COMPUTE WS-INTEREST-TRUNC = WS-INTEREST-RAW`：不写 `ROUNDED`，同样得 `15.06`。
5. `COMPUTE WS-INTEREST-ROUNDED ROUNDED = WS-INTEREST-RAW`：默认 `NEAREST-AWAY-FROM-ZERO`，得 `15.07`。
6. `COMPUTE WS-CLOSING-BALANCE = WS-PRE-INTEREST-BALANCE + WS-INTEREST-ROUNDED`：按本课记账规则，`1205.20 + 15.07 = 1220.27`。
7. 十一个 `DISPLAY` 按源码顺序输出标签和值，`STOP RUN` 正常结束。

第 2–5 步都源自同一个 `WS-INTEREST-RAW`，所以三个两位小数结果之间的差别只来自接收字段，不是重复计算造成的。`DISPLAY` 本身不改变任何字段。

### 固定格式提醒

源码是固定格式：第 7 列是指示符（`*` 为注释），Area A 从第 8 列开始（`01` 级声明、Division 名），Area B 从第 12 列开始（`COMPUTE`、`MOVE`、`DISPLAY` 等语句），有效程序文本不能越过第 72 列。这里有个本机实测过的坑：GnuCOBOL 3.2.0 按**字节**数判断这一列位置。日文字面量每个字符占 3 个字节，一行即使字符数看着不多，也可能在第 72 字节被截断，报出“缺少字符串结束引号”一类错误。所以你改 `DISPLAY` 文本时，别让那行贴到第 72 列；本课两条最长的 `DISPLAY`（含 `MOVE後利息` 与 `COMPUTE切捨て利息`）各为 62 字节，最长的注释行为 71 字节，都还没越线。

## 走一遍真实流程

把这段金额逻辑放进一条完整链路，它长这样：

1. **结息夜，调度器拉起计息批次。** 批次从账户主档取到期初余额和利率（真到那时是文件或数据库，本课先用程序内常量），把余额和利率交给本课这段 `MOVE` / `COMPUTE`，算出交易后余额、利息和期末余额。
2. **下游先看利息怎么定。** 期末余额要写回账户主档，对账程序第二天会拿它和核心系统重算的结果比。取舍规则一旦选错，两个系统的余额就差那么一分钱。
3. **同一批金额会被后面的课接着用。** 第 04 课开始给这些金额加条件，判断一笔交易该接受还是拒绝；第 15 课起金额从真实交易文件读进来，不再是常量；第 26 课统一处理溢出和失败上报；到第 32 课，整条金额链拿去和账户主档对账。

要说清楚的是，本课这一段还不是一个能上线的批次：它没有输入文件、没有拒绝逻辑、也没有溢出检查，把它单独丢进夜里跑，只能说明这一分钱的差到底是从哪一步冒出来的。

## 这份代码进了生产会怎样

- **谁调度它**：结息夜的批处理调度器，按作业依赖顺序拉起计息、写回、对账几个环节；它只认退出码，不看你的屏幕。
- **谁看它的输出**：运维看标准输出和标准错误，记账和对账岗看余额对不对得上；所以“哪几行是业务结果、哪一行只是环境警告”必须分得清。
- **下一个系统怎么接**：算出来的期末余额会写进账户主档，第二天由对账程序与核心系统的口径逐笔比对——差一分，整批就挂。
- **第一个月最容易出的事故**：把“没写 `ROUNDED` 就是截断”当成全行统一口径，结果和会计规则差一分钱；或者金额字段的整数位按眼前这笔钱凑，余额一大，高位就被静默丢掉，程序还报成功。

在银行批次里，`MOVE` 常见于字段间搬移、布局转换和输出准备，`COMPUTE` 常见于余额、费用、利息和控制总额。它们看着简单，却是金额正确性的落点：接收字段的小数位决定舍入、整数位容量决定溢出，任何一处与业务规则不符都会让余额和业务口径对不上，而程序未必报错。真实批次上线前至少要固定字段的币种、整数位、小数位、最大值、负数规则、舍入位置和超限策略，并用独立算例或控制总额核对。

本课只证明“同一笔利息按不同规则得到不同结果，期末余额随之相差 `0.01`”，还没有做出任何接受/拒绝判断：条件分支从第 04 课开始，用同一批金额字段决定交易是否被接受；文件输入从第 15 课开始，让金额来自真实交易文件而不是常量；溢出与失败上报在第 26 课统一处理；整条金额链最终在第 32 课的对账项目里与账户主档核对。
