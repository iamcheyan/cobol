# 第 04 課：IF 条件判断——1 件の取引を受け入れと拒否に振り分ける

取引が 1 件入ってきたとき、プログラムはまず判定を下さなければなりません。通すのか、通さないのか。通さないとすれば、どの規則で弾かれたのか。本課では 1 件のサンプル取引をプログラム内に固定し、3 重ネストの `IF` で「金額が正数であること → 金額が 1 回の取引上限を超えていないこと → 口座状態が有効であること」を順に判定し、**最初に該当した**失敗理由だけを報告します。

## 業務現場

金曜日の午後 4 時 50 分、営業店の窓口がまもなく閉まろうとしています。1 人の顧客が窓口で伝票を差し出し、送金を依頼しました。ほぼ同じ時刻、モバイルアプリ上でも誰かが「送金確定」をタップしました。この 2 つの操作は、システム内部ではまったく同じものになります。すなわち、検証待ちの 1 件の取引です。プログラムはその場で結果を出さなければなりません。通れば何も問題はありません。しかし、いったん「拒否」と判定されれば、面倒な事態はそこから始まります。

拒否そのものは決して終着点ではありません。窓口係の画面には「拒否されました」の 4 文字だけが表示されるわけではなく、顧客は必ず「なぜか」と問い詰めてきます。答えは 2 種類しかありません。**この金額自体がルールに反している**（正数でない、または 1 回の取引上限を超えている）か、あるいは**口座状態が不正である**（凍結されている、解約済みである）かのいずれかです。前者の場合、資金はまったく動いていないため、窓口係がその場で説明し、顧客が伝票を書き直せば済みます。一方、後者の場合はそもそも窓口で処理すべき業務ではなく、人手による確認へ回さなければなりません。同じ「拒否」という一言でも、一方はその場で完結し、もう一方は顧客に出直してもらう必要があります——その違いは、プログラムがどの理由を報告するかにかかっているのです。

最も事故を起こしやすいのは**順序**です。判定順序を逆に書いてしまうと、限度額超過かつ凍結されている取引が「金額超過」と報告されてしまう可能性があります。窓口係は顧客に金額を小さくしてやり直すよう案内しますが、結局また拒否されます。顧客は無駄足を運ばされ、窓口は再度説明を迫られます。そのため、本課では単に「受け入れと拒否を振り分けられる」だけでなく、**なぜ最初に該当した理由だけを報告するのか、その順序は誰が決めるのか**を説明できるようになる必要があります。

さらにもう 1 つ、最も曖昧にされがちな規則があります。1 回の上限は「1000.00 でも超過とみなす」のか、それとも「1000.00 を超えて初めて超過とみなす」のか。要件定義にはよく「1 回あたり 1000 円を超えないこと」と書かれますが、この一文には 2 通りの読み方があります。プログラム内では `>` と `>=` の違いはわずか 1 文字ですが、境界端点は異なる側に振り分けられます。このような曖昧さはプログラムのエラーにはならず、2 つのシステムがめいめい勝手に実装し、月末の照合が合わなくなる原因になります。本課では、この境界端点を必ず明記し、必ず検証すべきものとして扱います。

（この段落は教育用の想定シーンです。金融機関名、金額、時刻は規則を分かりやすく説明するために作成されたものであり、実在のいかなる機関の実データでもありません。）

## なぜ今これを学ぶか

こう思うかもしれません。「条件分岐なんて誰でも知っている、`if` なんて何年も書いてきた」と。

問題は、あなたがこれまで書いてきたものの多くが「1 回走れば終わる」スクリプトだったという点にあります。ここでの状況は異なります。**COBOL プログラムは上から下へと流れるように進み、途中で「立ち止まって確認する」場所はありません**。第 [02](../02_data-types/README.md) 課であなたは `PIC` を使って口座番号、状態、金額を正確に記述することを学び、第 [03](../03_move-compute/README.md) 課でそれらから計算結果を導き出すことを学びました。しかし、そこまでの段階では、プログラムは記述された文を先頭から末尾までなぞるだけでした。

金曜午後のあの取引を思い出してください。金額は `-5.00`、口座は凍結状態です。条件分岐がなければ、プログラムは構わず先へと進み——そのまま「計算を完了」し、処理完了のメッセージを印字してしまいます。拒否することもなければ、どこがおかしいかを知らせることもありません。これは業務上、プログラムがクラッシュするよりもはるかに深刻です。バッチジョブは正常終了（グリーン）しているのに、帳簿は間違っているからです。

慣れ親しんだ言葉で言い換えるなら、口座状態というフィールドには、実データの中ではどんな値でも入り得ます。あらかじめ人間がデータを選別し、別々のファイルに分けて投入するのではなく、プログラム自身にデータを見て進むべき道を選ばせなければならないのです。

COBOL が提供する道具は、関係条件と `IF` / `ELSE` / `END-IF` です。他の言語と似ているように聞こえるかもしれませんが、本課で確実に押さえておくべき落とし穴が 2 つあります。`ELSE` がどれに対応するかはインデントではなく完全に**スコープ**で決まること、そして**ネストの順序がそのまま拒否理由の優先順位になる**ことです。この 2 点は、以降のすべての分岐を扱う課で使用します。第 [05](../05_evaluate/README.md) 課での取引種別による分類、第 [08](../08_control-flow-practice/README.md) 課での複数取引に対する受け入れ・拒否の集計も、すべてここが土台となります。

## 这个知识点是什么，它解决什么问题

**この知識項目とは何か。** 一言で言えば、プログラムに**データを見ながら自ら進路を選ばせる**ことです。これを行うのは 2 つの要素です——*関係条件*（`=`、`<`、`>`、`<=`、`>=` で 2 つの値を比較して真または偽を判定する）と、*`IF` / `ELSE` / `END-IF`*（真なら一方の道を進み、偽なら他方を進み、`END-IF` でスコープを閉じる）です。第 [03](../03_move-compute/README.md) 課の算術演算と比べると、これは別の能力です。単に「いくらになるか」を問うのではなく、「資格を満たしているか」を問うようになります。

**業務において何を解決するか。** バリデーションという作業は、価値の半分が「正しく判定すること」にあり、もう半分は「明確に説明すること」にあります。窓口、カスタマーサポート、照合担当者が目にするのは、1 つの判定と 1 つの理由だけです。金額超過なのか、状態不正なのか、あるいは通過したのか。理由を間違えれば、後続のすべての担当者が誤った判断を下すことになります。`IF` とネストの組み合わせは、まさに**業務の優先順位をコードに書き込む**場所です——どれを先に判定し、どれを後に判定するかをソース上で明示し、問題が起きたときにその行を指差して説明できるようにします。

**どんなときにはまだ使うべきでないか（誤用するとより高くつく）。** 条件分岐を入力チェックの代用にしないでください。上流から渡された金額フィールドに英字が混入していたり、文字コードが不正だったりした場合、`IF` は壊れたデータに対して一見正常な判定を下すだけであり、データ自体の異常を発見してはくれません。そうした検査は後の課を待つ必要があります。また、忘れてはならないのは、本課の拒否はあくまで**業務上の判定**であり、終了コードは依然として `0` であるという点です。業務上の拒否をシステム障害とみなしてアラートを上げるのは、よくあるもう 1 つの事故パターンであり、第 [26](../26_error-handling/README.md) 課で専門に扱います。

## 本課修了時の能力と限界

本課を修了すると、以下のことができるようになります：

- `=`、`<`、`>`、`<=`、`>=` を用いて数値フィールドおよび文字フィールドを比較し、境界端点の値が受け入れ側と拒否側のどちらに含まれるかを説明できる。
- `IF` / `ELSE` / `END-IF` を用いて、各条件に対して明示的な受け入れ経路と拒否経路を記述でき、インデントやピリオドに頼って `ELSE` の所属を推測しない。
- 固定の優先順位に従って 3 段階の判定をネストさせ、なぜこれによって**1 つの**拒否理由のみが出力されるのか、また同階層の 3 つの `IF` に置き換えると複数の規則が同時に該当してしまう理由を説明できる。
- 境界値サンプル（`0.00`、`-0.01`、`0.01`、`1000.00`、`1000.01`、および状態が `A` 以外の場合）の判定結果を予測し、照合できる。
- 業務上の拒否とシステム障害を区別できる。本課のすべての拒否経路における終了コードは依然として `0` である。

限界：本課では端末、ファイル、データベースからの読み込みは行わず、サンプル値は `WORKING-STORAGE` の `VALUE` 句に記述します。取引は 1 件のみであり、残高の更新、件数カウント、集計は行いません。端数処理や算術桁あふれは扱いません（第 [03](../03_move-compute/README.md) 課で提示済み、第 [26](../26_error-handling/README.md) 課で体系的に扱います）。取引種別の分類（第 [05](../05_evaluate/README.md) 課）や複数件のバッチ処理（第 [08](../08_control-flow-practice/README.md) 課）も行いません。また、本課では口座権限チェック、同時実行制御、重複リクエスト検知、永続化は実装しません。これらはいずれも本課で証明すべき対象ではありません。

## 知識解説

### 関係条件：比較されるのは値であり、画面上の見かけではない

`=`、`<`、`>`、`<=`、`>=` の 5 つの演算子は馴染み深いものであり、`THEN` は省略可能な語で、書いても書かなくても同じです。真に覚えておく価値があるのは、次の 2 つの細部です。

第 1 に、2 つの数値オペランドを比較する際、COBOL はフィールドの `PIC` に何桁宣言されているか、符号が付いているか、`USAGE` が何かに関わらず、**実際の代数値**で比較します。`+0000125.50` と `125.50` は同一の値として扱われます。

第 2 に、文字フィールド同士は文字セットに従って 1 文字ずつ比較され、短い側の右側に空白が補われます。したがって `"A"` と `"a"` は異なる 2 つの文字です——口座状態を扱う際、この点は極めて重要になります。

本課では 3 つの関係条件を使用します：

```cobol
WS-TRANSACTION-AMOUNT <= ZERO
WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT
WS-ACCOUNT-STATUS = "A"
```

第 1 の `<= ZERO` はゼロおよび負の数の両方で成り立ちます。第 2 の `>` は上限を**厳密に超えた**場合にのみ成り立ちます。第 3 は文字比較であり、`a`、空白、`I` はいずれも `A` とは等しくありません。

ここで最も陥りやすい落とし穴は、**境界端点がどちら側に属するかは、完全に演算子によって決まる**ということです。`<=` は `0.00` を拒否側に振り分け、`>` は `1000.00` を受け入れ側に残します。もし何気なく `<=` を `<` と書いてしまえば、`0.00` は通過してしまいます。`>` を `>=` と書いてしまえば、ちょうど `1000.00` の取引が拒否されてしまいます。そのため、境界値は単独でレビューするのではなく、演算子とセットで確認しなければなりません——これこそが前述の「要件が曖昧で、システムごとにめいめい実装が異なってしまう」最も典型的な箇所です。

状態の比較は完全一致比較です。`WS-ACCOUNT-STATUS` は `X` 型であり、`a`（小文字）、空白、`I` はどれも `A` と等しくないため、すべて拒否ブランチに入ります。もし大文字小文字を両方通過させたいのであれば、それはインターフェース層の規約であり、明示的に記述する必要があります。COBOL は自動で正規化してくれたりはしません。

### IF / ELSE / END-IF とスコープの帰属

`IF` は条件が真のときに直後の文を実行し、`ELSE` は偽の場合を受け持ち、`END-IF` はこの条件文がどこで終了するかを明確に示します。

初心者はインデントによって `ELSE` がどれに対応するか決まると誤解しがちですが、COBOL はインデントを見ません。コンパイラの規則はただ 1 つ、**`ELSE` は直前のまだ終了していない最も近い `IF` に結びつく**ということです。どれほど綺麗にインデントを整えても、コンパイラは考慮してくれません。

本課の 3 つの `IF` にはすべて `END-IF` を対にし、最も内側から外側へと順にスコープを閉じています。こうすることで、3 つの `ELSE` がそれぞれ誰に属しているかがソースコード上で一目でわかり、空白の数を数えたり、ピリオドに頼って推測したりする必要がなくなります。

ついでにさらに厄介な落とし穴に触れておきます。**ピリオドは単なる「文末の句点」ではなく、文全体を完結させ、まだ終了していない文のスコープをまとめて閉じてしまいます**。本課では最初から最後まで、末尾の `STOP RUN.` にあるピリオド 1 つしかありません。先頭の 4 つの `DISPLAY` の間にはピリオドが**ありません**。これらは同一の文の中に並ぶ複数のステートメントであり、記述された順序に従って 1 つずつ実行されます。もし途中に何気なくピリオドを打ってしまうと、本来 `IF` の内側にあるべき文が条件の外に放り出されてしまう可能性があり、しかもコンパイラがエラーを出さないこともあります。

### ネスト順序が出力される拒否理由を決定する

3 つの規則が入れ子になっている順序こそが、拒否理由の優先順位です：

```text
金额 <= 0            → AMOUNT_NOT_POSITIVE     （最外层，先判）
  否则 金额 > 上限   → AMOUNT_OVER_LIMIT
     否则 状态 = A   → 接受
        否则          → ACCOUNT_INACTIVE      （最内层，最后判）
```

プログラムは**真となった最初の失敗条件**の箇所で理由を出力し、そこで処理を終えます。さらに深い階層の検査は一切実行されません。そのため、金額が `-5.00`、状態が `I` の取引は `AMOUNT_NOT_POSITIVE` だけを報告し、状態にも問題があることをついでに教えてくれたりはしません。

これは「なぜどうしてもネストにしなければならないのか」に対する直接の回答です。もし 3 つの検査を並列の `IF` として書いた場合、2 つの失敗条件がそれぞれ 1 回ずつ成立し、プログラムは互いに矛盾する 2 つの理由を出力してしまいます。ログを見る側もどちらを信じるべきか分かりません。業務上「何を先に伝えるべきか」はプロダクトや経理・会計が決めた規約であり、プログラマが適当に並べたものではありません——順序が変われば、外部への説明も連動して変わってしまうのです。

### Java / Python との相違点

分岐処理に関して言えば、Java では `if` / `else if` を用い、Python では `if` / `elif` / `else` を用いますが、考え方は同じです。違いは 2 点あります。COBOL では `END-IF` で文の終了を明示的に示すこと、そして `ELSE` はインデントを認識せず「直前の未終了の `IF`」に束縛されることです。比較の前に型を確認しなければならない点も同様です。口座状態はテキストであり、金額は符号付き 10 進数です。

COBOL は `AND` / `OR` を用いて複数の条件を 1 つの複合条件にまとめる記法もサポートしていますが、本課ではあえて使用していません。理由は、ネストを使うことで各ルールの優先順位をソースコード上に直接表現でき、「どの層を先に判定するか」の感覚を養うのに適しているからです。複合条件は、その構文を学ぶ段階になってから使えば十分です。

### 出力テキストの言語について

リポジトリには規約があります。ソースコードのコメントや README の解説には中国語を用いますが、**プログラム実行時に印字される業務テキストは日本語を踏襲します**。幸い推測する必要はありません——判定に必要なすべての情報は標準出力の `key=value` 行に含まれており、2 つの重要な値は `判定=` と `理由=` です。日本語の対応関係は次節で示します。

## 完全なサンプルソースコード

完全なソースコードは [`lesson.cob`](./lesson.cob) を参照してください。固定形式に従って記述されています（第 7 列が標識領域、Area A は第 8 列から、Area B は第 12 列から開始し、プログラムテキストは第 72 列を超えません）。

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. IF04.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 WS-TRANSACTION-REFERENCE PIC X(12)
          VALUE "TXN-00000001".
       01 WS-ACCOUNT-STATUS PIC X VALUE "A".
       01 WS-TRANSACTION-AMOUNT PIC S9(7)V99
          SIGN IS LEADING SEPARATE CHARACTER VALUE 125.50.
       01 WS-MAXIMUM-AMOUNT PIC 9(7)V99 VALUE 1000.00.
       PROCEDURE DIVISION.
           DISPLAY "取引参照番号="
               WS-TRANSACTION-REFERENCE
           DISPLAY "口座状態=" WS-ACCOUNT-STATUS
           DISPLAY "取引金額=" WS-TRANSACTION-AMOUNT
           DISPLAY "上限金額=" WS-MAXIMUM-AMOUNT
           IF WS-TRANSACTION-AMOUNT <= ZERO
               DISPLAY "判定=REJECTED"
               DISPLAY "理由=AMOUNT_NOT_POSITIVE"
           ELSE
               IF WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT
                   DISPLAY "判定=REJECTED"
                   DISPLAY "理由=AMOUNT_OVER_LIMIT"
               ELSE
                   IF WS-ACCOUNT-STATUS = "A"
                       DISPLAY "判定=ACCEPTED"
                       DISPLAY "理由=WITHIN_RULES"
                   ELSE
                       DISPLAY "判定=REJECTED"
                       DISPLAY "理由=ACCOUNT_INACTIVE"
                   END-IF
               END-IF
           END-IF
           STOP RUN.
```

上記ではソースコード中のコメント行を省略しています。ソースコード内のコメントは規則と規約（金額は正数必須、上限は端点を含む、最初の失敗理由のみ報告）を説明するにとどめ、`DISPLAY` のテキストを 1 行ずつ復唱することはしていません。

## データと規則

本課では入力ファイルは一切与えられません。サンプル取引はプログラム内に完全に固定されており、**外部入力はありません**。入力フィクスチャも結果ファイルもありません。判定に関わるのは以下の 4 つの値です：

| フィールド | `PIC` / 格納バイト数 | 初期値 | 役割 |
|---|---|---|---|
| `WS-TRANSACTION-REFERENCE` | `X(12)` / 12 バイト | `TXN-00000001` | 取引識別子。エコー表示のみで、判定には関与しない |
| `WS-ACCOUNT-STATUS` | `X(1)` / 1 バイト | `A` | 口座状態。本課では `A` のみが有効とみなされる |
| `WS-TRANSACTION-AMOUNT` | `S9(7)V99`、`SIGN IS LEADING SEPARATE CHARACTER` / 10 バイト | `125.50` | 符号付き金額。下限側から判定に関与する |
| `WS-MAXIMUM-AMOUNT` | `9(7)V99` / 9 バイト | `1000.00` | 1 回の取引金額上限。端点を含む |

金額フィールドの 10 バイト = 1 文字の独立した先頭符号部 + 7 桁の整数部 + 2 桁の小数部です。`V` は想定小数点であり、**格納領域を消費しません**。`DISPLAY` 時に位置に合わせて表示されるだけです。したがって格納領域は 10 バイトですが、画面上で確認できる `+0000125.50` は 11 文字になります。上記の 4 つのバイト数は実機上で `FUNCTION LENGTH` を用いて実測した値であり、以降の課でレコードレイアウトを確認する際の基準として利用できます。本課には通貨コードフィールドはなく、デモ用の規約として金額は小数第 2 位までの「円」とみなし、為替レートや端数処理には触れません。

規則と境界ポリシー：

| 規則 | 実装条件 | ポリシー |
|---|---|---|
| 金额必须为正 | `WS-TRANSACTION-AMOUNT <= ZERO` → 拒绝 | 零与负金额都拒绝；`0.01` 起接受 |
| 单笔上限 | `WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT` → 拒绝 | 上限**含端点**，等于 `1000.00` 接受，`1000.01` 起拒绝 |
| 账户状态 | `WS-ACCOUNT-STATUS = "A"` 才接受 | 只有精确的 `A` 有效；`I`、`a`、空格和其他字符都报同一个理由 |

已由代码校验的条件就是上表三条。**没有**校验的：交易参考号的格式与唯一性（本课只回显）、状态码的具体含义（程序不区分 `I` 表示什么）、金额上限本身的来源（它是本课的演示常量）。前提说明：`WS-MAXIMUM-AMOUNT` 与三个样例值都是教学演示数据，不代表任何真实业务政策或监管限额。

## 境界値はどこで分岐するか

先记住一件事：这里的拒绝全都是业务拒绝，退出码照样是 `0`，程序里根本没有系统故障那条分支。下表每一行都在本机实际编译运行过：

| 金额 | 状态 | 在哪个比较处分叉 | `判定=` | `理由=` |
|---|---|---|---|---|
| `125.50`（原始初值） | `A` | 三个条件全部通过 | `ACCEPTED` | `WITHIN_RULES` |
| `0.00` | `A` | 第 1 层为真 | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| `-0.01` | `A` | 第 1 层为真 | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| `0.01` | `A` | 紧贴下界，`<= ZERO` 为假 | `ACCEPTED` | `WITHIN_RULES` |
| `1000.00` | `A` | 第 2 层为假（端点被包含） | `ACCEPTED` | `WITHIN_RULES` |
| `1000.01` | `A` | 第 2 层为真 | `REJECTED` | `AMOUNT_OVER_LIMIT` |
| `125.50` | `I` | 第 3 层为假 | `REJECTED` | `ACCOUNT_INACTIVE` |
| `-5.00` | `I` | 第 1 层为真，第 3 层**未执行** | `REJECTED` | `AMOUNT_NOT_POSITIVE` |

谁决定哪条分叉：

| 观察目标 | 决定它的比较 | 结果 |
|---|---|---|
| 下界 | `AMOUNT <= ZERO` | `0.00` 与负数拒绝，`0.01` 起接受 |
| 上限 | `AMOUNT > MAXIMUM` | 严格大于才拒绝，等于 `1000.00` 被包含 |
| 状态 | `STATUS = "A"` | 仅精确 `A`；`a`、空格、`I` 都拒绝 |
| 报哪个原因 | 三层嵌套顺序 | 只报最先命中的失败规则 |

## ソースコード読解パス

顺着数据往下读，比按行号读要快得多：

1. 先看 `WORKING-STORAGE` 那四个字段：状态是 `X(1)` 文本，金额是带独立符号的数值——后面比较行为不一样，根子在这儿。
2. 再看 `PROCEDURE DIVISION` 后面那 4 条 `DISPLAY`：先把参与判断的输入值打出来，方便你拿输入对照判定。注意它们之间没有句点，是同一个句子里排着的几条语句。
3. 最外层 `IF WS-TRANSACTION-AMOUNT <= ZERO`：它的 `ELSE` 只兜住“金额为正”的情况，所以金额本身就不对时，不会再去看上限和状态。
4. 第二层 `IF WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT`：留意用的是严格大于，端点因此被包含进来。
5. 第三层 `IF WS-ACCOUNT-STATUS = "A"`：最内层那个 `ELSE`，才是状态拒绝。
6. 三个 `END-IF` 由内向外一层层闭合，最后 `STOP RUN.` 收尾。整段代码只有这一个句点。

## 実行と観察

**入力：** なし。4 つの値はすべて `lesson.cob` の `VALUE` 句から来ており、キーボード、ファイル、データベースからは読み込みません。そのため、判定は**常に再現**されます——この点は [第 15 課](../15_sequential-file-read/README.md) 以降のファイル処理の課とは異なります。

**コマンドとその役割：**

```sh
mkdir -p build                                   # 先建输出目录，否则 -o 会因目录不存在而失败
cobc -fsyntax-only lesson.cob                    # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_04 lesson.cob      # 编译并生成可执行文件
./build/lesson_04                                # 运行程序，判定结果写到标准输出
echo $?                                          # 查看上一条命令的退出码
rm -rf build                                     # 清理编译产物
```

四条命令证明的事情不同：`-fsyntax-only` 只说明源码能通过语法解析，不生成也不运行程序；`-x` 要求生成可执行文件，`-o` 指定产物路径，返回码 `0` 且无诊断才表示编译通过；运行可执行文件才能观察到判定结果；`rm -rf build` 只是删除编译产物，本课不产生业务数据文件，所以清理不会丢数据。

**期待される結果（元の初期値）：**

| 観察項目 | 期待値 |
|---|---|
| `cobc -fsyntax-only` 終了コード | `0` |
| `cobc -x -Wall` 終了コード | `0`、コンパイル診断なし |
| 標準出力 | 以下の 6 行 |
| プロセス終了コード（`echo $?`） | `0` |
| 生成ファイル | `build/lesson_04` のみ |

```text
取引参照番号=TXN-00000001
口座状態=A
取引金額=+0000125.50
上限金額=0001000.00
判定=ACCEPTED
理由=WITHIN_RULES
```

输出行与中文对照：`取引参照番号` = 交易参考号，`口座状態` = 账户状态，`取引金額` = 交易金额，`上限金額` = 单笔金额上限，`判定` = 判定结果，`理由` = 判定理由。4 个 `理由` 取值：`WITHIN_RULES` 表示三条规则全部通过，`AMOUNT_NOT_POSITIVE` 表示金额不是正数，`AMOUNT_OVER_LIMIT` 表示金额超过单笔上限，`ACCOUNT_INACTIVE` 表示账户状态不是 `A`。判断程序行为时以标准输出的 `判定=` / `理由=` 为准，README 的中文说明负责解释这些取值。

**実際に観察された環境の詳細：** 本ワークスペースで `./build/lesson_04` を実行した際、標準エラー出力に `Warning: program compiled against libxml 212 using older 209` が出力されます。これは実行環境の共有ライブラリのバージョン差異による警告であり、本プログラムの業務出力ではありません（トリガーコンポーネントは未特定）。プログラムの業務出力はすべて標準出力に出力され、終了コードは `0` です。

### 証拠の出所と検証範囲

本课 README 中的预期输出、`边界值在何处分叉` 一节的 8 行结果、以及练习答案里的每个场景，都在本工作区用 `cobc 3.2.0` 实际编译运行核对过：`-fsyntax-only` 与 `-x -Wall` 返回码均为 `0`、无编译诊断，运行退出码均为 `0`，标准输出与文档逐字节一致。字段的 12 / 1 / 10 / 9 字节由单独的 `FUNCTION LENGTH` 程序实测。知识讲解里“把 `<=` 改成 `<`，`0.00` 会被接受”与“把 `>` 改成 `>=`，`1000.00` 会被拒绝”两个说法也各改一处运算符实测过（结果分别为 `ACCEPTED` 与 `AMOUNT_OVER_LIMIT`）。**未验证**的场景：多笔交易、并发、超出 `S9(7)V99` 容量的金额（本课不处理算术溢出），以及任何文件或数据库输入——本课没有这些路径。

## 本番フローをたどる

本課のこの判定を実際の処理チェーンに当てはめると、次のような位置づけになります：

1. **窓口またはアプリでの受付**：窓口係が伝票を受け付けるか、顧客が確認ボタンを押し、上流システムがまずこの業務を検証待ちの 1 件の取引に変換します。このステップは本課の管轄外です。
2. **検証プログラムの実行**：金額と口座状態を読み込みます。本課ではこの 2 つの値は `VALUE` 句にハードコードされていますが、本番バージョンでは [第 15 課](../15_sequential-file-read/README.md) からファイル読み込みに変更されます。
3. **受け入れまたは拒否を判定し、理由を付与する**：これが本課の成果物です。理由は `AMOUNT_OVER_LIMIT` のような固定の短いコードです。
4. **理由を窓口／カスタマーサポートへ返却**：窓口システムが `AMOUNT_OVER_LIMIT` を人間が読める言葉——「該当の金額は 1 回の限度額を超えています」に翻訳します。顧客が見るのはコードではなくこの文言です。窓口係はこれに基づき、顧客に金額を変更してもらうか、人手確認に回すかを判断します。
5. **下流システムへの引き継ぎ**：受け入れられた取引はそのまま記帳・勘定転記へと進み、拒否された取引は記録に残されて再鑑を待つか、直接返却されます。2 つの道のどちらに進むかは、すべてステップ 3 で報告された理由によって決まります。

本課で行うのはステップ 3 だけであり、しかも取引は 1 件、規則は 3 つだけです。実際のチェーンにおいて、上流が状態コードの正当性をどう保証するか、拒否レコードがどこに保存されるか、誰が再鑑を行うかは、すべてこのコードの外側の話です——**しかし「なぜ拒否されたのか」という情報は、この課から正確でなければなりません**。後続のあらゆるステップがこの情報を利用するからです。

## このコードが本番に入るとどうなるか

- **誰がスケジュールするか**：実際のシステムでは、上流の検証フェーズにおける 1 つのプログラムであり、スケジューラやオンライン取引チェーンによって 1 件ごとにトリガーされます。本課では見通しをよくするため、直接実行するように簡略化しています。
- **誰がその出力を参照するか**：窓口システム、カスタマーサポートの問い合わせ票、照合担当者がその `理由=` を読み取ります。彼らはソースコードは見ず、コードに対応する文言のみを認識します。
- **トラブル時に誰が呼び出されるか**：理由を誤って報告した場合（例えば「状態凍結」を「金額超過」と報告）、まず窓口係が誤った説明をし、顧客に無駄足を運ばせ、続いて照合時にその取引が宙に浮いて引き取り手がいなくなります——最終的に呼び出されるのは、この検証ロジックを作成した担当者です。
- **運用開始の初月に最も発生しやすい事故**：2 つあります。1 つは境界が明確に書かれておらず、業務側が「1000 を超えない」と言っているのにプログラムが `>=` で実装され、月末照合で別のシステムと 1000.00 のキリの良い取引で大量の差異が出ること。もう 1 つは業務上の拒否をシステム障害として扱い、単に金額が規則に合致しなかっただけなのにバッチジョブ全体を赤色（異常終了）にしてしまうことです。
- **後続システムはどう引き継ぐか**：[第 05 課](../05_evaluate/README.md) で取引種別の分類を始め、[第 08 課](../08_control-flow-practice/README.md) で単件の判定を複数件に拡張して受け入れ／拒否を集計し、[第 26 課](../26_error-handling/README.md) で業務上の拒否とシステム障害を完全に分離します。

はっきりさせておきます：このコードは 3 つのローカル規則と 1 つの固定された口座状態をデモしているだけです。通貨コード、口座の認可限度額、重複リクエスト検知、取引時間帯の制限はなく、認可や永続化も行いません。「判定 + 理由」が出たからといって「この取引は勘定転記できる」と誤読しないでください。
