# 修正方針（版本兼容、迁移、回滚、并行验证）

## 0. 边界

变更对象是**独立、版本化的企业客户布局** `ENTERPRISE-CLASS`（独立名称，
不与 canonical 大记录 `ENTERPRISE-CUSTOMER-V1` 同名）。canonical
27 字节 CUSTOMER v1（第 27 字节 = 记录状态 A/D）与夜间流状态抽取
（`M11CUST.COB` / `customer-status.txt`）**保持不变**；绝不把企业区分放到
CUSTOMER v1 第 27 字节。

## 1. 版本与兼容

- 新增 `ENTERPRISE-CLASS-V2.CPY`（24 字节，布局 `002`），**保留**
  `ENTERPRISE-CLASS-V1.CPY`（23 字节，`001`）。两个版本并存，按文件/
  记录首部的 `LAYOUT-VERSION` 选择。
- 读取程序遇到宽度或版本与声明不符 → **RC8** 中止，禁止静默补齐/截断。
- 下游企业区分抽取版本化：`CLASS|<id>|<class>`，切换期两版可区分
  （V2 为 2 字符）。

## 2. 迁移（v1 → v2）

- 写**新文件**，不原地改写 V1：`migrate-customer.py to-v2`。
- 映射：`A→A1`、`B→B1`、`C→C1`、`D→D1`；`LAYOUT-VERSION` `001`→`002`。
- 无法映射的单字符或非 `001` 版本 → RC8（不猜测）。
- 并行期同时保留 V1 与 V2，切换在核对通过后进行。

## 3. 回滚（v2 → v1）

- `migrate-customer.py to-v1`：要求版本 `002` 且 V2 第 2 字符为 `1`，丢回
  1 字符、版本还原 `001`，**字节级还原**原始 V1。
- 回滚触发条件：下游不兼容、并行验证不一致、或业务要求暂缓。

## 4. 数据切换与并行验证

1. 迁移出 V2 输入；`verify` 逐条核对 V1 与 V2 的 id/status/name 相同、
   版本符合 `001`/`002`、分类满足映射。
2. 并行运行 V1（迁移前基准）与 V2 抽取，比较 id 集合与分类（V2 去除第 2
   字符后应等于 V1，或按映射对照）。
3. 全流程在 V2 输入上跑通（含异常/回滚），再切换下游。

## 5. 切换与发布

- 使用**新的输出目录/run_id**发布 V2 结果；旧 V1 结果仍可追溯。
- 切换前冻结 V1 结果与校验和，作为回滚基准。

## 6. 不受影响项（回归门禁）

- canonical CUSTOMER v1：27 字节、第 27 字节 = 记录状态（A/D）。
- 夜间流 `M11CUST.COB` → `publish/<run_id>/customer-status.txt`
  （`STATUS|<id>|<status>`）。
- `check.sh` 步骤 4/7b 以回归证明二者不被本变更影响。

## 7. 未验证项处理

- 真实 DB 列迁移与外部消费方适配**未验证**，须 DBA/接口方确认后再切换。
- 平台仅 Linux x86-64；其他平台未验证。
