# Git の行単位操作：gitsigns.nvim

コードを変更するたびに `git diff` でファイル全体を見るのは大ざっぱです。**知りたいのは「追加した 3 行が正しいか」であって、ファイル全体の履歴差分ではありません。**

gitsigns は Git の差分を行単位で表示します。左側の欄で追加、変更、削除された行が分かり、連続した変更のまとまりである**個々の hunk**を直接ステージしたり元に戻したりできます。

---

## 1. 解決する課題

| 要件 | gitsigns なし | gitsigns あり |
|---|---|---|
| この行が変更されたか確認 | `git diff` を実行 | 左側の欄にマークが表示 |
| 一部の変更だけをコミット | `git add -p` の対話操作 | hunk 上で 1 回押す |
| 一部の変更を元に戻す | 手作業で削除 | `<leader>gr` でリセット |
| この行を書いた人を確認 | ファイル全体に `git blame` | `<leader>gb` で現在の行だけ表示 |
| この変更の内容をプレビュー | ウィンドウを切り替える | `<leader>gp` でフローティングウィンドウ |

## 2. 現在の設定

`lua/plugins/gitsigns.lua` は `version = "v2.1.0"`、`event = "LazyFile"` です。

### 記号

```lua
signs = {
  add = { text = "▎" },
  change = { text = "▎" },
  delete = { text = "" },
  topdelete = { text = "" },
  changedelete = { text = "▎" },
  untracked = { text = "▎" },
},
```

左側の欄では縦棒 `▎` で変更を示します。削除は `` の矢印で示します。色は種類ごとに異なり、highlight group で決まります。

`signs_staged` にも同じ設定があり、ステージ後の変更には別の色を使います。

## 3. すべてのキー

### 移動

| キー | 動作 |
|---|---|
| `]h` | 次の hunk へ |
| `[h` | 前の hunk へ |
| `]H` | 最後の hunk へ |
| `[H` | 最初の hunk へ |

### ステージ（`<leader>gh` 系）

| キー | 動作（`n` / `x` モード） |
|---|---|
| `<leader>ghs` | 現在の hunk をステージ |
| `<leader>ghr` | 現在の hunk をリセット（変更を破棄） |
| `<leader>ghS` | buffer 全体をステージ |
| `<leader>ghR` | buffer 全体をリセット |
| `<leader>ghu` | 直前のステージを取り消す |
| `<leader>ghp` | 現在の hunk をインラインでプレビュー |
| `<leader>ghb` | 現在の行の blame を表示 |
| `<leader>ghB` | buffer 全体の blame を表示 |
| `<leader>ghd` | index との差分 |
| `<leader>ghD` | HEAD（`~`）との差分 |

### 短縮キー（`<leader>g` 系）

設定コメントによると、これは LazyVim 風のキーで、**`h` を付けません**。

| キー | 動作 |
|---|---|
| `<leader>gs` | 現在の hunk をステージ |
| `<leader>gr` | 現在の hunk をリセット |
| `<leader>gS` | buffer 全体をステージ |
| `<leader>gR` | buffer 全体をリセット |
| `<leader>gu` | ステージを取り消す |
| `<leader>gp` | 現在の hunk をプレビュー |
| `<leader>gb` | 現在の行の blame |
| `<leader>gB` | buffer 全体の blame |
| `<leader>gy` | 現在の hunk をコピー（`n` / `v`） |

### hunk をテキストオブジェクトとして選択

| キー | 動作 |
|---|---|
| `ih` | **テキストオブジェクト**：現在の hunk を選択（`o` / `x` モード） |

`ih` は便利です。`dih` で hunk 全体を削除、`yih` でコピー、`vih` で選択できます。他の演算子と組み合わせて使えます。

### 記号表示の切り替え

| キー | 動作 |
|---|---|
| `<leader>uG` | Git 記号の表示を切り替え |

## 4. 典型的なワークフロー

### ワークフロー 1：変更の一部だけをコミット

3 箇所を変更し、そのうち 2 箇所だけをコミットする場合：

1. `]h` で最初の hunk へ移動
2. `<leader>gs` でステージ
3. `]h` で次の hunk へ移動
4. `<leader>gs` でステージ
5. 不要な 3 つ目を `<leader>gr` でリセット
6. `:!git commit -m "..."`

**これは `git add -p` を画面上で行う方法です**。ターミナルで y/n に答える必要はありません。

### ワークフロー 2：誤った変更の一部を元に戻す

1. 誤った箇所へカーソルを移動
2. `<leader>gp` でその範囲をプレビューして確認
3. `<leader>gr` でリセット

**`<leader>gr` は（`u` を除いて）取り消せません**。リセット前に必ずプレビューしてください。

### ワークフロー 3：この行を書いた人を確認

1. 問題のありそうな行にカーソルを置く
2. `<leader>gb`
3. フローティングウィンドウで commit、作者、日付、commit message を確認

「この不思議な条件分岐はいつ、誰が追加したのか」を調べるときに役立ちます。

### ワークフロー 4：hunk をコピーして共有

1. `vih` または `yih` で hunk 全体を選択/コピー
2. チャットウィンドウに貼り付け

範囲を手動で選ぶ必要はありません。

## 5. COBOL での利用例

### 例 1：複数のフィールドを変更した後、hunk ごとに確認

grug-far で 8 ファイルを変更した場合、ファイルに戻って次のように操作します。

1. `]h` で hunk を 1 つずつ移動
2. それぞれ `<leader>gp` でプレビュー
3. 問題がないことを確認してからまとめてコミット

**`git diff` を全体にわたってスクロールするより信頼できます**。見落としにくくなります。

### 例 2：失敗した置換を元に戻す

grug-far の `\r` 置換を間違えた場合：

1. `]h` で誤った hunk を探す
2. `<leader>gr` でリセット

**注意**：この方法で元に戻せるのは**未ステージ**の変更だけです。すでに commit 済みの変更には `git revert` を使います。

### 例 3：列位置を壊していないか確認

COBOL を変更した後：

1. `]h` ですべての hunk を確認
2. 行頭のインデントに影響がないか注意する

COBOL は列位置に敏感です。`<leader>gp` のインラインプレビューで、インデントが壊れていないか直接確認できます。

### 例 4：バグが入った箇所を調べる

あるフィールドの処理に問題がある場合：

1. 問題の行にカーソルを置く
2. `<leader>gb` で blame を確認
3. 問題の変更を導入した commit を探す

## 6. 練習

### 練習 1：記号を確認

```sh
cd ~/development/cobol
nvim lessons/17_fixed-length-files/lesson.cob
```

1. 任意の行の文字をいくつか変更
2. 左側の欄に記号が表示されるか確認
3. `u` で元に戻し、記号が消えることを確認

**合格基準**：変更した行に `▎` が表示され、元に戻すと消える。

### 練習 2：hunk をプレビュー

1. 1 箇所を変更
2. `<leader>gp`

**合格基準**：フローティングウィンドウに変更箇所の diff（`-` が旧行、`+` が新しい行）が表示される。

### 練習 3：1 つの hunk をリセット

1. 離れた 2 箇所を変更
2. `]h` で最初の箇所へ移動
3. `<leader>gr` でリセット
4. 2 つ目の変更が残っていることを確認

**合格基準**：最初の箇所だけが元に戻り、2 つ目は残る。

### 練習 4：`ih` テキストオブジェクト

1. 1 箇所を変更
2. `vih`
3. 選択範囲を確認

**合格基準**：その hunk の変更行すべてが選択される。

### 練習 5：blame

1. 比較的古い commit にある行へカーソルを置く
2. `<leader>gb`

**合格基準**：フローティングウィンドウに commit hash、作者、日時が表示される。

### 練習 6：一部だけをステージ（重要）

**⚠️ コピーしたリポジトリで行い、このリポジトリでは操作しないでください。**

1. 2 箇所を変更
2. `<leader>gs` で最初の箇所をステージ
3. `:!git diff --cached` で最初の箇所だけがステージされていることを確認
4. `:!git reset` でステージを取り消す

**合格基準**：「ステージ済み」と「未ステージ」の変更を区別できる。

## 7. よくある問題

### 左側の欄に記号がない

考えられる原因：

1. ファイルが Git リポジトリにない
2. 変更がすでに commit されている（未コミットの差分がない）
3. `<leader>uG` で記号表示を無効にした

次で確認します。

```vim
:Gitsigns toggle_signs
```

### `<leader>gr` でリセットした変更を戻せない

`<leader>gr` は**変更を破棄**します。vim の undo stack で保護されている間だけ `u` で戻せますが、Neovim を終了すると戻せません。

**まず `<leader>gp` でプレビューし、その後に `<leader>gr` でリセットしてください。**

### `<leader>gs` と `<leader>gS` を間違える

`gs` は **hunk**（現在のまとまり）をステージし、`gS` は **buffer**（ファイル全体）をステージします。小文字は一部、大文字は全体です。

### blame の情報が少ない

`<leader>gb` は `blame_line({ full = true })` を使っており、1 行表示としては最も詳しい形式です。ファイル全体を見るには `<leader>gB` を使います。

### 記号の色がテーマに合わない

記号自体は設定で `▎` に固定され、色は highlight group（`GitSignsAdd` など）で決まります。テーマを変更すると色も変わります。

## 9. 対象範囲

- キー設定は `lua/plugins/gitsigns.lua` にあり、`<leader>gh*` と `<leader>g*` の 2 系統を使えます。後者は短縮形です。
- `version = "v2.1.0"` に固定されているため、動作はこのバージョンに基づきます。
- **`<leader>gr` / `<leader>gR` は変更を破棄します**。vim の undo stack がある間だけ保護されます。リセット前に必ず `<leader>gp` でプレビューしてください。
- ステージ操作が変更するのは Git index です。**自動的に commit はされません**。commit には引き続き `git commit` が必要です。
