# 第 05 课：EVALUATE——把交易码分类到明确的处理分支

一笔交易进来，你得先知道它“是什么”，才能决定对它做什么。本课教的就是这一步：用 `EVALUATE` 把同一个字段的多个取值分派到各自的处理分支，并让“不认识的取值”有明确出路。这套分类思路在[第 06 课](../06_perform-loops/README.md)的循环里按索引复用，到第 08 课汇总成多笔交易的计数。

## 业务现场

先看一个具体场面（机构、时间、量级都是教学演示，不是哪家真实机构的数据）。

某银行夜间批处理，凌晨两点开始跑当天柜面和 App 产生的交易。上游核心系统给的交易文件里，每笔交易只有一个字符说明它是什么：`D` 存款、`W` 取款、`T` 转账。这个字段的取值你怎么解释不算数——它是上游业务定的，加不加值、什么时候加，你在批处理这一侧只能跟着走。

这套逻辑最早是拿 `IF` 串出来的：一个 `IF` 判 `D`，`ELSE IF` 判 `W`，最后一个 `ELSE` 兜底。写的那天没问题，改的那天才要命。业务部先加了个 `F`（手续费），有人找地方插了一段；第二年又来了个 `R`（冲正），另一个人往嵌套里边再塞一层。等到审计或者排障的人问一句“还有哪些交易码是没人管的”——没人敢指着那段代码回答。那个 `ELSE` 兜的到底是什么，堆了三层之后连作者自己都得从上往下重读一遍。

而金融系统有条底线是硬的：**不认识的输入，不能当成正常交易默默处理掉。** 一笔不知道类型的交易，要是被顺手当成存款记进账户，比程序当场报个错严重得多——错了没人立刻知道，等对账发现时已经晚了一步。

所以你要的不是“再多写几个 `IF`”，而是一套能一眼看全、还能明确回答“剩下的去了哪儿”的分派结构。

## 为什么现在学

[第 04 课](../04_if-conditions/README.md)你已经能用 `IF` / `ELSE` / `END-IF` 干两件事：按金额区间接受或拒绝一笔交易，按账户状态决定要不要往下走。但那两处判断的对象，一个是数值范围、一个是单一状态，都只有两种去向。

你可能会想：那多几个取值，不就是多写几个 `ELSE IF` 吗？

先看它长什么样。用 `IF` 串表达 `D`/`W`/`T` 加一个兜底，大概是这个味道：

```cobol
IF WS-TRANSACTION-CODE = "D"
    ...
ELSE IF WS-TRANSACTION-CODE = "W"
    ...
ELSE IF WS-TRANSACTION-CODE = "T"
    ...
ELSE
    ...   *> 到这一步，兜的是"其他所有码"还是"我漏写的那个"，说不清
END-IF
```

能跑，也有三个具体的别扭：

1. **subject 每次都要重写一遍。** 同一个 `WS-TRANSACTION-CODE` 在这段里被比较了三次，将来字段改名，你得一处一处改。
2. **新增一个码要自己决定插哪儿。** 插在外层还是塞进内层，直接影响后面那个 `ELSE` 还归谁管。第 04 课讲过，`ELSE` 只跟最近一个还没结束的 `IF` 配对——嵌套一深，这条规则就开始咬人。
3. **最要命的是兜底说不清。** 最后那个 `ELSE` 名义上接住“已知三个之外的全部”，但你没法只看这一处就回答“还有哪些码没人管”。加分支的人可能插错位置，读的人得从上往下追。审计要的不是“我觉得都覆盖了”，是能一眼数出来的清单。

`EVALUATE` 就是来解决第 3 条的：subject 只写一次，已知值一个个平列出来，兜底那条也摆在明面上。**“哪些代码被显式承认、剩下的走哪条路”，一眼可见。**

## 这个知识点是什么，它解决什么问题

**它是什么。** 说人话：`EVALUATE` 是“一个字段、多个取值、每个取值走自己那一段”的选择结构。写完 subject 就只写一遍，下面每个 `WHEN` 列一个可能值，最后 `WHEN OTHER` 收尾。

**它在业务里解决什么问题。** 上游给的代码空间不会给你一份封口的清单。今天 `D`/`W`/`T`，下个月业务部加个 `F`，半年后真冒出个你从没见过的码——可能是上游上了新业务忘了通知你，也可能是文件坏了混进了脏字符。你写不全“所有可能的值”，所以需要的不是“把今天的码背下来”，而是一个能明确说出“剩下的去哪了”的结构。本课要教的就是这个：已知码各有明确处理类别，未知码统一走待人工核对，而不是继续按正常路径往下跑。

**什么时候不该用它、用错会怎样。** 两个常见误用，业务代价比语法错误贵得多。

一是把它当万能判断使。`EVALUATE` 的强项是“一个字段对一串精确值”。如果你要判的是金额区间、或者好几个字段的组合条件，硬塞进来反而绕。GnuCOBOL 支持 `EVALUATE TRUE` 配条件表达式，但那是后面的用法，本课先学 subject 对精确常量的简单形式。

二是把 `WHEN OTHER` 当成垃圾桶。它在本课的职责只有一个：接住契约之外的取值，标成未知。别顺手把“空值校验”“格式检查”“大小写归一化”都塞进去——那样一来，你就分不清“合法但未知的码”和“根本就是脏数据”，排障时最需要的那条线索也就丢了。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `EVALUATE <字段>` 配合多个 `WHEN "<值>"`，对同一个字符字段的多个精确取值分流。
- 用 `WHEN OTHER` 承接契约内未列出的取值，而不是让它们静默通过。
- 运行程序，读出 `D`、`W`、`T` 分别产生的分类标签和处理标签。
- 说明小写 `d`、空格和其他字符为什么都进入 `WHEN OTHER`（字符比较是精确匹配）。
- 说明本课只输出分类标签与处理标签，没有执行任何账户过账。

边界：本课不读文件、不做算术、不修改余额、不写日志或拒绝文件；大小写没有做归一化，空值/格式错误也没有专门的校验分支——它们只是落入 `WHEN OTHER`。文件读取从[第 15 课](../15_sequential-file-read/README.md)开始，拒绝结果写出从第 16 课开始，业务拒绝与系统故障的分流从第 26 课开始。

## 知识讲解

### EVALUATE 怎么写

批处理上游按接口契约给出单字符交易码，程序要在同一处把每个已知代码映射到对应的处理类别，并让没人处理的代码也有明确出路。写法就是“一个 subject 对多个常量”：

```cobol
EVALUATE WS-TRANSACTION-CODE
    WHEN "D"
        DISPLAY "分類=DEPOSIT"
    WHEN "W"
        DISPLAY "分類=WITHDRAWAL"
    WHEN OTHER
        DISPLAY "分類=UNKNOWN"
END-EVALUATE
```

- subject 是 `WS-TRANSACTION-CODE`，一次只取一个字段——这就是它比 `IF` 串省事的地方。
- 每个 `WHEN` 给出该字段的一个可能值；程序执行第一个匹配的分支，走到 `END-EVALUATE` 这一段选择就结束。
- `WHEN OTHER` 在没有任何显式 `WHEN` 匹配时执行，是本课的兜底路径。

### 反例 → 正例

上面那段 `IF / ELSE IF / ELSE` 就是反例：能跑，但“还有哪些码没人管”回答不了，加一个码还得纠结插哪儿。

换成 `EVALUATE`（正例）：

```cobol
EVALUATE WS-TRANSACTION-CODE
    WHEN "D"   ...
    WHEN "W"   ...
    WHEN "T"   ...
    WHEN OTHER ...   *> 契约之外的码，全在这
END-EVALUATE
```

两个好处一眼可辨：subject 只写一次，不用在每个条件里重复比较同一个字段；已知值与兜底值平列排开，“哪些代码被显式承认、其余走哪条路”看得见。新增一个交易码，只需在 `WHEN "T"` 和 `WHEN OTHER` 之间插一条 `WHEN`，不用去动任何 `ELSE` 的归属。第 04 课强调过 `ELSE` 与最近一个尚未结束的 `IF` 关联，`EVALUATE` 用 `END-EVALUATE` 划出明确范围，正好避开这类嵌套风险。

### 字符比较是精确的，不认“差不多”

`WS-TRANSACTION-CODE` 是 `PIC X` 文本字段，`WHEN "D"` 比较的是字符本身：小写 `d` 不等于大写 `D`，空格、数字、其他字符也都不等于 `D`/`W`/`T`。这些取值一律落进 `WHEN OTHER`，被标成 `UNKNOWN`。本例的接口约定就是大写 `D`、`W`、`T`。

这一点在真实批次里是能踩出事故的：上游哪天把码改成小写发过来，正常交易会整批被标成未知。想接受大小写变体或别名，必须先在契约里写清楚、再在程序里做归一化，不能默默给某个字符追加含义。本课没有做这层归一化——这是有意留的边界。

### 关于输出文本的语言

仓库约定：源文件注释与 README 讲解使用中文，程序运行输出的业务文本沿用日文。本课输出的 `取引参照番号` 意为“交易参考号”，`取引コード` 意为“交易代码”，`分類` 意为“分类”，`処理` 意为“处理标签”（例如 `処理=ADD_TO_ACCOUNT` 表示“处理建议=记入账户”）。判断程序行为时以实际输出和本节的中文说明为准。

## 完整示例源码

[`lesson.cob`](./lesson.cob) 用固定常量 `D` 展示存款分支：先显示交易参考号与代码，再输出一个分类标签和一个处理标签。

```cobol
      * 合法取引コード D/W/T 由接口契约定义；本课把它当作输入前提，不在程序内校验取值。
       IDENTIFICATION DIVISION.
       PROGRAM-ID. EVAL05.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 WS-TRANSACTION-REFERENCE PIC X(12)
          VALUE "TXN-00000001".
       01 WS-TRANSACTION-CODE PIC X VALUE "D".
       PROCEDURE DIVISION.
           DISPLAY "取引参照番号="
               WS-TRANSACTION-REFERENCE.
           DISPLAY "取引コード=" WS-TRANSACTION-CODE.
           EVALUATE WS-TRANSACTION-CODE
               WHEN "D"
                   DISPLAY "分類=DEPOSIT"
                   DISPLAY "処理=ADD_TO_ACCOUNT"
               WHEN "W"
                   DISPLAY "分類=WITHDRAWAL"
                   DISPLAY "処理=SUBTRACT_FROM_ACCOUNT"
               WHEN "T"
                   DISPLAY "分類=TRANSFER"
                   DISPLAY "処理=PROCESS_BOTH_ACCOUNTS"
      * 契约外取值统一归入待人工核对；本课只输出分类标签，不做任何过账。
               WHEN OTHER
                   DISPLAY "分類=UNKNOWN"
                   DISPLAY "処理=REJECT_FOR_REVIEW"
           END-EVALUATE
           STOP RUN.
```

### 数据字段

| 字段 | PIC / 初值 | 含义 |
|---|---|---|
| `WS-TRANSACTION-REFERENCE` | `X(12)` / `TXN-00000001` | 交易参考号文本，不参与算术 |
| `WS-TRANSACTION-CODE` | `X(1)` / `D` | 单字符交易码，取本课契约允许的 `D`/`W`/`T` |

### 过程逐步解析

1. `IDENTIFICATION DIVISION`、`PROGRAM-ID` 给程序命名；`WORKING-STORAGE SECTION` 用 `VALUE` 给出固定的参考号与交易码，程序没有其他输入。
2. 第一条 `DISPLAY` 输出交易参考号（`X(12)` 文本，不参与算术），第二条输出交易代码，方便核对当前固定样例。
3. `EVALUATE WS-TRANSACTION-CODE` 打开多路选择，subject 是那个单字符代码。
4. `WHEN "D"` 输出 `分類=DEPOSIT` 与 `処理=ADD_TO_ACCOUNT`；`WHEN "W"` 输出取款标签，`WHEN "T"` 输出转账标签。每条分支只输出两个静态标签。
5. `WHEN OTHER` 输出 `分類=UNKNOWN` 与 `処理=REJECT_FOR_REVIEW`，覆盖 `D`/`W`/`T` 之外的所有取值。
6. `END-EVALUATE` 显式结束选择范围，`STOP RUN.` 结束程序。

分类与处理标签都是 `DISPLAY` 的静态文本，程序不执行存款、取款或转账，也不改写任何余额。

## 运行与观察

本课不读键盘、文件、命令行参数或数据库，也不生成数据文件，因此在本课目录或任意目录执行结果都相同。下面按本课目录说明。

**输入：** 无外部输入。看到的每一行都来自 `lesson.cob` 里的程序内常量和 `DISPLAY` 字面量，不是文件或数据库数据。

**命令及作用：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                    # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_05 lesson.cob      # 编译并生成可执行文件
./build/lesson_05                                # 运行程序，业务输出写到标准输出
echo $?                                          # 查看上一条命令的退出码
rm -rf build                                     # 清理生成的可执行文件
```

`-fsyntax-only` 只验证语法路径，不生成也不运行程序，不能替代编译和运行观察；`-x` 要求 GnuCOBOL 生成可执行程序，`-o` 指定输出路径；`rm -rf build` 只删除本课生成的可执行文件，不触碰源码。

**想亲眼看分支。** 把 `lesson.cob` 里 `01 WS-TRANSACTION-CODE PIC X VALUE "D".` 的初值分别改成 `W`、`T`、`X`、`d` 各跑一次，你会看到：`W` → `分類=WITHDRAWAL` / `処理=SUBTRACT_FROM_ACCOUNT`，`T` → `分類=TRANSFER` / `処理=PROCESS_BOTH_ACCOUNTS`，`X` 和 `d` 都落进 `WHEN OTHER` → `分類=UNKNOWN` / `処理=REJECT_FOR_REVIEW`。四种情况退出码都是 `0`。**`d` 走未知这条路，就是“精确比较”最直接的证据。** 看完记得把初值改回 `D`，别把改动静悄悄留在文件里。

## 修改练习

从原始 [`lesson.cob`](./lesson.cob) 出发，为接口新增的交易码 `F`（手续费）增加一条 `WHEN "F"` 分支，并把样例代码改为 `F` 以便观察：在 `EVALUATE` 中 `WHEN "T"` 分支之后、`WHEN OTHER` 之前插入输出 `分類=FEE` / `処理=CHARGE_FEE` 的分支，同时把 `WS-TRANSACTION-CODE` 的初值 `VALUE "D"` 改为 `VALUE "F"`。约束是不改动 `D`/`W`/`T` 分支的输出、不改动 `WHEN OTHER` 的语义与输出、保持固定格式。完整题目、预期差异与原因见 [`exercise.md`](./exercise.md)，参考答案见 [`answer.md`](./answer.md)。

这道题就是上面“上游加了个 `F`”那件事的最小练习版：你会亲手体验一次“新增码 = 只插一条 `WHEN`”，然后回头验证兜底那条路没被碰坏。

## 走一遍真实流程

假设上游真的发来通知：从下个月起多一个交易码 `F`（手续费）。从收到通知到上线，你要走的步子大概是这些：

1. **先动契约，不动代码。** 让业务/上游把 `F` 的取值和含义写清楚：它要不要过账、要不要收费率、和 `D`/`W`/`T` 是不是互斥。契约没定，代码写了也是猜。
2. **插一条分支。** 在 `EVALUATE` 里 `WHEN "T"` 之后、`WHEN OTHER` 之前加 `WHEN "F"`，输出新的分类和处理标签。这就是本课修改练习做的事。
3. **把样例切成新码，跑一遍。** 初值改成 `F`，重新编译运行，确认 `取引コード=F`、`分類=FEE`、`処理=CHARGE_FEE`，退出码还是 `0`。
4. **回头验兜底。** 再把初值改成 `X` 和 `d` 各跑一次，确认它们仍然落在 `UNKNOWN` / `REJECT_FOR_REVIEW`。**新增分支没动兜底，这一步才算真的验过。** 最后把初值改回 `D`。
5. **同步这一课的配套。** 夹具（这里是程序内常量）、`exercise.md`、`answer.md` 和 README 里的预期输出要一起改，别只改程序——题目和答案预期值对不上，接手的人会被坑一整天。
6. **往下游交接。** 处理标签真要变成动作，还差好几课：多笔交易按索引循环是[第 06 课](../06_perform-loops/README.md)，接受/拒绝计数汇总到[第 08 课](../08_control-flow-practice/README.md)，把拒绝明细写成文件是[第 16 课](../16_file-writing/README.md)，区分业务拒绝与系统故障是[第 26 课](../26_error-handling/README.md)，带批次号和原始码的日志是[第 27 课](../27_logging/README.md)。

## 这份代码进了生产会怎样

- **谁调度它：** 夜间批处理的调度器按计划拉起它，只认可执行文件路径和退出码——本课所有分支退出码都是 `0`，调度器看不出这笔交易是不是被标成了未知。
- **谁看它的输出：** 排障和运营的人看标准输出。`分類=UNKNOWN` / `処理=REJECT_FOR_REVIEW` 这一行就是他们追“这笔怎么没入账”的起点。
- **未知码最后去了哪儿：** 在本课里它只是两个 `DISPLAY` 出来的标签，**没有**真的进待人工核对队列，也没有写拒绝文件。要让它变成真动作，得等第 16 课（写拒绝明细）和第 26 课（区分业务拒绝与系统故障）。
- **出事谁被叫起来：** 最危险的不是报错，是**不报错**。要是未知码被静默按正常路径处理了，可能一直没人被叫，直到对账发现金额对不上。所以“未知码必须走可见的兜底路径”这条规矩，比它看起来重要。
- **下一个系统怎么接：** 下游（第 06、08 课的循环与计数）依赖这里给出的分类标签做分派，标签改了，下游的统计口径就跟着变。
- **第一个月最容易出的事故：** 一是上游加了码却没通知，全批落进 `UNKNOWN`；二是上游哪天改成小写发送，正常交易整批被标成未知——这两件事本课都拦不住，只能靠契约和日志。

也要把话说清楚：本课不读文件、不做算术、不修改余额、不写日志或拒绝文件，处理标签只是 `DISPLAY` 出来的文本。它没有实现真实的过账、拒绝或审计流程，也不声称任何生产、审计或监管保证。真正把这条链路补齐，还要往后走好几课（见上一节）。
