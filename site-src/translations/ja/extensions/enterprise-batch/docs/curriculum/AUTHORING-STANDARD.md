# 課程制作と受け入れ確認の基準


## 1. 個別の実習単元で納品する構成

```text
curriculum/modules/07-matching/labs/03-one-to-many/
  README.md                 学習者の課題と受け入れ条件。答えを直接示さない
  DESIGN.md                 入出力、状態図、業務ルール、制約
  starter/                  ビルド可能な開始コード。TODOを明確に記載
  copybooks/                バージョン管理されたインターフェース
  fixtures/normal/           正常入力
  fixtures/boundary/         EOF、長さ、金額、空ファイルなどの境界
  fixtures/invalid/          原因を明確にした異常入力
  expected/                 独立して算出した出力、RC、統計、ルール説明
  scripts/                  build/run/check/reset。任意の起動ディレクトリから実行可能
  evidence/README.md         学習者が提出する証跡。合格結果を先に記入しない
instructor/modules/07/...   参考実装、根本原因、ヒントの段階、採点説明
```

共通の銀行モデルと共通プログラムは正本を1つだけ保守します。実習ではバージョン管理された設定、パッチ、または段階スナップショットで利用し、同名プログラムを大量に複製して別実装を作ってはいけません。小規模な実験では独立したソースコードを認めますが、銀行システムとの関係を説明してください。

## 2. READMEが答えるべき質問

1. なぜ業務上この処理が必要なのか。学習者はどのような要件を受け取るのか。
2. 入力ファイル/DBはどこから来るのか。形式は何か。どの前提条件が保証済みか。
3. クリーンなcheckoutから、どうビルド、実行、リセットするのか。実行でどの派生ファイルが上書きされるのか。
4. 期待する出力、RC、件数、金額はいくつか。独立してどう照合するのか。
5. どこを変更する必要があり、どのインターフェースを壊してはいけないか。
6. どの条件を意図的に壊し、どう調査・復旧するのか。
7. 問題箇所の特定にどのプラグイン操作が役立つか。端末だけで行う代替手段は何か。
8. 完了時に提出する証跡は何か。どの結果を失敗とするか。

DISPLAYで説明文を表示するだけのプログラムを、ファイル処理、DB、ソート、突合、統合プロジェクトの主要な実装としてはいけません。コードは付属データを実際に処理する必要があります。

## 3. fixtureのマトリックス

| 分類 | 最低限の対象 | 結果の要件 |
|---|---|---|
| 入力境界 | 欠落、0バイト、最終レコード、マッチなし、両側EOF、短い/長いレコード | RC、拒否、空ファイルを許可するかの方針を明記 |
| フィールド | 必須値が空、不正な数字、未知の状態、金額の上下限、符号/スケール | フィールド単位で理由を明示し、暗黙の切り詰めをしない |
| キー | Master重複、取引重複、逆順、同一キーの順番違い、孤立キー | 多重度と分類方針を明記 |
| DB | 結果なし、NULL、一意制約、接続失敗、トランザクションのロールバック | 元のDB状態と対応するRC |
| 環境 | 出力権限なし、一時領域不足、並行ロック、誤った日付 | 正式な出力を公開せず、ソースデータを上書きしない |
| 復旧 | コミット前/後、公開前/後のクラッシュ、同日の重複起動 | 二重適用を防ぎ、状態と証跡を一致させる |
| 潜在エラー | RC0だが金額が誤り、行不足/過剰、古いDB Snapshot | コントロール合計または差分受け入れ確認で必ず検出 |

ファイルfixtureには文字コード、改行、バイト長、チェックサムを記録します。不正バイト/不正Packed Decimalは実際のバイト列または再現可能な生成方法を含め、「ここに不正データがある」とREADMEに書くだけではいけません。乱数データ生成器は演習素材を作るためにのみ使い、学習者が実装する中核COBOLアルゴリズムの代わりにしてはいけません。

## 4. 期待結果と検証証跡

expectedは、実装を実行して結果を正解とみなすのではなく、業務ルール、手作業で照合できる小さな例、または独立した参照モデルから先に決めます。各expectedにルールの説明と計算過程を添えます。

検査では少なくとも、コンパイル、ソース形式、スクリプトの状態、終了コード、ファイルのバイト/論理内容、拒否分類、件数の保存、金額の保存、正式公開の状態を確認します。比較時に正規化を許す場合は、改行コード差のように項目ごとに明記します。固定長レコードの誤りを隠すために出力全体をtrimしてはいけません。

証跡の形式：バージョン/コミット、コンパイラとDBツールのバージョン、営業日、run_id、コマンド、生のRC、入力チェックサム、出力チェックサム、照合表、調査結果と制約。ログや出力がアサーションと一致しなければ失敗です。

## 5. 参考解答と障害資料の配布

学習者用パッケージには課題、利用可能な資料、段階的なヒントのみを含め、講師用パッケージには参考実装、根本原因、発生条件、最小修正、誤誘導する手掛かり、採点項目を保管します。公開リポジトリで解答を秘匿することはできません。instructorを含めずに再現可能な学習者用パッケージを提供し、自習者には解答の場所を知らせる必要があります。

障害資料には少なくともScheduler Flow/状態、JOB Log、Shell、ソースコード、Copybook、元の入力、パラメーター/Manifest、DB seedまたはSQL Logを含めます。障害は不正な数字、DB一意制約、空入力、Master逆順、システムリソース障害、RC0だが業務上の誤り、の6種類以上とします。それぞれに実際に再現できる入口を用意します。ホストのABEND名とGNUCOBOLの実際の動作は分けて説明します。

障害調査では、現象と影響範囲→タイムライン→仮説と証拠→最小再現→根本原因→修正/ロールバック→復旧と再実行→再発防止の順で成果を提出します。元入力を書き換えたり、アサーションを緩めたりして障害を「修正」してはいけません。

## 6. Legacy Maintenanceの変更パッケージ

要件：顧客区分を1桁から2桁に拡張します。コーディング前に次を提出します。

- 影響調査書：フィールド定義、すべての使用箇所、依存関係図、未確認事項。
- 修正対象一覧：Copybook、プログラム、ファイル、DB、Shell、JOB、設計書、下流インターフェース、担当ロール。
- 修正方針：レイアウトv1/v2、互換性方針、移行/ロールバック手順、データ切り替え、並行検証。
- Test Case：正常、境界、異常、バージョン間、エンドツーエンド、復旧シナリオ。
- Evidence計画：テストごとの期待結果と証跡の保存先。

調査レビューの後に変更します。完了時には変更前後のレイアウト、生成ファイル、DB結果、上流/下流テスト、ロールバック証跡を提出します。卒業プロジェクトの複雑さは、実際の業務、実行経路、依存関係で示します。Copybook、Shell、JOBノード、論理テーブルの役割を、システム構成一覧で追跡可能にしてください。

## 7. モジュール07ベンチマークの受け入れ確認

L1では両側EOFの状態と3種類の出力を扱います。L2では同じキーの連続累計、同一キー内の取引順、取引重複、オーバーフローを扱います。L3では複数ストリームの多重度表、状態遷移表、Snapshot日付の検証を提出します。L4では少なくとも150フィールドの一覧と独立した差分一覧を提出します。

中核処理にファイル全体の配列読み込み、SQL Join、Python突合がないことを確認します。独立したJOBとしてシステムSORTを使うことは認めますが、学習者は引き続きCOBOLで順編成突合と整列性検査を実装・検証する必要があります。メモリ証跡、件数保存、金額保存のいずれかが欠けていれば承認しません。

## 8. 卒業時の採点と必須ゲート

| 評価項目 | 配点 |
|---|---:|
| データ構造とバイト解釈 | 15 |
| ファイル/ソート/突合の正確さ | 25 |
| DB、JOB、復旧、冪等性 | 20 |
| 影響調査と安全な変更 | 20 |
| 障害調査と証跡 | 20 |

合計80/100以上に加え、すべての必須ゲートに合格する必要があります。二重引き落としがないこと、金額/件数の照合が正しいこと、失敗時に公開されないこと、上流/下流とのバージョン互換性に証拠があること、障害の根本原因を再現できること、調査してから変更していること。必須ゲートの失敗を他項目の得点で補うことはできません。修了時の実地演習には未知の障害を含め、すでに提示された解答の繰り返しだけにしません。

## 9. 段階リリースのチェックリスト

- [ ] 段階目標、前提知識、所要時間、業務成果が明確。
- [ ] 開始コードと参考実装をクリーンな環境でビルドできる。
- [ ] 読み込むすべてのファイルとDB seedが課程に含まれている。
- [ ] expectedには独立した計算根拠があり、RCとコントロール合計を確認済み。
- [ ] 学習者は解答を見ずに課題を完了できる。
- [ ] ソースは選定した固定形式に従い、例外となる自由形式の実験には印が付いている。
- [ ] プラットフォーム/ツールのバージョン、ABI、DBプリコンパイル、エラーコードの制約を明記。
- [ ] プラグインを使う課題と、端末だけで行う代替経路の両方を実行可能。
- [ ] 実行/リセットで元fixtureや他の実験成果物を壊さない。
- [ ] 課程/講師/証跡の各バージョンが対応し、「合格済み」と捏造していない。
