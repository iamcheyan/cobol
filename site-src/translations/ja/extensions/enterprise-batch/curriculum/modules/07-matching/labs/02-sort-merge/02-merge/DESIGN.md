# 07.2 MERGE：整列済み取引ストリームを統合

## インターフェースと順序

各sourceはTRANSACTION v1で、ASCII 55バイト + LFです。各ストリームはそれぞれ`(account_id 1–10, sequence_no 35–40, transaction_id 11–26)`の厳密昇順でなければなりません。空sourceは許可します。全体出力は同じ全キー昇順、標準LFとし、各行の元55バイトを維持します。`transaction_id`や`sequence`を再解釈/書換えません。日付、ID、方向、金額、status検証は07.1と同じです。金額0は下流業務分類用に保持し、statusはNのみです。全キー重複は全体transaction ID重複と等価でRC8となります。口座とsequenceが同じでもIDが異なれば有効で、ID順に並びます。複数source間またはどれだけ離れていてもID重複はRC8です。

MERGE前に各sourceをストリーム検査し、物理幅、LF、フィールド、source内順序を検証します。その後COBOLが実際に`MERGE ... USING source-1 source-2 ... OUTPUT PROCEDURE`を実行します。連結してからSORTする代替を使わず、入力ストリームの偶然の同順位順にも依存しません。全キーが同一なら重複ID契約で拒否されるため、source間の安定優先順位は定義しません。

手計算例：Feed-Aは(1,1,Z…001)、(1,2,M…003)、(2,1,B…005)を含み、Feed-Bは(1,2,A…002)、(1,3,A…004)、(2,1,A…006)を含みます。各入力は整列済みです。正しい出力ではFeed-BのA…002がFeed-AのM…003より先で、同じsequence内をID順に決めます。L2ブリッジはACCOUNT 1の期首1000、ACCOUNT 2の期首100、T01貸方500、同一sequenceのA…002貸方100/M…003借方50、T04がT01を取り消して借方500、口座2の貸方10/借方10を使います。期末残高はそれぞれ1050と100です。

## RCと公開

すべての入力検証、MERGE完了、全体ID一意性、SORT-RETURN=0、出力のバイト検証を通過した場合のみRC0で公開します。RC8は形式/日付/フィールド/source内順序/ID重複エラー、RC12はシステム/一時領域/権限/ロック/build/予期しないSORT-RETURN/検証/公開失敗です。成功以外のRCでは正式出力を作りません。ストリーム検証で各sourceとmerge後の件数、全キー順序、フィールドバイト保持、ストリームをまたぐ全体ID一意性を確認します。
