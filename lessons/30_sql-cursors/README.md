# 第 30 课：Cursor——一次打开，把整张表一行一行取到末尾

月末结账日凌晨，对账程序要扫的不是一个账户，是**整张**账户快照表：少说几万行，多的时候十几万行，柜面开门前得跑完，跑完还得把"到底取了多少行"报给值班的人。这一刻，你要的是一种"一次打开、逐行读完"的取数方式，而不是"报一个账号、回一行"的点名式查询。

本课就补这块能力：用一个游标 `ACCOUNT-CURSOR`，按 `DECLARE → OPEN → FETCH → CLOSE` 的生命周期把账户一行行读出来，写进 COBOL 宿主变量，并按 `SQLCODE` 分清楚"取到一行""结果集到头了""SQL 真出错了"。

## 业务现场

> 说明：下面的机构、时间、量级都是为了讲清知识点编的演示场景，不对应任何一家真实机构的真实数据。

凌晨 2:10，日终账务刚把当天的账户余额快照落进数据库。你的批次被调度器拉起来，任务一句话：**把这张快照表整个过一遍**，把每个账户的账号、客户号、余额逐行取出来，交给后面的核对环节。到底有多少行？没人提前告诉你——多的日子十几万，淡季可能就几千。程序不能假设"就两行"。

你可能会想：上一课不是刚学会查账户了吗，直接查不就行了？问题在于上一课那句 `SELECT ... INTO` 是"点名"的：你给它一个账号，它回你一行。现在的情形正好相反——**你不知道要查谁，你要的是所有行**。拿点名式查询去扫全表，多出来的行你根本接不住，而且它取完一行之后也没法告诉你"后面还有没有"。

这就是游标要解决的问题。它把一次查询变成一个**还在读的结果集**：`OPEN` 之后数据才算真的开始返回，然后你一行一行 `FETCH`，直到某一次 `FETCH` 告诉你"没有了"。这里最值钱、也最容易踩错的一点是：**"没有了"是正常收工，不是错误。**`SQLCODE = 100` 表示结果集读到头了，属于业务上的正常结束；`SQLCODE = 0` 表示这次取到了一行；只有其它值才代表数据库真出了事。

把这件事说透一点，因为它特别贵。如果你把 `100` 也扔进失败分支，第二天早上值班的人会看到批次**每天都报"失败"**，可实际上账目一条都没错——表就是被正常读完了而已。真实系统里这种"假失败"最磨人：报警一直响，查半天什么问题都没有，最后真出事的那天，反而淹没在这堆假报警里没人认真看。

## 为什么现在学

前一课（[第 29 课](../29_embedded-sql/README.md)）你已经能把 GixSQL 预编译跑通、连上本机 SQLite，用宿主变量取回一个账户。那是个了不起的起点，但它只够回答一种问题："账号 X 的余额是多少？"

而对账要回答的是另一种问题："**这批快照里都有谁、分别多少钱？**" 换句话讲，数据是一批，不是一个。

你可能会说，那我在程序里写个循环，一个账号一个账号挨个查不就完了？可以，但你首先得**先知道有哪些账号**——而这正是你此刻不知道的东西。你被迫干的事就变成了"先查一遍拿到全部账号，再按账号逐个查回去"，本来一趟能读完的数据，硬生生查了两遍，账号一多还得多占一份内存。

COBOL 给的答案就是游标：让数据库那边保留一个"正在被读的结果集"，你这边一行一行取，取到尽头为止，不用提前知道有多少行，也不用把账号先捞到内存里。它顺手还给了你三样东西——`DECLARE` 只登记查询、`OPEN` 才真正发请求、`FETCH` 每取一行都有一个明确的状态码。这三样合起来，才让你能写出"读完整张表并且数清楚读了多少行"的批次。

这一课的出口，就是"能一批一批、一行一行地把数据库侧数据当数据处理"这个能力。下一课（[第 31 课](../31_data-synchronization/README.md)）会在这个基础上把数据库快照与文件快照按键比对，做出差异清册；再往后到[第 32 课](../32_bank-reconciliation-project/README.md)汇成完整批次。所以这里如果把"什么时候算读完了"搞错，后面整条链子都会跟着错。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 游标是数据库查询的一个"把手"：先声明（`DECLARE`，只登记查询文本，不取数），再打开（`OPEN`，这才真的开始发请求），然后反复取（`FETCH ... INTO`，每执行一次往前挪一行，把当前行各列写进 COBOL 字段），最后关掉（`CLOSE`，把资源还给数据库）。这四步的顺序不能乱，而每一步之后 `SQLCODE` 的取值，就是你判断"接下来该怎么办"的唯一依据。

**它在业务里解决什么问题。**

- 让"读多少行"由数据自己决定，而不是写死在程序里。今天 3 行、明天 12 万行，你的代码一个字都不用改。
- 让"读完"变成一个**可以判断的状态**（`100`），而不是靠猜。批次跑完能报出"本次取到 002 行"，这个数字第二天要拿去和上游对账——对不上就说明有行被漏掉或重复。
- 让"空结果"和"真故障"分开。表的某一段今天可能一笔数据都没有，这是日常，不该触发报警；数据库连不上、表不存在，那才是要叫人起来的事。

**什么时候不该用它，用错会怎么样。**

- 只查一条已知主键的记录，用上一课的 `SELECT ... INTO` 就够了，上一条游标反而多写不少代码。
- 要读的是一批**文件**而不是数据库，那是一行行读文件（第 15 课起）的活，跟游标没有关系。
- 最容易出事的误用，就是前面说的那个：把 `SQLCODE = 100` 当故障，于是"读完了"变成"失败了"；反过来，把真正的 SQL 错误当成"读完了"一笔带过，那更糟——账没读全，批次却一路绿灯往下走。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `EXEC SQL DECLARE ... CURSOR FOR SELECT ... END-EXEC` 声明游标，并说明声明时**不执行**查询。
- 用 `OPEN` 真正发起查询、用 `FETCH ... INTO` 把每行各列写进 COBOL 宿主变量、用 `CLOSE` 释放游标。
- 用 `EVALUATE SQLCODE` 区分 `0`、`100`（结果集结束，正常）和错误值，并让错误以非零退出码结束进程。
- 分别运行两行夹具与空表夹具，核对"多行 + EOF"与"空结果集"两种形态，说明空结果集本身不是 SQL 故障。
- 指出两处容量边界：显示用余额字段只有 5 位整数，行计数只有 3 位（超过 999 行会回卷）。

边界：本课只读结果集，不做 `UPDATE/DELETE ... WHERE CURRENT OF`，不使用 `FOR UPDATE`，不涉及事务、并发与提交/回滚；游标每个进程只打开一次。示例数据库是本机 SQLite 文件（真实 SQL 引擎、真实文件），**不代表** Oracle/PostgreSQL/DB2 的游标行为——“空、单行、多行与 EOF”一节记录的“空表返回一条空白记录”只在本工作区的工具链上复现过。工具链只在本工作区的 x86-64 Linux + GixSQL v1.0.20b 上验证过。

## 工具链：为什么游标也得先预编译

`EXEC SQL` 那一行，GnuCOBOL 编译器本身不认识——它得先被 GixSQL 的预编译器换成一堆普通的 COBOL 调用。链路和第 29 课一模一样：

```text
lesson.cob --(gixpp -e)--> 预处理 COBOL --(cobc -fstatic-call -lgixsql)--> 可执行文件
                                              ↑
                                    运行期由 LD_LIBRARY_PATH 找到 libgixsql 与 SQLite 驱动
```

几个命令的分工别搞混，否则很容易白忙一场：

- `build.sh check` 只跑到预编译 + `cobc -fsyntax-only`，**不产出可执行文件**，所以它过了只说明语法和预编译没毛病，不等于程序能跑。
- `build.sh build` 才真正编译、链接出可执行文件。
- `build.sh run` / `run-empty` 会先重建数据库再运行。

**没有工具链时不要用模拟 SQL 顶替**——那等于把“没有验证过”当成“已经实现”写进文档。

## 游标生命周期与源码阅读路径

源码见 [`lesson.cob`](./lesson.cob)。下面按"数据什么时候真的动起来"的顺序走，不是按行号顺序——这样你读代码时脑子里那条时间线才对得上。

### 1. `DECLARE` 只是登记查询，一行都还没读

```cobol
           DECLARE ACCOUNT-CURSOR CURSOR FOR
               SELECT ACCOUNT_NO, CUSTOMER_ID, BALANCE
                 FROM ACCOUNT_SNAPSHOT
                ORDER BY ACCOUNT_NO
```

这条 `DECLARE` 只把查询文本登记给游标这个名字；此刻数据库**没有**开始取数，一行也不会读。这是最反直觉的一步——写程序时你会觉得"语句写了就该干活了"，但游标的活是 `OPEN` 才干的。

顺带说 `ORDER BY ACCOUNT_NO`。它管的是**输出顺序**：让每次运行的行序都一样。别小看它，关系数据库本来不保证返回顺序，删掉这一句，某次运行看起来照样对，下一次顺序就可能变了——做着做着你就开始怀疑自己。"稳定可复现"在批处理里是一件必须争来的东西，不是默认就有的。

### 2. `OPEN` 才真正发请求

`2000-OPEN-CURSOR` 执行 `OPEN ACCOUNT-CURSOR`。只有 `SQLCODE = 0` 时才把 `WS-CURSOR-OPEN` 置为 `"Y"`——源码注释解释了为什么非得这么守一下：**只有成功打开过的游标才允许 `CLOSE`**。`OPEN` 失败会输出 `オープン=エラー SQLSTATE=` 并置失败标志。

记住这个 `WS-CURSOR-OPEN` 标志的用意，它是"别对没打开的东西动手"这条规矩的落地。真实系统里不少麻烦都是从"资源没开成功却去用/去关"来的。

### 3. `FETCH` 循环：`SQLCODE` 的三种结果，三条路

`3000-FETCH-ROWS` 用 `PERFORM UNTIL WS-DONE = "Y"` 循环，每轮执行一次 `FETCH ... INTO :WS-ACCOUNT, :WS-CUSTOMER, :WS-BALANCE`，再按 `SQLCODE` 分流：

| `SQLCODE` | 含义 | 本课行为 | 退出码影响 |
|---:|---|---|---|
| `0` | 取到一行 | 计数 +1，显示 `行=...`，继续循环 | 无 |
| `100` | 结果集结束（正常） | 显示 `取得=EOF SQLCODE=100`，置 `WS-DONE` 结束循环 | 无 |
| 其他 | SQL 错误 | 显示 `取得=エラー SQLSTATE=`，同时置 `WS-FAILED` 与 `WS-DONE` | `1` |

`SQLCODE = 100` 是正常业务结果；把它当故障会让“表里没有账户”这种日常情况中止批次。反过来，把 SQL 错误当成“取完了”会掩盖真正的数据库问题——所以本课用 `EVALUATE SQLCODE` 把两者分得干干净净，绝不合并。`GIXSQL_NOREC_CODE=100` 在 `build.sh` 的 `run`/`run-empty` 中固定，保证“无数据”被判定为 100。

**失败路径（已实测）：** 本课的错误分支不是纸面设计，下面两条都是真跑出来的：

| 注入方式 | 实际输出 | 退出码 |
|---|---|---|
| `DATASRC` 指向不存在的目录 | `接続=エラー SQLSTATE=08001`、`行数=000`（连接没建立，所以**没有**断开那一行） | `1` |
| 库里没有 `ACCOUNT_SNAPSHOT` 表 | `接続=成功`、`オープン=エラー SQLSTATE=HY000`、`行数=000`、`切断=成功` | `1` |

第二种情况里的连锁反应值得看一遍：`OPEN` 失败，`WS-CURSOR-OPEN` 就一直是 `"N"`，程序于是跳过 `FETCH` 和 `CLOSE`（没打开的游标不能去关）；但连接是成功的，所以仍然要断开；最后 `WS-FAILED` 把进程退出码定成 `1`。这一串"哪一步能继续、哪一步必须跳过"，就是游标生命周期真正的难点所在。

### 4. `CLOSE` 与断开连接

`4000-CLOSE-CURSOR` 在正常 EOF 或 `FETCH` 出错后关闭**已打开**的游标；`9000-DISCONNECT-DATABASE` 执行 `CONNECT RESET`。连接、打开、读取、关闭、断开任一环节失败，都会让进程以状态 `1` 结束（`STOP RUN RETURNING 1`），方便 shell 作业立刻发现。调度器不看你的屏幕，它只看这个数字。

### 5. 和第 29 课的单行查询比一比

| 维度 | 第 29 课 `SELECT ... INTO` | 本课游标 |
|---|---|---|
| 取几行 | 一次一行，多行结果会报错 | 打开后逐行取到 100 为止 |
| 发起时机 | 执行 SQL 语句即查询 | `DECLARE` 只登记，`OPEN` 才查询 |
| 结束状态 | `SQLCODE = 100` 表示“无匹配行” | `SQLCODE = 100` 表示“结果集结束” |
| 资源释放 | 无可见游标 | 必须 `CLOSE`，且只关闭成功打开过的游标 |

注意最后一行表格里那个"同样的 100、不同的含义"：`100` 在第 29 课是"没查到"，在本课是"读完了"。语境不同，处理方式也不同——所以判断 `SQLCODE` 的时候，脑子里得清楚这个游标是"查一条"还是"读一批"。

## 空、单行、多行与 EOF

本课的主题就是结果集的形态和状态分叉，所以四种形态都真跑过。下表是关键观察（`行=` 的行数就是取到的记录数）：

| 形态 | 夹具 / 造法 | 关键实际输出 | 实际命令 | 退出码 |
|---|---|---|---|---|
| 多行（2 行） | `schema.sql` | 2 条 `行=`，`取得=EOF SQLCODE=100`，`行数=002` | `./build.sh run` | `0` |
| 空表 | `schema-empty.sql` | **1 条空白** `行=`，`取得=EOF SQLCODE=100`，`行数=001` | `./build.sh run-empty` | `0` |
| 单行 | 查询加 `WHERE ACCOUNT_NO = 'A000000002'` | 1 条 `行=`（`A000000002`），`行数=001` | 见[修改练习](#修改练习) 2 | `0` |
| 多行（3 行） | 临时夹具插 3 行 | 3 条 `行=`，`行数=003` | 手工建房后运行 | `0` |
| 多行（1005 行） | 临时夹具插 1005 行 | 1005 条 `行=`，但 `行数=005` | 手工建房后运行 | `0` |
| EOF | 任意夹具末尾 | `取得=EOF SQLCODE=100`（由 100 触发，不是错误） | 同上 | `0` |

**空表为什么会打印一条空白记录？** 这跟"表里其实有数据"是两回事，别被它带偏。用 `sqlite3 build/cursor.db "SELECT COUNT(*) FROM ACCOUNT_SNAPSHOT;"` 查空库会得到 `0`，所以表里确实没有行；但 GixSQL v1.0.20b 的 SQLite 驱动在 `OPEN` 后**第一次** `FETCH` 会返回 `SQLCODE 0`，同时把账户号、客户号填成全空格、余额填成 `0`，要到**下一次** `FETCH` 才返回 `100`。这条空白记录会被当成一行显示、也计入 `行数=`，所以 `行数=` 比表里的真实行数多 1（源码注释已经把这个特例标出来了）。[`expected-empty-output.txt`](./expected-empty-output.txt) 记的正是本工具链下的**实际**输出，而不是想当然的 `行数=000`。

**这条边界只限本工具链。** 目前能确认的只有一句："在本工作区的 GixSQL v1.0.20b + SQLite 上复现过"。换别的 GixSQL 版本、换 Oracle/PostgreSQL/DB2、或者直接用原生 SQLite C API，**都不能据此推断**首次 `FETCH` 也会先给一条空白记录。所以：真要拿游标去读一个可能为空的查询，上线前必须针对目标驱动单独验证"首次 FETCH 到底返回什么 SQLCODE"——这是本课最该带走的一条工程习惯。

## 容量边界（已实测）

源码里有两个比数据范围窄的字段，越界时是**静默**丢数据，不留痕迹，值得单独记住：

| 字段 | 声明 | 边界与实测行为 |
|---|---|---|
| `WS-EDITED-BALANCE` | `PIC 9(5).99` | 只有 5 位整数。插入余额 `1234567.89` 后，实际显示 `BALANCE=34567.89`（高位被丢）。`WS-BALANCE` 本身是 `PIC S9(7)V99`，数据能装下，**显示副本**装不下。 |
| `WS-ROW-COUNT` | `PIC 9(3)` | 只有 3 位。插入 1005 行后，仍逐行取完 1005 行，但末尾显示 `行数=005`（只留低三位）。 |

这两项是**已实现行为**的真实限制，不是错误处理：它们既不报错，也不置失败标志，出了事你从输出上完全看不出来。源码在字段声明处用注释标明了这两条约束。真在生产里，"行数悄悄回绕"意味着你对账的第一步就错了——数字看着正常，其实少了 1000 行。

## 走一遍真实流程

把这个游标批次放进月末那晚的链路里，它长这样：

1. **凌晨 2:10**，日终账务把账户余额快照写进数据库的 `ACCOUNT_SNAPSHOT`。你的批次被调度器拉起来，本课的游标就是这趟链路的第一棒——它负责把整张快照变成一串 COBOL 能处理的记录。
2. **同一天早些时候或夜里**，核心系统还导出了一份文件形式的账户快照。第 31 课要做的，是逐行读文件、按账号到数据库里查对应账户，两边**按键比对**，分出"两边都有且一致""两边都有但金额变了""只有一边有"这几类，产出差异清册。它在数据库那一侧用的是按主键单行查询，但"把数据库侧数据当一批数据处理、读一行处理一行"这套纪律，正是本课给你的。也就是说：本课负责"把数据库那边的数据一条不落地读出来"，第 31 课负责"两边对上"。
3. **跑完要留痕**。本课末尾那行 `行数=` 会写进日志（第 27 课的日志体系），第二天值班的人拿它跟上游报表的账户数对一下——对不上，就说明中间有行没读到或者读重了。
4. **最终汇合**。第 32 课的银行对账项目把这些环节串成一条完整批次：读文件、查/写数据库、比对、写结果、报表、失败后重跑。第 32 课在数据库侧用的是按主键的单行查询，但"数据是一批、要一行一行处理干净、还要数得清处理了多少行"这套纪律，源头就在本课。游标本身要不要用，取决于那一课处理的是"一批"还是"一条"。

一句话收束：**本课不是教你怎么写 SELECT，而是教你怎么把一张表可靠地"读干净"，并且明确知道自己读到了哪里。** 这件事后面每一课都还要用。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器，一般排在"数据库快照就绪检查"之后。它只认两样东西——可执行文件在不在、退出码是多少。
- **谁看它的输出**：值班的人先看退出码，再看 `行数=`。行数明显不对（比如本该几万行却只报 002），当晚就得查。
- **出事谁被叫起来**：退出码非 `0` 会触发报警。本课特意让连接失败（`SQLSTATE=08001`）、表缺失（`HY000`）、读取错误都以 `1` 结束，就是为了让报警该响的时候响。
- **下一个系统怎么接**：这一课练出的"逐行遍历数据库"能力，会被下一课（第 31 课）用来把数据库快照和文件快照对上；再往后进第 32 课的对账项目。本课本身是纯"取数"角色，不修改数据库。
- **第一个月最容易出的事故**：
  1. 把 `SQLCODE = 100` 当故障 → 批次天天"失败"，实际一笔都没错，渐渐没人认真看报警；
  2. 看到本工具链的空表空白记录，就以为"所有驱动都这样" → 换到别的数据库，空结果的行为完全不是你预期的那样；
  3. 行计数回绕或者余额显示字段截断 → 输出看着正常，数字其实是错的。

也要把话说清楚，本课**只**证明了一件事："在本机 SQLite + GixSQL v1.0.20b 下，这条游标链路按预期工作，且只读一次。" 可更新游标（`FOR UPDATE` / `WHERE CURRENT OF`）、跨数据库方言的游标行为、事务边界与并发、SQL 失败后的部分写入与重跑策略，都不在本课范围。别把这里跑通的东西直接当成生产保证。

## 证据与未验证项

**证据来源：** 上文所有"实际输出/退出码"都来自本工作区对 `lesson.cob` 的 `./build.sh check`、`build`、`run`、`run-empty` 实测，以及手工构造的单行 / 3 行 / 1005 行 / 超大余额数据库。`SQLCODE 100`、错误分支的 `SQLSTATE`（连接失败 `08001`、表缺失 `HY000`）都是实测值，不是推断值。

**未验证项：** `CLOSE` 失败分支（`クローズ=エラー`）与 `FETCH` 中途出错分支，在本环境里**没能稳定注入**——代码路径确实存在，但没有跑过，所以这里不敢说有实测结论。“空白记录”是否也会出现在其他 GixSQL 版本或其他数据库驱动上，同样未验证。
