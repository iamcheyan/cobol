# B04 / 07.6 Boss L4: field-by-field comparison of extended enterprise customer records

## Business boundary

B04 compares extended enterprise customer snapshots for the same CUSTOMER-ID across two batches and locates changes to each business field. It does not replace existing interfaces: CUSTOMER27 remains the basic teaching record, ACCOUNT v1 remains the 47B account master, and TRANSACTION v1 remains 55B. This lesson adds a separate fixed-binary `ENTERPRISE-CUSTOMER-V1`; it does not put 175+ business attributes into ACCOUNT or claim to be B03's offline Customer Snapshot.

V1 keeps an independent one-byte `CUSTOMER_CLASSIFICATION` baseline (A retail, B business, C private, D public-sector). `RECORD_STATUS` has a different business meaning (A active/I inactive) and must not be misused as customer classification. **Do not place V2 fields alongside V1 or claim one-byte and two-byte values are different classification semantics.** First investigate V1 impact, then design a new `ENTERPRISE-CUSTOMER-V2`: widen the same classification field from PIC X to PIC X(2), layout version 001 to 002, and review V2 code mapping/offset changes/upstream-downstream migration separately. Example mapping: A→A1, B→B1, C→C1, D→D1. Never overwrite V1 files in place.

This proposal has 175 named business leaf fields across Header/Identity/Classification/Address/Contact/Bank relationship/Risk compliance/Limits/Channel/Audit. Field IDs, physical offsets, and comparison rules are in the adjacent `FIELD-CATALOG.csv`. There is no FILLER; group items occupy no bytes; V1 uses neither REDEFINES nor variable OCCURS. Thus aliases are not counted twice and runtime records are not variable length.

## Proposed physical record layout

- Encoding: fixed single-byte ASCII. Every DISPLAY text/code/number is one ASCII byte/character. Reject non-ASCII input with RC8. The exercise uses synthetic roman-character customer data and does not cover production Unicode/EBCDIC conversion.
- Framing: old and new files are contiguous fixed-width binary records, **1,778 bytes each, with no separator or LF**; fields are tightly packed in Copybook declaration order without alignment padding. Do not read with LINE SEQUENTIAL, `splitlines()`, or text conversion. An empty file has zero records; a complete extra record is an additional business key, not an “overlong line.”
- Layout fields: first `LAYOUT_VERSION=X(3)` fixed at `001`; then `BINARY_ABI_CODE=X(8)` fixed at `GCOB32BE`, identifying this version's GnuCOBOL 3.2/Linux x86-64 PIC COMP big-endian ABI; then the ten-digit ASCII `CUSTOMER_ID` key at offset 12.
- Representations: ordinary text/code/date uses DISPLAY `PIC X`; unsigned counts/revisions use ASCII DISPLAY `PIC 9(n)`; 18 limit amounts are nonnegative `PIC S9(9)V99 COMP-3`, 6 bytes, two decimal places in PRIMARY_CURRENCY major units. `RISK_SCORE_ADJUSTMENT` is also 6-byte COMP-3 but uses risk points, range −9999.99..9999.99; these units are not interchangeable. `RISK_SCORE` is `PIC S9(9) COMP`, 4 bytes, measured big-endian in GnuCOBOL (for example, 0x01020304 outputs 01 02 03 04); do not infer from CPU native endianness. COMP-5 is measured native little-endian locally but is not used in V1. V1 avoids implicit alignment.
- Valid packed bytes: every digit nibble must be 0–9; this course contract accepts only positive C and negative D sign nibbles. A real GnuCOBOL primitive probe found that this compiler returns false for `IS NUMERIC` on PIC S with F sign nibble, so F is not considered valid. Validate every nibble before parsing; invalid packed data must never enter arithmetic. Positive and negative zero C/D encodings both mean numeric zero: distinct raw bytes but equal numeric values. A local primitive probe measured both as `IS NUMERIC` and equal in comparison (primitive evidence, not final field/layout acceptance).
- File/platform limits: acceptance is only for GnuCOBOL 3.2 on a Linux x86-64 host where PIC COMP is measured big-endian, with matching Copybook, compiler options, and ABI tag. Other compilers, endianness, PIC/optimization options need a new ABI version and independent measurement. Validate COMP range before comparison.
- Version and raw-length gate: while holding the lock, the runner snapshots inputs and checks by bytes that total file length is a multiple of 1,778; a partial trailing record returns RC8. Then COBOL fixed-record reads validate each row's version, ABI, key, required/code fields, DISPLAY numeric values, COMP range, packed nibbles, and strictly ascending key. A GnuCOBOL fixed sequential read shorter than a record may silently pad PIC X and return 00; therefore **the byte-length modulo check is a required outer raw-byte boundary**. Do not claim FILE STATUS alone detects short records. Inserting/removing a byte fails modulo; an additional full record is classified by key/cardinality semantics.

Field start offsets use 1-based byte positions. CSV offsets are design-derived; they become a verified layout only after generating a Copybook, using a real GnuCOBOL layout writer to emit named sentinels for every field, and an independent byte checker verifies all 175 field slices, total length, and catalog. Compiler `LENGTH OF` proves total width only and cannot replace per-leaf offset evidence. The primary agent's independent acceptance also cross-checks every field; do not change its acceptance contract.

## Comparison semantics

Old and new files are each strictly sorted by CUSTOMER-ID with at most one row per key. COBOL does a bounded two-cursor sequential merge: equal keys compare each field; smaller old key emits OLD-ONLY; smaller new key emits NEW-ONLY. EOF on either side is valid; both empty returns RC0; records on one side only produce record-level business differences RC4. Duplicate/descending keys, version/ABI conflict, width error, or invalid encoding/value are structural RC8 and the whole batch is not published. Tool/disk/lock/output/verification failures are RC12 and not published. Valid business differences return RC4 and publish only after independent verification of report and counters.

Field rules are explicit:

- `RAW`: byte-for-byte field equality. Used for keys, version, status/code, dates, and identifiers whose representation must be retained.
- `TEXT-NORM`: first validate printable ASCII; map a–z to A–Z using ASCII rules; then remove only trailing ASCII spaces. Do not trim leading spaces, collapse internal spaces, or use locale/Unicode conversion. Equal normalized values are not business differences, but count “bytes differ, same semantic value” in the summary.
- `NUMERIC`: validate raw DISPLAY/COMP/COMP-3 representation and field range, decode according to PIC sign/decimal scaling, and compare exact decimal semantics without floating point. Different legal bytes with equal values are not business differences and increment representation-equal.
- `IGNORE-AUDIT`: allow audit-maintenance fields to change; count as audit-only and locate field_id in the report. Does not increase business-difference RC or the “field differences” count.

Executable domain rules: all-space required DISPLAY text/code is invalid; nullable text/date can represent NULL only as all spaces, never partial spaces. Reject control bytes/high-bit non-ASCII in all X fields; validate code fields against exact per-field sets in CSV. Flags are Y/N/U; MFA/voiceprint Y/N; record status A/I; classification A/B/C/D; customer type IND/ORG/TRU; product family DEP/CRD/LON/INV; currency JPY/USD; country codes for this exercise JP/US. Review-status values are per field in CSV (for example, KYC N/P/C/R, AML C/P/H/R). Dates range 19000101..20991231 and use Gregorian validation; audit timestamp is valid YYYYMMDDHHMMSS with HH00..23 and MM/SS00..59; CONTACT_TIME_FROM/TO are valid HHMM. Each count field's PIC width and upper bound are in CSV. All limits allow only 0.00..999999999.99, not negative; risk adjustment allows positive/negative and uses risk points. Primary telephone country/area/number must be all present or all NULL; spaces in nullable=N fields are structural errors, not default values.

Difference rows contain run ID, input version, old/new row sequence, masked customer key, field_id/name, 1-based offset, length, rule, difference type, and old/new display value. Exact comma-delimited row format (COBOL emits it; oracle independently recomputes it):

```text
FIELD,<run_id>,<layout_version>,<old_seq>,<new_seq>,<redacted_key>,<field_id>,<cobol_name>,<offset>,<length>,<rule>[,REDACTED]
AUDIT,<run_id>,<layout_version>,<old_seq>,<new_seq>,<redacted_key>,<field_id>,<cobol_name>,<offset>,<length>,IGNORE-AUDIT
OLD|<old value>
NEW|<new value>
```

`<redacted_key>` is exactly `******` plus the last four digits of customer ID. `<old_seq>`/`<new_seq>` are 1-based record positions in each file (`OLD-COUNT`/`NEW-COUNT`). `<name>` is canonical `cobol_name` from FIELD-CATALOG.csv (human business name `business_name` can be resolved by field_id). For one matched record, emit IGNORE-AUDIT blocks first, then business field blocks. Sensitive old/new values are always `[REDACTED]`; never write plaintext to stdout/stderr/difference reports. Raw binary in reports uses only safe hexadecimal representation, still masked when sensitive. Dates are YYYYMMDD and Gregorian-validated. Summary includes at least old/new/matched/old-only/new-only records, business-different fields, audit-only fields, normalized-equal, numeric-representation-equal, and structural rejects. COBOL maintains all counters; an independent verifier recalculates from raw records and the change inventory.

## Independent acceptance and publication

The core algorithm is COBOL: read fixed records sequentially, compare two keys with cursors, compare all 175 leaf fields per the catalog, and write a candidate. Python may generate fixtures and verify with independent field metadata/manual change inventory; it does not replace field comparison. Follow the accepted course runner pattern for input snapshot, lock, private stage, RC mapping, candidate byte/count checks, and no-clobber atomic publication. Complete all hashes and candidate validation before rename; do not run a fallible check after rename.

Independent changes must include: identical records; first/middle/last single field; multiple fields; text case/trailing-space equivalence; equal numeric value encoded as distinct valid packed zero; numeric changes/sign/scaling/bounds; ignore audit; sensitive-value redaction; invalid packed digit/sign; invalid DISPLAY number/range; key/version/ABI; empty/one-sided EOF/short/long/duplicate/descending cases. Hand-write expected raw hex positions and semantic values before running the implementation.

## Impact-investigation exercise: customer classification from one byte to two

The migration target is not `RECORD_STATUS`. Trace V1 `CUSTOMER_CLASSIFICATION PIC X` reads/comparisons/sort/output positions, then propose V2 with the same semantic field as `PIC X(2)`, layout version 002, explicit mapping and unknown-value policy. Trace customer master, B03 customer key/snapshot, B04 old/new comparison, downstream notification/channel/limit consumers, batch parameters, and recovery points. Keep V1 frozen. V2 must explain that widening the classification shifts every later physical offset, plus old-file reject/conversion policy, dual-write/parallel comparison, cutover, rollback, and version-conflict tests. Do not insert a PIC into V1 and overwrite files without investigation.
