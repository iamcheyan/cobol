# 第 07 课：Paragraph 命名段落——把批次主流程拆成可命名阶段

## 业务现场

周五凌晨 1:10，城商行的日终批次正在跑（教学场景，机构、金额、时间都是编的）。这个作业三年前只有一百多行，如今长到了九百行：初始化、过账、汇总、打印全挤在 `PROCEDURE DIVISION` 里，中间还夹着两个当年应急加的补丁。

凌晨 2:03，上游的人打电话过来问："今晚的余额汇总怎么全是 0？"值班的新人小林去翻日志，看到的却是一片祥和——没有报错，没有异常，退出码 `0`。调度器早把这个作业标成成功，后面依赖它的几个作业也照常跑完了。

天亮对账才发现问题：有个清零步骤被挪到了过账之后，把刚算出来的余额又清回 0。钱没少，但账上的数字全错，而系统一声没吭。

段落名真正要解决的就是这件事。它不是"代码整洁"这种审美偏好，而是给运维和接手的人留路标：半夜出事时，你要能指着日志里的一行说"这是 `2000-PROCESS` 打的"。比定位更贵的是**顺序**——初始化、处理、汇总的先后一旦写反，程序照样跑完、照样返回 0，错要等第二天对账才浮出水面。

## 为什么现在学

上一课你已经能让同一套逻辑跑 N 遍了。现在回头看看你写的那个程序：所有语句从上到下平铺在 `PROCEDURE DIVISION` 里。

三四十行的时候这样没问题，一眼扫完。可批次程序不会停在四十行：读文件一段、校验金额一段、过账一段、汇总计数一段，几百行是常态。到那时候，你被叫起来最想知道的是"哪一段坏了"，而不是从第一行重新读起。

你可能会想：我用注释标一下不就行了？

注释是好事，但它不能被执行。主流程里写 `PERFORM 1000-INITIALIZE`，读的人一眼看出这一步是初始化；注释写着"下面开始初始化"，三个月后没人保证它还对得上。更要命的是顺序——注释不会提醒你"初始化必须在过账之前跑"。

`PERFORM 段落名` 做的事，就是把"这段叫什么"和"它什么时候被调用"一起摆到主流程里，让人一眼看完。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 命名段落：在 `PROCEDURE DIVISION` 里给一段逻辑起个名字（比如 `1000-INITIALIZE`），要在别处执行它就写 `PERFORM 1000-INITIALIZE`。名字从 Area A 开始，语句照旧从 Area B 开始。跑到这段的最后一条语句，控制自动回到 `PERFORM` 的下一行——它是一次"跳过去做完再回来"，不是新开一个程序。

**它在业务里解决什么问题。**

- **主流程变成一张看得懂的清单。** 原来要读完九百行才知道这个批次干了什么；现在读主段落那几行就够了。
- **日志和代码能对上号。** 每个阶段打一行自己的标记，出事时直接看是哪一步断的（本课输出里的 `段階=...` 就是这个作用）。
- **顺序依赖被摆到明面上。** 初始化、处理、汇总这三个词本身就说明了先后，审代码的人扫一眼主段落就能问："这个顺序对吗？"

**什么时候不该用它。** 段落只活在当前这个程序单元里，它不是独立子程序。另一个批次也要用同一条金额规则时，你要的是 `CALL`（第 24 课），而不是把段落抄一份。还有一点最容易看走眼：段落共享同一份 `WORKING-STORAGE`，它不像函数参数那样自带隔离——本课练习 2 会让你亲手踩这个坑。

## 本课完成后的能力与边界

学完本课后，你可以：

- 在 `PROCEDURE DIVISION` 中定义命名段落，并让段落名从 Area A 开始。
- 用 `PERFORM 段落名` 执行段落，并说清控制什么时候回到 `PERFORM` 之后的那条语句。
- 把批次主流程拆成初始化、处理、结束汇总三个阶段，并在主段落里排好调用顺序。
- 解释段落为什么共享当前程序的 `WORKING-STORAGE`，以及调换调用顺序后最终余额为什么会变。
- 说明程序内部的 `PERFORM` 和之后要学的 `CALL` 子程序不是一回事。

边界：本课只用写在源码里的金额，不读文件、命令行参数或数据库，也不用 `CALL` 调独立子程序。跨程序接口与参数契约在第 23–25 课（Copybook、`CALL`、`USING`）展开，记录级错误处理在第 26 课展开。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件是固定格式。
- Linux 终端；本课不依赖数据库或附加工具。
- 语法检查和编译都在 `build/` 下生成可执行文件，删掉重来即可。

## 段落和 PERFORM 到底怎么用

段落名写在 `PROCEDURE DIVISION` 里，本仓库的固定格式要求它从 Area A 顶格开始。`PERFORM 1000-INITIALIZE` 执行这个段落里的语句；跑到下一个段落或过程范围末端，控制回到 `PERFORM` 之后的那条语句。

这里有个新手容易懵的细节：段落共享当前程序的 `WORKING-STORAGE`。`PERFORM` 不创建新程序，也不复制一份数据。所以在 `2000-PROCESS` 里算出的余额，`9000-FINALIZE` 直接就能读到——这是本课好用的一面，也是练习 2 那个坑的来源。

本例把 `0000-MAIN` 放在第一个位置。程序从主段落开始，依次 PERFORM 初始化、计算、汇总；`STOP RUN.` 写在段落定义之前，结束普通顺序执行，免得主流程"掉"进后面那些段落定义里。三个被调用的段落各自只干一件事。

段落名是团队约定，不是业务逻辑。GnuCOBOL 手册允许过程名由字母、数字、连字符和下划线组成，例如 `0100-Read-Transaction`；名字不能以连字符或下划线开头或结尾。

### 反例 → 正例：同样的余额，两种写法

反例——顺序写反，程序一声不吭：

```cobol
       0000-MAIN.
           PERFORM 2000-PROCESS
           PERFORM 1000-INITIALIZE
           PERFORM 9000-FINALIZE
           STOP RUN.
```

正例——把清零放在最前面：

```cobol
       0000-MAIN.
           PERFORM 1000-INITIALIZE
           PERFORM 2000-PROCESS
           PERFORM 9000-FINALIZE
           STOP RUN.
```

两段代码都能编译、都能跑完、退出码都是 `0`，编译器一个字都不会提醒你。区别只在输出：反例的最后一行是 `最終残高=0000000.00`，钱被后跑的初始化清掉了。这大概就是业务误用比语法错误贵的地方——语法错误编译器当晚就拦住，顺序错误要等第二天对账。

## 完整示例

完整源码见 [`lesson.cob`](./lesson.cob)，按固定格式编写。

示例里的金额是写死的演示数据：期初 `1000.00`、存款 `125.50`、取款 `40.10`，处理段落算出期末余额 `1085.40`。

| 段落 | 职责 | 关键语句 |
|---|---|---|
| `0000-MAIN` | 按流程调用三个阶段；收到返回后报告批次完成 | `PERFORM ...`、`DISPLAY`、`STOP RUN` |
| `1000-INITIALIZE` | 清零期末余额字段 | `MOVE ZERO TO ...` |
| `2000-PROCESS` | 计算期末余额并显示 | `COMPUTE ...`、`DISPLAY` |
| `9000-FINALIZE` | 显示结束阶段与最终余额 | `DISPLAY` |

每个 `PERFORM` 用的名字都对应一个段落定义。主流程先初始化，再计算，最后汇总；所以 `9000-FINALIZE` 能读到 `2000-PROCESS` 写进共享余额字段的值。

## 执行顺序逐步解析

1. 程序到达第一个段落 `0000-MAIN`。
2. `PERFORM 1000-INITIALIZE` 输出 `段階=INITIALIZE`，并把期末余额置零；段落结束后返回主流程。
3. `PERFORM 2000-PROCESS` 输出 `段階=PROCESS`，算出 `1000.00 + 125.50 - 40.10 = 1085.40`，输出 `0001085.40`；随后返回主流程。
4. `PERFORM 9000-FINALIZE` 输出 `段階=FINALIZE` 和读到的共享字段 `最終残高=0001085.40`，再返回主流程。
5. 主流程输出 `バッチ=COMPLETE` 并执行 `STOP RUN.`。没有执行流落进后面的段落定义。

顺带说一句句点：句点结束 COBOL 的句子，也结束还没收尾的语句作用域。本例在每个被调用段落的最后一条语句放句点，主段落的句点放在 `STOP RUN` 之后。

## 运行与观察

本课不读终端、文件或数据库，所以在本课目录或任意目录执行结果都一样。下面按本课目录说明。

**输入：** 无。三个金额是程序内固定数据，全部来自 `WORKING-STORAGE` 的 `VALUE`。

**命令及作用：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                  # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_07 lesson.cob    # 编译并生成可执行文件
./build/lesson_07                              # 运行程序，输出写到标准输出
echo $?                                        # 查看退出码
rm -rf build                                   # 清理生成的可执行文件
```

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，无编译诊断 |
| 标准输出 | 6 行，见下方代码块；阶段顺序为 INITIALIZE → PROCESS → FINALIZE |
| 进程退出码 | `0` |

```text
段階=INITIALIZE
段階=PROCESS
期末残高=0001085.40
段階=FINALIZE
最終残高=0001085.40
バッチ=COMPLETE
```

**输出字段对照（日文输出 → 含义）：** `段階` = 当前阶段；`期末残高` = 处理段落算出的期末余额；`最終残高` = 汇总阶段读到的余额；`バッチ=COMPLETE` = 批次完成。余额字段是 `PIC 9(7)V99`，`1085.40` 按 7 位整数位补零显示为 `0001085.40`，隐含小数点在显示时省略。

**实际观察到的环境细节（未验证项）：** 在本工作区运行可执行文件时，标准错误会输出 `Warning: program compiled against libxml 212 using older 209`。这是运行环境的链接库版本警告，不是本程序的业务输出；产生它的组件尚未定位，所以这里只记录现象，不推断原因。程序输出在标准输出，退出码为 0。

## 修改练习

两项修改各自从原始 [`lesson.cob`](./lesson.cob) 开始，别叠加。

1. 改金额：把 `WS-OPENING-BALANCE` 改成 `2000.00`、`WS-DEPOSIT` 改成 `250.00`（`WS-WITHDRAWAL` 保持 `40.10`），重新编译运行。新的期末余额应该是 `0002209.90`。
2. 改顺序：在 `0000-MAIN` 中把 `PERFORM 2000-PROCESS` 挪到 `PERFORM 1000-INITIALIZE` 之前，其余语句不动。记下阶段标记和最终余额——应该是 `0000000.00`，并解释处理段落写进去的值为什么会被后跑的初始化覆盖。

这第二题就是"业务误用比语法错误贵"的现场演示：编译不报错，运行退出码还是 0，钱却没了。每项修改后运行：

```sh
cobc -fsyntax-only lesson.cob
cobc -x -Wall -o build/lesson_07 lesson.cob
./build/lesson_07
```

## 举一反三练习

把同样的小批次拆成四个命名段落：读取样例、校验交易码、计算余额、输出汇总。为主段落安排合理的调用次序，并在每个阶段打标记；然后调换其中两个有数据依赖的段落，记下输出差异。仍然只用固定值，不要引入文件、表格或 `CALL`。题目见 [`exercise.md`](./exercise.md)，本题不提供答案。

## 走一遍真实流程

把这个小批次放回夜里那条链路：

1. **凌晨 0:40**，上游把当天的交易导成文件放进共享目录（亲手读文件是第 15 课）。
2. **凌晨 1:00**，调度器拉起你的作业。开头先清零累计器、准备输出，这段就是 `1000-INITIALIZE` 的位置。
3. 中间逐笔处理，一行算一笔——`2000-PROCESS` 那种段落。
4. **收尾**：`9000-FINALIZE` 把总笔数、总金额打进日志（第 27 课细讲日志该记什么）。这些数字第二天要拿去和上游对账。
5. **交接**：算出来的结果交给下游，写结果文件是第 16 课，写数据库是第 29 课起。

所以主段落里那几行 `PERFORM` 不是装饰，它是整条链路的目录。以后你读任何一份几百行的批次程序，先找主段落，再看它按什么顺序叫了谁。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器，通常排在"文件就绪检查"之后。它只认退出码，不看你的屏幕。
- **谁看它的输出**：值班的人先看日志里的阶段标记，再看金额。余额不对，当晚就得查。
- **出事谁被叫起来**：跑这个作业的人。你能不能十秒钟指出坏在哪一段，取决于当初段落名起得好不好。
- **下一个系统怎么接**：结果写成文件交给下游（第 16 课），或者写进数据库（第 29 课起）。
- **第一个月最容易出的事故**：把初始化加到处理之后——或者为了"修"某个问题临时插一条清零。程序不报错，退出码 `0`，调度器显示成功，错到第二天对账才被看见。练习 2 就是让你先在安全环境里撞一次。
- **它还没做的事**：本课只在一个程序内部分工。跨程序接口属于 `CALL` 的范围，别把内部段落当成独立子程序；真需要参数契约和独立调用时，见第 24、25 课。

话说清楚：本课证明了"给流程起名字"能让主流程可读、能让调用顺序的后果被观察到。它没有实现生产级的日志、错误分类和资源清理——批次失败后该退什么码、该留什么文件，要到第 26 课才讲。
