# 第 04 课：IF 条件判断——为一笔交易分出接受与拒绝

一笔交易进来，程序得先给个说法：过，还是不过；不过，是哪一条规则拦下的。本课把一笔样例交易固定在程序里，用三层嵌套 `IF` 依次判定“金额得是正数 → 金额不能超单笔上限 → 账户状态得有效”，并且只报**最先命中**的那条失败原因。

## 业务现场

周五下午四点五十，网点快关门了。一位客户在柜面递单，要转一笔钱出去；差不多同一时间，手机 App 上也有人点了“确认转账”。这两个动作在系统里长成同一种东西：一条等着被校验的交易。程序得当场给个结果。放行就没事了；一旦判成“拒绝”，麻烦才刚开始。

拒绝本身从来不是终点。柜员屏幕上不会只写“被拒绝”三个字，客户一定会追问一句“为什么”。答案只有两类：要么是**这笔金额本身不合规**（不是正数，或者超过了单笔上限），那钱根本没动过，柜员当场解释、客户改单子就行；要么是**账户状态不对**（被冻结、已销户），那这笔业务压根不该在柜面办，得转人工核实。同样一句“拒绝”，一个能当场办完，一个得让客户改天再来——区别就在程序报出的是哪一条原因。

最容易出事的是**顺序**。判断顺序一写反，一笔既超限又冻结的交易可能报成“金额超限”，柜员就让客户把金额改小再试，结果还是被拒；客户白跑一趟，柜面还得再解释一遍。所以本课不只要你能“分出接受和拒绝”，还要你能说清**为什么只报第一条命中的原因、这个顺序又是谁定的**。

还有一条规则最容易被含糊过去：单笔上限是“1000.00 就算超了”，还是“超过 1000.00 才算超”？需求里常写成“单笔不超过 1000 元”，一句话两种读法。程序里 `>` 和 `>=` 只差一个字符，端点就被划到不同的一侧。这种含糊不会让程序报错，只会让两个系统各写各的，月底对不上账。本课把端点当成必须写清、必须验的东西。

（这段是教学场景：机构、金额、时刻都是为了讲清规则编出来的，不是任何真实机构的真实数据。）

## 为什么现在学

你可能会想：判断条件谁不会，`if` 我写了好多年了。

问题在于，你以前写的多半是“跑一遍就完”的脚本。这里的场景不一样：**COBOL 程序是顺着往下走的，中途没有“停下来问一句”的位置**。第 [02](../02_data-types/README.md) 课你学会用 `PIC` 把账户号、状态、金额描述清楚，第 [03](../03_move-compute/README.md) 课你学会把它们算出一个结果；可到这一步为止，程序只会把写好的语句从头走到尾。

回头看看那笔周五下午的交易：金额 `-5.00`，账户还是冻结的。没有条件判断，程序照样往下走——照样“算完”、照样打印一句处理完成。它不拒绝，也不会告诉你哪里不对。这在业务上比程序崩了还糟：作业绿着，账却是错的。

换成你熟悉的话说：账户状态这个字段，在真实数据里什么值都可能有，你得让程序对着数据决定走哪条路，而不是靠人提前把数据筛好、分成不同文件喂进来。

COBOL 给的工具就是关系条件和 `IF` / `ELSE` / `END-IF`。听起来跟别的语言差不多，但有两个坑必须在本课踩实：`ELSE` 归谁全看**作用域**而不是缩进；**嵌套顺序就是拒绝原因的优先级**。这两点后面每节分流课都要用——第 [05](../05_evaluate/README.md) 课按交易类型分类，第 [08](../08_control-flow-practice/README.md) 课对多笔交易统计接受和拒绝，底子都是这里打的。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 一句话：让程序**看着数据自己选路**。干这件事的是两样东西——*关系条件*（`=`、`<`、`>`、`<=`、`>=`，拿两个值比出真或假）和 *`IF` / `ELSE` / `END-IF`*（真的走一条路、假的走另一条，`END-IF` 负责封口）。比起第 [03](../03_move-compute/README.md) 课的算术，它是另一种能力：不再只问“算出多少”，而是问“够不够格”。

**它在业务里解决什么问题。** 校验这种活，价值一半在“判得对”，另一半在“说得清”。柜面、客服、对账的人看到的只有一条判定加一条原因：金额超限、状态不对、还是通过了。原因给错，后面所有人都会跟着做错决定。`IF` 加嵌套，就是你**把业务优先级写进代码**的地方——谁先判、谁后判，源码上看得见，出了事能指着那一行说清。

**什么时候还用不上它（用错了更贵）。** 别拿条件判断去顶替输入校验。要是上游给的金额字段里混进了字母、或者编码不对，`IF` 只是在一份坏数据上做了一个看着正确的判断，它不会替你发现数据本身有问题；这类检查要等后面的课。也别忘了：本课的拒绝只是**业务判定**，退出码仍然是 `0`。把业务拒绝当成系统故障去报警，是另一类常见事故，第 [26](../26_error-handling/README.md) 课专门处理。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `=`、`<`、`>`、`<=`、`>=` 比较数值字段和字符字段，并说明端点值落在接受侧还是拒绝侧。
- 用 `IF` / `ELSE` / `END-IF` 为每个条件写出显式的接受与拒绝路径，不靠缩进或句点猜测 `ELSE` 的归属。
- 按固定优先顺序嵌套三层判定，说明为什么这样只会输出**一个**拒绝原因，以及换成三个平级 `IF` 会同时命中多条规则。
- 预判并核对边界样例：`0.00`、`-0.01`、`0.01`、`1000.00`、`1000.01` 与状态非 `A` 时的判定结果。
- 区分业务拒绝与系统故障：本课所有拒绝路径的退出码仍是 `0`。

边界：本课不读终端、文件或数据库，样例值写在 `WORKING-STORAGE` 的 `VALUE` 子句里；只有一笔交易，不修改余额、不做计数或汇总；不处理舍入与算术溢出（第 [03](../03_move-compute/README.md) 课已提示，第 [26](../26_error-handling/README.md) 课系统处理）；不做交易类型分类（第 [05](../05_evaluate/README.md) 课）和多笔批次（第 [08](../08_control-flow-practice/README.md) 课）。本课也不实现账户授权、并发控制、重复请求检测或持久化，这些都不是本课要证明的东西。

## 知识讲解

### 关系条件：比的是值，不是屏幕上长什么样

`=`、`<`、`>`、`<=`、`>=` 这五个运算符你都认识，`THEN` 是个可选词，写不写都一样。真正值得记住的是两个细节。

第一，两个数值操作数比较时，COBOL 按**实际代数值**比，跟字段 `PIC` 写了多少位、带不带符号、`USAGE` 是什么都无关。`+0000125.50` 和 `125.50` 是一回事。

第二，字符字段之间按字符集逐字符比，短的一边在右边补空格。所以 `"A"` 和 `"a"` 是两个不同的字符——处理账户状态时这点特别要命。

本课用到三个关系条件：

```cobol
WS-TRANSACTION-AMOUNT <= ZERO
WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT
WS-ACCOUNT-STATUS = "A"
```

第一条 `<= ZERO` 对零和负数都成立；第二条 `>` 只有**严格超过**上限才成立；第三条是字符比较，`a`、空格、`I` 全都不等于 `A`。

这里最容易踩的坑是：**端点归哪一侧，完全由运算符决定。** `<=` 把 `0.00` 划进拒绝侧，`>` 把 `1000.00` 留在接受侧。你要是顺手把 `<=` 写成 `<`，`0.00` 就被放行了；把 `>` 写成 `>=`，一笔正好 `1000.00` 的交易就被拒了。所以边界值不能单独评审，得和运算符一起看——这正是前面说的“需求含糊、系统各写各的”最典型的地方。

状态比较是精确比较。`WS-ACCOUNT-STATUS` 是 `X` 类型，`a`（小写）、空格和 `I` 都不等于 `A`，一律落进拒绝分支。你要真想让大小写都能过，那是接口层的约定，得显式写出来；COBOL 不会替你自动归一化。

### IF / ELSE / END-IF 与作用域归属

`IF` 在条件为真时执行紧跟的语句，`ELSE` 管为假的情况，`END-IF` 明确标出这个条件语句到哪儿结束。

新手常以为缩进决定 `ELSE` 归谁——COBOL 不看缩进。编译器的规矩只有一条：**一个 `ELSE` 归到最近那个还没结束的 `IF`**。你缩进得再漂亮，编译器也不领情。

本课三个 `IF` 都配了 `END-IF`，从最里层往外一层层封口。这么做的好处是三个 `ELSE` 谁属于谁，在源码上一眼可见，不用数空格，也不用靠句点猜。

顺带说个更坑的：**句点不只是“句号”，它会结束整个句子，顺手把还没结束的语句作用域一起关掉**。本课从头到尾只有最后 `STOP RUN.` 那一个句点。开头四条 `DISPLAY` 之间**没有**句点，它们是同一个句子里排着的几条语句，就照书写顺序一条条执行。你要是在中间随手补一个句点，本来属于 `IF` 内部的语句可能就掉到条件外面去了——而且编译器不一定报错。

### 嵌套顺序决定报出的拒绝原因

三条规则套娃的顺序，就是拒绝原因的优先级：

```text
金额 <= 0            → AMOUNT_NOT_POSITIVE     （最外层，先判）
  否则 金额 > 上限   → AMOUNT_OVER_LIMIT
     否则 状态 = A   → 接受
        否则          → ACCOUNT_INACTIVE      （最内层，最后判）
```

程序在**第一个为真的失败条件**处输出原因，然后就结束了，更深层的检查根本不会执行。所以那笔金额 `-5.00`、状态 `I` 的交易只会报 `AMOUNT_NOT_POSITIVE`，不会顺手告诉你状态也有问题。

这直接回答了“为什么非得嵌套”。要是三个检查写成平级 `IF`，两个失败条件会各自命中一次，程序打出两条互相矛盾的原因，看日志的人也不知道该信哪条。业务上“先说什么”是产品和会计定下来的规矩，不是程序员随手排的——顺序一改，对外的解释就跟着变了。

### 与 Java / Python 的区别

分支这件事，Java 用 `if` / `else if`，Python 用 `if` / `elif` / `else`，思路是一样的。差别在两点：COBOL 用 `END-IF` 显式标出语句结束；`ELSE` 绑定的是“最近的未结束 `IF`”，不认缩进。比较之前同样得确认类型：账户状态是文本，金额是带符号的十进制数。

COBOL 也支持用 `AND` / `OR` 把多个条件拼成一个复合条件，本课故意不用。原因是嵌套能把每条规则的优先级直接摆在源码里，正好练“哪层先判”的手感。复合条件等你读到那段语法再上手。

### 关于输出文本的语言

仓库有个约定：源码注释和 README 讲解用中文，但**程序运行时打印的业务文本沿用日文**。好在你不用猜——判定需要的全部信息都在标准输出的 `key=value` 行里，两个关键值是 `判定=` 和 `理由=`，中文对照见下一节。

## 完整示例源码

完整源码见 [`lesson.cob`](./lesson.cob)，按固定格式编写（第 7 列指示符、Area A 从第 8 列、Area B 从第 12 列起，程序文本不越过第 72 列）。

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. IF04.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 WS-TRANSACTION-REFERENCE PIC X(12)
          VALUE "TXN-00000001".
       01 WS-ACCOUNT-STATUS PIC X VALUE "A".
       01 WS-TRANSACTION-AMOUNT PIC S9(7)V99
          SIGN IS LEADING SEPARATE CHARACTER VALUE 125.50.
       01 WS-MAXIMUM-AMOUNT PIC 9(7)V99 VALUE 1000.00.
       PROCEDURE DIVISION.
           DISPLAY "取引参照番号="
               WS-TRANSACTION-REFERENCE
           DISPLAY "口座状態=" WS-ACCOUNT-STATUS
           DISPLAY "取引金額=" WS-TRANSACTION-AMOUNT
           DISPLAY "上限金額=" WS-MAXIMUM-AMOUNT
           IF WS-TRANSACTION-AMOUNT <= ZERO
               DISPLAY "判定=REJECTED"
               DISPLAY "理由=AMOUNT_NOT_POSITIVE"
           ELSE
               IF WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT
                   DISPLAY "判定=REJECTED"
                   DISPLAY "理由=AMOUNT_OVER_LIMIT"
               ELSE
                   IF WS-ACCOUNT-STATUS = "A"
                       DISPLAY "判定=ACCEPTED"
                       DISPLAY "理由=WITHIN_RULES"
                   ELSE
                       DISPLAY "判定=REJECTED"
                       DISPLAY "理由=ACCOUNT_INACTIVE"
                   END-IF
               END-IF
           END-IF
           STOP RUN.
```

上面省略了源码中的注释行。源码里的注释只说明规则和契约（金额必须为正、上限含端点、只报首个失败原因），不逐条复述 `DISPLAY` 的文本。

## 数据与规则

本课没给你任何输入：样例交易完全固定在程序内，**没有外部输入**，也没有输入夹具和结果文件。参与判断的就是这么四个值：

| 字段 | `PIC` / 存储字节 | 初值 | 作用 |
|---|---|---|---|
| `WS-TRANSACTION-REFERENCE` | `X(12)` / 12 字节 | `TXN-00000001` | 交易标识，只回显，不参与判断 |
| `WS-ACCOUNT-STATUS` | `X(1)` / 1 字节 | `A` | 账户状态，只有 `A` 被本课视为有效 |
| `WS-TRANSACTION-AMOUNT` | `S9(7)V99`，`SIGN IS LEADING SEPARATE CHARACTER` / 10 字节 | `125.50` | 带符号金额，从下界一侧参与判断 |
| `WS-MAXIMUM-AMOUNT` | `9(7)V99` / 9 字节 | `1000.00` | 单笔金额上限，含端点 |

金额字段的 10 字节 = 1 个独立前导符号位 + 7 位整数 + 2 位小数；`V` 是隐含小数点，**不占存储**，只在 `DISPLAY` 时按位置渲染出来。所以存储是 10 字节，而屏幕上看到的 `+0000125.50` 是 11 个字符。上面四个字节数是本机用 `FUNCTION LENGTH` 实测得到的，可以作为后续课程核对记录布局的基准。本课没有币种字段，按演示约定金额视为两位小数的“元”，不涉及汇率与舍入。

规则与边界政策：

| 规则 | 实现条件 | 政策 |
|---|---|---|
| 金额必须为正 | `WS-TRANSACTION-AMOUNT <= ZERO` → 拒绝 | 零与负金额都拒绝；`0.01` 起接受 |
| 单笔上限 | `WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT` → 拒绝 | 上限**含端点**，等于 `1000.00` 接受，`1000.01` 起拒绝 |
| 账户状态 | `WS-ACCOUNT-STATUS = "A"` 才接受 | 只有精确的 `A` 有效；`I`、`a`、空格和其他字符都报同一个理由 |

已由代码校验的条件就是上表三条。**没有**校验的：交易参考号的格式与唯一性（本课只回显）、状态码的具体含义（程序不区分 `I` 表示什么）、金额上限本身的来源（它是本课的演示常量）。前提说明：`WS-MAXIMUM-AMOUNT` 与三个样例值都是教学演示数据，不代表任何真实业务政策或监管限额。

## 边界值在何处分叉

先记住一件事：这里的拒绝全都是业务拒绝，退出码照样是 `0`，程序里根本没有系统故障那条分支。下表每一行都在本机实际编译运行过：

| 金额 | 状态 | 在哪个比较处分叉 | `判定=` | `理由=` |
|---|---|---|---|---|
| `125.50`（原始初值） | `A` | 三个条件全部通过 | `ACCEPTED` | `WITHIN_RULES` |
| `0.00` | `A` | 第 1 层为真 | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| `-0.01` | `A` | 第 1 层为真 | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| `0.01` | `A` | 紧贴下界，`<= ZERO` 为假 | `ACCEPTED` | `WITHIN_RULES` |
| `1000.00` | `A` | 第 2 层为假（端点被包含） | `ACCEPTED` | `WITHIN_RULES` |
| `1000.01` | `A` | 第 2 层为真 | `REJECTED` | `AMOUNT_OVER_LIMIT` |
| `125.50` | `I` | 第 3 层为假 | `REJECTED` | `ACCOUNT_INACTIVE` |
| `-5.00` | `I` | 第 1 层为真，第 3 层**未执行** | `REJECTED` | `AMOUNT_NOT_POSITIVE` |

谁决定哪条分叉：

| 观察目标 | 决定它的比较 | 结果 |
|---|---|---|
| 下界 | `AMOUNT <= ZERO` | `0.00` 与负数拒绝，`0.01` 起接受 |
| 上限 | `AMOUNT > MAXIMUM` | 严格大于才拒绝，等于 `1000.00` 被包含 |
| 状态 | `STATUS = "A"` | 仅精确 `A`；`a`、空格、`I` 都拒绝 |
| 报哪个原因 | 三层嵌套顺序 | 只报最先命中的失败规则 |

## 源码阅读路径

顺着数据往下读，比按行号读要快得多：

1. 先看 `WORKING-STORAGE` 那四个字段：状态是 `X(1)` 文本，金额是带独立符号的数值——后面比较行为不一样，根子在这儿。
2. 再看 `PROCEDURE DIVISION` 后面那 4 条 `DISPLAY`：先把参与判断的输入值打出来，方便你拿输入对照判定。注意它们之间没有句点，是同一个句子里的几条语句。
3. 最外层 `IF WS-TRANSACTION-AMOUNT <= ZERO`：它的 `ELSE` 只兜住“金额为正”的情况，所以金额本身就不对时，不会再去看上限和状态。
4. 第二层 `IF WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT`：留意用的是严格大于，端点因此被包含进来。
5. 第三层 `IF WS-ACCOUNT-STATUS = "A"`：最内层那个 `ELSE`，才是状态拒绝。
6. 三个 `END-IF` 由内向外一层层闭合，最后 `STOP RUN.` 收尾。整段代码只有这一个句点。

## 运行与观察

**输入：** 无。四个值全部来自 `lesson.cob` 的 `VALUE` 子句，不读键盘、文件或数据库，所以判定会**固定复现**——这一点和[第 15 课](../15_sequential-file-read/README.md)之后的文件课不同。

**命令及作用：**

```sh
mkdir -p build                                   # 先建输出目录，否则 -o 会因目录不存在而失败
cobc -fsyntax-only lesson.cob                    # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_04 lesson.cob      # 编译并生成可执行文件
./build/lesson_04                                # 运行程序，判定结果写到标准输出
echo $?                                          # 查看上一条命令的退出码
rm -rf build                                     # 清理编译产物
```

四条命令证明的事情不同：`-fsyntax-only` 只说明源码能通过语法解析，不生成也不运行程序；`-x` 要求生成可执行文件，`-o` 指定产物路径，返回码 `0` 且无诊断才表示编译通过；运行可执行文件才能观察到判定结果；`rm -rf build` 只是删除编译产物，本课不产生业务数据文件，所以清理不会丢数据。

**预期结果（原始初值）：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x -Wall` 退出码 | `0`，无编译诊断 |
| 标准输出 | 下面 6 行 |
| 进程退出码（`echo $?`） | `0` |
| 生成文件 | 仅 `build/lesson_04` |

```text
取引参照番号=TXN-00000001
口座状態=A
取引金額=+0000125.50
上限金額=0001000.00
判定=ACCEPTED
理由=WITHIN_RULES
```

输出行与中文对照：`取引参照番号` = 交易参考号，`口座状態` = 账户状态，`取引金額` = 交易金额，`上限金額` = 单笔金额上限，`判定` = 判定结果，`理由` = 判定理由。4 个 `理由` 取值：`WITHIN_RULES` 表示三条规则全部通过，`AMOUNT_NOT_POSITIVE` 表示金额不是正数，`AMOUNT_OVER_LIMIT` 表示金额超过单笔上限，`ACCOUNT_INACTIVE` 表示账户状态不是 `A`。判断程序行为时以标准输出的 `判定=` / `理由=` 为准，README 的中文说明负责解释这些取值。

**实际观察到的环境细节：** 在本工作区运行 `./build/lesson_04` 时，标准错误会输出 `Warning: program compiled against libxml 212 using older 209`。这是运行环境链接库版本差异产生的警告，不是本程序的业务输出，触发组件尚未定位。程序的业务输出全部在标准输出，退出码为 `0`。

### 证据来源与验证范围

本课 README 中的预期输出、`边界值在何处分叉` 一节的 8 行结果、以及练习答案里的每个场景，都在本工作区用 `cobc 3.2.0` 实际编译运行核对过：`-fsyntax-only` 与 `-x -Wall` 返回码均为 `0`、无编译诊断，运行退出码均为 `0`，标准输出与文档逐字节一致。字段的 12 / 1 / 10 / 9 字节由单独的 `FUNCTION LENGTH` 程序实测。知识讲解里“把 `<=` 改成 `<`，`0.00` 会被接受”与“把 `>` 改成 `>=`，`1000.00` 会被拒绝”两个说法也各改一处运算符实测过（结果分别为 `ACCEPTED` 与 `AMOUNT_OVER_LIMIT`）。**未验证**的场景：多笔交易、并发、超出 `S9(7)V99` 容量的金额（本课不处理算术溢出），以及任何文件或数据库输入——本课没有这些路径。

## 修改练习

从原始 [`lesson.cob`](./lesson.cob) 开始，只改 `WS-TRANSACTION-AMOUNT` 和 `WS-ACCOUNT-STATUS` 的 `VALUE` 子句，观察到接受与拒绝在边界处分叉。七个场景的输入与预期判定：

| 场景 | 金额 `VALUE` | 状态 `VALUE` | `判定=` | `理由=` |
|---|---|---|---|---|
| 1 | `0.00` | `"A"` | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| 2 | `-0.01` | `"A"` | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| 3 | `0.01` | `"A"` | `ACCEPTED` | `WITHIN_RULES` |
| 4 | `1000.00` | `"A"` | `ACCEPTED` | `WITHIN_RULES` |
| 5 | `1000.01` | `"A"` | `REJECTED` | `AMOUNT_OVER_LIMIT` |
| 6 | `125.50`（保持初值） | `"I"` | `REJECTED` | `ACCOUNT_INACTIVE` |
| 7 | `-5.00` | `"I"` | `REJECTED` | `AMOUNT_NOT_POSITIVE` |

每个场景都要从原始源码重新开始，避免上一个场景的值影响下一个。完整题目（含基线、改动约束、重编译运行命令、逐场景预期输出和需要回答的问题）见 [`exercise.md`](./exercise.md)，参考答案见 [`answer.md`](./answer.md)。

## 举一反三练习

为转账校验设计规则：单笔最低金额 `5.00`、单笔最高金额 `5000.00`，并要求收款账户状态为 `A`。自己选择金额字段的 `PIC`（两位小数必须；是否需要符号由你判断并说明）、嵌套顺序和拒绝原因文本，依次验证低于最低金额、恰好等于最低金额、恰好等于最高金额、超过最高金额、以及非活动收款账户分别走哪条分支，并说明每个比较运算符把端点放在接受侧还是拒绝侧。题目见 [`exercise.md`](./exercise.md)，本题不提供答案。

限制：只使用本课已学的字段声明、`VALUE`、关系条件、`IF` / `ELSE` / `END-IF`、`DISPLAY` 和 `STOP RUN`；不要使用循环、段落、表格或 `EVALUATE`。你需要自己决定边界是否包含，并说明用什么值验证。

## 走一遍真实流程

把本课这段判定塞进一条真实链路，它是这么个位置：

1. **柜面或 App 发起**：柜员递单、客户点确认，上游系统先把这笔业务变成一条待校验的交易。这一步不归本课管。
2. **校验程序跑起来**：读进金额和账户状态。本课这两个值是写死在 `VALUE` 子句里的；真实版本从[第 15 课](../15_sequential-file-read/README.md)开始改成读文件。
3. **判出接受或拒绝，并带上原因**：这就是本课的产出。原因是固定短代码，比如 `AMOUNT_OVER_LIMIT`。
4. **原因交回柜面 / 客服**：柜面系统把 `AMOUNT_OVER_LIMIT` 翻成一句人话——“该笔金额超过单笔限额”。客户看到的是这句话不是代码；柜员据此决定是让客户改金额，还是转人工。
5. **下游接手**：接受的那笔继续去记账、过账；拒绝的那笔留在记录里等复核或直接退回。两条路怎么分，都看第 3 步报的是哪个原因。

本课只做第 3 步，而且只有一笔交易、三条规则。真实链路上游怎么保证状态码合法、拒绝记录存到哪儿、谁来复核，都在这份代码之外——**但“为什么被拒”这个信息，必须从这一课开始就是准的**，因为后面每一步都在用它。

## 这份代码进了生产会怎样

- **谁调度它**：真实系统里它是上游校验环节的一个程序，由调度器或联机交易链路按笔触发。本课为了看得清，把触发简化成了直接运行。
- **谁看它的输出**：柜面系统、客服工单和对账的人都会读那个 `理由=`。他们不看源码，只认代码对应的那句话。
- **出事谁被叫起来**：原因报错（比如把“状态冻结”报成“金额超限”），先是柜员解释错、客户白跑一趟，接着对账时那笔账挂在没人认领的地方——最后被叫起来的，是做这段校验的人。
- **第一个月最容易出的事故**：两件。一是边界没写清，业务说“不超过 1000”，程序实现成 `>=`，月底对账才发现和另一个系统差了一堆 1000.00 的整数笔；二是把业务拒绝当成系统故障处理，明明只是金额不合规，却让整批作业红了。
- **下一个系统怎么接**：[第 05 课](../05_evaluate/README.md)开始按交易类型分类，[第 08 课](../08_control-flow-practice/README.md)把单笔判定扩到多笔并统计接受 / 拒绝，[第 26 课](../26_error-handling/README.md)才把业务拒绝和系统故障彻底分开。

话说清楚：这份代码只演示了三条本地规则、一个写死的账户状态。它没有币种、账户授权额度、重复请求检测、交易时段限制，也不做授权和持久化。别把“判定 + 原因”读成“这笔交易可以过账了”。
