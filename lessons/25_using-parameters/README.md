# 第 25 课：USING——参数到底怎么交出去，谁有权改它

## 业务现场

接口评审会开到一半，隔壁团队的人抬头说了句：

> "你们那个校验子程序我们也要调。入参：金额。"

说完就翻页了。没人追问这个参数是只读还是要写回，也没人问子程序会不会动调用方传进去的那个字段——参数名都叫"金额"了，还能有什么花样？

你可能会想：看个金额而已，能出什么事。可三个月后真出了。给子程序加逻辑的同事在里面把金额改了一下。他以为改的是自己的局部变量——可 COBOL 的默认方式是 `BY REFERENCE`，改的就是调用方那块内存。你们主程序里那个字段跟着变了，而你们的代码还在拿"原值"继续算手续费。这类账很难倒查：错误发生的地方和表现的地方隔着好几个程序。

更贵的一种是两边说法不一致。调用方写一种方式、子程序声明另一种方式，**编译器不会拦你**，编译退出码照样是 `0`。跑起来要么当场信号中止——那天夜里批次就挂在那儿，值班电话响了；要么更糟，安安静静打印出一串没人认识的数字，报告照常算完，没人报警。本课把这两种都跑给你看。

所以本课就干一件事：把"这个参数调完之后会不会变、谁负责改、谁只能看"讲清楚。这是写接口时最该先说出口的一句话，也是三个人一起看同一段代码时最容易各自理解成不同版本的一句话。

（下面出现的方式名、数字和输出都是本课演示程序的实测结果，只用来讲语义，不代表任何机构的真实数据。）

## 为什么现在学

上一课（[第 24 课](../24_call-subprograms/README.md)）你已经把金额校验搬进了独立子程序，用的是 `CALL`、`LINKAGE SECTION`、`PROCEDURE DIVISION USING` 和 `GOBACK`。但那课有个地方故意没展开：它**只用了一种传递方式，就是默认的那种**。

你可能会想：默认能用就行了，何必专门学一课？

问题在于第 24 课的结果恰恰是靠默认方式带回来的——子程序改调用方的字段，调用方读回状态。那套写法一等你要问下面这三句话，就不够用了：

- 子程序只需要**读**一个金额，我怎么保证它不会顺手把我的字段改掉？
- 参数不是 `PIC 9(7)V99` 这种显示字段，而是一个二进制数值（比如要跟 C 那边的代码共享的整数），接口怎么写？
- 子程序内部看到的值，和我这边看到的值，到底是不是同一个东西？

这就是**数据方向**的问题：`USING` 后面接的参数，交出去的是地址还是数值、谁负责更新、调用方什么时候能看到变化。第 28 课要把多个子程序、多份 Copybook 拼成一个能重复构建的工程，到那时候每个参数都得有人说清它的读写方向；现在不定，后面只能靠猜。

而猜错要付多少代价，本课会用实跑结果摆出来（见下文"方式不一致会怎样"）。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** `CALL ... USING` 后面的每个参数，都可以标注一种"交出去的方式"：

- `BY REFERENCE`——把字段的**存储地址**交出去。子程序手里就是调用方那块内存，改了调用方就变。这也是不写方式时的默认。
- `BY CONTENT`——交出去的是内容的一份**临时副本**。子程序改它，调用方那块内存一动不动。
- `BY VALUE`——把**数值本身**交出去，不是地址。

三个词背下来不难，难的是它们回答的其实是同一个问题：**子程序手里那个东西，和调用方手里的是不是同一个。**

**它在业务里解决什么问题。** 模块化开发里，一段逻辑被拆出去之后，"谁能改这笔数据"就变成了责任划分。子程序想就地更新余额，那就用 `BY REFERENCE`；只想读一笔金额来判断合不合规，就用 `BY CONTENT`，免得将来有人在子程序里写一句顺手修改，把调用方的账悄悄改掉。交接代码、评审接口、排查"钱去哪儿了"的时候，第一个要问的就是这个。

**什么时候不该这么用。** `BY VALUE` 不适合当长期接口约定：本课的 GnuCOBOL 3.2.0 会在编译时明确警告它还没定稿（原文见下），所以本课只把它当"在当前工具链上可观察的语义演示"，不当生产接口。真正要跟别的语言共享二进制整数时，先针对你锁定的编译器版本验证；跨编译器、跨平台一致这件事，本课不作承诺。

## 本课完成后的能力与边界

学完本课后，你可以：

- 把同一个 `AMOUNT-ARGUMENT` 分别按三种方式交给子程序，读出调用后调用方字段分别是 `11`、`20`、`30`，并说出每个数字为什么是这个值（子程序改了调用方内存 / 子程序只改了副本 / 子程序只收到了数值）。
- 指出 `ADD-ONE` 的 `PROCEDURE DIVISION USING` 没写方式就等于 `BY REFERENCE`，而 `REPORT-BINARY` 写的是 `BY VALUE`；两边的写法必须对应。
- 用一份 Copybook 让调用方（`WORKING-STORAGE`）和两个子程序（`LINKAGE`）共享同一份参数声明，并说清宽度或符号不一致时接口为什么会失效。
- 读自检输出和退出码：三项全过时 `集計 合格=003 不合格=000`、退出码 `0`；任一项不符时出现 `確認=失敗`、退出码 `1`。
- 背下 GnuCOBOL 3.2.0 那条 `BY VALUE` 编译警告的原文，并说清为什么它意味着"不要拿它当稳定契约"。

边界：本课不实现业务规则，只演示三种传递方式的数据方向——不校验金额、不读写数据文件、不返回业务状态。参数个数、类型或传递方式不匹配时的行为不在本课承诺内，跨编译器或跨平台的 ABI 兼容也不在。用参数把 `VALID`/`REJECTED` 这类业务结论写回调用方，放到举一反三练习里；[第 28 课](../28_modular-batch-project/README.md)才用 `CALL ... USING` 组织多程序、多 Copybook 的工程。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端；不需要数据库或第三方工具。
- 三个源文件必须一起编译链接：主程序 `lesson.cob` 调用 `add_one_25.cob`（`PROGRAM-ID. ADD-ONE`）和 `report_binary_25.cob`（`PROGRAM-ID. REPORT-BINARY`）。
- 参数声明来自 `copybooks/AMOUNT-INTERFACE.CPY`，编译时要能解析 `COPY "AMOUNT-INTERFACE.CPY"`，所以命令里必须带 `-I copybooks`。这一条忘了，编译当场就炸（报错原文见下）。
- 程序不读也不写业务文件，结果只有标准输出；可执行文件放进 `build/`。

## 同一个参数，三种交法

主程序拿同一个参数做三次实验，就看一件事：这份存储到底归谁。

| 传递方式 | 调用方写什么 | 子程序看到什么 | 子程序能否改到调用方字段 | 本课调用后调用方字段 |
|---|---|---|---|---|
| `BY REFERENCE` | 把字段的存储地址交出去 | 同一个存储区 | 能 | `11` |
| `BY CONTENT` | 交出内容的一份临时副本 | 一份临时副本 | 不能（只改副本） | `20` |
| `BY VALUE` | 交出完整字长的数值本身 | 数值参数 | 不适用：`REPORT-BINARY` 只读 | `30` |

翻成用途就是三句话：要子程序**写回结果**，用 `BY REFERENCE`；只希望子程序**消费输入、不许污染调用方存储**，用 `BY CONTENT`；参数本身就是个二进制数值（比如要和 C 侧共享的整数），才轮到考虑 `BY VALUE`。

看第三行的时候顺手记一下：`BY VALUE` 那一路调用方字段没变，**不是因为它一定是安全的**，而是因为 `REPORT-BINARY` 里根本没有写回这个动作。方式决定了"能不能改"，子程序里写不写才是"改不改"。

## 参数靠位置对齐，形状靠 Copybook 锁住

`USING` 的参数按**位置次序**匹配，名字不参与：第 1 个实参配子程序 `PROCEDURE DIVISION USING` 里的第 1 个形参，第 2 个配第 2 个，中间没有名字可以对照。子程序还要在 `LINKAGE SECTION` 里用同样的声明把这块存储"接住"，所以调用方和两个子程序必须 `COPY` 同一份 `AMOUNT-INTERFACE.CPY`。

本课这个参数声明是：

```cobol
       01 AMOUNT-ARGUMENT USAGE BINARY-LONG.
```

它没有 `PIC`，是 GnuCOBOL 的完整字长二进制用法。本课用 `LENGTH OF` 探针实测为 **4 字节有符号**（能存 `-5` 并能原样读回），所以 `BY VALUE` 交出去的就是一个 4 字节整数。

想一想为什么这事儿必须写进共享 Copybook：位置对了但形状不对，接口一样废。要是调用方按 4 字节有符号声明、子程序那边错写成 2 字节，位置、方式全对，数字照样是错的——而且编译器不会替你发现。

## 跟第 24 课差在哪儿

第 24 课只有一种隐含的 `BY REFERENCE`，子程序总是就地改写调用方的结果字段，没有第二种可能。本课把"数据方向"变成**要显式选的一件事**，并且给出了核对手段：三种方式各跑一遍，再拿调用方字段跟程序里写死的预期值对一遍。

## 输入与规则

- **输入：** 没有外部文件，也没有命令行参数。三个测试值 `10`、`20`、`30` 和对应的预期值 `11`、`20`、`30` 都写死在 `lesson.cob` 的 `1100/1200/1300` 段落里，是演示数据，不是业务数据。
- **参数：** 只有一个 `AMOUNT-ARGUMENT`，类型 `USAGE BINARY-LONG`（4 字节有符号整数，无隐含小数）。它的含义就是"一个待加一或待显示的整数"。
- **前提：** 调用方的写法必须和子程序 `PROCEDURE DIVISION USING` 的声明方式一致；子程序对 `AMOUNT-ARGUMENT` 的修改，只有在 `BY REFERENCE` 下才会回到调用方存储。
- **代码真的会校验的：** `8100-CHECK-ACTUAL` 比较"调用后的调用方字段"和 `WS-EXPECTED`。相等 → 打印 `合格`，并按 `WS-MODE` 计入对应方式的计数；不等 → 打印 `不合格`，**而且不计入任何方式计数**。
- **代码真的会做的收尾：** `WS-FAIL-COUNT` 不为零时 `MOVE 1 TO RETURN-CODE`。
- **没人校验的：** 子程序实际收到的值是不是等于调用方字段，程序不检查（`BY CONTENT`/`BY VALUE` 的语义只能从外部观察）；调用方和子程序的传递方式是否一致，同样没人检查，编译器也不报错——这一点下一节就是活证据。

## 运行与观察

**在哪跑：** 本课目录。程序不依赖相对文件名，产物放进 `build/`。

**命令和各步在干什么：**

```sh
mkdir -p build
cobc -fsyntax-only -I copybooks lesson.cob add_one_25.cob report_binary_25.cob   # 只做语法检查
cobc -x -Wall -I copybooks -o build/lesson_25 \
  lesson.cob add_one_25.cob report_binary_25.cob                                 # 编译并链接三个程序
./build/lesson_25                                                                # 运行
echo $?                                                                          # 查看退出码
rm -rf build                                                                     # 清理可执行文件
```

- `-fsyntax-only` 只解析语法，**不**生成可执行文件、也**不**运行程序；它过了不等于程序能跑。
- `-x` 要求生成可执行程序，`-o` 指定输出路径；三个源文件写在同一条命令里，链接成一个可执行文件。
- `-I copybooks` 让 `COPY "AMOUNT-INTERFACE.CPY"` 找得到。**漏掉它就直接编译失败**，实测报错是：

  ```text
  lesson.cob:12: error: AMOUNT-INTERFACE.CPY: そのようなファイルやディレクトリはありません
  lesson.cob:35: error: 'AMOUNT-ARGUMENT' is not defined
  ...
  ```

  三个文件里的 `COPY` 全部报文件不存在，随后是一堆"`AMOUNT-ARGUMENT` 未定义"，合计 **6 条 `error`**，编译命令退出码 **`1`**。
- `rm -rf build` 只删本课自己生成的可执行文件；本课不产生业务数据文件。

**预期结果（正常路径）：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0`，标准错误有 1 条 `BY VALUE` 未完成功能的警告 |
| `cobc -x -Wall` 退出码 | `0`，标准错误仍只有同一条警告，无其他诊断 |
| 标准输出 | 11 行、540 字节（UTF-8），见下方代码块 |
| 进程退出码（`echo $?`） | `0` |
| 生成文件 | 仅 `build/lesson_25` |

```text
呼出側=呼出前 方式=BY REFERENCE 値=000000010
被呼出側=加算後 値=000000011
呼出側=呼出後 方式=BY REFERENCE 値=000000011 確認=合格
呼出側=呼出前 方式=BY CONTENT 値=000000020
被呼出側=加算後 値=000000021
呼出側=呼出後 方式=BY CONTENT 値=000000020 確認=合格
呼出側=呼出前 方式=BY VALUE 値=000000030
被呼出側=受取値=000000030
呼出側=呼出後 方式=BY VALUE 値=000000030 確認=合格
集計 合格=003 不合格=000
方式 BY REFERENCE=001 BY CONTENT=001 値=001
```

**那条编译警告，原文和含义。** 语法检查和 `-Wall` 编译都会在标准错误打印同一条（行号取自本课当前源码 `report_binary_25.cob` 第 11 行）：

```text
report_binary_25.cob:11: warning: handling of parameters passed BY VALUE is unfinished; implementation is likely to be changed [-Wunfinished]
```

翻成人话：GnuCOBOL 3.2.0 认为 `BY VALUE` 的实现还没定稿，后续版本可能改行为。所以它不适合当"已经稳定"的接口约定——编译照样成功（退出码 `0`），程序在本工具链上按上面的结果跑。本课留这个写法，是为了能用可观察的结果讲清数据方向，不是建议你把它用到生产接口上。真实的跨语言或长期接口，要么先针对你锁定的 GnuCOBOL 版本验证，要么就用本课另外两种方式。

**三条结果各说明什么：**

1. `BY REFERENCE`：调用前调用方是 `10`，`ADD-ONE` 加一后自己显示 `11`，返回后调用方也读到 `11`。子程序改的就是调用方那块存储。
2. `BY CONTENT`：调用前是 `20`，子程序内部显示 `21`，但返回后调用方还是 `20`。加的是临时副本，改完就丢。
3. `BY VALUE`：`REPORT-BINARY` 显示 `30`，只读不写，调用方字段保持 `30`。
4. 三项自检全过（`合格=003`），三种方式各计入一次，退出码 `0`。

**输出里的日文标签对照（标签 → 含义）：** `呼出側=呼出前` 调用方在 `CALL` 之前的字段值；`被呼出側=加算後` `ADD-ONE` 内部看到的值（`BY CONTENT` 时那是副本）；`被呼出側=受取値` `REPORT-BINARY` 收到的数值；`呼出側=呼出後` 调用返回后调用方的字段值；`確認=合格/失敗` 这一次自检的结论；`集計 合格/不合格` 三项自检的通过/失败数。

最后一行 `方式 BY REFERENCE=001 BY CONTENT=001 値=001` 的标签有点词不达意：它要分别打印三种方式的自检通过次数，但程序把第三列（`BY VALUE` 的计数）标成了 `値=`（"值"），不是 `BY VALUE=`。所以这个 `値=001` 是**次数**，不是前面那个数值 `30`。以上面这张对照表为准。

### 方式不一致会怎样（实测，不是预期行为）

`USING` 的方式由调用方和子程序各自声明，**编译器不核对两者是否一致**。本课在已验证的工具链上做了两组反例：

- **调用方写 `BY VALUE`、子程序仍是默认 `BY REFERENCE`：** 编译退出码还是 `0`（只有原来那条 `BY VALUE` 警告），但运行时立刻中止，标准错误出现 `attempt to reference invalid memory address (signal)`，进程退出码 **`139`**，标准输出只来得及打印第一行（`BY REFERENCE` 段的调用前值）。
- **调用方写 `BY REFERENCE`、子程序声明 `BY VALUE`：** 编译和运行都"成功"（退出码 `0`），子程序却把地址当数值打印出来。`被呼出側=受取値=` 每次运行的数字都不同——复跑时分别看到过 `248421696`、`238583104`、`101783872`、`423946432`，更早的记录里是 `802200896`、`631190208`、`646650048`、`937214656`。数字本身没有意义，它就是一块内存地址被当成整数打了出来。真正糟的是：调用方的自检**照样显示 `合格`**，因为 `8100-CHECK-ACTUAL` 只看调用方自己的存储，看不出子程序那边发生了什么。

这就是为什么接口约定得靠 Copybook、命名和评审固定死，而不能指望编译器或者自检替你拦。**本课不把这些观察当成跨平台结论**：它们只说明在 GnuCOBOL 3.2.0 / 本仓库工具链上，方式不一致既可能直接崩，也可能安静地给你一个错数字。

### 失败路径：自检不合格时的退出码

把 `1100-TEST-REFERENCE` 的 `WS-EXPECTED` 从 `11` 改成 `99`（别的都不动），重编译运行，实测：

| 观察项 | 实际值 |
|---|---|
| `cobc -x -Wall` 退出码 | `0` |
| 该行输出 | `呼出側=呼出後 方式=BY REFERENCE 値=000000011 確認=失敗` |
| 汇总行 | `集計 合格=002 不合格=001` |
| 方式计数行 | `方式 BY REFERENCE=000 BY CONTENT=001 値=001` |
| 进程退出码 | `1` |

两个细节值得记住：失败的那一项**不会**进方式计数（所以 `BY REFERENCE=000`），而 `RETURN-CODE` 被置成 `1`——调用它的脚本或构建流水线可以凭这个数字判定"接口行为不符合预期"。

**标准错误里的东西不都是你的输出。** 运行时标准错误还会出现 `Warning: program compiled against libxml 212 using older 209`。这是本工作区链接库版本差异产生的环境警告，跟编译期那条 `BY VALUE` 警告是两回事，都不属于本程序的业务输出。

## 源码阅读路径

按"数据方向"读，别逐行读：

1. `copybooks/AMOUNT-INTERFACE.CPY`：只有一行有效声明，`01 AMOUNT-ARGUMENT USAGE BINARY-LONG.`。它不做 `PIC` 编辑；三份程序共用同一份声明，接口才成立。
2. `lesson.cob` 的 `WORKING-STORAGE SECTION`：用 `COPY "AMOUNT-INTERFACE.CPY".` 把参数声明搬进来——调用方的参数住在 `WORKING-STORAGE`。`WS-EXPECTED`、`WS-ACTUAL` 是同类型的 `BINARY-LONG`，`WS-EDITED-ACTUAL` 是 `PIC 9(9)`，只负责把二进制值格式化成 9 位数字显示。
3. `1100-TEST-REFERENCE`：先写 `10` 和预期 `11`，然后显式写 `BY REFERENCE` 调 `ADD-ONE`。这里的"显式"是教学用的；不写方式，默认也是 `BY REFERENCE`。
4. `1200-TEST-CONTENT`：同一个子程序、同一个实参，只把方式换成 `BY CONTENT`，预期值设成 `20`（调用方不该被改动）。
5. `1300-TEST-VALUE`：换成另一个子程序 `REPORT-BINARY`，方式 `BY VALUE`，预期值 `30`。
6. `add_one_25.cob`：`LINKAGE SECTION` 里 `COPY` 同一份声明，`PROCEDURE DIVISION USING AMOUNT-ARGUMENT` 没写方式就是 `BY REFERENCE`，`ADD 1 TO AMOUNT-ARGUMENT` 直接写进调用方（或者副本）那块存储。
7. `report_binary_25.cob`：唯一差别是 `PROCEDURE DIVISION USING BY VALUE AMOUNT-ARGUMENT`；这里的 `AMOUNT-ARGUMENT` 是个"数值参数"，程序只用 `MOVE` 把它读出去。
8. `8100-CHECK-ACTUAL`：把调用后的调用方字段搬进 `WS-ACTUAL` 跟 `WS-EXPECTED` 比，相等就计数并打印 `合格`，不等就只加 `不合格`；`9000-DISPLAY-SUMMARY` 打汇总，`0000-MAIN` 在 `WS-FAIL-COUNT` 非零时把 `RETURN-CODE` 置 `1`。

## 固定格式核对（按字节）

`cobc` 3.2.0 在 UTF-8 源文件里按**字节**数列，所以中文注释也要数进去。下面三条命令核对本课四个源文件（`LC_ALL=C` 是让 `awk` 按字节计数）：

```sh
for f in lesson.cob add_one_25.cob report_binary_25.cob copybooks/AMOUNT-INTERFACE.CPY; do
  LC_ALL=C awk 'length($0)>72 {print "over72", FILENAME, FNR, length($0)}' "$f"
  LC_ALL=C awk '/^      \*/ {next} {i=match($0,/[^ ]/); if (i>0 && (i<8 || (i>=9 && i<=11))) print "bad column", FILENAME, FNR, i}' "$f"
  LC_ALL=C awk '{if (length($0)>m) {m=length($0); n=FNR}} END {print FILENAME, "max bytes", m, "line", n}' "$f"
done
```

实测：前两条对四个文件都没有输出；第三条分别给出 `lesson.cob max bytes 70`、`add_one_25.cob max bytes 69`、`report_binary_25.cob max bytes 71`、`copybooks/AMOUNT-INTERFACE.CPY max bytes 70`（都在第 1 行，也就是最长的那行中文注释）。所有可执行程序文本只从第 8 列（Division、`01` 级、段落名）和第 12 列（语句）开始；本课只有一个 `01` 级参数、没有 `05` 级字段，将来要在 Copybook 里给参数加从属层级，按仓库约定 `05` 级写在**第 11 列**。注释一律在第 7 列写 `*`。别忘了：列位置这事 `-fsyntax-only` 不会报，只能靠上面的命令，别指望编译器提醒你。

## 修改练习（有答案）

两项都从**当前源码**（上面这三个 `.cob` 加 Copybook）开始，改完都要重新执行同一条 `cobc -x -Wall -I copybooks ...`。完整题目与初始值见 [`exercise.md`](./exercise.md)，参考答案见 [`answer.md`](./answer.md)。

1. **把子程序增量改成 2**：在 `add_one_25.cob` 里把 `ADD 1 TO AMOUNT-ARGUMENT` 改成 `ADD 2 TO AMOUNT-ARGUMENT`，再把 `lesson.cob` 的 `1100-TEST-REFERENCE` 中 `WS-EXPECTED` 从 `11` 改成 `12`，其余不动。预期：`BY REFERENCE` 调用后调用方变 `12`；`BY CONTENT` 调用后调用方仍是 `20`（但子程序内部显示 `22`）；`BY VALUE` 段不变；`集計 合格=003 不合格=000`、退出码 `0`。
2. **把第二次调用改成 `BY REFERENCE`**：在 `lesson.cob` 的 `1200-TEST-CONTENT` 里把 `CALL "ADD-ONE" USING BY CONTENT AMOUNT-ARGUMENT` 改成 `BY REFERENCE`，同段 `WS-EXPECTED` 从 `20` 改成 `21`，`WS-MODE` 从 `"BY CONTENT"` 改成 `"BY REFERENCE"`。预期：调用后调用方变 `21`，这一次成功被计入 `BY REFERENCE`，汇总变成 `方式 BY REFERENCE=002 BY CONTENT=000 値=001`，退出码 `0`。

## 举一反三（无答案）

扩展接口：给 `AMOUNT-INTERFACE.CPY` 加第二个参数——一个由子程序写回 `VALID` 或 `REJECTED` 的状态字段。让子程序**只通过 `BY REFERENCE`** 把这个状态写回调用方，`CALL` 之后用状态字段决定分支；然后**单独**把状态参数改成 `BY CONTENT`，重新编译运行，记下调用方还能不能收到状态。要写清参数顺序、两个字段的 `PIC`/`USAGE`、调用前后各字段的值，并用至少两个输入值（一个合法、一个不合法）验证。作为边界核对，再故意让状态参数的传递方式和子程序声明不一致，记录你实际看到的现象：编译报不报错、运行正不正常、状态字段能不能信。

本题不提供答案。也不要把 `BY VALUE` 用在 group item 或任意长度的数据上，更不要假设三种传递方式的存储布局或跨平台行为是一样的。题目见 [`exercise.md`](./exercise.md)。

## 走一遍真实流程

把本课这套东西放回链路里，它长这样：

1. **先给接口定形。** 第 24 课把校验逻辑抽成独立子程序之后，接口就是"第 1 个参数传金额、第 2 个参数回状态"。本课补上的是那句最容易漏的话：第 1 个参数子程序**只读**，第 2 个参数由子程序**写回**。这份约定写给 `AMOUNT-INTERFACE.CPY` 这样的共享声明（第 23 课教的），调用方的 `WORKING-STORAGE` 和子程序的 `LINKAGE` 都 `COPY` 同一份——这是让两边"看到同一个形状"的唯一手段，也是本课最后那条实测反例存在的理由。
2. **调用方按约定摆参数。** 主程序在 `CALL ... USING` 里按位置排好，子程序在 `PROCEDURE DIVISION USING` 里按同样位置接住。名字不参与匹配，所以参数顺序本身也是契约。
3. **出问题要有人管。** 本课的 `RETURN-CODE` 只表示"自检过没过"。真实链路里，接口行为不对得先分清是业务拒绝还是系统故障（[第 26 课](../26_error-handling/README.md)），再写进日志（[第 27 课](../27_logging/README.md)）。
4. **交给下一个地方。** [第 28 课](../28_modular-batch-project/README.md)把多个子程序和多份 Copybook 组织成可重复构建的工程；[第 32 课](../32_bank-reconciliation-project/README.md)的对账项目就在这些模块边界上传递真实记录，按返回状态决定批次继续还是停。

一句话：本课产出的不是一个"能跑的程序"，而是**一份能被人复用的接口约定**——后面每一课都会用到它。

## 这份代码进了生产会怎样

- **谁调度它**：不是夜间调度器。这类程序是构建流水线或发布前的一次性检查——接口改动后跑一遍，看三种数据方向是不是还和预期一致。
- **谁看它的输出**：写接口的人、评审接口的人，以及三个月后来改这段代码的倒霉同事。他们看的就是那 11 行和退出码。
- **下一个系统怎么接**：Copybook 会被第 28、32 课的模块一起 `COPY`；参数宽动一字节，所有消费者的语义都要重算一遍。
- **第一个月最容易出的事故**：把"编译通过、退出码 `0`"当成"接口没问题"。上面那两组反例里，编译一次都没报错，可一组直接崩、一组安静地给出错数字。
- **第二个容易踩的坑**：把 `BY VALUE` 当成"干净的跨语言约定"直接上生产。编译器自己都在警告它还没定稿。
- **它还没做的事**：没有业务规则、没有错误码版本、没有可空值/缺失值策略，也没有"调用方和子程序必须一起重新编译"的强制手段。真接口还需要的这些东西，本课一个都没提供——下次跟人交接时说"接口没问题"之前，先想想缺的是哪几样。

## 证据来源与验证范围

本文的每条观察都来自在当前仓库按上面命令实际执行的结果，范围如下：

| 场景 | 实际执行的命令 | 观察结果 |
|---|---|---|
| 正常路径 | 见"命令和各步在干什么"整段（`-fsyntax-only`、`-x -Wall`、运行、`echo $?`） | 编译 `0`、运行 `0`、标准输出 11 行 540 字节，与上方代码块逐字一致 |
| 缺 `-I` 的失败路径 | `cobc -fsyntax-only lesson.cob add_one_25.cob report_binary_25.cob`（去掉 `-I copybooks`） | 三个 `COPY` 全部报文件不存在、`AMOUNT-ARGUMENT` 未定义，合计 6 条 `error`，退出码 `1` |
| 自检失败路径 | 把 `WS-EXPECTED` 改成 `99` 后重编译运行 | `確認=失敗`、`合格=002 不合格=001`、`BY REFERENCE=000`、退出码 `1` |
| 参数宽度探针 | 临时写一个只做 `LENGTH OF AMOUNT-ARGUMENT` 和 `MOVE -5` 往返的小程序（借同一份 Copybook，不进仓库） | 宽度 `4` 字节；`-5` 能原样读回，说明是有符号 |
| 主题边界（方式不一致） | 分别把一处 `CALL` 改成与子程序声明相反的方式 | 一种组合运行中止（退出码 `139`，标准输出只剩第一行），另一种运行给出每次都不一样的数值；详见"方式不一致会怎样" |
| 修改练习 1、2 | 在临时目录复制本课源码后按题目修改并重编译运行 | 预期输出见 [`answer.md`](./answer.md)，与实测逐字一致 |

没进验证范围的东西，以及为什么没验证：`BY VALUE` 与 C 侧函数、其他编译器或其他平台上是否一致——本机只有 GnuCOBOL 3.2.0 这一套工具链，没有第二个编译器或平台可对照；参数个数或 `PIC` 不匹配时的行为——要另外构造反例，不属于本课主题；`BY CONTENT` 副本在子程序里被改之后是否留下可观察痕迹——语言层面没有给你观察它的手段。这些都不在本课承诺之内。
