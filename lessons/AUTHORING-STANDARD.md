# 32 课主线课程改造分析与制作标准

> 适用范围：`lessons/01_*` 至 `lessons/32_*` 的 README、COBOL/Copybook、脚本、输入夹具、`exercise.md` 与 `answer.md`。本文件是下一轮逐课改造的执行与验收依据，不表示现有课程已经满足全部条款，也不授权本轮直接批量改课。

## 1. 目标与现状

面向已有编程、Linux 和数据文件基础但初学 COBOL 的读者，最终要能理解并运行银行夜间对账批次。课程必须同时让读者回答：这节课要解决哪一个业务问题？为什么当前知识还不够？代码实际处理了什么输入，产生什么结果？哪些保证已经实现，哪些只是生产环境的进一步要求？完整依赖链见 [`DIRECTORY.md`](DIRECTORY.md)。

现有材料并非缺少全部业务解释，而是入口与深度不齐：第 01–28 课常以相同的 GnuCOBOL 版本句开头，第 29–32 课则写专用工具链或项目摘要；第 02 课已解释 PIC 与接口契约，第 20 课已解释排序键与顺序匹配的关系，但读者要读到正文才知道本课的业务动机。第 15 课用四行交易展示文件读取和 EOF；第 28 课明确使用程序内五笔交易来聚焦模块接口；第 32 课已有真实文件、SQL、重跑与部分失败验证。应保留这些有效材料，再重组入口并补齐真正缺失的解释和证据。

主要审查点：

- `Makefile` 的 `course-check` 检查各课四类文件存在，只编译运行第 01 课；不能称为 32 课的行为验收。
- `01/exercise.md` 仍有“草稿、待课程验收”文字，且修改题要求英文问候语，README 与 `answer.md` 则要求日文问候语；逐课检查 README、练习、答案与实际状态，不能照搬旧验收声明。
- 文档以中文讲解，部分源码注释和终端输出为日文，另有英文接口标记。每课须让中文读者能解释关键输出；运行协议既有文本不应仅为语言统一而盲改。
- 部分注释重复语句行为，例如第 15 课源码末尾说明 EOF 标志和计数；第 03 课多次解释无 `ROUNDED` 的截断。业务规则、例外原因和接口前提比逐句翻译更值得留在源码。
- 第 15–21 课有明确的小型夹具和部分边界练习；第 22、32 课的输入输出、失败和恢复更完整。扩大课程复杂度要随教学阶段递进，不按代码行数评价。

## 2. 总原则与验收层级

**按课程能力增量设计，而不是按篇幅扩写。** 每课明确一项核心能力、其先修、一个能观察到该能力的业务动作，以及它交给后续课的结果。早期允许硬编码小数据以隔离概念；进入文件、工程和数据库阶段，处理对象须是真实夹具/文件/SQLite，不得把 `DISPLAY` 模拟结果称作读取、写入或 SQL 执行。

**区分三层承诺：**

| 层级 | 最低要求 | 不应被误称为 |
|---|---|---|
| 教学演示（01–14、部分单概念课） | 编译可运行；目标概念和关键边界可观察；硬编码、限制和未教授内容写清 | 可直接上线的业务批次 |
| 可重复的业务练习（15–31） | 实际处理所附输入或真实模块/数据库；写明契约、状态、输出、退出码与复位步骤；验证本课核心边界 | 完整运维、事务或审计保证 |
| 综合项目（08、14、22、28、32，按阶段加严） | 串接已学能力；完整说明输入→规则→输出、计数不变量、典型失败与重跑；结果可独立核算 | 自动拥有跨文件/数据库原子性或生产幂等性 |

按课题选择必要复杂度：优先增加有意义的业务分支、边界输入、状态变化与可核对结果；只有当新代码教会本课目标或支撑已学能力时才增加它。不要为了“更像生产”在第 02 课加入未教的文件 I/O，或在第 15 课提前实现整套交易记账。确需生产级设计时放到后续综合课，早期指出风险与承接课次。课程样例的真实业务名词应有明确规则；不要凭空声称示例达到银行监管、财务或安全规范。

## 3. 每课先做设计卡，再改文件

执行者在修改每课前记录以下项目，按该课实际情况填写，不能把空格填成泛泛的“掌握企业开发”：

1. **学习位置：** 本课号、先修能力、仅一两个核心新概念、下一课/项目怎样使用产物。
2. **业务任务：** 谁提供什么数据，程序根据哪条具体规则作出什么决定，结果交给谁；早期模拟数据明确标作演示数据。
3. **契约：** 输入来源、字段宽度/单位/编码（相关时）、排序与唯一性前提、输出文件/标准输出/DB 修改、正常和错误返回码。
4. **决策点：** 哪个字段/状态会改变哪条路径；明确由代码校验的条件与仅由夹具保证的条件。
5. **可观察证据：** 正常值、紧贴核心概念的边界或失败值、预期输出及独立计算过程。
6. **教学边界：** 本课尚未实现什么、以后哪课接上；该限制是否影响读者对例子的理解。
7. **改动清单：** README、源码、注释、练习、答案、夹具、脚本、总目录/跨课接口的影响；未改项及理由。

设计卡放在该课改造任务说明或交付报告中，不必每课新增一个永久文件。先核对相邻课和 `DIRECTORY.md`，再决定是否扩充代码。原课程已满足某项时保留，不因统一模板重复写同一内容。

## 4. README 写作标准

### 4.1 开篇顺序

1. 标题：课号和具体任务/概念。
2. **一句话导语**：用“业务场景 + 本课动作 + 产出/后续用途”表达本课要做什么。可用两句完成，禁止用纯版本号充当导语。
3. **为什么现在学**：先修能力已能做什么、碰到哪个具体缺口、该知识解决什么；基础课用一个简短业务例子即可。
4. **本课完成后的能力与边界**：3–5 个可观察动作，指出核心结果和未覆盖的后续能力。目标不能写成只有“了解、熟悉、掌握”。
5. **运行环境**：本课用到的 GnuCOBOL 版本、默认方言/固定格式、平台与附加工具；数据库课明确 GixSQL/SQLite 依赖、适用平台与构建入口。相同公共约定可链接总目录，专用限制写在本课。

例：第 15 课可以说明“银行每日交易以文本文件送达；本课逐条读取交易原文、识别文件结束与打开失败，为后续字段解析和对账建立输入流程。”随后说明为什么 EOF 不是业务错误，以及本课尚不解析字段。此句只是写法示范；真正改课时须核对代码能否支持每个动词。

### 4.2 正文必须回答的读者问题

- **业务与知识点：** 场景为何需要该能力；新语法如何完成动作；与上一课有何区别；为什么不用已经学过的方式处理该场景。
- **输入与规则：** 数据从何处来、关键字段和合法值、金额单位与精度、空值/重复/越界/未知码政策；无输入的课明确说是程序内常量。区分前提、已校验规则和故障后的行为。
- **运行与观察：** 从本课目录或任意目录执行的具体条件；语法检查、构建、运行、清理的不同作用；预期 stdout、文件内容、数据库变化与退出码分别列明。不要把 stderr 环境警告写成业务输出。
- **源码阅读路径：** 以数据和状态变化为顺序讲关键段落/字段；解释不直观的 COBOL 作用域、内存布局、调用接口或状态码，不必逐行复述显而易见的代码。
- **实战位置：** 本课产物如何服务后续银行对账，真实系统还需要什么保证；指出具体后续课次，不以“企业常用”代替用途。
- **练习与参考：** README 概括题目并链接 `exercise.md` / `answer.md`；两处题目、初始值、预期结果一致。无答案迁移题须说明独立完成的范围。
- **证据来源：** 已验证的命令及范围应与当前代码匹配；未运行的场景写作待验证/已知限制，禁止把期望输出写成实测结论。

可按课程调整章节名和篇幅。01–14 重在概念、状态变化和业务动机；15–22 增加文件格式、物理记录/EOF 与结果文件；23–28 增加模块职责和参数契约；29–32 增加预编译、SQL 状态、数据库前后状态与恢复边界。每节只写本节需要的知识，不批量套同一段“企业实战补充”。

## 5. COBOL 示例与工程标准

### 5.1 数据、状态和边界

- 所有源码保持固定格式：第 7 列指示符，Area A 从第 8 列、Area B 从第 12 列开始，有效程序文本不越过第 72 列；不启用严格 `-std=cobol85`，维持 GnuCOBOL 默认方言及现有 `COMP-3` / `FUNCTION TRIM` 等用法。
- 字段的 `PIC`、`USAGE`、初值、宽度与业务单位一致；区分标识符和数字、文本长度与物理字节、隐含小数与外部格式。若变更记录布局，沿所有生产者、消费者、Copybook、夹具、预期文件和 SQL 表检查影响。
- 代码的分支与文档一致：EOF、未找到、业务拒绝、系统失败不能混用。打印 `FAILED`、设置标志、返回非零码与关闭已打开资源应按所声称的契约执行；未实现的检查不可写成“自动拒绝”。
- 文件课明确行顺序与定长记录的差别、工作目录和文件名、覆盖/追加行为、记录宽度、键排序/唯一性、输入过长政策。数据库课明确 `EXEC SQL` 的真实预编译链路，SQLCODE 0/100/错误、连接/游标生命周期和该驱动的特殊行为；不把 SQLite 行为泛化为 Oracle/PostgreSQL。
- 综合课的计数和金额核对要有可手算的依据；失败后的输出或已提交数据库状态与恢复方案必须如实说明。第 32 课已有“SQL 失败可能留下前一笔更新”的边界，不可称其为原子提交。

### 5.2 复杂度递进

| 阶段 | 可以增加的真实任务 | 仍需控制的范围 |
|---|---|---|
| 01–08 语言与流程 | 账户号、余额、交易类型、金额等一致的微型规则；边界值与明确的接受/拒绝原因 | 不强制外部文件、完整财务授权或提前引入表格/SQL |
| 09–14 数据结构 | 记录布局、容量界限、视图切换、查找前提及匹配结果 | 不把内存小表宣称为大文件索引或生产主档 |
| 15–22 文件处理 | 真实夹具、空文件/短长记录/异步 EOF/孤立键、输出文件与文件状态 | 单概念课只覆盖与主题直接相关的故障；综合课再串接完整路径 |
| 23–28 工程化 | 参数顺序/方向、Copybook 共享、日志与业务错误分流、可重复构建 | 不要求每个接口课处理全部外部 I/O 故障 |
| 29–32 数据库和项目 | 真 SQL、查无数据与错误、快照差异、重跑与部分失败核查 | 不虚构事务、并发或平台移植保证 |

凡增加分支或字段，必须连带更新夹具、说明、练习和预期结果；若只是增大源码行数而无新可观察行为，应拒绝该扩写。

## 6. 源码注释规范：像维护业务程序那样写

**注释回答“为什么如此处理、基于什么约定、违反会怎样”；代码本身回答“做了什么”。** 写在规则或接口附近，使维护者只读源码也不会误用；README 承担概念教程，不能把全部教科书内容塞进源码。代码注释使用简洁中文或项目已定的业务术语；外部接口/运行输出需维持原语言时在 README 中解释，不为统一语言破坏实际输出契约。

应该注释：

- 接口契约与前提：例如外部记录的字段偏移/单位、按键升序且唯一由上游保证、`CALL USING` 的参数布局和谁负责更新。
- 业务决定：例如透支记为业务拒绝而不令整个批次失败，金额从整数分换算前须通过数字检查，未知交易码不能落入正常过账。
- 不直观的技术约束：例如 `REDEFINES` 是同一存储区视图，`PERFORM` 段落返回边界，GixSQL 的经验证特例，输出文件写失败后不可再报告为成功。
- 恢复和审计边界：例如同步前存在已写的接受文件，SQL 失败时已更新行可能保留；对账计数不变量及触发失败的规则。

不应注释：

- 每条 `MOVE`、`ADD`、`IF`、`DISPLAY` 的中文翻译；字段名或段落名已说明的动作。
- 与代码重复或过时的执行结果、未落实的生产保证、从 README 原样复制的大段说明。
- 把测试夹具常量伪装成正式业务政策，或只说“这里检查错误”而不指出是何种错误。

注释示意（固定格式，第 7 列 `*`；字段和状态名须以目标课真实源码为准）：

```cobol
      * 上游按账户号升序且去重；逆序会使顺序匹配漏报。
      * 本课将此条件视为输入契约，未在程序中校验。
           PERFORM 2000-MATCH-RECORDS
```

若目标课已经运行时校验有序性，第二句应改为准确描述失败路径；如果没有这样的前提，也不应照搬此注释。注释审阅逐条问：去掉后是否会丢失业务约束、意外行为或维护风险？答案为否则删除。已有日文注释若描述了有效规则，可用中文准确转写；不要一律翻译后再留下重复信息。程序注释、README、实际错误处理必须一致。

## 7. 练习、答案、夹具与验收证据

每课至少一项**有答案的修改练习**：指定从哪个基线开始、改动位置与约束、重新编译/运行命令、完整预期差异和原因；答案只回答这类题，且不能依赖先做了另一道题。另设一项**无答案的迁移练习**：换一个相似业务场景，需要学员独立选择字段/规则并说明验证方法；不得要求尚未教学的复杂机制，除非明确列为挑战题。README、exercise、answer 三处范围一致。

夹具与预期应让核心逻辑可独立核算：少量数据足以展示正常路径和紧邻本课主题的边界；文件处理关注字节宽度、换行、顺序与记录数；金额处理关注单位、舍入与守恒；数据库处理关注 SQL 查询与修改前后状态。列出输入是否可原地改写、运行会覆盖什么、如何从干净夹具重跑。不要用程序自己生成的输出直接宣布“这是正确预期”；先由规则人工算出或用独立参考方法核对。

验收按改动面选择场景，而不是要求所有课程跑同一巨型矩阵：

| 课程类型 | 至少运行与观察 |
|---|---|
| 语法/内存基础 | 本课语法检查、编译和实际输出；核心边界值变化后重跑 |
| 文件/排序 | 用本课真实夹具执行；校验文件内容、行/字节数和 RC；触及主题的 EOF/坏输入/排序边界 |
| 模块/脚本 | 从干净状态构建并运行主程序；检查接口、日志/输出与失败状态 |
| SQL/综合 | 使用真实工具链运行本课场景；核对 DB 查询、输出文件、计数和退出码；执行已声明的故障/重跑场景 |

`cobc -fsyntax-only` 只证明语法路径；`build.sh check` 是否还运行行为场景须逐课核对。缺工具链、无法稳定注入的故障或环境特有限制要写明实际验证范围，不补造“已通过”。改变 stdout、记录格式或接口时同步核对所有消费者和答案。修复旧题目、链接、草稿状态与失效的历史“实测”表述。

## 8. 逐课关注点清单

下表是**审阅提问**，不是预先判定每课都有缺陷；每一课仍须基于现有源码、夹具和相邻课程单独设计。`DIRECTORY.md` 给出完整先修与项目联系。

| 课 | 逐课设计时重点追问 |
|---|---|
| 01 Hello | 最小程序怎样成为批次入口？编译和运行分别证明什么？清掉草稿状态。 |
| 02 PIC | 账户号前导零、金额精度、日期形状各由什么保证？保留现有三项修改题的一致性。 |
| 03 MOVE/COMPUTE | 截断与舍入怎样影响期末余额？业务选哪种规则，何时报告溢出？ |
| 04 IF | 交易边界值在何处分叉？嵌套判断是否能让读者追踪接受/拒绝？ |
| 05 EVALUATE | 交易类型的已知、未知分支分别产生什么结果？分类与实际过账有何边界？ |
| 06 PERFORM | 零次、最后一次和越过固定映射范围时发生什么？别提前引入表格。 |
| 07 Paragraph | 主流程何时调用和返回？共享字段何时被修改？ |
| 08 控制流综合 | 多笔交易的余额及接受/拒绝计数如何逐笔核算？ |
| 09 Group Item | 组项、子项的布局与整组搬运如何关联外部记录？ |
| 10 REDEFINES | 同一字节的两种解释由什么业务类型选择？视图不会自动校验。 |
| 11 OCCURS | 表容量、已装载数量和遍历上界是否一致？ |
| 12 INDEXED BY | 索引和数字下标在查找中各负责什么？访问边界如何验证？ |
| 13 SEARCH | 查找成功/失败和有序性前提是否可观察？ |
| 14 数据结构综合 | 内存表怎样关联账户和交易；容量、重复键及余额规则是否明确？ |

## 9. 后续 goal 执行方式与交付门槛

1. **先定基线：** 主负责人核查现有树、工具链可用性、跨课记录/输出契约，建 32 课任务清单。总目录、全局 README、共用构建/检查入口由一名集成人负责，避免并行改出冲突。已有扩展课程的 [`AUTHORING-STANDARD.md`](../extensions/enterprise-batch/docs/curriculum/AUTHORING-STANDARD.md) 面向更严格的企业批处理实训；不要直接将其全部故障矩阵强加于主线基础课。
2. **按课分配：** 一个课目录由一个执行者负责设计卡、README、源码、注释、练习、答案、夹具及该课脚本，按先修顺序分阶段验收。相邻课可并行调查，接口或数据格式改变必须先由集成人确定契约，再批量实施。
3. **逐课提交：** 每课交“现状→设计决策→文件变化→正常/边界/失败的实际命令及结果→未验证项→跨课影响”。不要把不影响行为的解释性改动伪装成已测试的功能变化，也不要提交未完成的占位课程或伪造输出。
4. **交叉复核：** 另一位审阅者从零按 README 运行或复算关键数据，检查业务动机、前置知识、源码注释的真实性、练习能否独立完成、答案一致性、固定格式与本课范围。指出一项具体错误就回到该课修复，不能用“将来完善”代替当前承诺。
5. **阶段集成：** 每完成一阶段，集成人核对相邻课先修、命名和字段单位、目录链接、各课运行脚本及复位行为；做本阶段真实运行冒烟。第 29–32 课以受支持工具链为验收前提，工具链缺失时先记录环境阻塞，不能用 mock SQL 换取通过。
6. **完成定义：** 32 个课目录均有独立设计与验证证据；所有受影响的调用方、夹具、答案、总目录与共享入口同步更新；没有“草稿/待验收”的错误状态，课程目标与程序行为无冲突。最终全局完整性检查、各阶段代表路径、最终项目现有 `check.sh` 都通过后，再对外声称整套课程完成。

### 可直接分派的单课任务卡

集成人给执行者发任务时填写下列字段；未查清的字段先标为“待调查”，不得凭假设分派行为变更：

```text
课次/目录：
先修与后续承接：
本课必须教会的 1–2 项能力：
当前已有的正确内容与待解决的具体问题（附文件位置）：
允许修改的文件：该课目录；跨课接口须先取得集成人确定的契约。
业务输入→规则→输出/RC：
教学边界：本课不提前引入的知识；哪些只是上游前提。
验收场景：正常、紧贴本课主题的边界、适用的故障；每项的预期值及独立计算依据。
交付：设计卡、各文件修改、执行命令与实际观察、未验证项、跨课影响。
```

同一课的 README、代码、练习、答案和夹具由同一个执行者闭环维护，集成人只处理共享入口及跨课契约。按 `DIRECTORY.md` 的六个阶段推进：01–08、09–14、15–22、23–28、29–31、32；阶段内互不改同一目录的课可以并行，但后课若依赖前课改变的数据定义，先冻结共同字段宽度、单位、接口和预期输出，再分派。每课独立审阅通过后才计入阶段完成；阶段接口或约定发生变化时，回查所有已验收的消费者并重新执行受影响场景。

交付报告使用固定的证据表，不必为每课新建永久报告文件：

| 场景 | 从何种干净输入开始 | 预期 stdout/文件/DB/RC | 实际命令与观察 | 是否吻合、差异原因 |
|---|---|---|---|---|
| 正常路径 | 夹具及复位方法 | 独立计算的关键值 | 实际执行记录 | 结论 |
| 主题边界 | 最小变化及其目的 | 对应变化与不变量 | 实际执行记录 | 结论 |
| 故障路径（适用时） | 可重复的故障注入 | 失败状态及残留产物 | 实际执行记录或未验证原因 | 结论 |

任务卡和报告都须区分“文档中的预期”“亲自运行观察到的结果”“基于代码的推断”。若课程只改文字，核对与现有程序/夹具相符；若改程序行为，则重新运行受影响路径。一个代理不能以自己复述的 README 代替独立复核。

每课交付审阅表：

- [ ] 开篇讲清业务任务、当前知识缺口和本课产出；环境版本放到运行条件。
- [ ] 目标可在源码和运行结果中找到证据；新增概念没有越过先修链。
- [ ] 输入/输出、字段单位/宽度、前提、分支、错误与退出码对应真实代码。
- [ ] 注释解释规则、接口或非直观决定，删去逐句翻译与失效注释。
- [ ] 固定格式及所有受影响的 Copybook、脚本、夹具和消费者一致。
- [ ] 修改题、迁移题、答案与 README 一致；结果可独立核算。
- [ ] 完成实际编译运行与本课主题边界验证，记录命令、观察结果与未覆盖限制。
- [ ] 相邻课衔接和总目录项目联系保持准确；未宣称生产保证或伪造实测。
