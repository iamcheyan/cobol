# 第 17 課変更演習の解答例

この解答は [`exercise.md`](./exercise.md) の変更演習だけを扱い、応用演習の解答は含みません。

## 出力 FD で口座番号を先頭にする

変更箇所：`lesson.cob` の `FD BALANCE-FILE` にある `01 FD-BALANCE-RECORD`。

変更前：

```cobol
       01 FD-BALANCE-RECORD.
           05 FD-OUT-CUSTOMER-ID PIC X(8).
           05 FD-OUT-ACCOUNT-NUMBER PIC X(10).
           05 FD-OUT-BALANCE PIC 9(7)V99.
```

変更後：

```cobol
       01 FD-BALANCE-RECORD.
           05 FD-OUT-ACCOUNT-NUMBER PIC X(10).
           05 FD-OUT-CUSTOMER-ID PIC X(8).
           05 FD-OUT-BALANCE PIC 9(7)V99.
```

コマンド：

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob
cobc -x -Wall -o build/lesson_17 lesson.cob
cp accounts.dat build/
(cd build && ./lesson_17)
wc -c build/balances.dat
cmp accounts.dat build/balances.dat
rm -rf build
```

**標準出力：** ベースラインと完全に同じ 5 行です。3 つの `MOVE` 文はフィールド名で代入し、フィールド名は変わっていないため、各レコードに表示される口座番号、顧客番号、残高の値も変わりません。

```text
ファイルを開きました
出力 口座番号=0001234567 顧客番号=C0001042 残高=0001000.00
出力 口座番号=0002468101 顧客番号=C0002042 残高=0000020.00
出力 口座番号=0007654321 顧客番号=C0003042 残高=0000250.75
クローズ完了 件数=03
```

**出力ファイル：** `wc -c build/balances.dat` は `81` を出力します。これは `3 × 27` です。`cmp accounts.dat build/balances.dat` は何も出力せず、終了コード 0 となり、出力と入力がバイト単位で一致することを示します（ファイル内に改行はなく、以下の改行は表示のためだけです）：

```text
0001234567C00010420001000000
0002468101C0002042000002000
0007654321C0003042000025075
```

第 1 レコードでは、`0001234567` が出力バイト 1〜10、`C0001042` が 11〜18、`000100000` が 19〜27 を占めます。入力レコードのオフセットと一致しています。

**ベースラインとの完全な差分：**

| レコード | ベースラインの `balances.dat` | 並べ替え後の `balances.dat` |
|---:|---|---|
| 1 | `C00010420001234567000100000` | `0001234567C00010420001000000` |
| 2 | `C00020420002468101000002000` | `0002468101C0002042000002000` |
| 3 | `C00030420007654321000025075` | `0007654321C0003042000025075` |
| ファイル合計サイズ | 81 | 81 |

**理由：** `MOVE` は宣言順とは無関係にデータ名で代入します。`WRITE` は `01` レコード内で宣言された順にレコードの各バイトを書き出します。そのため `05` 宣言の順序を変えると出力上の各フィールドのオフセットが変わりますが、各レコードの幅は `PIC` 句が決める `10 + 8 + 9 = 27` バイトのままです。レコード数とファイル合計サイズ（`3 × 27 = 81`）は変わりません。

## 列ルーラーで位置を検証する：解答

[`exercise.md`](./exercise.md) の「列ルーラーで位置を検証する」3 課題への解答です。

### 課題 1

| 項目 | 開始桁 | 終了桁 | 幅 | `:PositionRange` の出力 |
|---|---:|---:|---:|---|
| 名義 | 19 | 48 | 30 | `POSITION(19:48)` |
| 残高 | 89 | 108 | 20 | `POSITION(89:108)` |
| 予備領域 | 177 | 200 | 24 | `POSITION(177:200)` |

幅は「終了桁 − 開始桁 + 1」で求めます。`48 − 19 + 1 = 30`、`108 − 89 + 1 = 20`、`200 − 177 + 1 = 24`。3 つとも README の定義表の「長さ」と一致するので、同じバイトを測れています。

**間違えやすい点**：`:PositionRange` は**両端を含む**区間を返します。`:PositionJump 48` から `:PositionJump 19` を引くと 29 になり、1 桁足りません。引き算せず、`:PositionRange` の出力をそのまま読んでください。

### 課題 2

1. 削除前、49〜56 桁目は `BR-TOKYO`（8 文字）です。
2. 19 桁目の `T` を削除すると、49〜56 桁目は `R-TOKYO2` になります。
3. 総バイト数は `600` から `599` になります。
4. プログラムはエラーを出しません。

**2 の答えが `R-TOKYO2` になる理由。** 19 桁目を削除すると、19 桁目以降の全バイトが 1 桁ずつ左へ移動します。19〜48 桁目の 30 バイトの名義が 1 文字減るため、49〜56 桁目にあった `BR-TOKYO` は 48〜55 桁目へ移ります。49 桁目からは `R-TOKYO`（元の `BR-TOKYO` から先頭 `B` を除いたもの）が読め、56 桁目には次のレコード（レコード 2）の口座番号の先頭 `2` が入ります。

**`600 ÷ 200` が意味を失う理由。** 600 はちょうど 3 × 200 でしたが、599 は 200 の倍数ではありません。`599 = 2 × 200 + 199` です。つまり完全に読めるレコードは 2 件だけで、3 件目は 199 バイトしかなく 1 バイト不足します。**これが本課で示した境界そのものです。プログラムは総バイト数を検証しません。** 3 回目の `READ` は 199 バイトを埋め、最後の 1 バイト位置には前のレコードの残りが残ります。`AT END` は通常どおり発火し、プログラムは何も言いません。

**エラーにならない理由。** 次の 3 つが検査されていません。

- `OPEN` はファイルを開けるかだけを見ます。599 バイトの普通のファイルは開けます。
- 各 `READ` は成功します（1〜2 件目は完全、3 件目は残りデータで埋まる）。`AT END` 以外の異常はありません。
- `WRITE` は切り詰められた項目を含む 200 バイトのレコードを書き、状態 `00` を返します。

したがって終了コードは `0` のままで、画面にも 3 行の `出力 …` が出ます。ただし 3 行目の残高はすでに誤って読まれています。**桁ルーラーで 1 列ずつ確認する人だけが気づけます。**

### 課題 3

```sh
cd lessons/17-fixed-length-files
cp account-master-200.dat build/account-master-200.dat   # フィクスチャを変更した場合は復元
wc -c account-master-200.dat                              # 600 と出力されること
cmp account-master-200.dat build/account-master-200.dat   # 元のフィクスチャと比較
```

**提出物：**

- 課題 1 の表
- 課題 2 の 4 つの回答
- `cmp` が無出力で終了コード `0`、`wc -c` が `600` を出力

`wc -c` が `599` なら削除した文字が戻っていません。`cmp` が `differ: byte 19` と言うなら戻す位置が違います。`cmp` は最初に異なるバイト位置を教えてくれるので、それ自体がよい位置特定の演習になります。
