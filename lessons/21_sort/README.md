# 第 21 课：用 SORT 整理账户主档——把无序输入变成有序输出

第 20 课的顺序匹配有个前提：两边都得按账户号升序——可上游送来的主档常常没排过序。本课用 `SORT` 把一份四条未排序的账户主档整理成升序：输入过程逐条 `READ` 再 `RELEASE` 进去，输出过程用 `RETURN` 按账户号取回来，得到的记录流正好喂给匹配扫描。

## 业务现场

凌晨两点多，对账作业跑到第二步：账户主档和当日流水要合起来过一遍。流水那边还算老实，交易系统按发生顺序往后追加；主档这边就随缘了——核心系统的导出作业压根不管顺序，从哪张数据页扫下来，就按什么排列写出文件。

运维把文件放到共享目录，撂下一句话："文件就长这样，你们自己处理。"

你如果直接把这份主档丢进第 20 课的匹配扫描，麻烦不会以报错的形式出现。归并扫描假定两边按键升序，顺序一乱，它就会把明明存在的账户判成"对面没有对应记录"——`口座のみ` 和 `取引のみ` 凭空多出一批，程序照常结束，退出码还是 `0`。第二天早上对账岗拿到一张不合的差异表，开始逐条找人核对那些"其实根本不存在"的差异。

所以真正的前置动作是：先把这份文件排好，再拿去做匹配。这一课学的就是这道整理工序。

（时间、条数和场景是教学示意，挑出来是为了说清问题，不是某家机构的真实数据。）

## 为什么现在学

前面几课你已经把文件这一摊摸熟了：第 15–19 课会让你读、会写、能让两条以上的流各自推进；第 20 课学会了按键归并，一次扫描就把记录分成"匹配/仅主档/仅交易"。但那套算法是有前提的——**两边都得有序**。上游给你文件的时候，可不会附一句"已经排好了"。

你可能会想：那我读一条、跟下一条比一下，自己在内存里排不行吗？

行，但代价不小。几百条还撑得住，几万条你就得先整份装进内存，还得处理"装不下"；排序算法本身也有讲究——谁快谁慢、相同键怎么排、数据量大了怎么办。这些跟你的业务一点关系都没有，却要你亲手背进程序。

COBOL 的答案是把这段活包起来：`SORT`。你只负责说清两件事——按哪个字段排、记录从哪来又到哪去；怎么排是它的事。

## 这个知识点是什么，它解决什么问题

**它是什么。** `SORT` 给你的是一条流水线：读进来 → 按键排好 → 按顺序吐出来。你要准备三样东西：一个排序键，一个输入过程，一个输出过程。输入过程把待排序的记录一条条送进排序工作文件（`RELEASE`），输出过程把排好的记录一条条取回来（`RETURN`），取回来的时候已经是升序的，你照常一条条处理。

**它在业务里解决什么问题。** 把"整理顺序"和"使用顺序"拆成两件事。上游按什么顺序给你都不重要，记录先进排序、出口就是有序的。对账链路上需要有序的地方不止一处——匹配、归并、跨文件比对都吃这个前提，而排序只该在一个地方做对。

**这一课的产物不是文件。** 找东西的时候别找错地方：程序没有写任何输出文件。它产出的是**一条有序的记录流**——输出过程取一条、处理一条（本课就是显示出来）。在完整批次里，这个流直接喂给第 20 课的匹配扫描，不需要先落成磁盘文件；把排好序的结果写成文件是第 22 课的事。

**重复键的次序，别指望。** 这是最容易想当然的一点。`SORT` 只承诺"按键升序"；两条记录的键相同时谁先谁后，标准没规定，你也不该假设每次跑出来都一样。要固定次序，就得把第二个排序键也写进声明里——比如账户号相同再按余额降序。本课夹具的账户号是唯一的，压根没有重复键，所以这个行为在本课**观测不到**，只能作为未验证项记着。

**什么时候不该用它。** 数据已经在内存里的小表、要按条件反复查找的记录，那是第 11–13 课 `OCCURS`/`SEARCH` 的活；只是把两条各自有序的流合并，第 20 课的直接扫描就够。另外，本课特意让你走完整的两个过程，因为排序键声明、`RELEASE`/`RETURN` 的边界和计数都藏在这里面；用 `USING`/`GIVING` 的写法会把它们遮住（练习里也不允许）。

## 本课完成后的能力与边界

学完本课后，你可以：

- 声明排序工作文件（`SELECT ... ASSIGN TO DISK` + `SD`）并指定升序排序键。
- 在 `INPUT PROCEDURE` 中打开输入、逐条 `READ` 并用 `RELEASE` 送入排序。
- 在 `OUTPUT PROCEDURE` 中用 `RETURN` 逐条取回已排序记录，并用 `AT END` 结束。
- 用 `SORT-RETURN` 区分排序工作成功与失败，并核对 `入力レコード数 = 出力レコード数`。
- 说明为什么对排序工作文件不能执行 `OPEN`/`CLOSE`，以及排序输出如何成为第 20 课匹配的输入。

边界：本课只排序并显示，**不生成排序结果文件**、不累计金额、不做匹配；夹具账户号唯一，因此重复键的相对次序在本课观察不到。排序键规则、重复键政策与排序失败的批次处置属于接口约定，正式的错误分流见第 26 课。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端；本课不依赖数据库或附加工具。
- `SELECT` 使用相对文件名，因此**从本课目录执行**；语法检查与编译在 `build/` 下生成可执行文件。

## 记录布局与数据流

[`accounts-unsorted.txt`](./accounts-unsorted.txt) 有 4 条 27 字符记录，**没排过序**：

| 字段 | `PIC` | 长度 |
|---|---|---:|
| 账户号 | `X(10)` | 10 |
| 客户号 | `X(8)` | 8 |
| 余额 | `9(7)V99` | 9 |

余额里的 `V` 是隐含小数点、不占字符，所以一行看得见的长度是 10 + 8 + 9 = 27。这跟第 17、20 课的主档布局是同一套。

程序声明了两样东西：`SELECT SORT-WORK ASSIGN TO DISK` 和 `SD SORT-WORK`。前者告诉编译器"有个排序工作文件"，后者描述它里面装什么记录——注意用的是 `SD`，不是普通输入输出文件那个 `FD`。

这个文件由 `SORT` 语句自己管，**你的程序不要 `OPEN` 也不要 `CLOSE` 它**。你只干两件事：输入过程往里 `RELEASE`，输出过程从里 `RETURN`。

## 三个排序阶段

1. `SORT SORT-WORK ON ASCENDING KEY SD-ACCOUNT-NUMBER` 这一句把排序键和两个过程的入口一次说清。
2. 输入过程 `1000-LOAD-INPUT` 打开行顺序输入，逐条 `READ`；读成功就把 27 字符记录移到 `SD` 记录里再 `RELEASE`。文件状态 `10` 表示正常的文件结束。
3. 记录交出去之后，GnuCOBOL 按 `SD-ACCOUNT-NUMBER` 把它们排好。
4. 输出过程 `2000-RETURN-SORTED` 反复 `RETURN`，每取回一条就显示一条，`AT END` 表示取完了。
5. 主段落回头检查 `SORT-RETURN`，最后显示输入/输出计数；只要输入读取或排序出问题，就返回非零码。

计数不变量：`入力レコード数 = 出力レコード数`。本课是 `004 = 004`——4 条全释放进去、又全取回来，说明排序过程既没丢记录，也没凭空多出记录。往后每次看批处理的结果，这个数都是你第一个要盯的东西。

## 前提与边界

| 前提 | 由谁保证 | 本课是否校验 |
|---|---|---|
| 输入每行满足 27 字符布局 | 夹具/上游 | 否，宽度不符会读错字段 |
| 账户号作为排序键，含前导零且等长 | 夹具设计 | 否，但等长文本按字符顺序比较就等于按账户号升序 |
| 账户号唯一 | 夹具 | 否，本课不处理重复键 |
| 排序键相同记录的先后次序 | 谁都没约定 | **未验证**：夹具里没有重复键，所以看不到并列记录怎么排；真要固定次序，得再声明一个排序键（见举一反三练习） |

最后一行值得单独说一句：它不是"本课没空讲"，而是这件事本来就没人替你保证。手上没有重复键的数据时，你永远观测不到它——这也正是"随便跑几组数据看看"不靠谱的原因。

再重复一遍前面那句：排序工作文件由 `SORT` 语句管理，程序既不 `OPEN`/`CLOSE` 它，也不直接读写它。输入文件在输入过程里打开、关闭；输出只写到终端，没生成任何排序结果文件。

## 运行与观察

**输入：** 本课目录下的 `accounts-unsorted.txt`（4 条未排序记录）。程序按相对路径打开，所以要先 `cd` 到本课目录。

**命令及作用：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                  # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_21 lesson.cob    # 编译并生成可执行文件
./build/lesson_21                              # 运行，读取当前目录下的夹具
echo $?                                        # 查看退出码
rm -rf build                                   # 清理生成的可执行文件
```

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，无编译诊断 |
| 标准输出 | 5 行，见下方代码块；4 条记录按账户号升序 |
| 进程退出码 | `0` |
| 生成的业务文件 | 无（排序工作文件由运行时内部管理） |

```text
ソート済み 口座番号=A000000001 顧客番号=C0001001 残高=0001000.00
ソート済み 口座番号=A000000002 顧客番号=C0001002 残高=0000002.00
ソート済み 口座番号=A000000004 顧客番号=C0001004 残高=0000025.00
ソート済み 口座番号=A000000005 顧客番号=C0001005 残高=0000250.75
入力レコード数=004 出力レコード数=004
```

**可独立核算：** 输入夹具的账户号依次是 `A000000005`、`A000000001`、`A000000004`、`A000000002`（未排序），输出必须是 `A000000001`、`A000000002`、`A000000004`、`A000000005`——排序做的只是重排，所以输出账户号集合必须与输入完全相同，变的只有顺序。计数行 `004 = 004` 印证没有丢记录。

**输出字段对照（日文输出 → 含义）：** `ソート済み` = 已排序；`口座番号` = 账户号；`顧客番号` = 客户号；`残高` = 余额；`入力レコード数` / `出力レコード数` = 输入 / 输出记录数。

**实际观察到的环境细节：** 在本工作区运行可执行文件时，标准错误会输出 `Warning: program compiled against libxml 212 using older 209`。这是运行环境的链接库版本警告，不是本程序的业务输出；其触发组件尚未定位。

## 修改练习

两项都在**临时目录里的夹具副本**上做，不要改动仓库内的 `accounts-unsorted.txt`：

1. 交换副本的前两行，运行后确认输出仍按账户号升序，且输入/输出计数相同。
2. 从原始夹具出发，在副本末尾追加一条 27 字符记录：账户号 `A000000006`、客户号 `C0001006`、余额数字 `000000001`。确认它排在最后一行，计数变为 `005`。

完整题目与预期见 [`exercise.md`](./exercise.md)，参考答案见 [`answer.md`](./answer.md)。

## 举一反三练习

给排序键加第二个字段：先按账户号升序，再按余额降序。至少准备两条账户号相同、余额不同的记录，观察结果，并说明在只声明一个排序键时，程序**是否**依赖相同键记录的相对次序。记录修改后的 `SORT` 键声明与完整输出。不许用 `OCCURS` 先装入全部记录，也不许改用 `USING`/`GIVING` 绕开本课的两个过程。题目见 [`exercise.md`](./exercise.md)，本题不提供答案。

## 走一遍真实流程

把这一课放回那条对账链路，它站在最前面：

1. 上游把账户主档和当日流水导出来，顺序谁都不保证——同时读两份文件的本事，第 19 课已经给过你。
2. **你在这里**：主档先过一遍 `SORT`，输出过程吐出来的就是按键升序的记录流。
3. 有序的记录流交给第 20 课的匹配扫描，跟同样有序的流水做一次归并，分出"匹配/仅主档/仅交易"。
4. 匹配结果再往下走：校验、写出结果文件、错误分流，最后汇进第 32 课的完整对账批次。

注意第 2 步和第 3 步之间**没有文件**：排序结果是内存里一条条记录，本课把它显示出来，第 22 课会把"排序 + 匹配 + 写结果"串进同一个程序，那时你就能看到这两步怎么接上。中途要是硬塞一个文件，你就得额外操心它的命名、覆盖和清理，而这一步本来不需要。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器，通常排在"输入文件就绪"检查之后、匹配作业之前。
- **谁看它的输出**：值班的人先看退出码，再看 `入力レコード数` 和 `出力レコード数` 是否相等。数字对不上，当晚就得查。
- **出事谁被叫起来**：排序失败（`SORT-RETURN` 非零）或者计数对不上，先接到告警的是运维/值班，再转给开发。
- **下一个系统怎么接**：排好序的记录流交给匹配扫描；把结果写成文件在第 22 课。
- **第一个月最容易出的事故**：默认"上游给的文件是有序的"。没人写下来的顺序约定，某天上游换个导出方式就变了，而你的程序不会报警，账差要到第二天对账才暴露。

边界也说清楚：这课只把顺序整理好，还没有写结果文件、没有累计金额、没有拒绝分类，也没有生产级的重跑和失败恢复。排序键规则、重复键政策、空文件怎么处理、源文件状态、排序失败后整批怎么处置，都得先跟上下游约定；这些约定没落地之前，这份代码还不能当成对账批次上线。
