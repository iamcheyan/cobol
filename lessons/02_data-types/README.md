# 第 02 课：用 PIC 描述账户快照的字段类型与宽度

银行夜间批次拿到的第一样东西是一份账户快照：一行一个账户的定长文本，账户号有几位、金额几位小数、日期什么形状，全靠约定。本课把这批字段（标识符、数量、金额、利率、业务编码）用 `PIC` 声明成程序内的数据项并打印出来，产出一份能逐字段对照上游文件的字段目录；第 03 课就在这份宽度和精度上做金额运算，第 09 课再把这些平铺字段收进记录分组。

## 业务现场

晚上 23:40，核心系统跑完当天最后一轮结账，把账户快照导出成文件，留给后半夜的批处理。这份文件是定长的，一行一个账户：哪几位是账户号、哪几位是姓名、哪几位是余额，上游的数据字典里都写死了。你的程序拿到它，第一件要做的事不是算钱，而是把这一行"读对"——从第几个字节切到第几个字节，切出来的到底是什么。

这里最容易翻车的地方不是难，是"看着对"。

先说账户号。很常见的场面是：第二天早上柜面接到客户电话，说账上少了一笔钱。一路查下去，问题出在账户号丢了前面的零。上游发来的是十二位 `000123456789`，程序里却把它声明成了数值字段——数值不存前导零，那串零被顺手抹掉了。可这串零不是"数值大小"里的零，它是账号本身的样子。前导零一丢，账号就跟账户主档对不上，对账环节把整条记录判成"找不到账户"。

再说一个更安静、也更贵的事故。上游把"客户姓名"从 12 位悄悄扩到 16 位，你没收到通知，程序里还是按 12 位往后数。于是多出来的 4 个字符被当成了下一个字段的开头，余额、日期、状态码全体右移四位。程序一行报错都没有，输出的金额却全是错的——这种错，往往等有人翻账才被发现。

日期也一样会骗人。开户日在文件里就是八位数字，`20261013` 看着挺正常，可 `20261399`（13 月 99 日）一样塞得进去。八位数字只保证"形状是八位数字"，保证不了它是不是一个真实存在的日子。

（上面这些字段和数值是课程编排的演示样例，用来说明字段契约为什么重要，不对应任何真实机构或真实账户。）

## 为什么现在学

你可能会想：字段宽度，写清楚不就行了？Python 里 `str` 不管你几位，Java 里 `String` 也不声明长度，凭什么 COBOL 要先把每一位数明白？

因为在这里，"宽度"不是一句建议，而是**这份文件本身的长相**。COBOL 读定长记录时，就是按你声明的宽度一个一个往后切：你声明账户号 `X(12)`，它就从这一行里切走 12 个字符；你声明 `9(7)V99`，它就认定接下来 9 个字符是一个七位整数、两位小数的金额。声明错了，切出来的就不是你想的那个东西。

第 01 课的程序只会打印写死的字面量，一个业务字段都没有。那套写法在这个场景里立刻不够用：字面量声明不了宽度，后面的语句也没法按名字引用它去计算或比较。所以这一课要回答三个问题——账户号这种"看着是数字、其实是编号"的字段该用哪种类型；金额的整数位和小数位怎么定；日期、状态码这类编码用什么形状。答完这三个问题，你手上就有了一份双方都认的**字段目录**：上游怎么发，程序就怎么读。

再往后看一步：第 03 课要拿这份宽度和精度做金额加减，第 09 课把这些平铺字段收进记录分组，第 17、18 课按这里的宽度和偏移去解析真实文件。这一课的宽度一含糊，后面就是连环账。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** `PIC`（`PICTURE` 的缩写）就是给一个字段画一张草图：几位、是字母还是任意字符、是不是数字、小数点在哪儿。`PIC X(12)` 说的是"12 个字符，什么都可能出现"；`PIC 9(7)V99` 说的是"七位整数加两位小数，小数点不占位置"。字段名、这张草图，再加上可选的初值 `VALUE`，就是一个完整的数据项声明。编译器照它分配存储，运行时照它解释字节。

**它在业务里解决什么问题。** 一份账户快照从来不止一个使用方：上游核心系统生产它，你们的批处理读它，后面的对账和报表再拿结果往下传。几方要能对上话，就得对每个字段的类别、宽度、精度有同一份说法。`PIC` 就是写在程序里的那份说法，而且是**编译期**的：格式对不上，编译这一关就过不去，不用等到夜里跑批才发现。维护的人也不用翻文档——账户号占 12 位、金额只留两位小数，代码里就写着。

**什么时候它还不够用。** 这条边界得说清楚：`PIC` 管形状，不管对错。`PIC 9(8)` 不保证那八位数字是合法日期，`PIC X(12)` 也不保证这个账户存在。本课已经实测过：把开户日初值改成 `20261399`（13 月 99 日），程序照常编译、照常打印。真正的校验——日期合不合法、金额会不会是负的、状态码认不认识——要等后面的业务规则（第 04 课起）和错误处理（第 26 课）来写。

## 本课完成后的能力与边界

学完这一课，你应该能：

- 读懂 `PIC A(12)`、`PIC X(10)`、`PIC 9(7)V99`、`PIC S9(7)V99` 各自允许哪些字符、几位数字、带不带符号。
- 按业务含义决定一个字段用 `X` 还是用 `9`，并能说清账户号为什么必须当文本，不能当数字。
- 说明 `VALUE` 给 `WORKING-STORAGE` 的是编译期初值，不是文件、数据库或命令行送进来的输入。
- 解释 `V` 声明的隐含小数点不占存储字符，但 GnuCOBOL 3.2.0 的 `DISPLAY` 照样会把它打印出来。
- 自己算出 `PIC 9(7)V99` 的 `125000.75` 为什么打印成 `0125000.75`，并说明 `SIGN LEADING SEPARATE` 让字段比同位数金额多占一个字符。

边界：本课只声明程序内常量再打印出来，不读文件、不连数据库、不取命令行参数，也不做运算和业务校验。日期数字、币种码、状态码的取值范围一律没检查；`USAGE COMP`/`COMP-3` 的物理字节、记录分组（`01` 组项）也不在本课。赋值与算术见[第 03 课](../03_move-compute/README.md)，业务条件与拒绝规则见[第 04 课](../04_if-conditions/README.md)，记录分组见第 09 课，文件输入见第 15 课。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`）。
- 源文件为固定格式：第 7 列是指示符，Area A 从第 8 列、Area B 从第 12 列起，程序文本不越过第 72 列。
- 本机 GnuCOBOL 3.2.0 的固定格式右边界是第 72 个**字节**：第 73 字节起的内容被忽略（实测：收尾引号落在第 72 字节可通过，落在第 73 字节即被截断）。日文每字符 3 字节，所以含日文的行会比等宽 ASCII 行更早触到该边界。
- Linux 终端；本课不依赖数据库、附加工具或第三方库。
- 运行不产生业务数据文件，只在课内 `build/` 目录下生成一个可执行文件。

## 把这份字段契约写下来

### 场景：账户快照的字段契约

上游送来的账户快照（本课先用程序内常量模拟，还没有真文件）里，有账户号、客户信息、余额、利率和各种业务编码。想读懂它，双方得先把每个字段说定：是文本还是数字、占几位、小数点在哪。COBOL 用数据描述项来表达这份说法——名字 + `PIC`，再挂上可选的 `VALUE` 和 `USAGE`。编译器据此分配存储，并按初值检查宽度合不合得来；运行时按同一份描述解释字节。

再强调一次那条容易被忽略的边界：`PIC` 描述形状，不等于描述业务有效性。`PIC 9(8)` 保证不了这八个数字是合法日期，`PIC X(12)` 也保证不了账户存在——本课已实测：把日期初值改成 `20261399`（13 月 99 日），程序照常编译、运行、打印该值。金额的单位和精度同样得先约好：本课所有金额都按“七位整数 + 两位小数”的隐含尺度声明，利率按四位小数。

### 本课用到的 PIC 符号

- `A`：只接受字母和空格。本例拿它描述客户姓名、客户类别和国家码。
- `X`：字母数字位置，字母、数字、标点、空格都能放。本例把账户号、客户号、邮编、币种、参考号、批次号都当文本。
- `9`：数字位置。`9(4)` 就是四个 `9`；本例的分行号、笔数、序号、日期数字字段都用它。
- `9(n)` 里的 `(n)`：重复次数。`X(12)` 是十二个字符位置，`9(7)V99` 是七位整数加两位小数。
- `S`：声明这个数字字段带符号。本例配上 `SIGN LEADING SEPARATE CHARACTER`，把正负号单独写成一个字符。
- `V`：声明小数点的隐含位置。它不占存储，打印成什么样由 `DISPLAY` 决定。
- `VALUE`：给数据项设一个编译期初值。本课这些值都是演示样例，不是运行时输入。

### 跟 Java / Python 对照一下

`PIC X(n)` 有点像定长字符串，`PIC 9(n)` 有点像定长十进制整数，`PIC 9(n)V9(m)` 有点像定点 `Decimal`。不一样的在于：`PIC` 一次把字符位置、小数尺度和存储布局都说清楚，而且它是编译期契约；Java 的 `String`、Python 的 `int` 都不声明宽度。类比只帮你理解用途，别当成类型等价。

### 最容易踩的几个坑

- 以为 `PIC 9(8)` 能管日期。它只管"八位数字"这个形状；闰年、每月多少天，都得另外写规则。
- 以为账户号用 `9` 就显示不出前导零，所以"必须用 `X`"。真正的原因不是显示：本课的 `DISPLAY` 路径上，`PIC X(10)` 和 `PIC 9(10)` 外观一样（都打印 `0002046819`，已实测）。选 `X` 是因为语义——账户号是逐字符保存的标识符，不参与算术，也不需要为进位预留数值宽度。
- 以为 `V` 占一个字节。它不占存储字符位置，只是 GnuCOBOL 3.2.0 的 `DISPLAY` 会把小数点打出来。
- 以为 `X(n)`、`A(n)` 的宽度就等于字节数。宽度是**字符数**；只有默认 `DISPLAY` 用法下，一个字符位置才占一个字节，换成 `COMP`/`COMP-3` 要另算，本课不涉及。
- 把 `VALUE` 当成数据库默认值或运行时收到的输入。它只是程序自己写的初值。

## 输入与规则

**本课没有外部输入。** 所有数据都来自 [`lesson.cob`](./lesson.cob) 里各数据项的 `VALUE` 子句，是编译期就定下来的演示样例：没有标准输入、没有文件、没有命令行参数、也没有数据库。所以同一个可执行文件跑多少次，输出都一模一样。

已经写在声明里的约定：

- 标识符（账户号、客户号、邮编、参考号、批次号、产品码）用 `X`/`A` 逐字符保存，前导零是数据本身的一部分。
- 数量和金额（分行号、笔数、序号、对账单日、余额、利率）用 `9`，按隐含小数位声明。
- 金额和利率的 `VALUE` 用十进制字面量写，隐含小数点由 `V` 声明，初值里不额外写小数位。
- 还没做的检查：日期合法性、币种码和状态码的合法取值、金额非负、字段间的一致性，本课一概不查，这些只是留给后面课的业务规则。

## 完整示例源码

完整源码见 [`lesson.cob`](./lesson.cob)，按固定格式编写。程序其实只干三件事：声明字段、给初值、按顺序打印。下面从源码里摘出几行（不连续）看结构，完整字段目录在下一节。

```cobol
       DATA DIVISION.
       WORKING-STORAGE SECTION.
      * 契约：账户号等数字标识符不是数量，
      * 用 X 保存以免丢前导零；金额才用 9。
       01 WS-ACCOUNT-KEY PIC X(12) VALUE "000123456789".
       01 WS-LEDGER-BALANCE PIC 9(7)V99 VALUE 125000.75.
       PROCEDURE DIVISION.
           DISPLAY "口座キー=" WS-ACCOUNT-KEY
           DISPLAY "帳簿残高=" WS-LEDGER-BALANCE
           STOP RUN.
```

摘录省略了其余二十多个字段和大部分 `DISPLAY`；运行输出是日文，逐行含义见“运行与观察”。

## 源码阅读路径

按数据和状态变化的顺序读，别逐行翻译：

1. **`IDENTIFICATION DIVISION` / `PROGRAM-ID`**：标识这个可执行程序单元，本程序叫 `DATA02`。
2. **`DATA DIVISION` → `WORKING-STORAGE SECTION`**：常驻工作数据在这里声明。本课的字段全在这儿，程序结束就释放，没有文件记录区。
3. **字段声明（`01` 级平铺）**：每个 `01 WS-...` 是一个独立的基本数据项。本课故意平铺，不分组，免得提前把第 09 课的组项混进来。
4. **`VALUE` 子句**：编译期就把初值写进去。程序运行期间没有任何语句改这些字段，所以输出等于初值——本课没有状态变化，状态变化从第 03 课的 `MOVE`/`COMPUTE` 才开始。
5. **`PROCEDURE DIVISION` 的 `DISPLAY`**：按源码顺序逐字段打印，没有段落、条件、循环。
6. **`STOP RUN`**：正常结束 run unit，退出码 0。

### 边界观察：字段宽度和形状决定了什么（已实测）

下面几项都落在本课主题里（`PIC` 的形状与宽度，以及固定格式的行宽），用临时目录里的独立小程序复现，不动本课源码：

| 场景 | 命令与观察 | 结论 |
|---|---|---|
| 日期形状不等于有效性 | 把开户日初值改为 `20261399`，`cobc -fsyntax-only`、`-x` 均返回 0，运行打印 `20261399` | `PIC 9(8)` 只约束位数，日历合法性必须另写规则 |
| 初值超出声明宽度 | `PIC 9(4) VALUE 12345` 编译时（无论是否加 `-Wall`）得到 `warning: value size exceeds data size [-Wothers]`，运行打印 `2345`，退出码仍为 0 | 宽度是硬约束；超宽只是编译警告，高位会被丢弃，不会运行期报错 |
| 文本与数值的填充方向 | `X(8) VALUE "AB"` 打印 `AB` + 六个空格；`9(6) VALUE 521` 打印 `000521` | 文本左对齐空格填充，数值右对齐补零 |
| 含日文的行更早触到第 72 列 | 收尾引号落在第 72 字节的 `DISPLAY` 行编译通过；落在第 73 字节时报 `error: continuation character expected`，字面量被截断。纯 ASCII 行测得同一边界 | 固定格式的 72 列边界在本工具链上按字节计；日文每字符 3 字节，含日文的行必须比等宽 ASCII 行更早结束 |

## 走一遍真实流程

把这一课产出的字段目录放进一条完整链路，它站在最前面：

1. **上游**（核心系统）夜里导出账户快照文件：一行一个账户、定长，字段顺序和宽度按双方约定来。本课声明的那批字段，就是这份约定在程序侧的样子。
2. **本课产物**交给[第 17 课](../17_fixed-length-files/README.md)和[第 18 课](../18_csv-processing/README.md)：那两课按这里的宽度和偏移，从定长文件、CSV 里把字段真的读出来。宽度不对，读出来的就是错位的垃圾。
3. 账户号这一列接下来要当**匹配键**用：第 13 课按它去账户主档里找账户，第 20 课按它把主档余额和当日交易配起来。这就是它必须用文本 `X(12)` 的原因——当数值处理会丢前导零，键就废了。
4. 金额那几列推进[第 03 课](../03_move-compute/README.md)做加减和利息计提；精度（两位小数还是四位小数）直接决定结果保留到哪一位。
5. 到第 23 课，这些散在每个程序里的声明会变成一份共享的 Copybook：改宽度只改一处，所有读它的程序一起变。本课先手动把它们排整齐。
6. 终点是[第 32 课](../32_bank-reconciliation-project/README.md)的夜间对账项目——字段宽度、金额精度、日期形状的约定必须全链条一致，否则对账结果无从核对。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批次由调度器按时拉起，没人盯着屏幕，程序跑完就退出，它是链条上的一环。
- **谁看它的输出**：本课只是把字段值打出来核对；真实批次里对账和运维看的是结果文件和日志。不过字段值印出来对不对，恰恰是排查上游格式变更时最直接的线索。
- **出事谁被叫起来**：上游悄悄改了字段宽度，或者账户号被声明成数值字段丢了前导零，夜里批处理通常一声不响，第二天对账才炸——被叫起来的常常是对账组，不是当初写这段声明的人。
- **下一个系统怎么接**：文件解析、匹配、写库都依赖这份宽度和精度的约定，声明是它们共同的锚点。
- **第一个月最容易出的事故**：把标识符声明成数值字段（丢前导零）、宽度跟上游文件对不上（整条记录错位）、以为 `PIC 9(8)` 顺手校验了日期。

也要把话说清楚：本课只证明了源码能编译、字段能按声明打印出来，而且这些值全是程序内写死的演示常量。它没有读任何业务数据，没有校验任何取值，也不是生产接口规范。数据库列类型映射、编码与区域设置一致性、跨平台字符集检查这些真实系统要处理的东西，本课都不涉及，更不能据此说这套声明已经达到生产接口规范。

## 证据来源

以下都是在编写本课时于本机实际执行的命令与观察结果；未执行的场景一律标注为未验证：

- 本课源码：`cobc -fsyntax-only lesson.cob`（RC 0）、`cobc -x -Wall -o build/lesson_02 lesson.cob`（RC 0）、`./build/lesson_02`（RC 0，stdout 29 行，与本 README 所列一致，stderr 仅 libxml 环境警告）。
- 修改练习：在临时目录复制 `lesson.cob`，只替换三处 `VALUE` 后编译运行，`diff` 显示恰好三行变化（`支店コード`、`通貨コード`、`顧客番号`），与 `answer.md` 一致。
- 边界观察：`PIC 9(8)` 初值 `20261399`、`PIC 9(4)` 初值 `12345`、`X(8)` 初值 `"AB"`、`9(6)` 初值 `521` 四个临时程序，输出与警告如上表；另用占位字面量把收尾引号分别放在第 72、第 73 字节（纯 ASCII 与含日文各一组），确认右边界就是第 72 字节。
- 字节数参考：临时程序用 `FUNCTION LENGTH(...)` 测得 `X(12)`=12、`9(7)V99`=9、`S9(7)V99 SIGN LEADING SEPARATE`=10、`9(2)V9(4)`=6 字节（默认 `DISPLAY` 用法）。该内建函数不是本课教学内容，只用于核对本 README 的字节说明。

- 未验证：`COMP`/`COMP-3` 等其他 `USAGE` 的物理布局、其他平台与编译选项下的输出格式、编码差异；本课不涉及。
