# 第 01 课：Hello COBOL——让你的第一个批处理程序在银行机房里跑起来

## 业务现场

周一早上八点半，你刚到城商行批处理组报到。师父没给你讲业务，只扔过来一句话：

> "今天你就干一件事：让这台机器执行你写的程序，我在屏幕上看见它。"

你可能会想，这有什么难的。但在银行里，这句话有个很实在的含义：**让调度器认你的程序。**

夜里两点没有人坐在电脑前敲命令。值班室的调度器（cron、Control-M 这类工具）会按时拉起一个个作业，而它判断成败只看两样东西：可执行文件在哪儿、进程退出时的状态码是多少。退出码 `0` 就往下走，非 `0` 就报警——报警就意味着有人半夜被电话叫醒。

所以你写的第一个程序不是为了打印一句话，而是为了证明一件事：这台机器能跑你写的东西，而且失败的时候，你知道去哪儿看。

## 为什么现在学

你可能会想：编译器、可执行文件、退出码，这些我用 Java、Python 的时候天天见，没必要专门学一课吧？

问题就出在"天天见"这三个字上。COBOL 跟你熟悉的语言长得完全不一样：

- 它的源文件是**固定格式**的——同一行代码写在第 8 列还是第 12 列，意思不一样，写错列编译器直接不认；
- 它的"编译"和"运行"是两步，中间隔着生成出来的可执行文件；
- 这两步各自会怎么失败、失败时该看什么，跟 `python xx.py` 完全是两回事。

这一课只干一件事：把"源文件 → 编译 → 可执行 → 输出 → 退出码"这条链路走通。后面 31 课全搭在这条链路上——不管后面是处理十二万笔交易，还是连数据库取余额，你都得先能编译、能运行、能看懂它为什么退出。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 一个最小的 COBOL 程序由四块构成：程序标识（`IDENTIFICATION DIVISION` + `PROGRAM-ID`）、执行过程（`PROCEDURE DIVISION`）、输出语句（`DISPLAY`）、结束语句（`STOP RUN`）。本课还要弄清怎么用 `cobc` 把它变成 Linux 上能跑的可执行文件。

**它在业务里解决什么问题。** 银行、保险这类系统靠夜间批处理跑账：白天柜面和 App 产生的交易，夜里由一批作业逐条处理。这些作业不是人手点出来的，是调度器拉起来的。所以每个程序都必须满足两个最低要求——能被自动拉起，能自己报告成败。本课教的就是"怎么让一个程序进入这套体系"：编译器能找到入口，调度器能启动它，值班的人能从退出码判断这次到底跑成了没有。

**什么时候还用不上它。** 本课的程序不读数据、不做判断、也不算金额。别小看这个边界：真实批次里"跑起来了但结果算错"远比"跑不起来"危险——前者可能没人发现，后者当晚就会报警。判断结果对不对的检查要等到处理文件和金额的课程（第 03 课起）才出现。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `cobc -fsyntax-only` 检查一个 `.cob` 源文件能不能通过语法解析。
- 用 `cobc -x -o <名称>` 把源文件编译成可执行文件，并根据命令返回码确认编译是否真的成功。
- 运行可执行文件，分清哪些内容走标准输出、哪些走标准错误，并用退出码判断程序是不是正常结束。
- 在一个最小程序里指出程序标识、执行入口、输出语句和正常结束语句各是哪一行。
- 说清为什么一个既不读数据、也没定义字段的程序不需要 `DATA DIVISION`。

边界：本课不定义数据项、不读文件/命令行参数/数据库、不做任何运算；除了语法错误，也还没处理运行期故障。字段从[第 02 课](../02_data-types/README.md)开始，文件从第 15 课开始，错误分类与返回码语义到第 26 课才系统讲。

## 运行环境

- GnuCOBOL 3.2.0，使用默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端；本课不需要数据库、附加工具或第三方库。
- 运行不会产生业务数据文件，只在 `build/` 下生成一个可执行文件。

## 把这段代码拆开看

### 程序里到底有什么

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. HELLO01.
       PROCEDURE DIVISION.
           DISPLAY "こんにちは、COBOL！".
           STOP RUN.
```

五行，四个概念：

- `IDENTIFICATION DIVISION`：告诉编译器"这是一个程序单元，下面开始描述它"。
- `PROGRAM-ID. HELLO01.`：给它起名。这个名字是程序的身份，不止影响编译，后面学 `CALL` 时别的程序就是靠它来找你（第 24 课）。
- `PROCEDURE DIVISION`：从这里开始才是"真正要执行的步骤"。前面的部分都只是声明。
- `DISPLAY` 把一段文字写到标准输出，`STOP RUN` 结束这次运行。

注意这里**没有 `DATA DIVISION`**。不是漏写了，而是这个程序确实没有任何数据要存——没有余额、没有账户号、没有计数器。COBOL 的规矩是"用到什么声明什么"，你会在第 02 课第一次需要它。

### 跟 Java / Python 比一比

`PROGRAM-ID` 大致相当于 Java 的类名或 Python 的模块名，`DISPLAY` 大致相当于 `System.out.println(...)` 或 `print(...)`。这个类比帮你快速理解用途，但别推得太远：COBOL 的 Division 是**源程序结构**，不是类，也不是函数；它没有"对象"，也不靠缩进决定层级。

### 固定格式：COBOL 最容易被劝退的地方

这门语言年轻的时候靠穿孔卡片输入，所以对"第几列"有硬性规定，一直保留到今天：

- **第 7 列**：指示符区。写 `*` 表示这一行是注释，写 `-` 表示续行。
- **第 8–11 列（Area A）**：Division 名称、`FD`、`01` 级声明、段落名从这儿开始。
- **第 12–72 列（Area B）**：`DISPLAY`、`MOVE` 这些语句写在这儿。
- **第 73 列往后**：识别区，编译器**完全不看**。代码写到这里会静默消失——这是新手最疼的坑之一。

本课程所有源码都按这个规矩写。你从别的语言带过来的"最左边对齐"习惯，在这里会直接报错。

### 输出里的日文是怎么回事

本课程有个约定：讲解和注释用中文，但**程序运行时打印的业务文本用日文**（教材按日本金融系统的实际场景写，输出的字段名、状态词都沿用日文）。所以本课输出的是 `こんにちは、COBOL！`，意思是"你好，COBOL！"。看程序行为时以实际输出为准，含义对不上就回来看 README 里的中文对照。

## 逐行解析

| 源码行 | 作用 | 运行时发生了什么 |
|---|---|---|
| `IDENTIFICATION DIVISION.` | 声明"这里开始是一个程序单元" | 编译阶段用来解析后面的程序声明，不产生任何输出 |
| `PROGRAM-ID. HELLO01.` | 给程序单元命名 | 编译器把这个名字写进生成的可执行程序 |
| `PROCEDURE DIVISION.` | 声明可执行过程开始 | 运行时从这里进入程序 |
| `DISPLAY "こんにちは、COBOL！".` | 把字面量写到标准输出 | 终端收到一行 `こんにちは、COBOL！`；本课还没有任何业务字段 |
| `STOP RUN.` | 正常结束 COBOL run unit | 把控制权交回操作系统，后面没有 COBOL 语句了 |

这里几乎没有"数据变化"可言：没有用户定义的数据项，也没有余额或记录被改动。唯一的输出就是那句问候语。

## 运行与观察

本课不读输入文件、命令行参数或数据库，所以在本课目录里跑、换个目录跑，结果都一样。

**输入：** 没有。屏幕上那句话来自 `lesson.cob` 里的字面量，不是外部数据。

**命令和各步在干什么：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                    # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_01 lesson.cob      # 编译并生成可执行文件
./build/lesson_01                                # 运行程序，输出写到标准输出
echo $?                                          # 查看上一条命令的退出码
rm -rf build                                     # 清理生成的可执行文件
```

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，没有编译诊断 |
| 标准输出（stdout） | 一行 `こんにちは、COBOL！` |
| 进程退出码（`echo $?`） | `0` |
| 生成文件 | 只有 `build/lesson_01` |

两个坑先说在这儿。第一，`-fsyntax-only` 只检查语法，它既不生成可执行文件也不运行程序，所以**它过了不等于程序能跑**。第二，标准输出和标准错误是两条流：本工作区运行时，标准错误上会出现一行 `Warning: program compiled against libxml 212 using older 209`。这是运行环境里链接库版本差异造成的警告，不是你的程序打印的；程序真正的输出在标准输出上，退出码是 0。这件事以后每课都会遇到，判断业务结果时别把它算进去。

## 走一遍真实流程

把这个程序放到一家银行的夜里，它长这样：

1. **凌晨 1:50**，调度器按计划拉起 `lesson_01`，它打印一行"批次已启动"性质的信息，退出码 `0`。
2. 调度器看到 `0`，继续拉下一个作业（真实批次里紧接着的就是读交易文件的那个）。
3. **某天它退出码非 0**，值班人员被叫起来，第一步就是去看标准输出和标准错误——这正是本课教你分清的那两条流。

真实批次当然不会只打印一句话。它会一路长下去：第 03 课开始算金额，第 15 课开始读文件，第 26 课开始区分"业务拒绝"和"系统故障"（那时候退出码才有正经的设计），第 32 课汇聚成一个完整的夜间对账项目。

## 这份代码进了生产会怎样

- **谁调度它**：值班室里的调度器或 shell 作业，只认可执行文件路径和退出码，不会看你屏幕。
- **谁看它的输出**：运维和排障的人看标准输出/标准错误；所以"编译成功""运行成功""退出码 0"这三件事必须能分得清。
- **第一个月最容易出的事故**：把标准错误里的环境警告当成程序报错，或者看到编译通过就以为程序能跑。

也要把话说清楚：本课只证明了源码能编译、能输出。它还没有读业务数据，没有核对金额，更没有生产级的错误处理——字段定义见[第 02 课](../02_data-types/README.md)，文件读取见第 15 课，错误分类与返回码设计见第 26 课。
