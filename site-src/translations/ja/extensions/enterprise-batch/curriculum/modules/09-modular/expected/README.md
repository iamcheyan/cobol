# 独立した期待結果と照合

`expected/<case>.txt` は RC0/RC4（公開）ケースにのみ存在します。期待結果は業務ルールと手計算の小さな例から決定し、参照プログラムを実行する**前に**作成してから、`scripts/oracle.py`（COBOL の出力を転記したものではない独立した Python 参照モデル）で生成します。最後に、参照 COBOL の出力とバイト単位で一致する必要があります。RC8 ケースには期待レポートがありません。正しい結果は「公開ディレクトリなし」だからです。各ケースの RC の概要は [cases.json](cases.json) を参照してください。

## normal（RC0）

| 口座 | 期首 | 取引 | 期末 |
|---|---:|---|---:|
| 0000000001 | +1000 | T01 `C`500→1500；T02 `D`200→1300 | +1300 |
| 0000000002 | +500 | T03 `C`100→600 | +600 |

顧客の通過数は 2/2。取引の照合は `3 = 接收 3 + 拒绝 0`（受入 3 + 拒否 0）、口座の照合は `2 = 有交易 2 + 无交易 0`（取引あり 2 + 取引なし 0）、金額の照合は 期首 1500 + 貸方 600 − 借方 200 = 期末 1900 です。件数は 12 桁のゼロ埋め、金額は符号付き固定幅（13/18 桁）です。

## 境界ケース

- `empty-customers`：顧客ファイルは空で、顧客の制御値は `0/0/0` です。口座と取引は通常どおり処理されます。RC0。
- `no-transactions`：取引ファイルは空です。2 口座それぞれについて、期末残高=期首残高で出力され、`TX=0`、`NOTX=2` となります。RC0。
- `max-amount`：口座1は期首残高 0 に 13 桁の 9 を入金し、残高が 13 桁の上限に達します。口座2は期首残高が 13 桁の 9 で、1 を出金します。全体の `OPENING + CREDIT − DEBIT = CLOSING` は 18 桁で正確に照合されます。RC0。
- `all-empty`：3 ファイルすべてが空で、すべての件数と金額が 0 です。RC0。

## 業務上の拒否（RC4、公開は継続）

| ケース | 条件 | 理由コード | 主要な期待結果 |
|---|---|---|---|
| customer-bad-status | 顧客状態 `Z` | `CUST-BAD-STATUS` | 顧客を拒否し、取引なし |
| customer-bad-id | 顧客 ID `ABCD0001` | `BAD-ID` | 同上 |
| customer-no-name | 名前がすべて空白 | `CUST-NO-NAME` | 同上 |
| zero-amount | 取引金額 0 | `ZERO-AMOUNT` | 残高に変化なし |
| overdraft | 出金 2000 > 期首残高 1000 | `OVERDRAFT` | 残高は 1000 のまま |
| overflow | 13 桁すべて 9 の残高に 1 を入金 | `OVERFLOW` | 残高は上限のまま |
| unknown-direction | 方向 `X` | `BAD-DIRECTION` | 残高に変化なし |
| no-account | 取引口座が口座ファイルに存在しない | `NO-ACCOUNT` | 口座ファイルに該当口座なし |
| frozen-account | 口座状態 `F` | `ACCOUNT-STATUS` | この口座には**取引がある**ため、`NOTX=0` |

拒否された金額は、残高や貸方・借方の累計に含めません。拒否された取引は `TX` と `REJECT` に計上され、`TX = ACCEPT + REJECT` が維持されます。

## 契約エラー（RC8、非公開）

| ケース | 条件 | 期待結果 |
|---|---|---|
| bad-layout-version | 口座レイアウトのバージョン `002` | 出力ディレクトリなし、stderr `CONTRACT-FAIL` |
| short-account | 口座レコードが 46 バイト | 同上 |
| bad-account-date | 口座の業務日 ≠ 営業日 | 同上 |
| unsorted-transactions | 取引が口座/連番/ID の昇順でない | 同上 |
| dup-global-txid | 同一口座内で連番が異なる取引の `transaction_id` が重複 | JOB の全体一意性チェック：RC8、出力ディレクトリなし、stderr `duplicate global transaction_id` |
| dup-cross-account | 口座をまたいで `transaction_id` が重複 | 同上 |

全体重複のケースは、**ファイル内では厳密に昇順**（同一口座内で連番が異なり、口座は昇順）です。そのため、全体一意性チェックでのみ検出でき、順序チェックでは見逃します。`oracle.py` は独立した集合で再検証し、`run.sh` は外部ソート（`sort`）を使って入金前に検出します。

## バイト単位の比較に関する説明

`check.py` は RC0/RC4 ケースについて、定幅フィールドの誤りを検出できるようファイル全体の `trim` を行わず、`report.txt` と `expected/<case>.txt` をバイト単位で比較します。ログでは GnuCOBOL の `LINE SEQUENTIAL` が行末の空白を削除するため、モデルも同様に削除します。
