# Independent Expected Results and Reconciliation

`expected/<case>.txt` exists only for RC0/RC4 (published) cases. The expected results are determined from business rules and manually calculated small examples **before** running the reference program, then generated by `scripts/oracle.py` (an independent Python reference model, not copied back from COBOL output). Finally, they must match the reference COBOL output byte for byte. RC8 cases have no expected report because the correct result is “no publish directory.” See [cases.json](cases.json) for the RC summary of each case.

## normal (RC0)

| Account | Opening | Transactions | Closing |
|---|---:|---|---:|
| 0000000001 | +1000 | T01 `C`500→1500; T02 `D`200→1300 | +1300 |
| 0000000002 | +500 | T03 `C`100→600 | +600 |

Customers passed: 2/2. Transaction reconciliation: `3 = 接收 3 + 拒绝 0` (3 accepted + 0 rejected); account reconciliation: `2 = 有交易 2 + 无交易 0` (2 with transactions + 0 without transactions); amount reconciliation: opening 1500 + credits 600 − debits 200 = closing 1900. Counts are zero-padded to 12 digits; amounts use signed fixed-width fields (13/18 digits).

## Boundary Cases

- `empty-customers`: The customer file is empty; customer control totals are `0/0/0`. Accounts and transactions are processed as usual; RC0.
- `no-transactions`: The transaction file is empty. Each of the two accounts is output with closing balance=opening balance, `TX=0`, `NOTX=2`; RC0.
- `max-amount`: Account 1 starts at 0 and receives 13 digits of 9, reaching the 13-digit balance limit; account 2 starts with 13 digits of 9 and makes a debit of 1. The global `OPENING + CREDIT − DEBIT = CLOSING` is reconciled exactly using 18 digits; RC0.
- `all-empty`: All three files are empty; all counts and amounts are 0; RC0.

## Business Rejections (RC4, still published)

| Case | Trigger | Reason code | Key expected result |
|---|---|---|---|
| customer-bad-status | Customer status `Z` | `CUST-BAD-STATUS` | Customer rejected; no transactions |
| customer-bad-id | Customer ID `ABCD0001` | `BAD-ID` | Same as above |
| customer-no-name | Name consists entirely of spaces | `CUST-NO-NAME` | Same as above |
| zero-amount | Transaction amount 0 | `ZERO-AMOUNT` | Balance unchanged |
| overdraft | Debit 2000 > opening balance 1000 | `OVERDRAFT` | Balance remains 1000 |
| overflow | Credit of 1 to a balance of 13 digits of 9 | `OVERFLOW` | Balance remains at the limit |
| unknown-direction | Direction `X` | `BAD-DIRECTION` | Balance unchanged |
| no-account | Transaction account is absent from the account file | `NO-ACCOUNT` | No such account in the account file |
| frozen-account | Account status `F` | `ACCOUNT-STATUS` | This account **has transactions**, so `NOTX=0` |

Rejected amounts are excluded from all balances and credit/debit totals; rejected transactions count toward `TX` and `REJECT`, maintaining `TX = ACCEPT + REJECT`.

## Contract Errors (RC8, not published)

| Case | Trigger | Expected result |
|---|---|---|
| bad-layout-version | Account layout version `002` | No output directory, stderr `CONTRACT-FAIL` |
| short-account | Account row is 46 bytes | Same as above |
| bad-account-date | Account business date ≠ business date | Same as above |
| unsorted-transactions | Transactions not sorted by account/sequence/ID in ascending order | Same as above |
| dup-global-txid | Duplicate `transaction_id` in the same account with different sequence numbers | JOB global uniqueness check: RC8, no output directory, stderr `duplicate global transaction_id` |
| dup-cross-account | Duplicate `transaction_id` across accounts | Same as above |

The global-duplicate cases remain **strictly sorted within the file** (different sequence numbers within the same account, accounts in ascending order), so they can only be detected by the global uniqueness check; a sort-order check would miss them. `oracle.py` independently rechecks them using a set, and `run.sh` intercepts them before posting by using an external sort (`sort`).

## Byte-for-Byte Comparison Notes

For RC0/RC4 cases, `check.py` compares `report.txt` with `expected/<case>.txt` byte for byte, without applying `trim` to the whole file, to expose fixed-width field errors. GnuCOBOL `LINE SEQUENTIAL` trims trailing spaces from lines in logs, so the model does the same.
