# 修正方針：レイアウト v1/v2、互換性、移行、ロールバック

## 1. レイアウト方針

- **書き換えではなく追加**：企業レイアウト v2 = v1 の 31 バイト + 区分サブコードの 2 桁目。第 1–27 バイト（canonical CUSTOMER v1 の接頭部と第 27 バイトのレコード状態を含む）は意味を維持します。そのため「先頭 27 バイトのみ読む」旧 reader は位置ずれを起こしません。
- v1 区分のアップグレード規則：`A` → `A1`、`B` → `B1`、`C` → `C1`、`D` → `D1`（サブコード `1` は「v1 基準の細分」を表す）。モジュール 07 L4 のマッピングと一致します。
- v2 の有効コード：`[ABCD][0-9]`。それ以外は `BADCLASS`（業務拒否、RC4）。
- レコード状態は引き続き `A`/`D` のみ許可し、区分とは独立に検証します。それ以外は `BADSTATUS`（RC4）。
- layout_version は宣言されたレイアウト（`001`/`002`）と一致する必要があります。一致しない場合は `BADVERSION`（RC4）。
- ファイル全体が同一レイアウトであること。同一ファイル内で 31/32 を混在させると構造エラー（RC8）。

## 2. 互換性方針

| reader | v1 ファイル | v2 ファイル |
|---|---|---|
| v1 のみ対応する旧プログラム | 正常 | **拒否**（幅 32 ≠ 31、RC8 / 未完成版では RC12） |
| v2 プログラム（今回の成果物） | 31B を読み、v2 にアップグレード | 32B を読む |
| DB customer.table | — | v2（32B）に統一して保存 |
| 下流 `customer-day.dat` | 区分列を `A1`..`D1` に拡張 | 区分列は v2 コード |

## 3. 移行手順

1. 上流は MANIFEST で `layout_customer=002` を宣言し、企業レイアウト v2 ファイルを送信します。
2. 本システムは JOB002a で宣言レイアウトと物理幅を照合し、不一致なら RC8 で公開しません。
3. JOB002d が v1/v2 を v2 に統一し、DB の `customer.table`（32B）に書き込みます。
4. DB に既存の 31B 行がある場合、`capdb.read_customer_records` が自動アップグレードするため、停止スクリプトは不要です。一括で物理移行する場合は同じ関数で `customer.table` を書き直します。
5. 下流を v2 読み取りに切り替えます。移行中は NIGHTRPT の v1 読み取り経路で照合を続けられます。

## 4. ロールバック手順

- v1 専用バージョンにコードを戻せば v1 ファイルを読めます（v2 ファイルは拒否されます）。
- データを戻す場合：DB の `customer.table` を 32B から 31B に投影し（第 29 バイトのサブコードを破棄）、**サブコードが失われる**ことを理解してください。下流がサブコードを使っていないと確認し、元の v2 バックアップを保持している場合のみ実行します。
- ロールバックで元の入力 fixture は変更せず、派生データのみ変更します。ロールバック後、当日分を再実行し制御総数を再照合してください。
- **canonical CUSTOMER v1 の 27 バイトと第 27 バイトの状態の意味はロールバック対象外で、常に不変です。**

## 5. データ切替と並行検証

- 並行期間：同じ v1 日を新旧両バージョンでそれぞれ実行し、`customer-day.dat` と制御総数を比較します。
- 切替条件：v1 日、v2 日、バージョン跨ぎの日の 3 種類すべてが成功し、事故資料を元入力を変更せず再現できること。
