# 第 02 课：用 PIC 描述账户快照的字段类型与宽度

银行夜间批次拿到的第一样东西是一份账户快照，程序必须知道账户号有几位、金额有几位小数、日期是什么形状，才能和上游文件、下游接口按同一份格式说话。本课把一批账户字段（标识符、数量、金额、利率和业务编码）用 `PIC` 声明成程序内的数据项并打印出来，产出一份可逐字段对照上游文件的字段目录；第 03 课在这份宽度和精度上做金额运算，第 09 课再把这些平铺字段收进记录分组。

## 为什么现在学

第 01 课已经能编译、运行最小程序并观察退出码，但那个程序只会输出写死的字面量，还没有任何业务数据。一旦开始处理账户数据，就要先回答三个问题：账户号占几位、能不能丢前导零；金额的整数位和小数位各多少；日期、状态码用什么形状表示。COBOL 把这些约定写成 `PIC`，编译器会用它在编译期检查初值与宽度是否相容，维护者也能从代码直接读到这份接口契约。缺了这一步，后面的 `MOVE`、`COMPUTE`、条件判断和文件读取都不知道自己在处理多宽、多少位小数的数据。也不能沿用第 01 课把值写进 `DISPLAY` 字面量的做法：字面量声明不了字段宽度，也无法被后续语句引用。

## 本课完成后的能力与边界

学完本课后，你可以：

- 读懂 `PIC A(12)`、`PIC X(10)`、`PIC 9(7)V99`、`PIC S9(7)V99` 分别允许哪些字符、几位数字、是否带符号。
- 按业务含义决定字段用 `X` 还是 `9`，并说明账户号为什么必须用文本类型而不是数值类型。
- 说明 `VALUE` 给 `WORKING-STORAGE` 提供的是编译期初值，不是文件、数据库或命令行输入。
- 解释 `V` 的隐含小数点不占存储字符，却会在 GnuCOBOL 3.2.0 的 `DISPLAY` 输出中显示出来。
- 独立算出 `PIC 9(7)V99` 的 `125000.75` 为什么打印成 `0125000.75`，并说明 `SIGN LEADING SEPARATE` 让字段比同位数金额多占一个字符。

边界：本课只声明程序内常量并打印，不读文件、数据库或命令行参数，也不做运算和业务校验。日期数字、币种码、状态码的取值范围本课一律没有检查；`USAGE COMP`/`COMP-3` 的物理字节、记录分组（`01` 组项）也不在本课。赋值与算术见[第 03 课](../03_move-compute/README.md)，业务条件与拒绝规则见[第 04 课](../04_if-conditions/README.md)，记录分组见第 09 课，文件输入见第 15 课。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`）。
- 源文件为固定格式：第 7 列是指示符，Area A 从第 8 列、Area B 从第 12 列起，程序文本不越过第 72 列。
- 本机 GnuCOBOL 3.2.0 的固定格式右边界是第 72 个**字节**：第 73 字节起的内容被忽略（实测：收尾引号落在第 72 字节可通过，落在第 73 字节即被截断）。日文每字符 3 字节，所以含日文的行会比等宽 ASCII 行更早触到该边界。
- Linux 终端；本课不依赖数据库、附加工具或第三方库。
- 运行不产生业务数据文件，只在课内 `build/` 目录下生成一个可执行文件。

## 业务与知识点

### 场景：账户快照的字段契约

上游系统送来的账户快照（本课先用程序内常量模拟）包含账户号、客户信息、余额、利率和各类业务编码。要解读它，双方必须先对每个字段达成一致：类别（文本还是数字）、宽度、小数位置。COBOL 用数据描述项表达这份契约：名字 + `PIC` + 可选 `VALUE` 和 `USAGE`。编译器据此分配存储，并根据初值检查宽度是否相容；运行时按同一描述解释字节。

`PIC` 描述的是形状，不是业务有效性。`PIC 9(8)` 不能保证这八个数字是合法日期，`PIC X(12)` 也不能保证账户存在——本课已验证：把日期初值改成 `20261399`（13 月 99 日）后程序照常编译运行并打印该值。金额单位与精度同样必须先约定：本课所有金额按“七位整数 + 两位小数”的隐含尺度声明，利率按四位小数。

### 本课使用的 PIC 符号

- `A`：字母位置，只接受字母和空格。本例用它描述客户姓名、客户类别和国家码。
- `X`：字母数字位置，可承载字母、数字、标点和空格。本例把账户号、客户号、邮编、币种、参考号和批次号作为文本。
- `9`：数字位置。`9(4)` 等价于四个 `9`；用在本例的分行号、笔数、序号和日期数字字段。
- `9(n)` 中的 `(n)`：重复次数。`X(12)` 是十二个字符位置，`9(7)V99` 是七位整数加两位小数。
- `S`：声明数值字段带符号。本例配 `SIGN LEADING SEPARATE CHARACTER`，把正负号写成独立字符。
- `V`：声明小数点的隐含位置。它不占存储位置，输出格式由 `DISPLAY` 决定。
- `VALUE`：给数据项设定编译期初值。本课的值是演示样例，不是运行时输入。

### 与 Java / Python 的对照

`PIC X(n)` 接近定长字符串，`PIC 9(n)` 接近定长十进制整数，`PIC 9(n)V9(m)` 接近定点 `Decimal`。差别在于 COBOL 的 `PIC` 同时描述字符位置、小数尺度和存储布局，并且是编译期契约；Java 的 `String` 或 Python 的 `int` 不声明宽度。类比只能帮助理解用途，不能当成类型等价。

### 常见误区

- `PIC 9(8)` 只规定八位数字的形状，不代替日历校验；闰年、月份天数都要另写规则。
- `PIC X(10)` 和 `PIC 9(10)` 在本课的 `DISPLAY` 路径上外观相同（都打印 `0002046819`，已实测）。选 `X` 的理由是语义：账户号是逐字符保存的标识符，不参与算术，也不需要为进位预留数值宽度；而不是“数值字段会显示不出前导零”。
- `V` 不占存储字符位置，但 GnuCOBOL 3.2.0 的 `DISPLAY` 会把小数点打印出来；不能据此认为 `V` 是一个字节。
- `X(n)`、`A(n)` 的宽度是字符数，不直接等于字节数。只有默认 `DISPLAY` 用法下每个字符位置才占一个字节；换成 `COMP`/`COMP-3` 要另算，本课不涉及。
- `VALUE` 是程序自己的初值，不是数据库默认值，也不是运行时会收到的输入值。

## 输入与规则

**本课没有外部输入。** 所有数据都来自 [`lesson.cob`](./lesson.cob) 中各数据项的 `VALUE` 子句，是编译期确定的演示样例：没有标准输入、文件、命令行参数或数据库。因此同一可执行文件运行任意多次，输出必然相同。

已声明的前提与规则：

- 标识符（账户号、客户号、邮编、参考号、批次号、产品码）用 `X`/`A` 逐字符保存，前导零是数据本身的一部分。
- 数量与金额（分行号、笔数、序号、对账单日、余额、利率）用 `9`，按隐含小数位声明。
- 金额与利率的 `VALUE` 用十进制字面量书写，隐含小数点由 `V` 声明，不在初值里写额外的小数位。
- 未实施的政策：日期合法性、币种码与状态码的合法取值、金额非负性、字段间一致性，本课都没有检查，只作为后续课的业务规则输入。

## 完整示例源码

完整源码见 [`lesson.cob`](./lesson.cob)，按固定格式编写。程序只做三件事：声明字段、给初值、按顺序打印。下面从源码逐字摘出几行（非连续）说明结构，完整字段目录见下一节。

```cobol
       DATA DIVISION.
       WORKING-STORAGE SECTION.
      * 契约：账户号等数字标识符不是数量，
      * 用 X 保存以免丢前导零；金额才用 9。
       01 WS-ACCOUNT-KEY PIC X(12) VALUE "000123456789".
       01 WS-LEDGER-BALANCE PIC 9(7)V99 VALUE 125000.75.
       PROCEDURE DIVISION.
           DISPLAY "口座キー=" WS-ACCOUNT-KEY
           DISPLAY "帳簿残高=" WS-LEDGER-BALANCE
           STOP RUN.
```

摘录省略了其余二十多个字段和大部分 `DISPLAY`；运行输出是日文，逐行含义见“运行与观察”。

## 源码阅读路径

按数据和状态变化的顺序读，而不是逐行翻译：

1. **`IDENTIFICATION DIVISION` / `PROGRAM-ID`**：标识可执行程序单元，本程序名叫 `DATA02`。
2. **`DATA DIVISION` → `WORKING-STORAGE SECTION`**：声明常驻工作数据。本课的字段全部在这里定义，程序结束后释放，没有文件记录区。
3. **字段声明（`01` 级平铺）**：每个 `01 WS-...` 是一个独立的基本数据项。本课故意平铺而不分组，避免提前引入第 09 课的组项。
4. **`VALUE` 子句**：编译期写入初值。程序运行期间没有任何语句修改这些字段，所以输出等于初值——本课没有状态变化，状态变化从第 03 课的 `MOVE`/`COMPUTE` 开始。
5. **`PROCEDURE DIVISION` 的 `DISPLAY`**：按源码顺序逐字段打印，没有段落、条件或循环。
6. **`STOP RUN`**：正常结束 run unit，退出码 0。

### 边界观察：字段宽度和形状决定了什么（已实测）

下表各项都在本课主题（`PIC` 的形状与宽度，以及固定格式行宽）之内，用临时目录的独立小程序复现，不改动本课源码：

| 场景 | 命令与观察 | 结论 |
|---|---|---|
| 日期形状不等于有效性 | 把开户日初值改为 `20261399`，`cobc -fsyntax-only`、`-x` 均返回 0，运行打印 `20261399` | `PIC 9(8)` 只约束位数，日历合法性必须另写规则 |
| 初值超出声明宽度 | `PIC 9(4) VALUE 12345` 编译时（无论是否加 `-Wall`）得到 `warning: value size exceeds data size [-Wothers]`，运行打印 `2345`，退出码仍为 0 | 宽度是硬约束；超宽只是编译警告，高位会被丢弃，不会运行期报错 |
| 文本与数值的填充方向 | `X(8) VALUE "AB"` 打印 `AB` + 六个空格；`9(6) VALUE 521` 打印 `000521` | 文本左对齐空格填充，数值右对齐补零 |
| 含日文的行更早触到第 72 列 | 收尾引号落在第 72 字节的 `DISPLAY` 行编译通过；落在第 73 字节时报 `error: continuation character expected`，字面量被截断。纯 ASCII 行测得同一边界 | 固定格式的 72 列边界在本工具链上按字节计；日文每字符 3 字节，含日文的行必须比等宽 ASCII 行更早结束 |

## 实战位置

字段定义就是文件布局和下游接口契约的第一部分。银行对账批次后续要从定长文件和 CSV 中按这里的宽度与偏移解析记录（第 17、18 课），要用这里的金额尺度做余额运算（第 03 课），并在发现问题时按业务规则拒绝而不是让批次崩溃（第 04、26 课）。真实系统还需要数据库列类型映射、编码与区域设置一致性、跨平台字节序或字符集检查，本课不涉及，也不能据此声称已达到生产接口规范。

## 证据来源

以下都是在编写本课时于本机实际执行的命令与观察结果；未执行的场景一律标注为未验证：

- 本课源码：`cobc -fsyntax-only lesson.cob`（RC 0）、`cobc -x -Wall -o build/lesson_02 lesson.cob`（RC 0）、`./build/lesson_02`（RC 0，stdout 29 行，与本 README 所列一致，stderr 仅 libxml 环境警告）。
- 修改练习：在临时目录复制 `lesson.cob`，只替换三处 `VALUE` 后编译运行，`diff` 显示恰好三行变化（`支店コード`、`通貨コード`、`顧客番号`），与 `answer.md` 一致。
- 边界观察：`PIC 9(8)` 初值 `20261399`、`PIC 9(4)` 初值 `12345`、`X(8)` 初值 `"AB"`、`9(6)` 初值 `521` 四个临时程序，输出与警告如上表；另用占位字面量把收尾引号分别放在第 72、第 73 字节（纯 ASCII 与含日文各一组），确认右边界就是第 72 字节。
- 字节数参考：临时程序用 `FUNCTION LENGTH(...)` 测得 `X(12)`=12、`9(7)V99`=9、`S9(7)V99 SIGN LEADING SEPARATE`=10、`9(2)V9(4)`=6 字节（默认 `DISPLAY` 用法）。该内建函数不是本课教学内容，只用于核对本 README 的字节说明。
- 行宽事实：改写前的源码里有一条日文注释达到 92 字节，编译器的诊断回显在 72 字节处截断并转义半个字符——这也说明超过字节边界的注释内容不会被编译器完整读到。本课改写后的注释每行都在 72 字节以内。
- 未验证：`COMP`/`COMP-3` 等其他 `USAGE` 的物理布局、其他平台与编译选项下的输出格式、编码差异；本课不涉及。
