# 第 16 課変更演習：参考解答

この解答は [`exercise.md`](./exercise.md) の2つの変更演習だけを扱い、「学んだことを応用する」の解答はありません。以下の出力、バイト数、戻りコードは、すべてこのワークスペースで GnuCOBOL 3.2.0 を使って実際に確認しました。実行ディレクトリーは課の `build/` です。

## 1. 4件目を受理結果にする

### 変更内容

元の `lesson.cob` から始め、`1000-LOAD-RESULTS` の次の2行だけを変更します。

```cobol
           MOVE "A" TO WS-RESULT-DESTINATION(4)
           MOVE "TXN-000004|0009999999|T|000020.00|A"
               TO WS-RESULT-TEXT(4)
```

`PIC`、`FD` レコード幅、`OCCURS 4 TIMES` の上限、ループ上限、他の3レコード、すべての `DISPLAY` テキストは変更しません。

コマンド：

```sh
mkdir -p build
cp lesson.cob build/
cobc -fsyntax-only build/lesson.cob
cobc -x -Wall -o build/lesson_16 build/lesson.cob
(cd build && ./lesson_16)
echo $?
wc -lc build/accepted.txt build/rejected.txt
```

構文検査、コンパイル、プログラムの終了コードはいずれも `0` で、コンパイル時の診断はありません。

### 変更後の出力全体

```text
オープン=受理 成功
オープン=拒否 成功
書込=受理 取引=000001
書込=受理 取引=000002
書込=拒否 取引=000003
書込=受理 取引=000004
クローズ=受理 成功
クローズ=拒否 成功
SUMMARY 受理=03 拒否=01
```

元の初期状態から変わるのは2行だけです。

| 行 | 元の値 | 変更後 | 理由 |
|---|---|---|---|
| 6 | `書込=拒否 取引=000004` | `書込=受理 取引=000004` | 振り分け先マーカーを `A` にしたため、`EVALUATE` が受理ファイルの分岐を選びます。 |
| 9 | `SUMMARY 受理=02 拒否=02` | `SUMMARY 受理=03 拒否=01` | 受理ファイルへの書き込みが1件増え、拒否ファイルへの書き込みが1件減ります。 |

残り7行はバイト単位で変わりません。

### 変更後の出力ファイル

`accepted.txt`（3行、108バイト）

```text
TXN-000001|0001234567|D|000125.50|A
TXN-000002|0007654321|T|000040.00|A
TXN-000004|0009999999|T|000020.00|A
```

`rejected.txt`（1行、36バイト）

```text
TXN-000003|0002468101|X|000000.00|R
```

独立検算：各行は35文字で末尾は空白ではないため、1行は `35 + 1 = 36` バイトです。よって `3 × 36 = 108`、`1 × 36 = 36` です。2ファイルの合計は4行でテーブルの4項目に一致し、`03 + 01 = 04` です。

### 各質問への回答

**1. なぜ振り分け先マーカーと一緒にレコードテキストも変更する必要がありますか。**

2つは独立したフィールドです。`WS-RESULT-DESTINATION(4)` は `EVALUATE` が出力先ファイルを選ぶためだけに使い、`WS-RESULT-TEXT(4)` はファイルに書き込む35文字を保持します。プログラム内にこの2つの値を比較する文はありません。

振り分け先だけ変更し、レコードテキスト末尾を `R` のままにした場合の実測結果：`accepted.txt` は3行、108バイトとなり、3行目は次のとおりです。

```text
TXN-000004|0009999999|T|000020.00|R
```

つまり、**受理ファイルに拒否と記されたレコードが入ります**。プログラムはエラーを報告しません。`cobc` は `0` を返し、プログラムの終了コードも `0` です。`SUMMARY 受理=03 拒否=01` も両方の値を変更した場合と同じです。レコード末尾のマーカーと出力先ファイルの一致をプログラムは検査しません。サンプルデータを用意する人が整合性を保つ責任を負います。

**2. 変更後の `accepted.txt` の3行の順番は何で決まりますか。**

次の `PERFORM VARYING WS-RESULT-NUMBER FROM 1 BY 1 UNTIL WS-RESULT-NUMBER > 4` の処理順、すなわち結果テーブルのロード順（1件目、2件目、4件目）で決まります。ファイルは順次書き込まれるため、先に書いた行が先頭になります。ファイルシステムは内容を並べ替えず、`EVALUATE` は書き込み先を選ぶだけで順序を変えません。

**3. 4件目の振り分け先を `X`（`A` でも `R` でもない値）にするとどうなりますか。**

`WS-RESULT-DESTINATION(4)` を `"X"` にし、他は変更しない場合の実測値：

```text
オープン=受理 成功
オープン=拒否 成功
書込=受理 取引=000001
書込=受理 取引=000002
書込=拒否 取引=000003
書込=FAILED REASON=UNKNOWN_DESTINATION
クローズ=受理 成功
クローズ=拒否 成功
SUMMARY 受理=02 拒否=01
```

| 確認項目 | 実測値 |
|---|---|
| 分岐 | `WHEN OTHER` に進み、`書込=FAILED REASON=UNKNOWN_DESTINATION` を表示 |
| `accepted.txt` | 2行、72バイト（1、2件目のみ） |
| `rejected.txt` | 1行、36バイト（3件目のみ） |
| `SUMMARY` | `受理=02 拒否=01` |
| 終了コード | `1` |

4件目はどちらのファイルにも入らないため、**2つの件数の合計はテーブルの4件より少ない3件**です。件数の不変条件が崩れますが、これは本課で検出したい信号です。`WHEN OTHER` はエラーフラグを立てるだけで、書き込みも件数加算もしません。最後に `IF WS-WRITE-ERROR = "Y"` が終了コードを1にして、1件欠けたまま成功扱いになることを防ぎます。4件目は最後なので、`UNTIL ... OR WS-WRITE-ERROR = "Y"` による早期終了に追加の影響はありません。最初の項目でエラーが起きれば、残り3件は書き込まれません（本課では部分出力をロールバックしません）。

## 2. 上書き動作と再実行を確認

### 操作と観察結果

変更していない元の `lesson.cob` を使用し、実行前に両ファイルへ `OLD` の1行を入れます。

```sh
mkdir -p build
cp lesson.cob build/
cobc -x -Wall -o build/lesson_16 build/lesson.cob
printf 'OLD\n' > build/accepted.txt
printf 'OLD\n' > build/rejected.txt
wc -c build/accepted.txt build/rejected.txt   # 各4バイト
(cd build && ./lesson_16)
echo $?                                         # 0
wc -lc build/accepted.txt build/rejected.txt    # 各2行、72バイト
cat build/accepted.txt build/rejected.txt
```

| 確認項目 | 実行前 | 実行後 |
|---|---|---|
| `accepted.txt` | 4バイト、内容 `OLD` | 72バイト、サンプルの受理レコード2件だけ |
| `rejected.txt` | 4バイト、内容 `OLD` | 72バイト、サンプルの拒否レコード2件だけ |
| 標準出力 | — | 通常経路とバイト単位で同じ9行 |
| 終了コード | — | `0` |

連続して2回実行した場合：標準出力はどちらもバイト単位で同一で、各ファイルは144バイトに増えず72バイトのままです。

### 各質問への回答

**1. `OLD` が消える理由と原因の文は何ですか。**

`OPEN OUTPUT 受理-FILE` と `OPEN OUTPUT 拒否-FILE` は、ファイルを新規作成するか、空の状態で作り直します。既存ファイルは書き込み開始前に長さ0へ切り詰められます。「削除してから作成」ではなく（パスは同じファイルを指したままです）、事前に存在確認する必要もありません。

**2. 2回で144バイトになると予想した場合、実際のサイズはいくつですか。**

各ファイルは72バイトのままです。実行のたびに `OPEN OUTPUT` が内容を切り詰めて再作成するため、2回目は追加ではなく同じ4件のサンプルレコードで上書きします。この再実行結果が安定するのは、毎回同じ件数を書き込む間だけです。上書き動作と固定テーブル上限による結果であり、冪等性検査によるものではありません。将来3件だけを書き込むことになっても、古い4件目が自動的に消えるわけではありません。本課では途中までの出力を掃除しません。

**3. 実行前に `accepted.txt` がディレクトリーの場合はどうなりますか。**

`mkdir accepted.txt` を実行した場合の実測出力：

```text
オープン=受理 失敗 状態=37
```

終了コードは `1` で、`rejected.txt` は作成されません。最初の `IF WS-受理-STATUS NOT = "00"` 分岐で `MOVE 1 TO RETURN-CODE` と `STOP RUN` を実行して停止するため、レコードは書き込まれません。状態コード `37` は GnuCOBOL の状態コード表で権限拒否の分類です。この環境では、対象がディレクトリーの場合、読み取り専用ファイル（`0444`）の場合、書き込み不可のディレクトリーの場合に同じ `37` を確認しました。これはオープン失敗を検出して終了コード1を返すことを示すものです。本番環境であらゆるディスク書き込み障害がすぐ検出されることを示すものではありません（README の「根拠と検証範囲」を参照）。
