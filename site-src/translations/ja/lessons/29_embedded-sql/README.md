# 第 29 課：Embedded SQL――COBOLプログラムからデータベースへ接続して口座を検索する

第1課から第28課までは、データはファイルにあり、`OPEN` → `READ` → `CLOSE` で取得できました。しかし口座残高はファイルではなくデータベースにあります。本課では、COBOLプログラム自身がデータベース（ここではローカルのSQLiteファイルデータベース）へ接続し、口座番号をキーに1行を検索して、顧客番号と残高を取得します。そして「見つかった」「見つからなかった」「SQLエラー」をそれぞれ別の結果として扱います。第30課では、この流れを発展させて、1行取得をカーソルによる全件走査に置き換えます。

## 業務の現場

午前1時10分、日次締めバッチが最後の工程である抜き取り確認に入ります。日中、カスタマーサポートから問い合わせがありました。口座 `A000000001` の昨夜の残高はいくらだったのでしょうか。

手元にあるのは取引明細ファイルだけです。そこには「誰が、何時に、いくら動かしたか」は載っていますが、「いま口座にいくら残っているか」は載っていません。残高は基幹システムから出力された口座スナップショットデータベースにあります（本課では実際のSQLエンジンとファイルを使う小さなSQLiteデータベースで示します。`DISPLAY` で検索を装う例ではありません）。

このコードは、これまで書いてきたものとは異なります。`OPEN ... READ` ではなく、**データベースに接続し、検索を発行して結果を受け取ります**。操作自体は小さく、1行を取得するだけですが、データベースから返る結果は3通りあります。

- **1行見つかった**（ちょうど1行）。
- **見つからなかった**（0行）。
- **SQLが正常に実行されず**、データベースがエラーを返した。

最初の2つは**業務上の結果**で、3つ目は**障害**です。似て聞こえますが、処理方法はまったく異なります。

3つを2つにまとめてしまうと、この種のプログラムで典型的な2つの事故が起きます。一つ目は「見つからない」（`SQLCODE = 100`）をエラー扱いすることです。プログラムがエラー終了し、深夜に当番が呼び出されます。調べてみると、口座がもともと存在しなかっただけで、一晩中無駄に対応したことになります。もう一つはさらに深刻です。データベースに接続できない、テーブル名が間違っている、列が存在しない、といった状況でも「口座が見つかりません」と表示し、データベース障害を「今日はこの口座がない」という結果に見せかけてしまいます。残高不一致が長い間発見されないおそれがあります。

本課で学ぶのは3点です。環境変数から接続情報を取得し、主キー検索で1行を取得し、3種類の `SQLCODE` をそれぞれ別の経路で処理します。

## なぜ今学ぶのか

第15～22課ではファイルを読み込み、内容を照合できるようになりました。第23～28課では、ビルドして再利用できるモジュール構成に分けました。しかし、データソースは一貫してテキストファイルでした。問題はファイルを読みづらいことではなく、**口座の現在の状態がファイルにない**ことです。

ファイルは「何が起きたか」を記録し、データベースは「現在どうなっているか」を保持します。残高、口座状態、顧客番号を調べるには、データベースに問い合わせる必要があります。そこで、これまで直面しなかった疑問が出てきます。

- 接続文字列はどこから取得するのか。ソースに固定するのか、デプロイ環境に任せるのか。
- `EXEC SQL` を変換するのは誰か。`cobc` はこれを理解できるのか。
- データベースの列をどうやってCOBOLフィールドに入れるのか。
- 「行が見つからない」と「SQLが失敗した」は同じ結果なのか。

最初の3つは本課でまとめて説明し、4つ目を重点的に扱います。まず最も単純な経路、単一行の `SELECT ... INTO` を動かします。なぜ1行だけなのかというと、「主キーで口座を1件検索する」は最も一般的な処理だからです。第30課でスナップショット全体を走査するときは `SELECT ... INTO` では足りないため、カーソルに切り替えます。

## この概念と、解決する問題

**これは何か。** 一言でいえば、COBOLプログラムから直接SQLを実行する方法です。COBOLソースに `EXEC SQL ... END-EXEC` と書き、その中に通常のSQL文（本課では `SELECT ... INTO`）を置きます。コロンで始まるCOBOLフィールドは**ホスト変数**です。データベースから返る値を受け取り、検索条件の値をデータベースへ渡します。

**なぜ必要なのか。** 口座の現状を知っているのはデータベースだけです。バッチプログラムから直接接続するか、毎日手作業で残高ファイルを出力するかのどちらかです。手作業は、いつか実行し忘れたり途中で失敗したりしますし、どの時点のデータなのかも分からなくなります。もう一つ注意点があります。GnuCOBOLコンパイラーは `EXEC SQL` を**理解しません**。この4語はコンパイラーにとってCOBOLではありません。まずプリコンパイラーが `EXEC SQL` を通常のCOBOLへ変換し、その後コンパイラーが処理します。SQLの書き方が間違っていると思い込んで、ここで午後を費やす人を見たことがあります。

**実務での利用例。** 照合、残高照会、リスクの抜き取り確認、下流システムへの状態出力など、プログラムがデータベースの現在状態を「ちょっと確認」する場面で使います。

**誤用するとどうなるか。** 前述の事故のとおり、3種類の結果を2種類にまとめることになります。`100` を障害扱いすれば、通常の業務ケースで毎日アラームが鳴ります。障害を `100` として扱えば、本当のデータベース問題が黙って見過ごされます。この違いはコンパイラーでは検出できません。深夜の電話で初めて気づくことになります。

**使わないほうがよい場合。** 次の2つのケースでは、すぐにデータベースへ接続しないでください。1つ目は、データがすでにファイルにある場合（取引明細や上流システムからの出力など）です。「新しい方法だから」という理由で接続を加えると、バッチに接続処理と障害点を一つ増やすだけです。2つ目は、テーブル全体を順番に走査する場合です。`SELECT ... INTO` は一度に1行しか処理できず、複数行を順次取得できません。その用途には第30課のカーソルを使います。

## 本課の到達点と範囲

本課を終えると、次のことができるようになります。

- GnuCOBOLコンパイラーと、`EXEC SQL` を変換する**プリコンパイラー**が別のツールであると説明する。
- 環境変数からSQLite接続文字列を読み、`CONNECT` を実行し、`CONNECT RESET` で切断する。
- COBOLフィールドをSQLホスト変数（`:フィールド名`）として使い、主キー検索を `SELECT ... INTO` で実行する。
- `SQLCODE` によって1行取得（`0`）、該当行なし（`100`）、SQLエラー（その他）を区別し、エラー時には0以外の終了コードを返す。
- [`expected-output.txt`](./expected-output.txt) と標準出力4行を照合し、接続情報をソースに書かない理由を説明する。

範囲：本課では主キーによる単一行検索だけを扱い、ループ、データベースへの書き込み、トランザクションは扱いません。カーソルは第30課、ファイルとデータベースの同期比較は第31課で扱います。サンプルデータベースはローカルSQLiteファイルで、実際のSQLエンジンとファイルを使いますが、Oracle/PostgreSQL/DB2の動作を**代表するものではありません**。ツールチェーンは、このワークスペースのx86-64 Linux + GixSQL v1.0.20b環境でのみ検証しています。

## ツールチェーン：なぜプリコンパイラーが必要なのか

`cobc` は `EXEC SQL` を解析できないため、第29～32課のデータ処理経路は次のようになります。

```text
lesson.cob --(gixpp -e)--> 预处理 COBOL --(cobc -fstatic-call -lgixsql)--> 可执行文件
                                              ↑
                                    运行期由 LD_LIBRARY_PATH 找到 libgixsql 与 SQLite 驱动
```

3段階は順番に動きます。`gixpp` が `EXEC SQL` を含むソースを通常のCOBOLへ変換し（出力名は `lesson_29.cbsql`）、次に `cobc` が変換結果をコンパイルして実行ファイルをリンクします。実行時には `LD_LIBRARY_PATH` が `libgixsql` とSQLiteドライバーを見つけます。どれか一つでも欠けるとプログラムは動きません。

3つのサブコマンドの役割を混同しないでください。`build.sh check` はプリコンパイルと `cobc -fsyntax-only` までを行い（実行ファイルは作りません）、`build.sh build` は実行ファイルをリンクし、`build.sh run` はデータベースを再作成してから実行します。

**ツールチェーンがない場合、SQLを模擬出力で置き換えないでください。** `DISPLAY` で出した偽の結果を「データベースを検索した」と扱うのは、「未検証」を「実装済み」と書くのと同じです。

## SQLとCOBOLのインターフェース

### 1. 接続情報はソースではなく環境から取得する

`WS-DATASRC`、`WS-DBUSER`、`WS-DBPASS` は通常のCOBOLフィールドです。プログラムは `DISPLAY ... UPON ENVIRONMENT-NAME` で読み込む環境変数名を指定し、`ACCEPT ... FROM ENVIRONMENT-VALUE` で値を取得してから `CONNECT` を実行します。そのため、ソースやテスト用データには、マシン固有のパスやパスワードを**保存しません**。`build.sh run` は `DATASRC=sqlite://<absolute-path>` のような環境変数で値を渡します。本番環境でも環境変数やシークレット管理から提供してください。マシン、DB、パスワードを変えるたびにプログラムを修正する必要はありません。

### 2. ホスト変数と単一行検索

SQL内でコロンから始まるフィールドはホスト変数（例：`:WS-LOOKUP-ACCOUNT`）です。GixSQLがSQLiteのパラメーターに変換します。

```cobol
           EXEC SQL
               SELECT ACCOUNT_NO, CUSTOMER_ID, BALANCE
                 INTO :WS-ACCOUNT, :WS-CUSTOMER, :WS-BALANCE
                 FROM ACCOUNT_SNAPSHOT
                WHERE ACCOUNT_NO = :WS-LOOKUP-ACCOUNT
           END-EXEC
```

`INTO` の後にある3項目は受け取り先です。データベースの3列が、位置に対応する3つのCOBOLフィールドに書き込まれます。

幅を一致させる必要があります。口座番号はテーブルとCOBOLの両方で10文字、顧客番号は両方で8文字です。固定長 `PIC X` はフィールド幅を保持します。ホスト変数の幅をデータベース列および実際の値の規約に合わせないと、文字列に末尾空白が付いたり、切り捨てられたりします。残高はCOBOL側の `PIC 9(7)V99` で受け取ります（ソースでは `PIC S9(7)V99 COMP-3`、整数7桁、小数2桁）。表示前に `PIC 9(5).99` の表示用フィールドへ移すため、`1250.75` は `01250.75` と表示されます。整数部を5桁までゼロ埋めし、小数部は2桁のままです。

見落としやすい点がもう一つあります。検索前に受け取りフィールドをクリアします（`MOVE SPACES` / `MOVE ZERO`）。クリアしないと、今回「見つからない」経路を通った場合に前回の値が残り、別の口座の残高を表示してしまうことがあります。

### 3. `SQLCODE`：3種類の結果を分ける

| `SQLCODE` | 意味 | 本課での処理 | 終了コードへの影響 |
|---:|---|---|---|
| `0` | 検索成功、1行を返した | `状態=FOUND` と顧客番号・残高を表示 | なし |
| `100` | 該当行なし | `状態=NOT_FOUND` を表示（**エラーではない**） | なし |
| その他 | SQLエラー | `状態=エラー SQLSTATE=` を表示し、失敗フラグを設定 | `1` |

`SQLCODE = 100` は通常の業務結果です。これを障害扱いすると、「口座が見つからない」という日常的なケースでバッチが停止します。逆にSQLエラーを「見つからない」と扱うと、実際のデータベース問題を隠してしまいます。そこでコードでは `EVALUATE SQLCODE` で3種類を分け、`0` と `100` 以外の値だけを `WHEN OTHER` に進めます。

反例と正例を並べると違いが分かります（どちらも説明用コードです。反例の出力文字列は本課の実際の出力ではありません）。

```cobol
      * 反例：把"没查到"和"SQL 出错"压成同一个失败分支
      *       正常业务结果被当成故障，真故障也失去了轻重
           IF SQLCODE NOT = 0
               DISPLAY "查询失败"
               MOVE "Y" TO WS-FAILED
           END-IF

      * 正例：三种结果各走各的路（lesson.cob 就是这么写的）
           EVALUATE SQLCODE
             WHEN 0     ...查到一行，取客户号与余额
             WHEN 100   ...没匹配行，正常业务结果
             WHEN OTHER ...SQL 错误，置失败标志、退出码 1
           END-EVALUATE
```

上の正例では `WHEN 0` と `WHEN 100` のどちらも失敗ではありません。そのため本課の2回の検索（該当1回、未検出1回）は終了コード `0` で終わります。`1` を返すのは `WHEN OTHER` に進んだ場合だけです。

### 4. 後片付け

接続に成功した後、`9000-DISCONNECT-DATABASE` は `CONNECT RESET` を実行して `SQLCODE` を確認します。ここで失敗した場合も失敗フラグが設定され、メイン処理は状態 `1` で終了するため、シェルジョブが検出できます。

## 実際の処理の流れ

夜間処理の中で本課がどこに入るかを見てみましょう。

1. 日中の窓口やモバイルバンキングで発生した取引がファイルに出力され、共有ディレクトリーに置かれます。ファイル読込は第15～22課で扱いました。
2. 夜間バッチがまずファイル側を処理し、結果をまとめます。
3. 口座の現状を確認するとき、**本課のコード**がDBへ接続し、口座番号で1行を取得して顧客番号と残高を読みます。これは「1行検索」です。口座スナップショット全体を順番に読む場合は、第30課のカーソルを使います。
4. ファイル側とDB側の両方が揃ったら、口座ごとに照合し、`MATCH` / `CHANGED` / `FILE_ONLY` に分類して差異ファイルを作成します。これは第31課です。
5. 第32課の総合プロジェクトでは、一連の処理を完全なバッチとしてつなぎ、件数チェックとSQLの部分失敗後のリカバリー説明を加えます。

本課は「口座を1件取得する」だけに見えますが、後続3課の土台です。実際にDBへ接続し、3種類の `SQLCODE` を区別できなければ、後続の照合や再実行は成り立ちません。

## このコードを本番で使うとしたら

- **誰が起動するか：** 夜間バッチスケジューラーやシェルジョブです。画面ではなく終了コードを確認します。
- **誰が出力を見るか：** 当番やトラブル対応担当者が、終了コードの後に日本語ラベルを確認します。`FOUND` なら続行、`NOT_FOUND` は慌てる必要なし、`エラー` があれば調査が必要です。
- **次のシステムがどう使うか：** 本課は値を表示するだけです。次にその値を判定処理（第30・31課）に使い、最終的には照合結果テーブルや差異ファイル（第32課）へつなげます。
- **最初の1か月で起きやすい事故：** `100` と「SQLエラー」を1つの分岐にまとめてしまうことです。`EVALUATE` を数行省いた代わりに、レポート上で「見つからない」と本当のDB障害を区別できなくなります。前者は毎日起こり、後者は起きれば重大です。
- **まだできないこと：** 1行検索だけで、DBへの書込みやトランザクション管理はしません。SQL失敗後に書込み済みの行が残るか、安全な再実行をどう行うかは本課では扱わず、第31・32課で扱います。本課をもって「本番利用可能」とは**言えません**。

**未検証項目（理由）：**

- DB間の方言差は未検証です。このワークスペースではx86-64 Linux + GixSQL v1.0.20b + SQLiteファイルDBのみ実測しています。Oracle/PostgreSQL/DB2での動作について本課は結論を出しません。
- 3つのSQLエラー分岐（`接続=エラー`、`検索=エラー`、`切断=エラー`）には実測記録がありません。接続不能なデータソースや壊れたスキーマなど、再現可能な障害注入方法がないため、コードと上記の `SQLCODE` 表に基づく説明にとどまり、実行済みとはしていません。
- 標準エラーの `libxml 212 / older 209` 警告は、実行環境のリンクライブラリーのバージョン差に由来します。発生元は特定されていません。プログラムの標準出力ではないため、業務結果の確認には含めないでください。
