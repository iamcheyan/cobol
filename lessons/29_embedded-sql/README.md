# 第 29 课：Embedded SQL——让 COBOL 程序自己连上数据库取账户

前面 28 课，你要的数据都在文件里，`OPEN`→`READ`→`CLOSE` 就能拿到。可账户余额不住在文件里，它在数据库里。本课让 COBOL 程序自己连上数据库（本课是本机 SQLite 文件库），按账号取回一行账户的客户号与余额，并把"查到了""查不到""SQL 出错"这三件完全不同的事分开处理。第 30 课会顺着这条链路，把"取一行"换成游标扫全表。

## 业务现场

夜里 1:10，日终对账批次跑到最后一段：抽查。白天客服留了一张工单——`A000000001` 这个账户昨晚余额到底是多少？

你手边只有交易流水文件，那上面写的是"谁在几点动了多少钱"，没有"现在账上还剩多少"。余额在核心系统导出的账户快照库里（本课用小型的 SQLite 文件来演：真实引擎、真实文件，不是拿 `DISPLAY` 假装查库）。

所以这段代码和你前面写的都不一样：不是 `OPEN ... READ`，而是**连库、发一条查询、把结果接回来**。动作看着很小，就取一行。但数据库给你的回答其实有三种可能：

- **查到了**，正好一行；
- **没查到**，零行；
- **SQL 根本没执行成功**，数据库报错。

前两种是**业务结果**，第三种是**故障**。麻烦就在这三种听着差不多，处理方式却完全相反。

把三种混成两种，就是这类程序最经典的两起事故。一起是把"没查到"（`SQLCODE = 100`）当错误：程序报错退出、返回非零码，值班的人凌晨被叫起来，跑过去一看——这个账户本来就不存在，白折腾一晚上。另一起更吓人：库连不上、表名写错、列不存在，程序却照样打印一句"没找到这个账户"，把数据库故障糊成"今天确实没这个账户"。余额对不上，很长时间都不会有人发现。

这一课就三件事：连接信息从环境变量拿进来、用一个主键查询取回一行、再把三种 `SQLCODE` 各走各的路。

## 为什么现在学

第 15–22 课你已经能把文件读进来做匹配，第 23–28 课又把它拆成能构建、能复用的模块工程——但数据源一直是文本文件。文件的问题不是读不动，而是：**账户的当前状态根本不在里面。**

文件是一串"发生过什么"，数据库才存"现在是什么"。查余额、查账户状态、查客户号，都得去问数据库。于是一堆前面从没遇到过的问题冒出来了：

- 连接串从哪儿来？写死在源码里，还是交给部署环境？
- `EXEC SQL` 这段东西谁来翻译，`cobc` 认识它吗？
- 数据库的一列，怎么落进一个 COBOL 字段里？
- "查不到行"和"SQL 失败"是两回事还是一回事？

前三个问题本课一次讲通，第四个是本课的重点。本课先把最简单的一条链路跑顺：单行 `SELECT ... INTO`。为什么只取一行？因为"按主键查一个账户"本身就是最常见的动作；等第 30 课要扫整张快照表，`SELECT ... INTO` 就力不从心了，那时换成游标。

## 这个知识点是什么，它解决什么问题

**它是什么。** 一句话：让 COBOL 程序直接说 SQL。你在 COBOL 源码里写 `EXEC SQL ... END-EXEC`，中间夹一条普通 SQL 语句（本课是 `SELECT ... INTO`）；冒号开头的 COBOL 字段是**宿主变量**——数据库查出来的值从这儿进来，查询条件的值也从这儿出去。

**为什么非用它不可。** 因为账户的现状只有数据库知道。你要么让批处理程序自己连库，要么每天手工导一份余额文件——手工那一步迟早忘了跑，或者导到一半失败，而且没人说得清它是哪个时点的。还有个坑要先说：GnuCOBOL 编译器**根本不认识** `EXEC SQL`，这四个字在它眼里不是 COBOL。所以链路里多了一个角色——预编译器，它先把 `EXEC SQL` 翻译成普通 COBOL，编译器才接手。我见过有人在这上面耗了一下午，一直以为是自己 SQL 写错了。

**真实业务里谁在用它。** 对账、余额查询、风控抽查、给下游导状态——只要程序要"顺手看一眼数据库里的现状"，走的就是这条路。

**用错了会怎样。** 就是前面那起事故：三种结果被压成两种。把 `100` 当故障，正常业务天天报警；把故障当 `100`，真正的数据库问题被静默吞掉。这个区别不是编译错误，编译器不会提醒你——它只会在半夜的电话里提醒你。

**什么时候不该用它。** 两种情况下别急着连库。一是数据本来就在文件里（流水明细、上游导出），为了"先进"去连库，只是给批次多塞了一个连接和一处可能失败的点。二是要按顺序扫整张表——`SELECT ... INTO` 一次只处理一行，多行没法逐个取出来，那种场景第 30 课用游标。

## 本课完成后的能力与边界

学完本课后，你可以：

- 说清 GnuCOBOL 编译器与负责转换 `EXEC SQL` 的**预编译器**是两件事。
- 从环境变量读取 SQLite 连接串并 `CONNECT`，成功后用 `CONNECT RESET` 断开。
- 用 COBOL 字段做 SQL 宿主变量（`:字段名`），执行 `SELECT ... INTO` 主键查询。
- 用 `SQLCODE` 区分查到一行（`0`）、没有匹配行（`100`）和 SQL 错误（其他值），并让错误以非零退出码结束。
- 用 [`expected-output.txt`](./expected-output.txt) 核对四条标准输出，并说明为什么连接信息不写在源码里。

边界：本课只做单行主键查询，不循环、不写库、不做事务；游标在第 30 课，文件与数据库的对比同步在第 31 课。示例数据库是本机 SQLite 文件（真实 SQL 引擎、真实文件），**不代表** Oracle/PostgreSQL/DB2 的行为。工具链只在本工作区的 x86-64 Linux + GixSQL v1.0.20b 上验证过。

## 运行环境

- GnuCOBOL 3.2.x（`cobc`）+ `sqlite3` 命令行程序。
- **预编译器与运行库**：[GixSQL](https://github.com/mridoni/gixsql) `v1.0.20b`（Ubuntu 22.04 包）及其 `libfmt8` 运行时。`./install-toolchain.sh` 从官方 Release 与 Ubuntu 镜像下载两个 `.deb`、校验固定 SHA-256 后解包到 `build/toolchain/`，**不改动系统软件包**；仓库不提交这些二进制。
- 还需 `curl`、`dpkg-deb`、`sha256sum`（安装脚本会用）。
- 非 x86-64 Linux 或想用别的 GixSQL 版本时，自行安装兼容版本并把 `GIXSQL_ROOT` 指向其 `usr` 目录。
- 构建目录是课内 `build/`（`BUILD_DIR` 可覆盖），已被仓库忽略。

## 工具链：为什么还要多装一个预编译器

![Embedded SQL precompile, compile, link, and runtime pipeline](assets/embedded-sql-pipeline.svg)

`cobc` 不解析 `EXEC SQL`，所以第 29–32 课的数据链路长这样：

```text
lesson.cob --(gixpp -e)--> 预处理 COBOL --(cobc -fstatic-call -lgixsql)--> 可执行文件
                                              ↑
                                    运行期由 LD_LIBRARY_PATH 找到 libgixsql 与 SQLite 驱动
```

按顺序理解这三步：`gixpp` 把带 `EXEC SQL` 的源码翻译成纯 COBOL（产物叫 `lesson_29.cbsql`），`cobc` 再把翻译结果编译链接成可执行文件，运行时靠 `LD_LIBRARY_PATH` 找到 `libgixsql` 和 SQLite 驱动。三者缺一个，程序都跑不起来。

三个子命令的分工别搞混：`build.sh check` 只跑到预编译 + `cobc -fsyntax-only`（不产出可执行文件）；`build.sh build` 才链接出可执行文件；`build.sh run` 会先重建数据库再运行。

**没有工具链时不要用模拟 SQL 顶替**——把 `DISPLAY` 出来的假结果当成"查过库了"，等于把"没有验证过"写成"已经实现"。

## 构建和运行

```sh
./install-toolchain.sh    # 只需一次：下载并解包 GixSQL（写入 build/toolchain/）
./build.sh check          # 预编译 + 语法检查
./build.sh build          # 预编译 + 编译 + 链接
./build.sh run            # 重建 build/accounts.db 并运行
echo $?                   # 查看退出码
./build.sh clean          # 删除 build/（含工具链、预编译文件与数据库）与预编译器日志 gixsql.log
```

没错，`clean` 连工具链一起删。第 30–32 课默认复用这里的 `build/toolchain/usr`，所以清理后想继续后面几课，得先重新跑一次 `./install-toolchain.sh`。

`run` 用 [`schema.sql`](./schema.sql) 新建 `build/accounts.db`，所以每次运行都从干净数据开始：表 `ACCOUNT_SNAPSHOT` 有 2 行，`A000000001` 余额 `1250.75`、`A000000002` 余额 `875.00`。

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `./build.sh check` 退出码 | `0` |
| `./build.sh build` 退出码 | `0` |
| `./build.sh run` 退出码 | `0` |
| 标准输出 | 4 行，与 [`expected-output.txt`](./expected-output.txt) 逐行一致 |
| 生成物 | `build/accounts.db`、`build/lesson_29.cbsql`、`build/lesson_29`，以及工具链日志 `gixsql.log`（GixSQL 预编译器写在源文件旁、运行库追加到进程工作目录；已被 `.gitignore` 覆盖） |

```text
接続=成功
検索=A000000001 状態=FOUND 顧客=C0001001 BALANCE=01250.75
検索=A99999999X 状態=NOT_FOUND
切断=成功
```

**输出对照（实际标签 → 含义）：** `接続=成功` = 连接成功；`検索=` = 查询键；`状態=FOUND` / `状態=NOT_FOUND` = 查到 / 未查到（`NOT_FOUND` 来自 SQLCODE `100`）；`顧客` = 客户号；`BALANCE` = 余额；`切断=成功` = 断开成功。

**实际观察到的环境细节：** 在本工作区运行可执行文件时，标准错误会输出 `Warning: program compiled against libxml 212 using older 209`。这是运行环境的链接库版本警告，不是本程序的标准输出；其触发组件尚未定位。

## SQL 与 COBOL 的接口

### 1. 连接信息来自环境，不写进源码

`WS-DATASRC`、`WS-DBUSER`、`WS-DBPASS` 是三个普通 COBOL 字段。程序先用 `DISPLAY ... UPON ENVIRONMENT-NAME` 报出要读哪个变量名，再用 `ACCEPT ... FROM ENVIRONMENT-VALUE` 把值取进来，然后才执行 `CONNECT`。所以源码和夹具里**不保存**机器专属路径或口令；`build.sh run` 通过 `DATASRC=sqlite://<绝对路径>` 等环境变量注入。生产部署也应该由环境或密钥管理提供这些值——换机器、换库、改口令都不该动程序。

### 2. 宿主变量与单行查询

SQL 里以冒号开头的字段就是宿主变量（如 `:WS-LOOKUP-ACCOUNT`），GixSQL 会把它们转成 SQLite 参数：

```cobol
           EXEC SQL
               SELECT ACCOUNT_NO, CUSTOMER_ID, BALANCE
                 INTO :WS-ACCOUNT, :WS-CUSTOMER, :WS-BALANCE
                 FROM ACCOUNT_SNAPSHOT
                WHERE ACCOUNT_NO = :WS-LOOKUP-ACCOUNT
           END-EXEC
```

`INTO` 后面三个就是"接收项"：数据库的三列，按位置分别写进三个 COBOL 字段。

宽度必须对得上：账户号在表里和 COBOL 里都是 10 字符、客户号都是 8 字符。固定长度 `PIC X` 会保留字段宽度，宿主变量的宽度得和数据库字段、实际取值约定一致，否则字符串会带上尾随空格或者被截断。余额在 COBOL 侧按 `PIC 9(7)V99` 的约定接住（源码里是 `PIC S9(7)V99 COMP-3`，7 位整数 + 2 位小数），显示前先搬到 `PIC 9(5).99` 的显示字段，所以 `1250.75` 打印出来是 `01250.75`——整数位补零补满 5 位，小数位照常两位。

还有个小地方别漏：查之前程序先把接收项清空（`MOVE SPACES` / `MOVE ZERO`）。不清的话，万一这次走的是"没查到"分支，字段里还留着上一笔的值——打印出来是别人的余额。

### 3. SQLCODE：三种结果必须分开

| `SQLCODE` | 含义 | 本课行为 | 退出码影响 |
|---:|---|---|---|
| `0` | 查询成功，返回一行 | 显示 `状態=FOUND` 与客户号、余额 | 无 |
| `100` | 没有匹配行 | 显示 `状態=NOT_FOUND`（**不是错误**） | 无 |
| 其他 | SQL 错误 | 显示 `状態=エラー SQLSTATE=` 并置失败标志 | `1` |

`SQLCODE = 100` 是正常业务结果；把它当故障，"查不到账户"这种日常情况就会中止批次。反过来，把 SQL 错误当成"查不到"，真正的数据库问题就被掩盖了——所以代码用 `EVALUATE SQLCODE` 把三者分开，只有 `0` 和 `100` 之外的值才走 `WHEN OTHER`。

反例和正例摆在一起看最清楚（下面都是示意代码，反例里的输出文本不是本课的真实输出）：

```cobol
      * 反例：把"没查到"和"SQL 出错"压成同一个失败分支
      *       正常业务结果被当成故障，真故障也失去了轻重
           IF SQLCODE NOT = 0
               DISPLAY "查询失败"
               MOVE "Y" TO WS-FAILED
           END-IF

      * 正例：三种结果各走各的路（lesson.cob 就是这么写的）
           EVALUATE SQLCODE
             WHEN 0     ...查到一行，取客户号与余额
             WHEN 100   ...没匹配行，正常业务结果
             WHEN OTHER ...SQL 错误，置失败标志、退出码 1
           END-EVALUATE
```

上面正例里 `WHEN 0` 与 `WHEN 100` 两个分支都不算失败，所以本课的两次查询（一个命中、一个查不到）跑完退出码仍是 `0`；只有落进 `WHEN OTHER` 才会返回 `1`。

### 4. 收尾

连接成功后，`9000-DISCONNECT-DATABASE` 执行 `CONNECT RESET` 并检查 `SQLCODE`；这一步失败同样会把失败标志置上，让主流程以状态 `1` 结束，便于 shell 作业发现。

## 走一遍真实流程

把这一课放进那条夜间链路，它长这样：

1. 白天柜面和手机银行产生的交易被导成文件，落在共享目录——读文件是第 15–22 课的事。
2. 夜里批次先跑文件侧的处理，把结果整理好。
3. 需要对账户现状时，**就是本课这段代码**：连库、按账号取一行，拿到客户号和余额。这只是"查一行"；要按顺序扫完整张账户快照表，是第 30 课的游标。
4. 文件侧和数据库侧两边都齐了，才能按账号逐条比对，判定 `MATCH` / `CHANGED` / `FILE_ONLY` 并生成差异文件——这是第 31 课。
5. 第 32 课的毕业项目把这条链路串成完整批次，并补上计数核对和 SQL 部分失败后的恢复说明。

也就是说，本课看着只是"取一个账户"，它其实是后面三课的地基：没有真实连库、没有分清 `SQLCODE` 三种结果，后面那些比对和重跑都无从谈起。

## 修改练习

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器或 shell 作业，它只看退出码，不看屏幕。
- **谁看它的输出**：值班和排障的人先看退出码，再看那几行日文标签。看到 `FOUND` 就继续，看到 `NOT_FOUND` 不紧张，看到 `エラー` 才要动。
- **下一个系统怎么接**：本课只把值打印出来。下一步是让这些值参与判定（第 30、31 课），最后进到对账结果表和差异文件（第 32 课）。
- **第一个月最容易出的事故**：把 `100` 和"SQL 错误"合成一个分支。省了几行 `EVALUATE`，代价是报表上的"查不到"和真正的数据库故障再也分不清——前者天天有，后者一出就是大事故，混在一起谁也看不出来。
- **它还做不到的事**：只查一行、不写库、不管事务。SQL 失败后已写入的行会不会残留、重跑该怎么做，本课一律没碰——第 31、32 课才有；本课也**不能**说成"已经能上生产"。

**未验证项（为什么没验证）：**

- 跨数据库方言未验证：本工作区只在 x86-64 Linux + GixSQL v1.0.20b + SQLite 文件库上实测过；换成 Oracle/PostgreSQL/DB2 会怎样，本课不下结论。
- 三个 SQL 失败分支（`接続=エラー`、`検索=エラー`、`切断=エラー`）没有实测记录：本课没有可重复的故障注入手段（比如连不上的数据源、坏掉的表结构），所以它们只按代码和上面的 `SQLCODE` 表说明，不算跑过。
- 标准错误里的 `libxml 212 / older 209` 警告，来自运行环境的链接库版本差异，触发组件尚未定位；它不是程序的标准输出，核对业务结果时不要把它算进去。
