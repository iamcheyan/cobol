# モジュール04 設計：複雑な構造とレイアウトオフセット

本設計ではモジュール07のcanonical Copybookを読み取り専用で再利用します。既存の07/tasks/docs/Makefileなどのファイル、およびCUSTOMER v1=27B、ACCOUNT v1=47B、TRANSACTION v1=55Bは変更しません。

## 構造の意味（04.1）

- **REDEFINES**：別名ビューは再定義対象と同じ記憶域を共有し、**長さを二重に数えません**。設計では `01 WRAP` / `05 PAYLOAD`（8+7+3=18B）/ `05 PAYLOAD-RAW REDEFINES PAYLOAD PIC X(18)` とし、`LENGTH OF WRAP = 18`（36ではない）になります。実測値は04.1レポートを参照してください。
- **66 RENAMES**：連続する複数フィールドをひとつのグループとして再命名します。長さはRENAMES対象フィールドの合計です（例：3+4=7）。
- **OCCURS ... INDEXED BY**：固定長の反復項目と索引です。`SET idx TO n` で番号を指定して読み取り、添字の算術をハードコードしないようにします。
- **OCCURS DEPENDING ON（ODO）**：反復数はカウンター項目で決まり、**グループ内の最後の項目でなければなりません**。この構成ではグループ項目の `LENGTH OF` が**実行時の長さ**を返します。count=3 → 2+3×5=17、count=7 → 2+7×5=37です。「コンパイル時に長さが固定される」という前提とは異なり、これが本モジュールでの重要な実測結果です。

## COPY とレイアウトのバージョン（04.2）

- `COPY 'ENTERPRISE-CUSTOMER-V1.CPY'` でV1を読み込みます。次に `COPY ... REPLACING ==CUSTOMER-CLASSIFICATION PIC X(1)== BY ==... PIC X(2)==` を使い、このフィールドだけを拡張してV2を作ります。二つの01グループは同名なので、参照には必ず `OF ENT-V1` / `OF ENT-V2` を付けます。
- 結果：`CUSTOMER-CLASSIFICATION` 自身のオフセットは変わらず（1起算で460）、その後の**すべてのフィールドが+1**となり、総長は1,778から1,779になります。「フィールドをひとつ変更すると後続のどの項目が移動するか」を再現できる最小の実験です。
- 参照修飾（reference modification）：固定長フィールドから `WS-ID(1:4)`、`WS-ID(5:6)` のように部分文字列を取り出します。
- レイアウトのバージョン方針：V1は凍結します。幅を変える場合は新バージョン（`LAYOUT-VERSION=002`）を作り、旧ファイルを拒否または変換し、並行比較、切り替え、ロールバックを行います。既存ファイルをその場で書き換えてはいけません。

## 175フィールドのレコードとフィールド位置（04.3）

- レコード単位は1,778バイトです。フィールドはCopybookの順序で隙間なく並び、アラインメント用パディング、区切り文字、LFはありません。
- 外側の境界確認：ファイルのバイト数は1,778の整数倍でなければなりません。そうでない場合はRC8で公開物を作りません（GnuCOBOLの固定長読み取りは静かに空白を補って00を返す場合があるため、FILE STATUSだけに頼れません）。プログラム内でも `LAYOUT-VERSION=001`、`BINARY-ABI-CODE=GCOB32BE`、`CUSTOMER-ID` が10桁の数字であることを検査します。
- カタログ：`FIELD-CATALOG.csv`（175個の葉フィールド。各フィールドのoffset/長さ/単位/比較規則を記載）はモジュール07 canonicalカタログの複製です。**実測による検証**は `scripts/check.py` が `ADDRESS OF` で全フィールドを個別に測定します。総長の `LENGTH OF` を葉フィールドごとの証拠の代わりにはしません。
- フィールド位置の演習：04.3は `CUSTOMER-ID`/`RECORD-STATUS`/`LEGAL-SURNAME`/`CUSTOMER-CLASSIFICATION`/`RISK-SCORE`/`SYNC-STATE` を出力します。学習者はまずカタログから切り出し位置を計算し、その後に照合します。

## 出力契約

- 04.1：`LESSON,04.1` と `REDEFINES,<key>,<val>` / `RENAMES,...` / `OCCURS,...` / `ODO,...`。
- 04.2：`LESSON,04.2` と `LEN,V1/V2,<n>` / `SHIFT,V2-V1,<n>` / `CLASSIFICATION,...` / `REFMOD,...`。
- 04.3：`LESSON,04.3` と `LAYOUT,...`、各レコードの `REC,<n>,ID,<id>`、`  STATUS/`SURNAME/`CLASS/RISK/`SYNC` 行、`RECORDS,<n>`。

行の順序は固定で、チェッカーが逐行比較します。

## 実測根拠と環境

- コンパイラー：GnuCOBOL 3.2.0、Linux x86-64、デフォルト方言。
- `ADDRESS OF` によるフィールド別測定：175個の葉フィールドのオフセットはカタログとすべて一致し、レコード総長は1,778です。
- V1/V2プローブ：`S2-S1`（`SYNC-STATE`のオフセット差）=1、`LENGTH OF`の差=1、`CUSTOMER-CLASSIFICATION`のオフセットは両バージョンとも460です。
- 実行時の `Warning: program compiled against libxml ...` は環境由来のノイズとして `stderr.txt` に記録します。

## 制限

- 実測対象はLinux x86-64 / GnuCOBOL 3.2のみです。他のコンパイラーやバイト順では別のABIバージョンが必要です。
- 04.3で行うのは構造、長さ/バージョン/キーの検査です。モジュール07の全フィールド業務ドメイン比較（07.6の範囲）は行いません。
- ODOの `LENGTH OF` の動作はこのコンパイラーでの実測です。別のコンパイラーでは再測定し、結果をそのまま流用しないでください。
