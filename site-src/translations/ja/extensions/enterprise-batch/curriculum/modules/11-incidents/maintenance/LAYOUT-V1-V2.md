# 企業顧客区分を1桁から2桁へ：インターフェース変更仕様（提示仕様）

対象はモジュール11の**独立してバージョン管理される企業顧客レイアウト** `ENTERPRISE-CLASS` です。27バイトの canonical CUSTOMER v1 ではありません（第27バイトはレコード状態 A/D です）。

> **名称と関係（同名によるずれを防止）**：コース canonical の大規模レコードは、モジュール07 L4 の `ENTERPRISE-CUSTOMER-V1`（175フィールド／1778バイト）です。本演習のレイアウトは、同じ `CUSTOMER-CLASSIFICATION` フィールドの意味だけを引き継ぐ23→24バイトの独立した `ENTERPRISE-CLASS` を意図的に使います。canonical と同じ名前を再利用してレイアウトの違いを見えにくくすることはありません。

## 1. レイアウト比較

| 項目 | V1（現状、ベースライン） | V2（目標） |
|---|---|---|
| レイアウトバージョン | `001` | `002` |
| レコード幅 | **23バイト** | **24バイト** |
| 顧客区分フィールド | `CUSTOMER-CLASSIFICATION PIC X(1)` | `CUSTOMER-CLASSIFICATION PIC X(2)` |
| 区分値 | `A` / `B` / `C` / `D` | `A1` / `B1` / `C1` / `D1` |
| マッピング | — | `A→A1`、`B→B1`、`C→C1`、`D→D1` |

ベースライン定義：`maintenance/copybooks/ENTERPRISE-CLASS-V1.CPY`。

## 2. バイトオフセット（1始まり）

| バイト | V1 長さ | V2 長さ | フィールド |
|---:|---:|---:|---|
| 1–3 | 3 | 3 | `LAYOUT-VERSION`（`001`→`002`） |
| 4–11 | 8 | 8 | `CUSTOMER-ID` |
| 12 | 1 | 1 | `RECORD-STATUS`（A 有効／I 停止） |
| 13–22 | 10 | 10 | `CUSTOMER-NAME` |
| 23 | 1 | — | `CUSTOMER-CLASSIFICATION`（V1 1桁） |
| 23–24 | — | 2 | `CUSTOMER-CLASSIFICATION`（V2 2桁） |

**主な影響**：区分フィールドはレコードの**末尾**にあるため、幅の拡張でレコードが長くなるだけ（+1バイト）で、V2 でも区分より前のフィールドオフセットは変わりません。ただし、**レコード全体の長さが変わる**ため、固定長読み込み、ファイルヘッダー／末尾の処理、チェックサム、バイト単位で切り出す下流利用者に影響します。`RECORD-STATUS` は別の業務上の意味を持つため、顧客区分として誤用してはいけません。

## 3. 互換性と移行の制約

- **V1 ファイルをその場で書き換えてはいけません**。移行ツールは新しい V2 ファイルを書き出し、並行検証とロールバックに備えて元ファイルを保持します。
- 読み込みプログラムはバージョンに応じて幅を選択します：`001` → 23バイト、`002` → 24バイト。バージョンと幅が一致しない場合は `RC8` で中止し、黙って補完／切り詰めをしてはいけません。
- 下流インターフェース（`CLASS|<id>|<class>`）もバージョン管理が必要です。V1 の class は1文字、V2 は2文字です。切り替え中に両バージョンを識別できなければなりません。
- ロールバック：V2 → V1 は損失なく行います（V2 の第2文字が `1` であることが条件）。元の V1 をバイト単位で復元できなければなりません。
