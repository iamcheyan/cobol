# 07.2: Combine two sorted transaction streams with COBOL MERGE

The two independent input streams in this lesson are each strictly ascending by a composite key. COBOL `MERGE ... USING FEED-A FEED-B` repeatedly selects the smallest key; the OUTPUT PROCEDURE uses `RETURN` to write the original 55 bytes. The program first scans both sources byte by byte to verify LF, record width, fields, valid dates, and strict per-stream ordering, then runs a real `MERGE`. There is no concatenate-then-SORT substitute.

See [DESIGN.md](DESIGN.md) and the [field catalog](../common/FIELD-CATALOG.md) for business keys, byte boundaries, status, and RCs. The source structure uses only the canonical [TRANSACTION-V1.CPY](../../../../../bank/copybooks/TRANSACTION-V1.CPY). Different IDs with the same account and sequence are valid; a repeated full key within a stream, descending input, any duplicate global ID across either source, or invalid raw bytes return RC8. If both sources are empty, output is empty and RC0.

## Learning path

1. Hand-calculate the three-part keys in [Feed-A](fixtures/normal/feed-a.dat) and [Feed-B](fixtures/normal/feed-b.dat). Stream A has Z(seq1), M(seq2), B(acct2/seq1); stream B has A(seq2), A(seq3), A(acct2/seq1). Advance each of two cursors and repeatedly select the smallest key; independently derive the Z,A,M,A,A,B order in [expected/normal.dat](expected/normal.dat).
2. In reference `instructor/modules/07/02-sort-merge/MERGETX.COB`, find `VALIDATE-SOURCE`, `CHECK-FIELDS`, `CHECK-ORDER`, `MERGE ... USING`, and `WRITE-MERGED`. Explain why the pre-scan checks each input's own order while MERGE determines order across streams.
3. Use `:CobolGotoDef` from `MAIN-PROCEDURE` to `VALIDATE-SOURCE`, then to `WRITE-MERGED`. At the `COPY "TRANSACTION-V1.CPY"` line under SD, use `:CobolGotoCopybook` to inspect canonical fields. Terminal equivalents: `rg -n 'VALIDATE-SOURCE|CHECK-ORDER|MERGE|USING|RETURN|TRANSACTION-V1' instructor/modules/07/02-sort-merge/MERGETX.COB` and `nl -ba curriculum/bank/copybooks/TRANSACTION-V1.CPY`.
4. Experiment: swap Feed-A's first two rows; MERGE must return RC8 and not publish. Change only an ID to lowercase; it should still return RC8. Put the same `transaction_id` far apart in the two inputs; the global check must return RC8. Then use the zero-amount boundary streams: MERGE still returns RC0 and copies bytes unchanged; downstream L2 classifies ZERO-AMOUNT as RC4.
5. Compare SORT and MERGE responsibilities: SORT builds order from unordered input with `RELEASE`; MERGE reads sorted sources only and selects the minimum key as it streams. Explain why concatenating text then sorting does not count as MERGE.

For an external comparison, sort explicitly by bytes 1–10, 35–40, and 11–26:

```bash
LC_ALL=C sort -k1.1,1.10 -k1.35,1.40 -k1.11,1.26 \
  fixtures/normal/feed-a.dat fixtures/normal/feed-b.dat
```

This is an external comparison, not the course algorithm. Production output is generated by COBOL MERGE; the external sort in acceptance scripts checks only global ID uniqueness and the byte multiset.

## Starter, build, run, check, reset

```bash
lab=$PWD/curriculum/modules/07-matching/labs/02-sort-merge/02-merge
work=$(mktemp -d)
bash "$lab/scripts/init-workspace.sh" "$work"
cd "$work"
bash "$lab/scripts/build.sh" "$work/mergetx"
bash "$lab/scripts/run.sh" \
  "$lab/fixtures/normal/feed-a.dat" "$lab/fixtures/normal/feed-b.dat" \
  "$work/merged.dat"
cd "$lab/.."
sha256sum -c SHA256SUMS
bash "$lab/scripts/check.sh"
```

The starter builds but returns RC12, ensuring incorrect implementations are not published:

```bash
set +e
COURSE_SOURCE="$lab/starter/MERGETX.COB" \
  bash "$lab/scripts/run.sh" "$lab/fixtures/normal/feed-a.dat" \
  "$lab/fixtures/normal/feed-b.dat" "$work/starter-output.dat"
rc=$?
set -e
test "$rc" -eq 12
test ! -e "$work/starter-output.dat"
```
