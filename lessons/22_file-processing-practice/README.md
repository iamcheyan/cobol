# 第 22 课：综合练习——排序、校验、匹配与结果写出

第三阶段到这里要把文件处理串成一条完整链路：读入未排序的交易、按账户号排序、与账户主档顺序匹配、按固定规则校验后把记录分流写进接受文件和拒绝文件，最后用控制计数交代每条记录去了哪里。本课把第 15–21 课的顺序文件、定长字段、匹配与 `SORT` 组装成一个可运行的小型批次，并给出可逐条核对的结果文件内容。

## 为什么现在学

你已经分别会读文件、写文件、解析定长记录、按顺序匹配和排序，但它们还是五个独立动作。缺口是“串起来”：一段真实批次的输出不是一个数字，而是“接受文件、拒绝文件、孤立主档账户清单和控制计数”这四样必须互相吻合的结果。本课把它们连起来，并让失败路径（缺账户、坏类型、坏金额）都留下可核对的痕迹。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `SORT` 与 `INPUT PROCEDURE`/`RELEASE` 把未排序交易整理成升序，并在释放前检查记录宽度。
- 在一次归并扫描中把每条交易归为“已接受”“因无主档被拒”“因字段非法被拒”，把剩余主档账户记为仅主档。
- 分别写出 `accepted.txt` 与 `rejected.txt`，并逐行核对文件内容与记录宽度。
- 用计数不变量检查无遗漏：`接受 + 拒绝 = 输入记录数`、`主档匹配数 + 仅主档 = 主档记录数`。
- 说明 `OPEN OUTPUT` 会覆盖旧结果文件、排序的前提和本课不做的账务控制。

边界：程序只做**分类与写出**，不累计余额、不实施借贷金额规则、不提供双文件原子交付；主档必须已升序且键唯一，但程序**不校验**顺序与重复键。重复交易账户不受支持。批次标识、重跑策略、输出原子交付与金额规则属于第 26–32 课。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端；本课不依赖数据库或附加工具。
- `SELECT` 使用相对文件名，程序在**当前工作目录**读写 4 个文件：读 `transactions-unsorted.txt`、`accounts.txt`，写 `accepted.txt`、`rejected.txt`。
- 两个输出用 `OPEN OUTPUT`，**每次运行都会覆盖同名旧文件**。因此本课在 `build/` 目录里准备一份输入副本再运行，避免把结果写进源码目录；`build/` 已被仓库忽略。

## 输入与输出记录

| 文件 | 字段顺序 | 字段宽度 | 记录宽度 |
|---|---|---:|---:|
| `transactions-unsorted.txt`（输入） | 账户号、类型、金额分 | 10 + 1 + 9 | 20 |
| `accounts.txt`（输入） | 账户号、客户号、余额分 | 10 + 8 + 9 | 27 |
| `accepted.txt`（输出） | 账户号、客户号、类型、金额分 | 10 + 8 + 1 + 9 | 28 |
| `rejected.txt`（输出） | 账户号、原因、类型、金额分 | 10 + 10 + 1 + 9 | 30 |

金额九位数字表示 `PIC 9(7)V99`，`V` 不占物理字符：`000012550` 表示 `125.50`。输入每行一条记录、没有分隔符，换行符不计入 `FD` 宽度。夹具主档已按账户号升序（`A000000001`、`A000000003`、`A000000005`、`A000000007`、`A000000009`），交易刻意打乱顺序；夹具里同时包含匹配交易、没有主档的交易、坏类型、坏金额和没有交易的主档账户。

拒绝原因固定为十字符：`NO_ACCOUNT`、`BAD_TYPE__`（不足十位处以 `_` 补齐）、`BAD_AMOUNT`。**缺少主档优先判为 `NO_ACCOUNT`**，所以无主档交易的类型/金额错误不会再被归为字段错误。

## 批次如何处理记录

1. 主程序调用 `SORT ... ON ASCENDING KEY SD-TRANSACTION-ACCOUNT`。
2. `1000-LOAD-TRANSACTIONS` 打开交易输入；每行先检查实际宽度，只有 20 字符的记录才 `RELEASE` 进排序工作文件。
3. `2000-RECONCILE-TRANSACTIONS` 打开主档与两个结果文件，读入第一条主档记录。
4. 输出过程逐条 `RETURN` 排序后的交易：主档键较小则把该主档账户计为仅主档并读下一条；两键相同则进入校验；交易键较小或主档已结束则记为无主档。
5. 匹配上主档时，类型必须是 `D` 或 `C`、金额必须全为数字：有效记录写 `accepted.txt`，无效记录写 `rejected.txt`。
6. 交易处理完后，剩余主档账户逐条计为仅主档。程序关闭已打开的文件并显示计数；检测到 I/O、宽度或排序错误时返回非零码。

## 计数不变量与可核对结果

本课夹具：交易 6 条、主档 5 条。

| 不变量 | 代入本课 | 含义 |
|---|---|---|
| `接受记录数 + 拒绝记录数 = 输入记录数` | `3 + 3 = 6` | 每条交易都留下了痕迹，去向只有一个 |
| `主档匹配数 + 仅主档记录数 = 主档记录数` | `4 + 1 = 5` | 每条主档记录都被认领一次；主档匹配数 = 输入记录数 − 无主档拒绝数 = `6 − 2` |

两类文件的行数也要与计数吻合：`accepted.txt` 3 行、`rejected.txt` 3 行。把这两个文件与标准输出一起核对，才能确认批次结果自洽，而不是只看一个汇总数字。

## 错误处理和边界

- 交易行宽必须为 20、主档行宽必须为 27；宽度不符会中止批次并返回非零码。
- 交易类型只允许大写 `D` 和 `C`；金额字段必须全为数字。
- `OPEN`/`READ`/`WRITE`/`CLOSE` 状态与 `SORT`/`RELEASE`/`RETURN` 结果都参与错误判断；EOF 状态 `10` 是正常结束。
- 输出用 `OPEN OUTPUT`，目录权限或文件系统错误会让打开/写入失败；**失败的批次不能当作成功交付**。
- 主档顺序与唯一键由上游保证，程序不扫描校验，也不处理重复交易账户。
- 输入/排序/分类计数用三位数字字段，微型夹具上限 999 条；生产批次要按最大规模选宽度。
- 本课不累计余额、不提供原子化的双文件交付；真实账务还要定义重复键、回滚、批次标识与输出交付策略。

## 运行与观察

**输入：** 本课目录下的 `transactions-unsorted.txt`（6 行）与 `accounts.txt`（5 行）。它们在下面被复制进 `build/`，程序在 `build/` 里运行并写出两个结果文件。

**命令及作用：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                    # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_22 lesson.cob      # 编译，可执行文件也放进 build/
cp accounts.txt transactions-unsorted.txt build/ # 把输入副本放进同一个工作目录
(cd build && ./lesson_22)                        # 在 build/ 里运行，结果文件写在这里
echo $?                                          # 查看退出码
rm -rf build                                     # 一次清掉可执行文件、输入副本与结果文件
```

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，无编译诊断 |
| 标准输出 | 10 行，见下方代码块 |
| 进程退出码 | `0` |
| 生成文件 | `build/accepted.txt`（3 行）、`build/rejected.txt`（3 行） |

```text
ACCEPTED 账号=A000000001
ACCEPTED 账号=A000000003
被拒绝 账号=A000000004 REASON=NO_ACCOUNT
ACCEPTED 账号=A000000005
被拒绝 账号=A000000006 REASON=NO_ACCOUNT
被拒绝 账号=A000000007 REASON=BAD_AMOUNT
MASTER_ONLY账户 账号=A000000009
输入记录数=006 排序记录数=006
接受记录数=003
拒绝记录数=003 MASTER_ONLY账户记录数=001
```

`build/accepted.txt`（3 行，每行 28 字符；含换行共 87 字节）：

```text
A000000001C0001001D000012550
A000000003C0001003C000000200
A000000005C0001005D000004000
```

`build/rejected.txt`（3 行，每行 30 字符；含换行共 93 字节）：

```text
A000000004NO_ACCOUNTD000007500
A000000006NO_ACCOUNTX000000100
A000000007BAD_AMOUNTD00000X001
```

**可逐条核对：** 交易 6 条按账户号排序后为 `001, 003, 004, 005, 006, 007`。其中 `001/003/005` 匹配主档且字段合法 → 接受；`004`、`006` 无主档 → `NO_ACCOUNT`；`007` 匹配主档但金额含 `X` → `BAD_AMOUNT`。主档 `009` 没有交易 → 仅主档。`输入记录数=006 排序记录数=006` 说明 6 条 20 字符记录全部通过宽度检查并进入排序。

**输出字段对照（输出标签 → 含义）：** `ACCEPTED` 已接受；`被拒绝` 已拒绝；`账号` 账户号；`REASON=` 拒绝原因；`MASTER_ONLY账户` 仅主档账户；`输入记录数`/`排序记录数`/`接受记录数`/`拒绝记录数`/`MASTER_ONLY账户记录数` 分别对应各项计数。示例的运行时标签混用了英文关键字与中文词（`ACCEPTED` 与 `被拒绝` 并存），以本节对照表为准。

**实际观察到的环境细节：** 在本工作区运行可执行文件时，标准错误会输出 `Warning: program compiled against libxml 212 using older 209`。这是运行环境的链接库版本警告，不是本程序的业务输出；其触发组件尚未定位。

## 修改练习

两项都在**夹具副本**上做（建议照上面的命令把副本放进 `build/`），不要改动仓库内的夹具：

1. 把交易账户 `A000000004` 改为主档中存在的 `A000000009`，其它字段不动。确认该笔进入接受文件、仅主档计数归零，并逐行核对两个输出文件。
2. 从原始夹具出发，把账户 `A000000007` 的金额从 `00000X001` 改为 `000000001`。确认该笔由拒绝变为接受，且主档记录仍用于匹配。

## 在企业中的位置

日终对账的常见链路就是：标准化输入、排序、按键匹配、保留拒绝记录、生成控制计数。本课用两个独立输出文件呈现这条链路，并让每一类失败都留下可核对的记录。

部署前还必须定义输入签名与批次日期、重复记录策略、金额借贷规则、失败重跑和输出原子交付——这些控制本示例都没有实现。重复键与缺失记录分类在第 20、26 课展开，模块化与日志在第 27 课，完整对账项目在第 32 课。
