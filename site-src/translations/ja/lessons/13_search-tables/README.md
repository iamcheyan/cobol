# 第 13 課：SEARCH と SEARCH ALL——取引の口座番号を該当口座に結びつける

取引ファイルのレコードには口座番号だけがあり、残高は含まれていません。本課では 4 口座をメモリテーブルに格納し、逐次検索 `SEARCH` と二分検索 `SEARCH ALL` で口座 `0002468101` と残高 `520.00` を探します。その後、見つからない場合の経路も個別に確認します。

## 業務現場

照合日の午前 7 時 30 分、昨夜の取引明細がファイルになりました。問題は明らかです。各取引にあるのは `0002468101` のような口座番号だけで、**残高、状態、顧客名はありません**。取引の正当性を判断するには、まず口座番号で口座マスタのレコードを探さなければなりません。残高の照合はその後です。

見つかったかどうかで取引の進路が決まります。見つかれば通常の照合へ、なければ手作業の確認キューへ送ります。担当者は新規口座か、マスタの同期漏れか、取引自体の入力誤りかを調べます。

手間を省いて「見つからない口座は残高 0 として扱おう」と言う人もいます。それはやめてください。**「見つからない」と「残高が 0」は別の結果です。** 見つからない口座を 0 として計算すると、本来人が確認すべき金額が報告書から静かに消えます。帳簿は合っているように見え、発覚するのは締め日を過ぎてからかもしれません。そこで本課では、存在しない `0005550000` を検索し、`AT END` がどこへ進むかを確認します。

口座マスタは通常、口座番号順に管理されます。そのため「二分検索 `SEARCH ALL` を使えばよい」と考えがちです。使えますが、前提があります。`SEARCH ALL` は**テーブルが整列済みで、キーに重複がないことを利用者が保証済み**だと仮定します。前提が違っていてもエラーにはなりません。本課では二つの確認用ケースを試します。ロード順を逆にし、さらに 5 項目に拡張して降順で格納します。コンパイラは何も言わず、この環境では基準ケースと一行ずつ同じ結果が出ます。覚えるべきなのは「二分検索は速い」だけではありません。**検索の正しさは前提を誰が保証するかにかかり、テストで捕捉できない前提は運用手順で守る必要がある**ということです。

## なぜ今学ぶのか

前課では `INDEXED BY` 索引を使って一項目ずつ進む方法を学びました。しかしそれは走査であり、口座番号による検索ではありません。走査で検索するなら、自分でループを書いて項目を一件ずつ比較し、「見つかったか」を記録するフラグも管理します。テーブルが大きければ遅くなり、フラグの更新漏れは誤った結果につながります。

COBOL には値による検索方法が二つあります。

- `SEARCH`：指定した項目から一件ずつ前へ比較し、見つかるかテーブル末尾に達するまで進みます。
- `SEARCH ALL`：二分検索です。比較回数を大きく減らせますが、テーブルが宣言どおりに整列し、キーに重複がないことが必要です。

「二分検索の前にソートすればよい」と思うかもしれません。方向性は正しいですが、COBOL の整列条件は二つの要素で決まります。`ASCENDING KEY` の宣言と、ロード処理が**実際に**その順序でデータを入れることです。宣言は `SEARCH ALL` に対する条件の記述であり、テーブルを自動的にソートしません。順序が誤っていてもコンパイラは検出しません。本課ではそれを確認します。

## この知識項目と解決する問題

**知識項目とは。** ロード済みテーブルでキーを使って項目を検索することです。逐次 `SEARCH` は整列を要求せず、開始位置を指定します。二分 `SEARCH ALL` は `INDEXED BY` 索引、`ASCENDING KEY`／`DESCENDING KEY` の宣言と一致するキー順、重複のないキーを要求します。見つかった後、同じ出現項目の別フィールドも読めます。本課では口座番号が一致した直後に残高を取得します。

**業務で解決する問題。** 「この取引はどの口座に属するか」「この商品にはどの料率を適用するか」といった対応を、担当者の判断ではなく確定的な検索にします。照合、利息計算、月次締め、資格判定は、口座番号・顧客番号・商品コードでマスタレコードを探すことから始まります。この段階がなければ、残高照合や状態判定に進めません。

**見つからない場合の処理も知識の一部です。** `AT END` は「テーブルにない」場合の経路です。業務上は「残高 0」ではなく、手動確認キューへの振り分け、ログ記録、記帳拒否など、別に扱う結果です。プログラマは見つからない場合の処理を明示し、通常経路に紛れ込ませてはいけません。

**使うべきでない場合。** テーブルが整列されていない、またはキー重複の可能性がある場合は `SEARCH` を使います。データが実行ごとに変わり、順序を保証できないのに `SEARCH ALL` を無理に使うのは危険です。本当に大きなマスタ全体をメモリテーブルに入れるべきでもありません。ファイル検索や `SORT` は第 17、21 課の内容です。

## 本課修了後にできることと限界

本課を終えると、次のことができます。

- 指定した索引位置から `SEARCH` でテーブルキーを逐次検索し、未検出を `AT END` で処理する。
- `ASCENDING KEY` と `INDEXED BY` を宣言したテーブルに `SEARCH ALL` の二分検索を使う。
- `SEARCH ALL` が索引、キー順、キー一意性に求める条件と、それぞれを維持する担当を説明する。
- 同じ口座番号を二つの方法で検索し、同じ残高が返ることを確認する。存在しない口座ではどちらも `NOT_FOUND` を出すことを確認する。
- `ASCENDING KEY` の宣言だけではデータが整列しないと指摘し、本課の確認で分かることと分からないことを説明する。

限界：本課はプログラム内固定データの 4 項目テーブルだけを使い、ファイル、データベース、索引編成ファイルは扱いません。`SEARCH` は整列を要求しませんが、`SEARCH ALL` は宣言に合ったキー順と一意性を要求します。ロードとソートの手順は第 17、21 課で扱います。

## 実行環境

- GnuCOBOL 3.2.0、デフォルト方言（`-std=cobol85` なし）、固定形式ソース。
- Linux 端末。データベースや追加ツールは不要です。
- 入力用フィクスチャや出力データファイルはありません。ビルド成果物は `build/` に作成し、削除して再作成できます。

## サンプル口座テーブル

完全なソースは [`lesson.cob`](./lesson.cob) を参照してください。プログラムは口座番号 `X(10)` の昇順に 4 口座を `OCCURS` テーブルへ格納します。口座番号は一意で、第 3 項の残高は `520.00` です。

この 4 項目は `1000-LOAD-ACCOUNTS` で格納されるプログラム内の**デモデータ**であり、ファイルから読み込まれるものではありません。この違いが、本課で証明できることとできないことを決めます。

| 項目 | 口座番号 | 残高 |
|---:|---|---:|
| 1 | `0000000042` | 0.00 |
| 2 | `0001234567` | 1000.00 |
| 3 | `0002468101` | 520.00 |
| 4 | `0007654321` | 250.75 |

テーブルには `ASCENDING KEY IS WS-ACCOUNT-NUMBER` を宣言し、`INDEXED BY WS-ACCOUNT-IDX` で検索索引を用意します。口座番号は先頭ゼロを含む同じ長さの固定幅テキストなので、文字列の昇順と口座番号の昇順が一致します。

存在する `0002468101` と存在しない `0005550000` の二つを、それぞれ二つの方法で検索します。

## SEARCH と SEARCH ALL

`SEARCH WS-ACCOUNT-ENTRY` は逐次検索です。まず `SET WS-ACCOUNT-IDX TO 1` で索引を第 1 項に置き、各 `WHEN` で現在項目の口座番号と検索対象を比較します。一致しなければ `SEARCH` が自動的に一つ進みます。末尾まで一致しなければ `AT END` に進みます。つまり、**開始位置はこちらが指定し、検索が順に進みます。**

`SEARCH ALL WS-ACCOUNT-ENTRY` は二分検索です。最初にどこを調べ、次にどちら半分を捨てるかを検索が決めるため、比較回数を大幅に減らせます。その分、前提があります。テーブルに `INDEXED BY` 索引と `ASCENDING KEY`（または `DESCENDING KEY`）宣言が必要で、**実際に格納したキー順が宣言と一致し**、キーが一意でなければなりません。一つでも満たさなければ結果は保証されません。

| 検索方法 | 比較方法 | 前提条件 |
|---|---|---|
| `SEARCH` | 現在の索引から逐次確認し、見つかるか末尾に達するまで進む | キー整列は不要。実行前に適切な開始位置へ索引を設定する |
| `SEARCH ALL` | 整列済みテーブルの範囲を二分して狭める | `INDEXED BY`、宣言どおりのキー順、一意なキーが必要 |

**宣言はソートではありません。** `ASCENDING KEY` は `SEARCH ALL` で使う場合に必要な順序を宣言するだけです。ソート命令ではなく、プログラムがテーブルを並べ替えることもありません。実際の順序はロード処理が決め、本課では `1000-LOAD-ACCOUNTS` が担当します。

## プログラムの各部分の役割

- `1000-LOAD-ACCOUNTS`：固定添字で 4 口座をテーブルに格納します。口座番号は厳密な昇順で重複しません。**本課で順序を保証する唯一の場所はこの段落**であり、`ASCENDING KEY` の宣言ではありません。
- `0000-MAIN`：検索対象を `0002468101` に設定し、逐次検索と二分検索を実行します。続いて `0005550000` に変更し、二つの検索を行います。
- `2000-SEQUENTIAL-SEARCH`：`検索=SEQUENTIAL` とキーを出力し、`SET WS-ACCOUNT-IDX TO 1` で索引を第 1 項に戻してから `SEARCH` します。この初期化は省けません。`SEARCH` は**現在の**索引位置から始まるため、戻さないと二回目の検索は前回の停止位置から続きます。
- `3000-BINARY-SEARCH`：`検索=BINARY` を出力し、`SEARCH ALL` を実行します。開始位置は指定せず、検索自身が選びます。
- 一致した場合は `検出 口座=... 残高=...` を出力し、一致しない場合は専用の `AT END` で `NOT_FOUND` を出力します。
- `WS-ACCOUNT-IDX` は `WS-ACCOUNT-NUMBER(WS-ACCOUNT-IDX)` のようにテーブル項目を参照するためだけに使い、通常の算術演算には使いません。

入力ファイル、コマンドライン引数、データベースは使用しないため、本課のディレクトリ以外で実行しても同じ結果です。以下は本課ディレクトリで実行する手順です。

**期待される結果：**

| 観察項目 | 期待値 |
|---|---|
| `cobc -fsyntax-only` 終了コード | `0` |
| `cobc -x` 終了コード | `0`、コンパイル診断なし |
| 標準出力 | 下記 8 行 |

```text

逐次検索=検出 口座=0002468101  残高=0000520.00
```

**出力用語（日本語出力から意味への対応）：** `検索` = 検索方式（`SEQUENTIAL` は逐次、`BINARY` は二分）；`キー` = 今回の検索キー；`逐次検索`／`二分検索` = 各方式の結果；`検出` = 発見；`口座` = 見つかった口座番号；`残高` = 口座残高（`PIC 9(7)V99`、`520.00` はゼロ埋めして `0000520.00`）；`NOT_FOUND` = 未検出。

**実際に観察した環境の詳細：** 本ワークスペースで実行ファイルを起動すると、標準エラーに `Warning: program compiled against libxml 212 using older 209` が出力されます。実行環境のリンクライブラリ版の警告で、プログラムの出力ではありません。発生元のコンポーネントは特定されていません。プログラム出力は標準出力にあり、終了コードは 0 です。

## 整列の前提をこの環境で観察できるか

`SEARCH ALL` は `ASCENDING KEY` と一致する項目順に依存します。コンパイルや一度の実行で前提違反を検知できるでしょうか。本ワークスペースでは [`lesson.cob`](./lesson.cob) の一時コピーを使い、二つのケースを試しました。

1. `ASCENDING KEY` 宣言はそのままに、4 項目のロード順全体を逆にする。
2. テーブルを 5 項目に拡張して降順で格納し、宣言は変更しない。

**観察結果：** どちらもコンパイルに成功しました（`cobc -x -Wall` の終了コード `0`、診断なし）。実行結果は上表と一行ずつ同じで、`SEARCH ALL` は `0002468101` を見つけ、存在しないキーには `NOT_FOUND` を出力しました。

**結論（本機の GnuCOBOL 3.2.0 とこの規模に限定）：** 本課の小さなテーブルでは `ASCENDING KEY` 違反をコンパイラは止めず、実行結果にも異常が現れません。順序の正しさは一度の実行テストでは確認できません。ロードまたはソートの工程が順序を保証し、レビューでデータの出所を個別に確認する必要があります。`SEARCH ALL` は比較回数を減らす代わりに、正しさを保証しにくくします。**この確認を「順序が違っても問題ない」と受け取らないでください。** この規模ではテストで問題が見えなかったというだけで、本番データに問題がない証明ではありません。

## 応用演習

5 商品コードと在庫数のテーブルを作ります。まず `SEARCH` で中央付近の商品と存在しない商品を検索します。次に `SEARCH ALL` に適切なキーを宣言し、商品コードを一意にして宣言どおりに実際に整列させ、ヒットと未ヒットをそれぞれ試します。テーブル順だけを変更してキー宣言を更新しない場合の危険性と、本課の確認では自動検出できない理由を説明してください。固定メモリテーブルだけを使い、ファイルやデータベースは追加しません。課題は [`exercise.md`](./exercise.md)。解答はありません。

## 実際の業務フロー

この検索を照合処理に配置すると、早い段階に位置します。

1. 上流が当日の取引をファイルに出力し、共有ディレクトリに配置します（第 15 課でファイルを読みます）。
2. 口座マスタを口座番号順に並べてメモリテーブルにロードします。これは `SEARCH ALL` の前提です（固定長マスタは第 17 課、ソートは第 21 課）。
3. **本課の処理：** 各取引の口座番号で検索します。見つかれば残高を照合工程に渡し、見つからなければ担当者確認キューに送ります。
4. 照合結果は結果ファイル（第 16 課）またはデータベース（第 29 課以降）へ送り、ログにも記録します（第 27 課）。ログ内の `NOT_FOUND` は翌日に人が確認する項目です。
5. 口座テーブルと取引テーブルを結合して処理する工程は第 14 課でメモリ版を学びます。第 20 課では同じ「整列済み、キー一意」の条件がファイル照合に現れます。

つまり、本課の検索は照合処理の入口です。入口で口座を誤れば、後続の結果もすべて誤ります。

## このコードが本番に入ると

- **誰がスケジュールするか：** 取引ファイルの準備と口座マスタのロード・ソートが完了した後の夜間バッチです。前段が済んでいなければ検索結果に意味はありません。
- **誰が出力を見るか：** 当直担当者は `NOT_FOUND` などの例外を確認します。取引が口座に結びつかなければ、その晩に調査しなければなりません。
- **後続システムとの接続：** 見つかった口座と残高を照合工程へ渡します（第 14 課のメモリ版、第 20 課のファイル版）。
- **初月に起きやすい事故：** ロード順と `ASCENDING KEY` 宣言が不一致になることです。本課の二つの確認から、コンパイルでは検出されず小さな表の実行でも分からない場合があると分かります。稼働前に上流の整列方法とソート工程の実施有無をレビューで確認します。
- **同じく重大な別の誤り：** 「口座が見つからない」を「残高 0」として処理することです。プログラムは停止せず、帳簿を静かに誤らせるため、発見が難しい種類の問題です。
- **未実装の処理：** ファイル読み込み、ソート、口座番号形式の検証、ログ、業務用戻りコードです。重複キーの方針と欠損レコードの分類は第 20 課、拒否レコードの出力は第 16 課で扱います。ファイル読み込み、ソート、エラー分類、ログはそれぞれ第 15、21、26、27 課で補います。本課は検索の教材であり、そのまま本番投入できる照合プログラムではありません。
