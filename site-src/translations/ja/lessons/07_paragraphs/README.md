# 第 07 課：名前付き段落——バッチの主処理フローを名前付きフェーズに分割する

## 業務現場

金曜日の深夜 1:10、地方銀行の日次締めバッチが実行されています（教育用の想定シーンであり、機関名、金額、時刻は架空のものです）。このジョブは 3 年前には 100 行余りしかありませんでしたが、今では 900 行に膨れ上がっています：初期化、勘定転記、集計、帳票印字がすべて `PROCEDURE DIVISION` に詰め込まれ、その間には当時緊急対応で追加された 2 つのパッチコードまで挟まっています。

深夜 2:03、上流の担当者から電話がかかってきました。「今夜の残高集計がなぜか全部 0 になっているのですが？」当直の新任担当者・小林がログを確認しに行きますが、画面上は至って平穏でした——エラーなし、例外なし、終了コード `0`。スケジューラはずっと前にこのジョブを成功とマークし、それに依存する後続のいくつかのジョブも通常通り最後まで走りきっていました。

夜が明けてからの照合でようやく原因が判明しました：あるクリアのステップが勘定転記の後に移動されており、計算したばかりの残高を再び 0 に戻してしまっていたのです。資金が失われたわけではありませんが、帳簿上の数字はすべて狂っており、しかもシステムは何のアラートも発しませんでした。

段落名が真に解決しようとしているのはまさにこの問題です。これは「コードの美しさ」といった審美的な好みの問題ではなく、運用担当者や後任者のために道標を残すということです：深夜に障害が発生した際、ログの 1 行を指差して「これは `2000-PROCESS` が出力したものだ」と言えなければなりません。場所の特定以上に高くつくのが**順序**です——初期化、処理、集計の前後関係をひとたび逆に書いてしまえば、プログラムは通常通り完走し、同様に 0 を返し、誤りは翌日の照合まで浮上しません。

## なぜ今これを学ぶか

前の課で、あなた自身の手で同じロジックを N 回実行できるようになりました。ここで、あなたが書いたあのプログラムを振り返ってみてください：すべての文が `PROCEDURE DIVISION` の中に上から下へとフラットに並んでいます。

30〜40 行のうちはそれでも問題ありません。一目で全体を見渡せます。しかし、バッチプログラムが 40 行で留まることはありません：ファイル読み込みで一区切り、金額検証で一区切り、勘定転記で一区切り、集計カウントで一区切りと、数百行になるのが常態です。その時が来て叩き起こされたとき、あなたが最も知りたいのは「どの区間が壊れているか」であって、1 行目から読み直すことではありません。

「コメントで目印を付けておけばいいのではないか」と思うかもしれません。

コメントがあるのは良いことですが、コメントは実行されません。主フローに `PERFORM 1000-INITIALIZE` と書いてあれば、読む人はこのステップが初期化であると一目で分かります。一方、コメントに「以下、初期化開始」と書かれていても、3 か月後にそれが実態と一致している保証は誰にもできません。さらに致命的なのは順序です——コメントは「初期化は勘定転記の前に実行しなければならない」と強制してはくれません。

`PERFORM 段落名` が行うのは、「その区間が何と呼ばれるか」と「それがいつ呼び出されるか」を主フローの中にセットで提示し、誰もが一目で把握できるようにすることです。

## この知識項目とは何か，何を解決するか

**この知識項目とは何か。** 命名段落：`PROCEDURE DIVISION` の中でロジックの一区切りに名前を付け（例：`1000-INITIALIZE`）、別の場所からそれを実行したいときに `PERFORM 1000-INITIALIZE` と記述します。名前は Area A から開始し、文は通常通り Area B から開始します。その区間の最後の文まで進むと、制御は自動的に `PERFORM` の次の行へ戻ります——これは「ジャンプして処理を終えたら戻ってくる」動作であり、新しいプログラムを起動するわけではありません。

**業務において何を解決するか。**

- **主フローが理解しやすいチェックリストになる。** 以前は 900 行すべてを読み通さなければバッチが何をしているか分かりませんでしたが、今では主段落の数行を読むだけで十分です。
- **ログとコードを一致させられる。** 各フェーズがそれぞれ独自の目印を出力することで、障害発生時にどのステップで中断したのかを直接確認できます（本課の出力における `段階=...` がまさにこの役割を果たします）。
- **順序の依存関係が白日の下に晒される。** 初期化、処理、集計という 3 つの言葉自体が前後関係を表しており、コードレビュー時に主段落をひと目見るだけで「この順序は正しいか？」と問いかけることができます。

**どんなときに使うべきでないか。** 段落は現在のプログラムユニット内でのみ生存するものであり、独立したサブプログラムではありません。別のバッチでも同一の金額計算ルールを使用したい場合、必要になるのは `CALL`（第 24 課）であり、段落をコピーして持ってくることではありません。また、最も見落としやすい落とし穴があります：段落同士は同一の `WORKING-STORAGE` を共有しており、関数の引数のようなスコープの分離はありません——本課の演習 2 で、この落とし穴を自らの手で体験することになります。

## 本課修了時の能力と限界

本課を修了すると、以下のことができるようになります：

- `PROCEDURE DIVISION` 内で名前付き段落を定義し、段落名を Area A から開始できる。
- `PERFORM 段落名` を用いて段落を実行し、制御が `PERFORM` の直後の文にいつ戻るかを明確に説明できる。
- バッチの主フローを初期化、処理、終了集計の 3 つのフェーズに分解し、主段落内で適切な呼び出し順序を組み立てられる。
- 段落が現在のプログラムの `WORKING-STORAGE` を共有する理由、および呼び出し順序を入れ替えると最終残高が変化する理由を説明できる。
- プログラム内部の `PERFORM` と、後で学ぶ `CALL` によるサブプログラム呼び出しが別物であることを説明できる。

限界：本課ではソースコード内に記述された金額のみを使用し、ファイル、コマンドライン引数、データベースの読み込みは行わず、独立したサブプログラムを呼び出す `CALL` も使用しません。プログラム間インターフェースとパラメータ規約は第 23–25 課（Copybook、`CALL`、`USING`）で扱い、レコードレベルのエラー処理は第 26 課で扱います。

## 実行環境

- GnuCOBOL 3.2.0、デフォルト方言（`-std=cobol85` は付加しない）、ソースファイルは固定形式。
- Linux 端末。本課はデータベースや追加ツールに依存しません。
- 構文チェックおよびコンパイルはいずれも `build/` 配下に実行可能ファイルを生成します。削除してやり直せば問題ありません。

## 段落と PERFORM は実際にどう使うか

段落名は `PROCEDURE DIVISION` 内に記述し、本リポジトリの固定形式では Area A の左端から開始することが求められます。`PERFORM 1000-INITIALIZE` はその段落内の文を実行します。次の段落または手続き範囲の末尾に達すると、制御は `PERFORM` の直後の文に戻ります。

ここで初心者が混乱しやすい詳細があります：段落は現在のプログラムの `WORKING-STORAGE` を共有します。`PERFORM` は新しいプログラムを生成するわけでもなく、データの複製を作成するわけでもありません。そのため、`2000-PROCESS` で計算された残高は、`9000-FINALIZE` から直接読み取ることができます——これは本課の便利な一面であると同時に、演習 2 の落とし穴の出所でもあります。

本例では `0000-MAIN` を先頭に配置しています。プログラムは主段落から開始し、順に初期化、計算、集計を PERFORM します。`STOP RUN.` は段落定義の前に記述して通常の順次実行を終了させ、主フローが後続の段落定義の中に「転落」するのを防いでいます。呼び出される 3 つの段落は、それぞれ 1 つの役割のみを担当します。

段落名はチームの規約であり、業務ロジックではありません。GnuCOBOL マニュアルでは、手続き名（段落名）に英文字、数字、ハイフン、アンダースコアを使用することが許可されています（例：`0100-Read-Transaction`）。ただし、名前の先頭や末尾にハイフンやアンダースコアを置くことはできません。

### 悪い例 → 良い例：同じ残高、2 通りの書き方

悪い例——順序が逆転しており、プログラムは沈黙したまま：

```cobol
       0000-MAIN.
           PERFORM 2000-PROCESS
           PERFORM 1000-INITIALIZE
           PERFORM 9000-FINALIZE
           STOP RUN.
```

良い例——クリア処理を最前頭に配置：

```cobol
       0000-MAIN.
           PERFORM 1000-INITIALIZE
           PERFORM 2000-PROCESS
           PERFORM 9000-FINALIZE
           STOP RUN.
```

どちらのコードもコンパイル可能で、完走し、終了コードも `0` であり、コンパイラは何の警告も発しません。違いは出力だけに現れます：悪い例の最終行は `最終残高=0000000.00` となり、資金は後から走った初期化によってクリアされてしまっています。これこそが業務上の誤用が構文エラーよりも高くつく理由です——構文エラーならコンパイラがその日の夜に阻止してくれますが、順序の誤りは翌日の照合まで見つかりません。

## 完全なサンプル

完全なソースコードは [`lesson.cob`](./lesson.cob) を参照してください。固定形式で記述されています。

サンプル内の金額は固定のデモ用データです：期首 `1000.00`、預金 `125.50`、引出 `40.10`、処理段落が計算する期末残高は `1085.40` です。

| 段落 | 責務 | 主要な文 |
|---|---|---|
| `0000-MAIN` | 処理フローに沿って 3 つのフェーズを呼び出す。復帰後にバッチ完了を報告 | `PERFORM ...`、`DISPLAY`、`STOP RUN` |
| `1000-INITIALIZE` | 期末残高フィールドをゼロクリア | `MOVE ZERO TO ...` |
| `2000-PROCESS` | 期末残高を計算して表示 | `COMPUTE ...`、`DISPLAY` |
| `9000-FINALIZE` | 終了フェーズと最終残高を表示 | `DISPLAY` |

各 `PERFORM` で使用されている名前は、いずれも 1 つの段落定義に対応しています。主フローはまず初期化を行い、次に計算し、最後に集計します。そのため、`9000-FINALIZE` は `2000-PROCESS` が共有残高フィールドに書き込んだ値を正しく読み取ることができます。

## 実行順序の段階的解説

1. プログラムは最初の段落 `0000-MAIN` に到達します。
2. `PERFORM 1000-INITIALIZE` が `段階=INITIALIZE` を出力し、期末残高をゼロにします。段落終了後、制御は主フローに戻ります。
3. `PERFORM 2000-PROCESS` が `段階=PROCESS` を出力し、`1000.00 + 125.50 - 40.10 = 1085.40` を計算して `0001085.40` を出力します。その後、主フローに戻ります。
4. `PERFORM 9000-FINALIZE` が `段階=FINALIZE` と、読み取った共有フィールド `最終残高=0001085.40` を出力し、主フローに戻ります。
5. 主フローが `バッチ=COMPLETE` を出力し、`STOP RUN.` を実行します。実行フローが後続の段落定義へ流れ込むことはありません。

ついでにピリオドについて補足します：ピリオドは COBOL の文を完結させ、まだ閉じられていない文のスコープも終了させます。本例では、呼び出される各段落の最後の文にピリオドを置き、主段落のピリオドは `STOP RUN` の後に置いています。

## 実行と観察

本課は端末、ファイル、データベースからの読み込みを行わないため、本課のディレクトリでも任意のディレクトリでも実行結果は同一です。以下では本課のディレクトリを基準に説明します。

**入力：** なし。3 つの金額はプログラム内の固定データであり、すべて `WORKING-STORAGE` の `VALUE` から来ています。

**コマンドとその役割：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                  # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_07 lesson.cob    # 编译并生成可执行文件
./build/lesson_07                              # 运行程序，输出写到标准输出
echo $?                                        # 查看退出码
rm -rf build                                   # 清理生成的可执行文件
```

**期待される結果：**

| 観察項目 | 期待値 |
|---|---|
| `cobc -fsyntax-only` 終了コード | `0` |
| `cobc -x` 終了コード | `0`、コンパイル診断なし |
| 標準出力 | 6 行、下記コードブロック参照。フェーズの順序は INITIALIZE → PROCESS → FINALIZE |
| プロセス終了コード | `0` |

```text
段階=INITIALIZE
段階=PROCESS
期末残高=0001085.40
段階=FINALIZE
最終残高=0001085.40
バッチ=COMPLETE
```

**出力フィールドの対応（日本語出力 → 意味）：** `段階` = 現在のフェーズ、`期末残高` = 処理段落が計算した期末残高、`最終残高` = 集計フェーズで読み取った残高、`バッチ=COMPLETE` = バッチ完了。残高フィールドは `PIC 9(7)V99` であり、`1085.40` は 7 桁の整数部にゼロ埋めされて `0001085.40` と表示され、想定小数点（V）は表示時には省略されます。

**実際に観察された環境の詳細（未検証事項）：** 本ワークスペースで実行可能ファイルを実行した際、標準エラー出力に `Warning: program compiled against libxml 212 using older 209` が出力されます。これは実行環境の共有ライブラリのバージョン警告であり、本プログラムの業務出力ではありません。それを引き起こしているコンポーネントは未特定のため、ここでは現象を記録するにとどめ、原因の推測は行いません。プログラムの出力は標準出力にあり、終了コードは 0 です。

## 修正演習

2 つの修正は、それぞれ元の [`lesson.cob`](./lesson.cob) から開始し、重ねて変更しないでください。

1. 金額の変更：`WS-OPENING-BALANCE` を `2000.00`、`WS-DEPOSIT` を `250.00` に変更し（`WS-WITHDRAWAL` は `40.10` のまま維持）、再コンパイルして実行します。新しい期末残高は `0002209.90` になるはずです。
2. 順序の変更：`0000-MAIN` の中で `PERFORM 2000-PROCESS` を `PERFORM 1000-INITIALIZE` の前に移動し、他の文はそのままにします。フェーズの目印と最終残高を記録してください——最終残高は `0000000.00` になるはずです。処理段落が書き込んだ値が、後から走った初期化によってなぜ上書きされてしまうのかを説明してください。

この 2 つ目の課題は、「業務上の誤用が構文エラーよりも高くつく」現場の実演です：コンパイルエラーは出ず、実行終了コードも 0 のままなのに、資金の数字が消えてしまいます。各修正の後に実行します：

```sh
cobc -fsyntax-only lesson.cob
cobc -x -Wall -o build/lesson_07 lesson.cob
./build/lesson_07
```

完全な課題は [`exercise.md`](./exercise.md) を、参考解答は [`answer.md`](./answer.md) を参照してください。

## 応用演習

同様の小規模バッチを 4 つの名前付き段落に分割してください：サンプルの読み込み、取引コードの検証、残高の計算、集計の出力。主段落に適切な呼び出し順序を配置し、各フェーズで目印を出力します。その上で、データ依存関係のある 2 つの段落を入れ替え、出力の差異を記録してください。依然として固定値のみを使用し、ファイル、テーブル、`CALL` は導入しないでください。課題は [`exercise.md`](./exercise.md) にあります。本問には解答は提供されません。

## 本番フローをたどる

この小規模バッチを、深夜の実際の処理チェーンに戻してみましょう：

1. **深夜 0:40**、上流が当日の取引をファイルにエクスポートして共有ディレクトリに配置します（実際にファイルを読み込むのは第 15 課です）。
2. **深夜 1:00**、スケジューラがあなたのジョブを起動します。冒頭でまずアキュムレータをゼロクリアし、出力を準備します。この区間が `1000-INITIALIZE` の位置です。
3. 中間で 1 件ずつ処理し、1 行ごとに 1 件を計算します——`2000-PROCESS` のような段落です。
4. **締めくくり**：`9000-FINALIZE` が総件数と総金額をログに出力します（第 27 課でログに何を記録すべきかを詳しく解説します）。これらの数字は翌日、上流との照合に使用されます。
5. **引き継ぎ**：計算された結果を下流に引き渡します。結果ファイルの出力は第 16 課、データベースへの書き込みは第 29 課以降です。

したがって、主段落にある数行の `PERFORM` は飾りではなく、処理チェーン全体の目次なのです。今後、数百行に及ぶバッチプログラムを読むときは、まず主段落を探し、それがどのような順序で誰を呼び出しているかを確認してください。

## このコードが本番に入るとどうなるか

- **誰がスケジュールするか**：夜間バッチスケジューラであり、通常は「ファイル到着確認」の後に配置されます。スケジューラは終了コードのみを認識し、画面の出力は見ません。
- **誰がその出力を参照するか**：当直担当者がまずログのフェーズ目印を確認し、次に金額を確認します。残高が合わなければ、その日の夜のうちに調査しなければなりません。
- **トラブル時に誰が呼び出されるか**：このジョブを実行している担当者です。10 秒でどの区間が壊れているかを指摘できるかどうかは、当初の段落名の付け方が適切だったかどうかにかかっています。
- **後続システムはどう引き継ぐか**：結果をファイルに出力して下流に引き渡すか（第 16 課）、データベースに書き込みます（第 29 課以降）。
- **運用開始の初月に最も発生しやすい事故**：初期化を処理の後に追加してしまうこと——あるいは特定の問題を「修正」するために場当たり的にクリア処理を差し込むことです。プログラムはエラーを出さず、終了コードは `0`、スケジューラは成功を示し、誤りは翌日の照合になって初めて発覚します。演習 2 は、安全な環境で事前にその失敗を経験するためのものです。
- **まだ行っていないこと**：本課は 1 つのプログラム内部での役割分担のみを扱っています。プログラム間インターフェースは `CALL` の担当範囲であり、内部段落を独立したサブプログラムと混同しないでください。パラメータ規約と独立した呼び出しが真に必要となる場合は、第 24、25 課を参照してください。

はっきりさせておきます：本課は「処理に名前を付けること」によって主フローが読みやすくなり、呼び出し順序の影響を観察できることを証明しました。本番レベルのログ出力、エラー分類、リソースのクリーンアップは実装していません——バッチが失敗した際にどのようなコードを返すべきか、どのようなファイルを残すべきかは、第 26 課で初めて扱います。
