# 第30課：SQLカーソル——一度開き、表の全行を末尾まで取得する

月末締めの早朝、照合作業で走査するのは一つの口座ではなく、口座スナップショット表**全体**です。少なくとも数万行、多ければ十数万行になり、窓口が開く前に処理を終えて、当直担当者に「正確に何行取得したか」も報告しなければなりません。ここで必要なのは、一度開いて末尾まで一行ずつ読む方法です。「口座番号を一つ指定して一行返す」単件検索ではありません。

本課ではその方法を学びます。`ACCOUNT-CURSOR` というカーソルを使い、`DECLARE → OPEN → FETCH → CLOSE` のライフサイクルに沿って口座を一行ずつ読み、COBOL のホスト変数に格納します。`SQLCODE` を見て、「一行取得」「結果セットの終端」「SQL の実エラー」を区別します。

## 業務現場

> 注：以下の機関、時刻、件数は知識項目を説明するための架空のデモ設定であり、実在する機関の実データとは関係ありません。

午前 2:10、日次締め処理がその日の口座残高スナップショットをデータベースに保存したところです。スケジューラがバッチを起動し、指示は一つだけです。**このスナップショット表全体を走査し**、各口座の口座番号、顧客番号、残高を一行ずつ取得して、後続の照合処理に渡します。行数は事前に分かりません。多い日は十数万行、閑散期には数千行かもしれません。プログラムは「二行だけ」と仮定できません。

「前課で口座検索を学んだばかりだから、そのまま検索すればよいのでは」と思うかもしれません。しかし前課の `SELECT ... INTO` は「口座番号を指定する」検索です。口座番号を渡すと一行返ります。今回は正反対で、**誰を検索するか分からず、必要なのは全行**です。単件検索で全表を走査しようとしても余分な行を受け取れませんし、一行取得した後に続きがあるかも分かりません。

これがカーソルで解決する問題です。一つのクエリを**読み取り中の結果セット**にします。`OPEN` の後にデータが返り始め、`FETCH` を一行ずつ繰り返し、次の `FETCH` が「もうありません」と返すまで進みます。ここで最も大切で、間違えやすいのは、**「もうありません」は正常終了であり、エラーではない**という点です。`SQLCODE = 100` は結果セットの終端を表す正常な業務結果、`SQLCODE = 0` は今回一行取得できたことを表します。それ以外の値だけが SQL の実エラーです。

この違いは大きなコストにつながるので、はっきり理解してください。`100` も失敗分岐に送ると、翌朝、当直担当者は**毎日「失敗」と報告される**バッチを見ることになります。実際には一件も間違っておらず、表を正常に最後まで読んだだけです。実システムでは、このような「誤報」が特に厄介です。警報が鳴り続け、調べても問題は見つからず、本当に障害が起きた日には大量の誤報に埋もれて注意されなくなります。

## なぜ今学ぶのか

前課（[第29課](../29_embedded-sql/README.md)）では GixSQL のプリコンパイルを動かし、ローカルの SQLite に接続し、ホスト変数で口座を一件取得できるようになりました。これは立派な出発点ですが、答えられるのは「口座 X の残高はいくらか」という一種類の質問だけです。

一方、照合で答える必要があるのは別の質問です。**「このスナップショットには誰がいて、それぞれいくら持っているか？」**つまり、データは一件ではなく一括です。

「プログラムにループを書いて、口座を一件ずつ検索すればよいのでは」と言うかもしれません。それも可能ですが、まず**どの口座があるかを知る必要があります**。そして今はそれが分かりません。最初に全口座番号を取得し、それから番号ごとにもう一度検索することになります。一度で読めるデータを二度検索するうえ、口座が多ければ余分なメモリも必要です。

COBOL が用意する答えがカーソルです。データベース側に「読み取り中の結果セット」を保持させ、プログラム側は件数を前もって知らなくても、口座番号を先にメモリへ集めなくても、末尾まで一行ずつ取得できます。さらに三つの段階が明確です。`DECLARE` はクエリを登録するだけ、`OPEN` で実際に要求を送り、`FETCH` は一行取得するたびに明確な状態コードを返します。これらが揃うことで、表全体を読み切り、取得行数も正確に数えるバッチを書けます。

本課の到達点は、データベース側のデータを一括データとして、一行ずつ処理できるようになることです。次の[第31課](../31_data-synchronization/README.md)では、これを土台にデータベースのスナップショットとファイルのスナップショットをキーで照合し、差異一覧を作ります。その先の[第32課](../32_bank-reconciliation-project/README.md)で一連のバッチにまとめます。ここで「いつ読み終わったか」を間違えると、後続の流れ全体が誤ります。

## この知識項目とは何か、どんな問題を解決するのか

**知識項目の内容。** カーソルはデータベースクエリの「取っ手」です。まず宣言し（`DECLARE`。クエリ文字列を登録するだけで、データは取得しません）、次に開き（`OPEN`。ここで初めて要求を送ります）、繰り返し取得し（`FETCH ... INTO`。実行ごとに一行進み、現在行の各列を COBOL のフィールドに書き込みます）、最後に閉じます（`CLOSE`。リソースをデータベースに返します）。この四段階の順序は変えられません。各段階の後の `SQLCODE` が、次に何をするかを判断する唯一の根拠です。

**業務上どんな問題を解決するか。**

- 読み取る行数をプログラムに固定せず、データに決めさせます。今日は 3 行、明日は 12 万行でも、コードを変える必要はありません。
- 「読み終わり」を推測ではなく、**判定できる状態**（`100`）にします。バッチ終了時に「今回は 002 行取得」と報告でき、翌日その数字を上流の報告と照合できます。不一致なら行の欠落または重複を示します。
- 「空の結果」と「実際の障害」を分けます。表の一部に今日は一件もデータがないことは日常的で、警報を出すべきではありません。データベースに接続できない、表がない、といった場合こそ担当者を呼び出す必要があります。

**使うべきでない場合と、誤用した場合。**

- 主キーが分かっている一件だけを検索するなら、前課の `SELECT ... INTO` で十分です。カーソルでは不要なコードが増えます。
- 読む対象がデータベースではなく**ファイル**なら、第15課以降で学ぶ一行ずつのファイル読み込みを使います。カーソルとは関係ありません。
- 最も危険な誤用は前述のとおり `SQLCODE = 100` を障害扱いすることです。「読み終えた」が「失敗した」になります。逆に、本当の SQL エラーを「読み終えた」として見逃すのはさらに深刻です。口座を読み切れていないのにバッチが正常扱いで先へ進みます。

## 本課の完了後にできることと範囲

本課を終えると、次のことができるようになります。

- `EXEC SQL DECLARE ... CURSOR FOR SELECT ... END-EXEC` でカーソルを宣言し、宣言時にはクエリが**実行されない**と説明する。
- `OPEN` でクエリを実行し、`FETCH ... INTO` で取得した各行の列を COBOL のホスト変数に格納し、`CLOSE` でカーソルを解放する。
- `EVALUATE SQLCODE` で `0`、`100`（結果セットの正常終了）、エラー値を区別し、エラー時はゼロ以外の終了コードでプロセスを終える。
- 2 行のフィクスチャと空表フィクスチャを別々に実行し、「複数行 + EOF」と「空の結果セット」の二つの形を照合して、空の結果セットそのものは SQL 障害ではないと説明する。
- 容量の境界を二つ挙げる。表示用残高フィールドは整数部が 5 桁だけで、行カウンターは 3 桁だけ（999 行を超えると桁あふれで一周する）。

範囲：本課は結果セットの読み取りだけを扱います。`UPDATE/DELETE ... WHERE CURRENT OF` は行わず、`FOR UPDATE` も使いません。トランザクション、並行処理、コミット／ロールバックは扱わず、各プロセスでカーソルを開くのは一度だけです。サンプルデータベースはローカル SQLite ファイル（実際の SQL エンジンと実ファイル）ですが、Oracle/PostgreSQL/DB2 のカーソル動作を**代表するものではありません**。「空・単一行・複数行と EOF」の節にある「空表から空白レコードが一行返る」挙動は、このワークスペースのツールチェーンでのみ再現しています。ツールチェーンを検証したのも、本ワークスペースの x86-64 Linux + GixSQL v1.0.20b だけです。

## ツールチェーン：カーソルにもプリコンパイルが必要な理由

`EXEC SQL` の行は GnuCOBOL コンパイラだけでは解釈できません。まず GixSQL プリコンパイラで通常の COBOL 呼び出しに変換します。処理の流れは第29課と同じです。

```text
lesson.cob --(gixpp -e)--> 预处理 COBOL --(cobc -fstatic-call -lgixsql)--> 可执行文件

                                    运行期由 LD_LIBRARY_PATH 找到 libgixsql 与 SQLite 驱动
```

各コマンドの役割を混同すると、無駄な作業になりやすいので注意してください。

- `build.sh run` / `run-empty` はデータベースを再作成してから実行します。

**ツールチェーンがない場合に模擬 SQL で代用しないでください。**「未検証」を「実装済み」として文書に書くことになります。

## カーソルのライフサイクルとソースの読み方

ソースは [`lesson.cob`](./lesson.cob) を参照してください。以下では行番号順ではなく「データがいつ実際に動くか」の順に説明します。そうすると、頭の中の時間軸とコードが一致します。

### 1. `DECLARE` はクエリを登録するだけで、まだ一行も読まない

```cobol
           DECLARE ACCOUNT-CURSOR CURSOR FOR
               SELECT ACCOUNT_NO, CUSTOMER_ID, BALANCE
                 FROM ACCOUNT_SNAPSHOT
                ORDER BY ACCOUNT_NO
```

この `DECLARE` はクエリ文字列をカーソル名に登録するだけです。この時点ではデータベースは**取得を開始しておらず**、一行も読みません。最も直感に反する部分です。文を書けばすぐ実行されるように感じますが、カーソルが動き始めるのは `OPEN` です。

`ORDER BY ACCOUNT_NO` について補足します。これは**出力順**を決め、実行ごとの行順を同じにします。軽視しないでください。リレーショナルデータベースは返却順を保証しません。この句を外すと、ある実行では正しく見えても次の実行では順番が変わり、自分が何を変えたのか分からなくなることがあります。バッチ処理では「安定して再現できること」は自分で確保する必要があり、最初から保証されているわけではありません。

### 2. `OPEN` で初めて要求を送る

`2000-OPEN-CURSOR` は `OPEN ACCOUNT-CURSOR` を実行します。`SQLCODE = 0` の場合だけ `WS-CURSOR-OPEN` を `"Y"` にします。ソースのコメントが説明しているとおり、**正常にオープンできたカーソルだけを `CLOSE` できます**。`OPEN` に失敗すると `オープン=エラー SQLSTATE=` を出力し、失敗フラグを立てます。

`WS-CURSOR-OPEN` フラグの目的を覚えておいてください。「開けなかったものを操作しない」というルールを実装しています。実システムでは、リソースのオープンに失敗したのに使ったり閉じたりして、問題が起きることがよくあります。

### 3. `FETCH` ループ：`SQLCODE` の三つの結果と三つの処理

`3000-FETCH-ROWS` は `PERFORM UNTIL WS-DONE = "Y"` のループを使います。各反復で `FETCH ... INTO :WS-ACCOUNT, :WS-CUSTOMER, :WS-BALANCE` を一度実行し、その後 `SQLCODE` によって分岐します。

| `SQLCODE` | 意味 | 本課での動作 | 終了コードへの影響 |
|---:|---|---|---|
| `0` | 一行取得 | 件数を +1 し、`行=...` を表示してループ継続 | なし |
| `100` | 結果セットの終端（正常） | `取得=EOF SQLCODE=100` を表示し、`WS-DONE` を設定してループ終了 | なし |
| その他 | SQL エラー | `取得=エラー SQLSTATE=` を表示し、`WS-FAILED` と `WS-DONE` を設定 | `1` |

`SQLCODE = 100` は正常な業務結果です。「表に口座がない」という日常的な状況でバッチを中止するのは誤りです。逆に SQL エラーを「取得完了」と扱うと、本当のデータベース問題を隠してしまいます。そのため本課では `EVALUATE SQLCODE` を使って両者を明確に分け、まとめて扱いません。`build.sh` の `run` / `run-empty` では `GIXSQL_NOREC_CODE=100` を固定し、「データなし」が 100 と判定されるようにしています。

**失敗経路（実測済み）：** 本課のエラー分岐は設計上だけのものではありません。以下の二つは実際に実行しました。

| 注入方法 | 実際の出力 | 終了コード |
|---|---|---|
| `DATASRC` を存在しないディレクトリに向ける | `接続=エラー SQLSTATE=08001`、`行数=000`（接続が確立されないため、切断行は**ありません**） | `1` |
| データベースに `ACCOUNT_SNAPSHOT` 表がない | `接続=成功`、`オープン=エラー SQLSTATE=HY000`、`行数=000`、`切断=成功` | `1` |

二つ目のケースで起きる連鎖を追ってみましょう。`OPEN` に失敗すると `WS-CURSOR-OPEN` は `"N"` のままです。そのため `FETCH` と `CLOSE` をスキップします（開いていないカーソルは閉じられません）。接続は成功しているので切断は行います。最後に `WS-FAILED` によりプロセス終了コードが `1` になります。「どの段階を続け、どの段階を飛ばすか」の判断が、カーソルのライフサイクルの本当の難所です。

### 4. `CLOSE` と接続の切断

`4000-CLOSE-CURSOR` は正常な EOF または `FETCH` エラーの後に、**正常にオープンした**カーソルを閉じます。`9000-DISCONNECT-DATABASE` は `CONNECT RESET` を実行します。接続、オープン、読み取り、クローズ、切断のどれかが失敗すると、プロセスはステータス `1` で終了します（`STOP RUN RETURNING 1`）。これによりシェルのジョブがすぐ検知できます。スケジューラは画面を見ず、この数字だけを見ます。

### 5. 第29課の単一行検索との比較

| 比較項目 | 第29課 `SELECT ... INTO` | 本課のカーソル |
|---|---|---|
| 取得する行数 | 一回の検索で一行。複数行ならエラー | オープン後、100 になるまで一行ずつ取得 |
| クエリの開始時点 | SQL 文の実行時に検索 | `DECLARE` は登録だけ、`OPEN` で検索 |
| 終了状態 | `SQLCODE = 100` は「一致する行なし」 | `SQLCODE = 100` は「結果セットの終端」 |
| リソース解放 | 見えるカーソルなし | `CLOSE` が必要。正常にオープンしたカーソルだけを閉じる |

表の最後の行にある「同じ 100 でも意味が異なる」点に注意してください。第29課では `100` は「見つからない」、本課では「読み終えた」です。文脈で処理が変わるので、`SQLCODE` を判定するときは、カーソルが「一行検索」なのか「一括読み込み」なのかを明確にしてください。

## 空、単一行、複数行、EOF のケース

本課のテーマは結果セットの形と状態による分岐なので、四つのケースをすべて実行しました。下表は主な観測結果です（`行=` の行数が取得レコード数です）。

| ケース | フィクスチャ／作り方 | 主な実測出力 | 実行コマンド | 終了コード |
|---|---|---|---|---|
| 複数行（2 行） | `schema.sql` | `行=` が 2 行、`取得=EOF SQLCODE=100`、`行数=002` | `./build.sh run` | `0` |
| 空表 | `schema-empty.sql` | 空白の `行=` が **1 行**、`取得=EOF SQLCODE=100`、`行数=001` | `./build.sh run-empty` | `0` |
| 単一行 | クエリに `WHERE ACCOUNT_NO = 'A000000002'` を追加 | `行=` が 1 行（`A000000002`）、`行数=001` | [変更演習](#変更演習) の 2 を参照 | `0` |
| 複数行（3 行） | 3 行を挿入した一時フィクスチャ | `行=` が 3 行、`行数=003` | 手動でデータベースを作成後に実行 | `0` |
| 複数行（1005 行） | 1005 行を挿入した一時フィクスチャ | `行=` が 1005 行、ただし `行数=005` | 手動でデータベースを作成後に実行 | `0` |
| EOF | 各フィクスチャの末尾 | `取得=EOF SQLCODE=100`（100 によって発生。エラーではない） | 同上 | `0` |

**空表なのに空白レコードが一行表示されるのはなぜか。** 表に実際のデータがあるという意味ではありません。誤解しないでください。空のデータベースで `sqlite3 build/cursor.db "SELECT COUNT(*) FROM ACCOUNT_SNAPSHOT;"` を実行すると `0` なので、表に行がないことは確かです。しかし GixSQL v1.0.20b の SQLite ドライバーは、`OPEN` 後の**最初の** `FETCH` で `SQLCODE 0` を返し、口座番号と顧客番号をすべて空白、残高を `0` にします。`100` を返すのは**次の** `FETCH` です。この空白レコードは一行として表示され、`行数=` にも加算されるため、`行数=` の件数が表の実際の行数より 1 多くなります（ソースのコメントにも例外として記載しています）。[`expected-empty-output.txt`](./expected-empty-output.txt) には、想定上の `行数=000` ではなく、このツールチェーンでの**実際の**出力を記録しています。

**この挙動は本ツールチェーンに限られます。** 確認できているのは「本ワークスペースの GixSQL v1.0.20b + SQLite で再現した」ということだけです。別バージョンの GixSQL、Oracle/PostgreSQL/DB2、あるいは SQLite のネイティブ C API でも最初の `FETCH` が空白レコードを返すとは推測できません。空になる可能性のあるクエリにカーソルを使う場合は、本番投入前に対象ドライバーで「最初の FETCH がどの SQLCODE を返すか」を個別に検証してください。これが本課から持ち帰ってほしい技術習慣です。

## 容量の境界（実測済み）

ソースにはデータ範囲より小さいフィールドが二つあります。上限を超えると気付かれないままデータが失われるため、覚えておいてください。

| フィールド | 宣言 | 上限と実測動作 |
|---|---|---|
| `WS-EDITED-BALANCE` | `PIC 9(5).99` | 整数部は 5 桁だけ。残高 `1234567.89` を挿入すると実際の表示は `BALANCE=34567.89`（上位桁が失われる）。`WS-BALANCE` 自体は `PIC S9(7)V99` で値を保持できますが、**表示用コピー**には入りません。 |
| `WS-ROW-COUNT` | `PIC 9(3)` | 3 桁だけ。1005 行を挿入すると、1005 行すべてを一行ずつ取得しますが、最後の表示は `行数=005`（下位 3 桁だけ）です。 |

この二つは**実装された動作**にある実際の制限で、エラー処理ではありません。エラーも失敗フラグも出ないため、出力から問題に気付けません。フィールド宣言のコメントにも記載されています。本番で行数が気付かれずに一周すると、照合の最初の段階ですでに誤りです。数字は正常に見えても実際には 1000 行少なくなっています。

## 実際の業務フローをたどる

このカーソルバッチを月末夜間処理に置くと、次のような流れになります。

1. **午前 2:10：** 日次締め処理が口座残高スナップショットを `ACCOUNT_SNAPSHOT` データベース表に書き込みます。スケジューラがバッチを起動し、本課のカーソルが最初の工程として、スナップショット全体を COBOL で処理できるレコード列に変換します。
2. **同日の早い時間または夜間：** 基幹システムもファイル形式で口座スナップショットを出力します。第31課ではファイルを一行ずつ読み、口座番号を使ってデータベースから対応する口座を検索し、両者を**キーで照合**します。「両方にあり一致」「両方にあるが金額が異なる」「片方にしかない」に分け、差異一覧を作ります。データベース側の検索は主キーによる単一行検索ですが、データベースのデータを一括として扱い、一行ずつ処理する規律は本課で身につけます。つまり本課はデータベース側を漏れなく読み、第31課は両側を突き合わせます。
3. **実行記録を残す：** 本課の最後に出る `行数=` はログ（第27課のログ体系）に記録します。翌日、当直担当者はその数を上流の口座件数報告と照合します。不一致なら途中で行を読み飛ばしたか、重複して読んだ可能性があります。
4. **最後に統合する：** 第32課の銀行照合プロジェクトでは、ファイル読み込み、データベースの検索／書き込み、照合、結果出力、レポート、障害後の再実行を一つのバッチにまとめます。第32課はデータベース側で主キーによる単一行検索を使いますが、「データは一括なので、一行ずつ漏れなく処理し、件数を数える」という規律の出発点は本課です。カーソルを使うかどうかは、その課題が一括データを処理するか一件を処理するかで決まります。

一言でまとめると、**本課は SELECT の書き方ではなく、表全体を確実に「読み切り」、どこまで読んだかを明確に把握する方法を学びます。** この能力は後続の各課でも使います。

## このコードを本番に入れた場合

- **誰がスケジュールするか：** 通常「データベーススナップショット準備完了」の確認後に実行する夜間バッチスケジューラです。見るのは実行ファイルの有無と終了コードの二つだけです。
- **誰が出力を見るか：** 当直担当者が最初に終了コードを見て、次に `行数=` を確認します。数万行のはずなのに 002 と出るなど、件数が明らかに違えばその夜のうちに調査します。
- **障害時に誰が呼び出されるか：** 終了コードが `0` 以外なら警報が発生します。接続失敗（`SQLSTATE=08001`）、表の欠落（`HY000`）、読み取りエラーを `1` で終了させているのは、必要なときに警報を出すためです。
- **次のシステムへの受け渡し：** 本課で学ぶデータベースの行単位走査を使い、次の第31課でデータベースとファイルのスナップショットを照合し、続いて第32課の照合プロジェクトに進みます。本課はデータ取得だけを担当し、データベースは変更しません。
- **最初の一か月で起こりやすい障害：**
  1. `SQLCODE = 100` を障害扱いする → 実際は何も間違っていないのに毎日「失敗」となり、やがて警報を真剣に見なくなる。
  2. 本ツールチェーンで空表から空白行が出たのを見て「どのドライバーも同じ」と思い込む → 別のデータベースでは空結果の動作が想定と異なる。
  3. 行カウンターが一周する、または表示用残高フィールドが切り詰められる → 出力は正常に見えても数字が間違っている。

証明範囲も明確にしてください。本課で確認したのは、**「ローカル SQLite + GixSQL v1.0.20b では、このカーソル処理が想定どおりに動き、一度だけ読み取る」**ことだけです。更新可能カーソル（`FOR UPDATE` / `WHERE CURRENT OF`）、データベース方言をまたいだカーソルの挙動、トランザクション境界と並行処理、SQL 失敗後の部分書き込みや再実行方針は範囲外です。ここで動いたことを本番保証とみなさないでください。

## 根拠と未検証項目

**根拠：** 上記の「実際の出力／終了コード」はすべて、本ワークスペースで `lesson.cob` に対して `./build.sh check`、`build`、`run`、`run-empty` を実行して確認したものです。一行、3 行、1005 行、桁あふれする残高のデータベースも手作業で作成しました。`SQLCODE 100` とエラー分岐の `SQLSTATE`（接続失敗 `08001`、表の欠落 `HY000`）も推測ではなく実測値です。

**未検証：** `CLOSE` 失敗分岐（`クローズ=エラー`）と `FETCH` 途中のエラー分岐は、本環境で**安定して再現できませんでした**。コードパスはありますが、実行できていないため、実測結果としては報告できません。「空白レコード」が他の GixSQL バージョンやデータベースドライバーでも発生するかも未検証です。
