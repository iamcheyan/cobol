# 第 15 课：顺序读取每日交易文本——先分清“文件没到”和“文件是空的”

银行每天把当日交易以文本文件送进批处理目录，程序得自己打开它、按送达顺序逐行读完，并把“读完了”和“文件根本打不开”报成两种不同的结果。本课用四行 [`transactions.txt`](./transactions.txt) 把这条输入流程搭起来：`SELECT` 和 `FD` 负责把程序和真实文件绑在一起，`OPEN INPUT` 检查打开结果，`READ` 配 `AT END` 把文件走到底，最后在标准输出报告实际读到的条数。

## 业务现场

凌晨两点，值班室里没人在敲键盘。日终批次的第一个作业已经跑完，第二个作业正等着上游把当天的交易导成一个文本文件、扔进约定目录。**批处理的第一步往往不是算账，是等文件。**

等文件最怕的是两种结局被报成一样：

- **文件根本没送到。** 上游生成失败，或者传输卡住了。这是事故——值班的人得立刻知道，去重传、去重跑。程序要是安静地报个成功，这批交易就凭空消失，没人会去找。
- **文件送到了，但是空的。** 这是合法情形：周末、节假日，或者那天确实一笔都没有。它不该惊动任何人。
- **还有最阴的第三种：文件读了一半就停了。** 程序没认出结尾，把“读到一半”当成“读完了”，照样报成功，实际漏掉一批。

所以这一步的验收标准只有一句话：**“没送到”和“是空的”必须分得开——因为它们后面要做的事完全相反。** 混在一起，你要么每天半夜被假警报叫醒，要么真丢了一批交易却没人知道。本课要讲的，正是把这件事做成的那几个零件：`SELECT`/`FD`/`FILE STATUS` 把程序和文件绑定，`READ` 按送达顺序逐行取记录，`AT END` 认结尾。

（教学演示：这里的时点、机构、交易都是编的，不是某家真实机构的真实数据；本课也不声称达到任何审计或监管要求。）

## 为什么现在学

前 09–14 课你已经能给记录搭层级、用 `REDEFINES` 换角度看同一段字节、用 `OCCURS` 建表并按 `SEARCH ALL` 查找。但这些记录有个共同点：**全写死在源码里**。写死的数据从不迟到、不会缺失，也不会某天突然变成三倍。

真实批处理的第一道门就在这儿：数据得从程序外面进来。

你可能会想，读文件有什么难的，`open()` / `readline()` 我熟。对，思路是熟的，但 COBOL 把这件熟事摊到了好几处声明上，而每一处都对着一个业务判断：

- 文件叫什么、在哪个目录：写在 `SELECT ... ASSIGN TO` 里，是**运行时当前工作目录**下的相对路径，不是命令行参数；
- 每读一条放在哪：由 `FD` 下面的记录项决定，本课是 `PIC X(100)` 的缓冲区；
- 这一步成没成：看 `FILE STATUS IS` 收到的两位状态码；
- 读到头了：不是错误码，是 `READ` 的 `AT END` 分支。

四件事凑齐，你才能回答值班的人那一句——“今天这批到底读到没有？”

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 它给程序加了一种新能力：**从外部文件按行取数据**。`FILE-CONTROL` 的 `SELECT` 给文件起个 COBOL 里的名字并绑到真实路径，`FILE SECTION` 的 `FD` 声明每条记录读进哪个缓冲区，`READ` 一次取一行，`AT END` 告诉你取完了，`FILE STATUS` 让你能问“刚才那步到底成没成”。

**它在业务里解决什么问题。** 它把“文件到没到”从一句嘴上的猜测，变成程序能判断、值班的人能据以行动的事实：

| 结局 | 程序怎么报 | 值班的人怎么接 |
|---|---|---|
| 打不开 | `オープン=FAILED STATUS=35` + 退出码 `1`，不做任何 `READ` | 报警：先查上游有没有出文件，再决定重传还是重跑 |
| 打得开、一条没有 | `EOF=はい レコード数=00` + 退出码 `0` | 不用管：今天没有交易 |
| 打得开、有数据 | 逐条 `レコード=`，末尾 `レコード数=04` + 退出码 `0` | 拿这个条数跟上游报的条数对 |

最后那一栏值得多说一句。**“实际读到多少条”是后面对账的起点**：它跟上游说的条数对不上，就说明中途有事。本课只负责把这个数如实报出来，怎么核、核不上怎么办是后面的事。

**什么时候不该拿它当“读对了”。** 本课只做认文件、读行、认结尾，文件里的内容它一个字都不看：不按竖线拆字段、不校验日期/类型码/账户号/金额，也不拒绝任何记录。拿“读完了”去证明“读对了”，是这课最常见的误用——程序一声不响地读完 12 万行乱码，表面上跟顺利收工一模一样。字段解析与校验要到[第 18 课](../18_csv-processing/README.md)和[第 26 课](../26_error-handling/README.md)。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `FILE-CONTROL` 的 `SELECT ... ASSIGN TO "transactions.txt"` 把 COBOL 文件接到**运行时当前工作目录**下的真实文本文件，并用 `FILE STATUS IS` 保存每次 I/O 的状态码。
- 用 `ORGANIZATION IS LINE SEQUENTIAL` 加 `FD` 的 `01 FD-TRANSACTION-RECORD PIC X(100)` 描述行顺序文本，说明行长可变、FD 记录区固定 100 字符、短行右侧补空格、超过 100 字符的行被拆成多条记录。
- 用 `PERFORM UNTIL` 加 `READ ... AT END` 读完全部记录，并说明 EOF 是正常结束、EOF 分支不增加记录数。
- 从标准输出核对三个结果：四行夹具报告 `EOF=はい レコード数=04`；空文件报告 `00`；文件缺失报告 `オープン=FAILED STATUS=35` 并以退出码 `1` 结束。
- 用内容比对证明本程序只读输入，不创建、不覆盖任何数据文件。

边界：程序把整行当作一段文本，只计数和显示，不按竖线拆字段、不校验日期/类型码/账户号/金额，也不拒绝任何记录；这些判断要等[第 18 课](../18_csv-processing/README.md)和[第 26 课](../26_error-handling/README.md)。文件缺失时它在 `READ` 之前就结束，因此不会执行 `CLOSE`，也没有日志或资源回收。记录计数域只有两位，超过 99 条会回绕，本课不处理这个上限。

## 文件输入到底多了什么

### 内存里的表和文件里的行，差在哪

内存里的 `OCCURS` 表格，条数和内容你在写源码时就定死了；文件里的条数、行长和内容都由程序外部决定，程序只能在运行时一条条去取。所以文件课一上手就多了两件必须应付的事：**条数不确定**（可能 0 条，也可能几十万条）和**结果不确定**（可能根本打不开）。前一件用 `PERFORM UNTIL` 加 `AT END` 收进循环条件，后一件用 `FILE STATUS` 变成可判断的状态码。

### 一行到底在哪里结束：行顺序和定长记录不是一回事

`ORGANIZATION IS LINE SEQUENTIAL` 说的是：这个文件按**行**组织，一行的结束符（Linux 上是换行符）就是记录边界，所以行长可以各不相同。另一种常见输入是“定长记录”——每条记录固定 N 字节、没有换行符：

| | 记录边界由谁定 | 行长 | 在哪一课 |
|---|---|---|---|
| 行顺序（本课处理这种） | 换行符 | 可变 | 第 15 课 |
| 定长 | 固定字节数 | 必须由接口约定 | [第 17 课](../17_fixed-length-files/README.md) |

接着是这个课最容易看错的一行：

```cobol
FD TRANSACTION-FILE.
      * FD 记录区固定 100 字符，短行右侧补空格。
       01 FD-TRANSACTION-RECORD PIC X(100).
```

`PIC X(100)` **不是**“每行 100 字符”，它是**读入缓冲区的大小**：每次成功的 `READ` 把一整行塞进这 100 字节，不足的右边补空格；超过 100 字符的行塞不下，会被切成连续的 100 字符记录一条条读出来。所以 `FUNCTION TRIM(... TRAILING)` 只在显示时去掉补齐的空格，它不改记录区，也不代表文件里真存了空格。

这也是一个容易出事故的地方：最长行长必须由上游约定，本课不校验。上游哪天多加一个字段、行长顶过 100 字符，程序不会报错，只会把那一行悄悄切成两条记录——条数对不上，字段还从中间断开。

### `FILE STATUS` 和 EOF 不是一码事

`FILE STATUS IS WS-FILE-STATUS` 让每次文件操作之后的状态码落进 `WS-FILE-STATUS`。本课只检查 `OPEN` 和 `CLOSE` 之后的值：

| 操作 | 状态码 | 含义 |
|---|---|---|
| `OPEN INPUT` 成功 | `00` | 文件已打开，可以 `READ` |
| `OPEN INPUT` 文件缺失 | `35` | 本课工具链实测值，程序据此报告 `オープン=FAILED` 并退出码 `1` |
| `CLOSE` 成功 | `00` | 文件已关闭 |

EOF 不走状态码分支，而是由 `READ` 的 `AT END` 分支表达：读完最后一条后的那次 `READ` 找不到下一行，于是执行 `AT END`，把 `WS-END-OF-FILE` 置为 `"Y"`，循环随之结束。这就是“EOF 不是错误”的由来——它是正常读完的标志，真正的错误是打不开文件。作为参考，本工具链在 EOF 时也会把文件状态置为 `10`（用临时探针程序观察，本课源码不读取该值）。

## 输入与规则

**输入夹具**：[`transactions.txt`](./transactions.txt)，竖线分隔的可见文本，本课不解析字段。

| 项 | 值 |
|---|---|
| 文件名与位置 | `transactions.txt`，运行时当前工作目录（硬编码在 `ASSIGN TO`） |
| 组织 | `LINE SEQUENTIAL`，一行一条记录，行结束符为换行符 |
| 行数 | 4 |
| 各行可见字符数 | 43、53、42、53（合计 191） |
| 文件总字节数 | 195（191 个可见字符 + 4 个换行符） |
| 分隔字段数 | 每行 5 或 6 段（转账行多一个收款账户），本课不检查段数 |
| FD 记录区 | `PIC X(100)`；短行右侧补空格至 100 字节 |
| 排序与唯一性前提 | 无：程序按物理顺序读出，既不要求有序也不查重 |

夹具第一行的原始内容（竖线只作可读分隔，本课不解析）：

```text
DAY-20261013|TXN-000001|D|0001234567|125.50
```

**由代码校验的条件**（源码里真的有对应分支）：

- `OPEN INPUT` 之后 `WS-FILE-STATUS` 是否为 `00`；不是则打印状态、置退出码 `1`、`STOP RUN`，不执行任何 `READ`。
- 每次 `READ` 是否到达文件尾（`AT END` / `NOT AT END`）。
- `CLOSE` 之后状态是否为 `00`，否则打印 `クローズ=FAILED` 并置退出码 `1`。

**仅由夹具或上游保证的条件**（本课不校验）：

- 文件存在、可读、是文本行，且每行不超过 100 字符——本课把这几项当作上游前提，不做校验。
- 每行字段个数、日期、类型码、账户号、金额的业务合法性：本课一概不检查（连段数都不数），夹具内容只作演示数据；字段解析与校验留给第 18、26 课。

**边界与故障政策**：

- **空输入**：空文件是合法输入，能成功打开，第一次 `READ` 立即 `AT END`，记录数报告 `00`，退出码 `0`。
- **空行**：文件中间的空行也是一条记录——会被 `READ` 成功读出、计数加一，`TRIM` 之后显示为空的记录行。
- **文件末尾没有换行符**：最后一行仍会被读出（行顺序读取不依赖文件以换行符结束）。
- **输入过长**：超过 100 字符的行会被拆成多条记录，总记录数因此大于物理行数；最大行长必须由上游约定。
- **打开失败**：报告真实状态码并用退出码 `1` 结束；本课不关闭文件、不写日志。

## 源码阅读路径

读这份源码别从第一行顺着念，按“状态什么时候变”来读更省事。完整源码见 [`lesson.cob`](./lesson.cob)。

| 位置 | 职责 | 关键语句 | 状态变化 |
|---|---|---|---|
| `FILE-CONTROL` 的 `SELECT TRANSACTION-FILE` | 绑定外部文件与状态域 | `ASSIGN TO`、`ORGANIZATION IS LINE SEQUENTIAL`、`FILE STATUS IS` | 之后每次 I/O 都会刷新 `WS-FILE-STATUS` |
| `FILE SECTION` 的 `FD` 与 `01` 记录项 | 定义 100 字符读入缓冲区 | `FD`、`PIC X(100)` | 每次成功的 `READ` 覆盖这 100 字节 |
| `0000-MAIN` 开头 | 打开并分流 | `OPEN INPUT`、`IF WS-FILE-STATUS NOT = "00"` | 成功 → `00` 继续；缺失 → `35` 并结束（退出码 1） |
| `0000-MAIN` 循环 | 驱动逐条读取 | `PERFORM UNTIL WS-END-OF-FILE = "Y"` | 退出条件由 `AT END` 置位，不由计数控制 |
| `1000-READ-ONE-RECORD` | 读一条并按结果分流 | `READ`、`AT END`、`NOT AT END`、`ADD 1`、`FUNCTION TRIM` | 成功 → 计数 +1、打印该行；EOF → 置标志、计数不变 |
| `0000-MAIN` 收尾 | 报告、关闭 | `DISPLAY "EOF=..."`、`CLOSE`、状态检查 | EOF 行在关闭之前打印；关闭失败同样置退出码 1 |

## 运行与观察

程序会以**运行时当前工作目录**去找 `transactions.txt`，所以下面把夹具复制到临时目录，再在临时目录里运行，仓库内不会留下任何产物。

```sh
cd lessons/15_sequential-file-read                # 进入本课目录（或任意包含 lesson.cob 的路径）
scratch_dir=$(mktemp -d)
trap 'rm -rf "$scratch_dir"' EXIT                 # clean：退出 shell 时删除临时目录

cobc -fsyntax-only lesson.cob                     # check：只做语法分析，不生成可执行文件
cobc -x -Wall -o "$scratch_dir/lesson_15" lesson.cob   # build：生成可执行文件到临时目录
cp transactions.txt "$scratch_dir/"               # 复制夹具副本，不碰仓库文件
( cd "$scratch_dir" && ./lesson_15 )              # run：从夹具所在目录执行
echo $?                                           # 查看退出码
```

`-fsyntax-only` 只验证源码能否被解析；`-x` 才生成可执行文件；`run` 必须让当前工作目录包含夹具；`clean` 在本课就是删掉上面这个临时目录。

**预期结果（正常路径）：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，无编译诊断 |
| 标准输出 | 7 行，见下方代码块 |
| 进程退出码 | `0` |
| 生成文件 | 临时目录内只有可执行文件与夹具副本；程序不生成数据文件 |
| 夹具变化 | 无。夹具内容与运行前一致（运行前 `md5sum transactions.txt` 为 `a715090ba2436ed2a9feedf549558e77`） |

```text
オープン=OK
レコード=DAY-20261013|TXN-000001|D|0001234567|125.50
レコード=DAY-20261013|TXN-000002|T|0001234567|0007654321|40.00
レコード=DAY-20261013|TXN-000003|D|0002468101|75.00
レコード=DAY-20261013|TXN-000004|T|0007654321|0009999999|20.00
EOF=はい レコード数=04
クローズ=OK
```

**输出对照（日文输出 → 含义）：** `オープン=OK` = 打开成功；`オープン=FAILED STATUS=xx` = 打开失败并给出文件状态码；`レコード=` = 成功读出的一条原始行；`EOF=はい レコード数=nn` = 已到文件尾、成功读出的记录数；`クローズ=OK` / `クローズ=FAILED` = 关闭结果。`はい` 意为“是”。仓库约定程序输出用日文；判断行为以实际输出和本节的中文说明为准。

**空文件路径：**

```sh
: > "$scratch_dir/transactions.txt"      # 清空夹具副本
( cd "$scratch_dir" && ./lesson_15 )     # 退出码 0
```

```text
オープン=OK
EOF=はい レコード数=00
クローズ=OK
```

空文件仍然可以打开，所以没有失败信息；区别只体现在一条 `レコード=` 都没有、计数为 `00`。

**文件缺失路径：**

```sh
rm -f "$scratch_dir/transactions.txt"    # 让当前目录里没有夹具
( cd "$scratch_dir" && ./lesson_15 )     # 退出码 1
```

```text
オープン=FAILED STATUS=35
```

这一次输出停在打开失败：没有 `EOF=` 行，也没有 `クローズ=` 行，因为程序在 `READ` 之前就结束了。状态码 `35`、退出码 `1` 就是判断“文件没到位”和“文件读完了”的事实依据——两者一个要打电话，一个不用管。

**实际观察到的环境细节：** 在本工作区运行可执行文件时，标准错误会输出 `Warning: program compiled against libxml 212 using older 209`。这是运行环境链接库版本警告，不是程序的业务输出（业务输出全部写在标准输出）；其触发组件尚未定位。

## 走一遍真实流程

把这一课放进那条夜链，它前后是这样接的：

1. **文件从哪来。** 上游系统把当日交易导成文本、落进约定目录。这一步不在本课程里，是别人的作业；你的程序只被保证“文件会在某个时刻出现在当前工作目录”。
2. **本课这一环。** 打开、逐行读、认结尾、报条数。产物就三行结论：打开了没有、读了多少条、关了没有。
3. **往下走。** 读出来的记录交给[第 16 课](../16_file-writing/README.md)写成接受/拒绝结果文件；换成定长记录是[第 17 课](../17_fixed-length-files/README.md)；同时读多个流、按顺序匹配是[第 19](../19_multiple-files/README.md)、[20 课](../20_file-matching/README.md)；[第 22 课](../22_file-processing-practice/README.md)把它们串成端到端批次；[第 26 课](../26_error-handling/README.md)补上错误分类和资源清理，[第 27 课](../27_logging/README.md)把条数和失败写进日志，[第 32 课](../32_bank-reconciliation-project/README.md)是这条链的终点。
4. **谁在看这条路。** 值班的人看退出码；第二个来问 `レコード数` 的人是拿它对上游条数的人。这两个数对得上，这条链才算走通。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器，通常排在“文件就绪检查”后面——真实系统会先等文件出现、等大小不再变化，再拉起这个作业。本课没有这个检查，文件没到它就直接报失败。
- **谁看它的输出**：值班的人先看退出码，`0` 就是这批读完了；`レコード数` 会有人拿去跟上游核对。
- **出事谁被叫起来**：文件缺失、退出码 `1`，调度器报警，值班的人先确认上游到底出没出文件，再决定重传还是重跑。这正是本课坚持把“没送到”和“空文件”分开报的原因——分不开，半夜的电话就白打了。
- **下一个系统怎么接**：读出来的记录给[第 16 课](../16_file-writing/README.md)写结果文件；条数和失败进[第 27 课](../27_logging/README.md)的日志。
- **第一个月最容易出的事故**：两件。一是把“空文件”和“文件没到”当成一件事处理，要么天天被假警报叫醒，要么真丢了交易没人知道。二是上游哪天把行长顶过 100 字符，程序不吭声，只把它切成两条记录，等计数对不上时已经是第二天早上了。
- **它还没做的事**：解析字段、校验记录、写结果文件、写日志、重跑策略，以及打开失败后的资源清理。文件缺失时它连 `CLOSE` 都不执行。字段解析与校验在第 18、26 课，错误分类与资源清理在第 26 课，结果文件在第 16 课，日志在第 27 课，重跑策略要到[第 31](../31_data-synchronization/README.md)、[32 课](../32_bank-reconciliation-project/README.md)。

说到底，本课证明的是“在四行夹具上，打开、逐行读、认 EOF、报条数这四步分别走对了”——**不是**“这就是一个能上线的批次入口”，更不是任何合规或审计保证。
