# 第 22 课：综合练习——排序、校验、匹配与一次说清去向的写出

这一课交付的是一个小批次：接一份乱序的交易文件、一份排好序的账户主档，跑一遍，交出**接受文件、拒绝文件、仅主档清单和控制计数**四样东西，而且四样必须互相对得上。本课不加新语法，只把第 15–21 课的零件接成一条能被人和系统接手的流水线，同时讲清"跑到一半失败时，目录里会剩下什么"。

## 业务现场

周五夜里，日终批次轮到对账这一环。上游两个作业刚把文件扔进工作目录：账户主档是白天从主机抽出来的，按账户号升序排好了；交易文件是柜面和手机银行一天的流水按录入顺序导的，**顺序是乱的**，而且没人保证每笔交易都能在主档里找到对应的账户。

这一环跑完之后，东西不是交给屏幕，而是交给别人：

- 接受明细交给下一个作业去过账；
- 拒绝明细交给运营——明天上午客户打电话问"我那笔为什么没到账"，柜面查的就是这个文件；
- 仅主档账户要给对账的人，那是"有账户、当天没动"的名单；
- 几个计数要跟上游报的笔数核一遍。

所以"程序跑完了"和"这批能交出去"是两件事。跑完了只说明进程退出了；能交出去，意味着**每一笔都有交代，每条主档都被认领过一次，而且这几个数能对得上**。

这里有个不太体面但必须说的事实：两个结果文件是 `OPEN OUTPUT` 打开，**每次运行都会把上一次的内容覆盖掉**。要是跑到一半挂了（读主档出错、磁盘写不进去），目录里留下的是**半份结果**——不是旧的那份，也不是完整的新那份。没有回滚，也没有"失败就以旧文件为准"这回事。所以交出去之前，计数和文件行数必须一次核到位。

（教学演示：这里的机构、账户号、金额、批次日时都是编的，不是哪家真实机构的真实数据。）

## 为什么现在学

读文件、排序、按键匹配、写结果文件，这四个动作你分开都做过一遍。真正没做过的是：**让它们在同一次运行里交接**。

分开练的时候，每份夹具都只演一个概念——第 21 课的输入只是"没排序"，第 20 课的输入只是"两边都有序"，第 16 课的结果早就分好了类。真实批次不给你这种待遇：扔给你的一坨数据里，同时有无序的记录、找不到主档的账户、类型打错的交易、金额混进字母的脏数据，还有整整一条主档记录压根没有交易。

你要在一次跑里把它们全部分开、各自留下痕迹，还要能回答那两句最讨厌的问题：**"这条记录去哪儿了？""这批是不是一条都没漏？"** 前者靠拒绝原因和文件行数，后者靠计数不变量。这就是这一课真正要练的东西——不再是"某个语法对不对"，而是"这一环能不能交付"。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 说白了，没有任何新语法。要做的事就一句：把已经会的四件事排成固定顺序——先 `SORT` 把交易按账户号排好，再和主档做一次从头到尾的顺序匹配，匹配上的按规则校验后分进两个结果文件，最后把计数打出来。顺序匹配的老规矩还在：两边键相同就配成一对，谁小谁先走一步。

**它在业务里解决什么问题。** 两条，都很实在。

第一条是**每条记录都要有交代**。办法是把去向写成两个等式：

- `接受记录数 + 拒绝记录数 = 输入记录数`。一笔交易不是进接受，就是进拒绝，没有第三种结局，也不能两边都进。
- `主档匹配数 + 仅主档记录数 = 主档记录数`。每条主档记录都被认领一次，没被交易碰过的那些就是"仅主档"。

两个式子一摆，谁都能拿计算器当场验。组长问"这批有没有漏"，你不用翻日志，直接念数。

第二条是**失败时的产物状态**。输出文件是覆盖打开的，程序又是边跑边写，所以中途出错时，目录里是"写了一半的新结果"，覆盖掉的旧结果要不回来。知道这一点，你才知道为什么跑完必须核对计数和行数，而不是看到退出码 0 就觉得万事大吉。

**什么时候会栽、用错会怎样。** 三句话：

- 别把这一课当成"过账"。它只**分类和写出**，不动余额、不套借贷规则。把它说成"账已经记好了"是要出事的。
- 别把顺序匹配的前提当成程序保证。主档必须升序且账户号唯一，这是上游的前提，**本程序不检查**；主档逆序或键重复，匹配会悄悄漏报。
- 别把两个文件的写出说成"原子交付"。两次 `OPEN OUTPUT` 加两次 `WRITE`，中间任何一步失败都可能留下不完整结果，这个承诺本课没有。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `SORT` 与 `INPUT PROCEDURE`/`RELEASE` 把未排序交易整理成升序，并在释放前检查记录宽度。
- 在一次归并扫描中把每条交易归为"已接受""因无主档被拒""因字段非法被拒"，把剩余主档账户记为仅主档。
- 分别写出 `accepted.txt` 与 `rejected.txt`，并逐行核对文件内容与记录宽度。
- 用计数不变量检查无遗漏：`接受 + 拒绝 = 输入记录数`、`主档匹配数 + 仅主档 = 主档记录数`。
- 说明 `OPEN OUTPUT` 会覆盖旧结果文件、排序的前提和本课不做的账务控制。

边界：程序只做**分类与写出**，不累计余额、不实施借贷金额规则、不提供双文件原子交付；主档必须已升序且键唯一，但程序**不校验**顺序与重复键。重复交易账户不受支持。批次标识、重跑策略、输出原子交付与金额规则属于第 26–32 课。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端；本课不依赖数据库或附加工具。
- `SELECT` 使用相对文件名，程序在**当前工作目录**读写 4 个文件：读 `transactions-unsorted.txt`、`accounts.txt`，写 `accepted.txt`、`rejected.txt`。
- 两个输出用 `OPEN OUTPUT`，**每次运行都会覆盖同名旧文件**。因此本课在 `build/` 目录里准备一份输入副本再运行，避免把结果写进源码目录；`build/` 已被仓库忽略。

## 输入与输出记录

先看两边手里都是什么，再看程序写回去什么。

| 文件 | 字段顺序 | 字段宽度 | 记录宽度 |
|---|---|---:|---:|
| `transactions-unsorted.txt`（输入） | 账户号、类型、金额分 | 10 + 1 + 9 | 20 |
| `accounts.txt`（输入） | 账户号、客户号、余额分 | 10 + 8 + 9 | 27 |
| `accepted.txt`（输出） | 账户号、客户号、类型、金额分 | 10 + 8 + 1 + 9 | 28 |
| `rejected.txt`（输出） | 账户号、原因、类型、金额分 | 10 + 10 + 1 + 9 | 30 |

金额九位数字表示 `PIC 9(7)V99`，`V` 不占物理字符：`000012550` 表示 `125.50`。输入每行一条记录、没有分隔符，换行符不计入 `FD` 宽度。

账户主档是排好序给的（`A000000001`、`A000000003`、`A000000005`、`A000000007`、`A000000009`），交易文件则故意打乱。夹具里同时塞进了四类情况：匹配得上且字段合法的、压根没有主档的、类型写错的、金额混进字母的，外加一条没有交易的主档账户。

拒绝原因固定为十字符：`NO_ACCOUNT`、`BAD_TYPE__`（不足十位处以 `_` 补齐）、`BAD_AMOUNT`。**先查主档再查字段**，所以找不到主档的交易直接记 `NO_ACCOUNT`——哪怕它的类型和金额也一塌糊涂，原因也不再算字段错误。这个顺序是有意的：没有账户，谈字段合法性没有意义。

## 一次跑完，每条记录都去了哪儿

1. 主程序直接调用 `SORT ... ON ASCENDING KEY SD-TRANSACTION-ACCOUNT`，把排序和分类写在一句里。
2. `1000-LOAD-TRANSACTIONS` 打开交易输入；每行先量实际宽度，只有 20 字符的记录才 `RELEASE` 进排序工作文件——短一行、长一位，整批就当场停。
3. `2000-RECONCILE-TRANSACTIONS` 打开主档和两个结果文件，先把第一条主档读进来。
4. 输出过程逐条 `RETURN` 排序后的交易：主档键更小，说明这条主档没有交易，计为仅主档后读下一条；两键相同，进入校验；交易键更小、或者主档已经读完，就判为没有主档。
5. 匹配上主档的，类型必须是 `D` 或 `C`、金额必须全是数字：合法的写 `accepted.txt`，不合法的写 `rejected.txt` 并带上原因。
6. 交易处理完，剩下没被认领的主档账户逐条计为仅主档。程序关掉所有打开的文件、显示计数；`SORT`、读、写、关闭任何一步报错，都会让返回码变成非零。

## 计数不变量：两个数就能回答"有没有漏账"

本课夹具：交易 6 条、主档 5 条。

| 不变量 | 代入本课 | 含义 |
|---|---|---|
| `接受记录数 + 拒绝记录数 = 输入记录数` | `3 + 3 = 6` | 每条交易都留下了痕迹，去向只有一个 |
| `主档匹配数 + 仅主档记录数 = 主档记录数` | `4 + 1 = 5` | 每条主档记录都被认领一次；主档匹配数 = 输入记录数 − 无主档拒绝数 = `6 − 2` |

光看计数还不够，两个文件的行数也得对上：`accepted.txt` 3 行、`rejected.txt` 3 行。标准输出、两个结果文件三方一起核，才算确认这批自洽——只报一个汇总数字，出了事你连丢的是哪一条都说不出来。

## 出错和边界：哪些会让你白跑一晚

- 交易行宽必须为 20、主档行宽必须为 27；量出来不对就中止批次并返回非零码，不会"凑合着读"。
- 交易类型只允许大写 `D` 和 `C`；金额字段必须全为数字。别小看这两条，交易所导出的脏数据基本就栽在这里。
- `OPEN`/`READ`/`WRITE`/`CLOSE` 状态与 `SORT`/`RELEASE`/`RETURN` 结果都参与错误判断；EOF 状态 `10` 是正常结束，不算错误。
- 输出用 `OPEN OUTPUT`：目录没权限、磁盘写满，会让打开或写入失败。**失败的批次不能当作成功交付**，此时目录里可能留着半份结果。
- 主档顺序与唯一键由上游保证，程序不扫描校验，也不处理同一账户的多笔交易。
- 输入、排序、分类的计数字段都是三位数字，这个微型夹具的上限是 999 条；真上生产得按最大规模重新选宽度。
- 本课不累计余额、不提供原子化的双文件交付；重复键、回滚、批次标识与输出交付策略要等后面几课再谈。

## 运行与观察

**输入：** 本课目录下的 `transactions-unsorted.txt`（6 行）与 `accounts.txt`（5 行）。它们被复制进 `build/`，程序也在 `build/` 里运行并写出两个结果文件。

**命令及作用：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                    # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_22 lesson.cob      # 编译，可执行文件也放进 build/
cp accounts.txt transactions-unsorted.txt build/ # 把输入副本放进同一个工作目录
(cd build && ./lesson_22)                        # 在 build/ 里运行，结果文件写在这里
echo $?                                          # 查看退出码
rm -rf build                                     # 一次清掉可执行文件、输入副本与结果文件
```

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，无编译诊断 |
| 标准输出 | 10 行，见下方代码块 |
| 进程退出码 | `0` |
| 生成文件 | `build/accepted.txt`（3 行）、`build/rejected.txt`（3 行） |

```text
ACCEPTED 账号=A000000001
ACCEPTED 账号=A000000003
被拒绝 账号=A000000004 REASON=NO_ACCOUNT
ACCEPTED 账号=A000000005
被拒绝 账号=A000000006 REASON=NO_ACCOUNT
被拒绝 账号=A000000007 REASON=BAD_AMOUNT
MASTER_ONLY账户 账号=A000000009
输入记录数=006 排序记录数=006
接受记录数=003
拒绝记录数=003 MASTER_ONLY账户记录数=001
```

注意输出的顺序：`ACCEPTED` 和 `被拒绝` 是按交易账户号掺杂出现的，因为它们是在同一次归并扫描里一条条流出来的；只有最后三行才是收尾的计数。你要是看到某条拒绝记录迟到，先想想是不是匹配逻辑被改了。

`build/accepted.txt`（3 行，每行 28 字符；含换行共 87 字节）：

```text
A000000001C0001001D000012550
A000000003C0001003C000000200
A000000005C0001005D000004000
```

`build/rejected.txt`（3 行，每行 30 字符；含换行共 93 字节）：

```text
A000000004NO_ACCOUNTD000007500
A000000006NO_ACCOUNTX000000100
A000000007BAD_AMOUNTD00000X001
```

**别只看最后一行，自己在纸上推一遍：** 6 条交易按账户号排完是 `001, 003, 004, 005, 006, 007`。`001/003/005` 在主档里且字段合法 → 接受；`004`、`006` 主档里没有 → `NO_ACCOUNT`；`007` 主档里有，但金额里那个 `X` 让它变成 `BAD_AMOUNT`。主档 `009` 一条交易都没有 → 仅主档。`接受 3 + 拒绝 3 = 输入 6`，`主档匹配 4 + 仅主档 1 = 主档 5`，两个式子都能当场验。

计数那几行里有一句值得琢磨：`输入记录数=006 排序记录数=006`——6 条 20 字符记录全都通过了宽度检查并进了排序，一条没被吞掉。要是这两个数不等，说明有记录在 `RELEASE` 那一步被卡住了，得回头查输入行的实际宽度。

**输出字段对照（输出标签 → 含义）：** `ACCEPTED` 已接受；`被拒绝` 已拒绝；`账号` 账户号；`REASON=` 拒绝原因；`MASTER_ONLY账户` 仅主档账户；`输入记录数`/`排序记录数`/`接受记录数`/`拒绝记录数`/`MASTER_ONLY账户记录数` 分别对应各项计数。运行时的标签混用了英文关键字和中文词（`ACCEPTED` 与 `被拒绝` 并存），以本对照表为准。

**未验证项（照旧挂着）：** 在本工作区运行可执行文件时，标准错误上会多出一行 `Warning: program compiled against libxml 212 using older 209`。这是运行环境的链接库版本警告，不是本程序的业务输出；**为什么没验证**：产生它的组件还没定位，本课核对业务结果也用不到它。真正的输出在标准输出，退出码是 `0`。

## 修改练习

两项都在**夹具副本**上做（照上面的命令把副本放进 `build/`），不要改动仓库里的夹具；每次运行都从副本重新开始，因为结果文件会被覆盖：

1. 把交易账户 `A000000004` 改为主档中存在的 `A000000009`，其它字段不动。确认该笔进入接受文件、仅主档计数归零，并逐行核对两个输出文件。
2. 从原始夹具出发，把账户 `A000000007` 的金额从 `00000X001` 改为 `000000001`。确认该笔由拒绝变为接受，且主档记录仍用于匹配。

## 走一遍真实流程

把这一环放进那条日终链路，前后是这样接的：

1. **上游把数据送进来。** 交易和主档文件都在工作目录里等着——读文件是[第 15 课](../15_sequential-file-read/README.md)，定长记录的字节偏移是[第 17 课](../17_fixed-length-files/README.md)，CSV 的字段边界是[第 18 课](../18_csv-processing/README.md)。这些都不归本课管，本课只管"文件已经躺在当前目录里"。
2. **本课这一环。** 先 `SORT` 把乱序交易排好（工具本身是[第 21 课](../21_sort/README.md)），再按升序键跟主档做一次归并扫描（匹配规则是[第 20 课](../20_file-matching/README.md)），校验后分流写出，最后报计数。产物是两份结果文件 + 一份仅主档清单 + 四个计数。
3. **拒绝明细要留痕。** 本课把拒绝写进 `rejected.txt`；谁在什么场景下写文件、写失败会怎样，[第 16 课](../16_file-writing/README.md)讲得更细，[第 26 课](../26_error-handling/README.md)把"业务拒绝"和"系统故障"彻底分开——这两件事分不清，半夜就可能为一个仅主档账户把人叫起来。
4. **计数要进日志。** 现在这几个数只打在屏幕上，进程一结束就没了；[第 27 课](../27_logging/README.md)把它们写进可查的日志，第二天对账的人拿上游报的笔数一比，就知道这批能不能过。
5. **再往后一步。** 让结果回写数据库、把这条链做成能重跑的工程，是[第 29 课](../29_embedded-sql/README.md)和[第 32 课](../32_bank-reconciliation-project/README.md)的事。

同一条链上，本课这句话就是那道防线：`接受 + 拒绝 = 输入`、`主档匹配 + 仅主档 = 主档`。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器，排在"两个输入文件都就绪"之后、下游过账作业之前。它不看你屏幕，只看退出码和生成的文件。
- **谁看它的输出**：值班的人先看退出码，再看 `接受记录数`/`拒绝记录数`/`MASTER_ONLY账户记录数` 三行；运营第二天查 `rejected.txt`；对账的人拿计数跟上游报的笔数核。数字对不上，当晚就要查，不能等早上柜面开门。
- **出事谁被叫起来**：多半是"计数对不上"或者"结果文件半截"。前一种查匹配和校验分支，后一种查磁盘、权限和输出文件状态——记住本课没有回滚，覆掉的旧结果找不回来。
- **下一个系统怎么接**：`accepted.txt` 交过账作业，`rejected.txt` 交运营复核，仅主档清单交对账，计数进日志。字段宽度和拒绝原因码就是这几条链路之间的接口约定，改谁都有人跟着坏。
- **第一个月最容易出的事故**：三种。一是**行宽不对**——上游少写一位，或者多带一个非空格字符（行尾补的空格会被 `TRIM` 掉，行内多出来的字符不会），整批停在那一行；二是**把"没主档"和"字段非法"的顺序写反**，拒绝原因码全错，运营看着 `BAD_TYPE__` 去追一个根本不存在的账户；三是**看到退出码 0 就交**，没核两个文件的行数——覆盖写出不留旧版本，半份结果和完整结果在目录里长得一样。
- **它还没做的事**：不累计余额、不套金额借贷规则、不校验主档有序性和唯一键、不处理同一账户的多笔交易；没有批次标识、没有重跑策略、没有输出原子交付和回滚，也没有日志。这些分别从[第 26 课](../26_error-handling/README.md)、[第 27 课](../27_logging/README.md)和第 29–32 课开始补。

也得把话说清楚：本课证明的是"这一组夹具上，读、排、配、写接得对，计数能闭环，结果能手算核对"，**不是**"这是一套能上生产的账务批次"，更不是原子交付。哪天两个结果文件要同时生效、跑挂了要能原地重来，那都得另外设计。
