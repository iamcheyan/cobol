# 第 04 課：IF 条件分岐——1 件の取引を受け入れと拒否に分ける

取引が入ってきたら、プログラムは即座に判定を返さなければなりません。通すか通さないか、通さないならどのルールに弾かれたか。本課ではサンプル取引 1 件をプログラム内に固定し、3 階層のネストした `IF` で「金額は正 → 金額は単取引上限を超えない → 口座ステータスは有効」を順に判定し、ヒットした**最初の**失敗理由のみを報告します。

## 業務の現場

金曜日の午後 4 時 50 分、支店がもうすぐ閉まります。窓口に来た顧客が送金伝票を出すのとほぼ同時に、モバイルアプリでも「振込確認」をタップします。システム内部では、これらは同じもの——検証待ちの取引——になります。プログラムは即座に結果を返さなければなりません。通すのは簡単なケースで、問題は「拒否」と判定された瞬間から始まります。

拒否は決してゴールではありません。窓口の画面に「拒否されました」とだけ表示されることはなく、顧客は必ず「なぜ？」と聞いてきます。その答えは常に 2 種類です。**この金額自体が規定違反**（正の数値でない、または単取引上限超過）ならば、お金は一切動いていないので窓口で説明すれば済み、顧客が伝票を書き直せばよい。あるいは**口座ステータスが誤り**（凍結、閉鎖）であれば、そもそも窓口で扱う案件ではなく、人手による確認が必要です。同じ「拒否」でも、片方はその場で完了し、もう片方は顧客が後日また来店する必要があり、区別するものは「プログラムがどの理由を返すか」だけです。

最も起こりやすい事故は**順序**です。判定順を逆に書くと、上限超過かつ凍結中の取引が「金額超過」と報告され、窓口係は顧客に「金額を下げて再挑戦してください」と促し、それでも拒否されます。顧客は無駄足、窓口はもう一度説明。本課で求めるのは「受け入れと拒否を分けられる」ことだけでなく、**なぜ最初のヒットした理由だけ報告するのか、その順序は誰が定めたのか**を説明できることです。

曖昧にされやすい別ルール：「単取引上限 1000 は『1000.00 で拒否』『1000.00 を超えて拒否』、どちらか」という問い。仕様ではよく「単取引 1000 円以下」と書かれ、1 文で 2 通りの読み方ができます。プログラムでは `>` と `>=` の 1 文字差で端点が別の側に落ちます。この曖昧さはプログラムエラーを起こさず、2 つのシステムがそれぞれ書き、月次で帳が合わなくなります。本課では端点を明示・検証すべきものとして扱います。

（この場面は教学用で、機関・金額・時刻はルールを説明するために構成したものであり、実在する機関の実際のデータではありません。）

## なぜ今学ぶか

「条件分岐？ `if` はもう何年も書いてる」と思うかもしれません。

問題は、従来の書き方の多くが「一度走ったら終わり」のスクリプトだったことです。ここでのシナリオは違います。**COBOL のプログラムは上から下へ一直線に流れ、「途中で立ち止まって聞く」場所がない。** 第 [02](../02_data-types/README.md) 課で `PIC` を使って口座番号・ステータス・金額を記述する方法を学び、第 [03](../03_move-compute/README.md) 課でそれらから結果を算出する方法を学びましたが、ここまでのプログラムはただ上から下へ進むだけです。

その金曜午後の取引を見返してください。金額は `-5.00`、口座はまだ凍結中。条件分岐がなければ、プログラムはそのまま進み——そのまま「計算」し——そのまま「処理完了」を印字します。拒否もせず、どこが間違っているかも教えない。業務上、これはクラッシュより悪いことです。ジョブは緑、しかし台帳は誤り。

慣れた言語で言えば：口座ステータスのフィールドには実データでは何でも入る可能性があるので、データを人が事前に筛い、分け、別ファイルで投入するのではなく、データを見てプログラム自身が経路を選ぶようにしなければなりません。

COBOL が提供する道具が関係条件と `IF` / `ELSE` / `END-IF` です。他言語と聞こえは似ていますが、本課で踏み固めるべき 2 つの落とし穴があります。`ELSE` が誰に属するかは**スコープ**で決まり、インデントは関係ない。**ネスティングの順序が拒否理由の優先順になる。** その後のすべての分岐レッスンでこの 2 点が再利用されます——第 [05](../05_evaluate/README.md) 課で取引タイプ別に分類、第 [08](../08_control-flow-practice/README.md) 課で複数取引の受否を集計。地盤はここで打ちます。

## この知識項目とは何か、何を解決するか

**この知識項目とは。** 一言で：**データを見てプログラム自身が経路を選ぶようにする**。これを行うのが 2 つのものです——*関係条件*（`=`、`<`、`>`、`<=`、`>=`：2 つの値を比較し真偽を返す）と *`IF` / `ELSE` / `END-IF`*（真の経路と偽の経路、`END-IF` で終端を明示）。第 [03](../03_move-compute/README.md) 課の算術と比べると異なる能力です。「いくら？」ではなく「資格があるか否か？」を問う。

**業務上の何を解決するか。** 検査の仕事は価値の半分が「正しく判定する」、もう半分が「明確に説明する」。窓口・サポート・照合担当が見るのは常に 1 つの判定と 1 つの理由：金額超過、ステータス異常、またはパス。理由を間違えれば、下流の全員が誤った判断をします。`IF` とネスティングは、**業務優先順をコードに書き込む**場所です。先に誰を判定するか、後に誰を判定するか。ソース上で見え、何かあったらあの行を指して説明できる。

**それでも足りない場面（誤用はより高くつく）。** 入力検証の代わりに条件分岐を使ってはいけない。上流の金額フィールドに文字が紛れ込んだり、エンコーディングが間違っていても、`IF` は壊れたデータの上で「正しく見える」判定を行うだけで、データ自体が壊れていることに気づかない。その種の検査は後の課を待たなければならない。また本課の拒否は**業務判定**に過ぎず、終了コードは依然 `0` であることも忘れないでください。業務拒否をシステム障害とみなしてアラートを上げるのは別の典型事故で、第 [26](../26_error-handling/README.md) 課で扱います。

## この課を終えたときに身につくことと限界

この課を終えると、あなたは次のことができるようになります。

- `=`、`<`、`>`、`<=`、`>=` で数値フィールドと文字フィールドを比較し、境界値が受容側と拒否側のどちらに落ちるかを説明できる。
- `IF` / `ELSE` / `END-IF` で各条件に対し明示的な受容・拒否パスを書き、インデントや句点で `ELSE` の所属を推測しない。
- 固定の優先順で 3 階層の判定をネストし、これにより**たった 1 つの**拒否理由が出力されること、および 3 つの並列 `IF` であれば複数のルールに同時にヒットすることを説明できる。
- 境界サンプルを予測し照合する：`0.00`、`-0.01`、`0.01`、`1000.00`、`1000.01`、およびステータスが `A` でないときの判定結果。
- 業務拒否とシステム障害を区別する：本課のすべての拒否パスでも終了コードは `0`。

限界：本課は端末・ファイル・データベースを読みません。サンプル値は `WORKING-STORAGE` の `VALUE` 句に書かれています。取引は 1 件のみで、残高変更・件数集計は行いません。丸めと算術オーバーフローも扱いません（第 [03](../03_move-compute/README.md) 課で示唆、第 [26](../26_error-handling/README.md) 課で体系化）。取引タイプの分類（第 [05](../05_evaluate/README.md) 課）と複数取引バッチ（第 [08](../08_control-flow-practice/README.md) 課）も扱いません。口座認証、並行制御、重複リクエスト検出、永続化も本課では実装しません。本課が証明しようとしているものとは別です。

## 知識解説

### 関係条件：比較しているのは値、画面表示ではない

`=`、`<>`、`>`、`<=`、`>=` という 5 つの演算子は既知でしょう。`THEN` は任意の語で、書いても書かなくても同じ。本当に覚えるべきは 2 つの詳細です。

第 1 に、2 つの数値オペランドを比較するとき、COBOL は**実際の代数値**で比較します。`PIC` が何桁か、符号があるか、`USAGE` が何か、には依存しません。`+0000125.50` と `125.50` は同じものです。

第 2 に、文字フィールドは文字セットの単位で逐文字比較し、短い側は右にスペースでパディングされます。したがって `"A"` と `"a"` は別の文字です——口座ステータスを扱う際は特に致命的。

本課では 3 つの関係条件を用います。

```cobol
WS-TRANSACTION-AMOUNT <= ZERO
WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT
WS-ACCOUNT-STATUS = "A"
```

1 番目 `<= ZERO` はゼロと負数に真。2 番目 `>` は上限を**厳密に超える**ときにのみ真。3 番目は文字比較で、`a`、スペース、`I` はすべて `A` と等しくない。

最も踏みがちな落とし穴は、**境界の所属は完全に演算子で決まる**ということです。`<=` は `0.00` を拒否側に置き、`>` は `1000.00` を受容側に残します。`<=` を `<` に書き換えれば `0.00` が通され、`>` を `>=` にすれば `1000.00` の取引が拒否されます。だから境界値は単独でレビューできず、演算子と一緒に見なければなりません。これが前述の「仕様の曖昧、システム各々」の最も典型的な形です。

ステータスの比較は厳密一致です。`WS-ACCOUNT-STATUS` は `X` 型なので、`a`（小文字）、スペース、`I` はすべて `A` と等しくなく、拒否ブランチに落ちます。大文字小文字どちらでも通したい場合はインターフェース層の規約として明示的に書く必要があります。COBOL は自動正規化しません。

### IF / ELSE / END-IF とスコープ帰属

`IF` は条件が真のとき直後の文を実行し、`ELSE` は偽の場合を扱い、`END-IF` は条件文の終端を明示します。

初心者はインデントで `ELSE` の所属が決まると考えがちです。COBOL はインデントを見ません。コンパイラのルールは 1 つ：**ある `ELSE` は、まだ閉じられていない直近の `IF` に帰属する。** インデントがどれほどきれいでも、コンパイラは気にしません。

本課の 3 つの `IF` はすべて `END-IF` を持ち、内側から外へ一層ずつ閉じます。これ的好处是哪个 `ELSE` 属于哪个在源码上一目了然，不用数空格，也不靠句点去猜。

さらに厄介なこと：**句点は単なる「文末」ではなく、文全体を終わり、まだ閉じていない文のスコープも一緒に閉じる役割を持つ。** 本課全体を通じて句点は最後の `STOP RUN.` の 1 箇所だけ。冒頭の 4 件の `DISPLAY` の**間には句点がない**。これらは同じ文内に並んだ複数の文であり、記述順に実行される。途中にうっかり句点を 1 つ挟めば、本来 `IF` の本体だった文が条件の外に落ちる可能性があり、しかもコンパイラがエラーを出さないかもしれない。

### ネスティング順が報告される拒否理由を決める

3 つのルールをネストする順番が、拒否理由の優先順です。

```text
金額 <= 0             → AMOUNT_NOT_POSITIVE     （最外層、先に判定）
  さもなければ 金額 > 上限 → AMOUNT_OVER_LIMIT
     さもなければ ステータス = "A" → 受け入れ
        さもなければ      → ACCOUNT_INACTIVE     （最内層、最後に判定）
```

プログラムは**最初の失敗条件が真**の箇所で理由を出力して終わり、より深い検査は実行されません。したがって、金額 `-5.00`、ステータス `I` の取引は `AMOUNT_NOT_POSITIVE` だけを報告し、ステータスにも問題があるとは教えてくれません。

これは「なぜネストしなければならないか」に直接答えます。3 つのチェックを並列の `IF` で書けば、2 つの失敗条件がそれぞれヒットし、プログラムは矛盾する 2 つの理由を出力し、ログを読む人はどちらを信じればよいか分からなくなります。業務上「最初に何と言うか」はプロダクトと会計が定めたルールであり、プログラマが勝手に並べるものではありません。順序を変えれば、外部への説明も変わります。

### Java / Python との違い

分岐这件事、Java は `if` / `else if`、Python は `if` / `elif` / `else` で、考え方は同じです。違いは 2 点：COBOL は `END-IF` で文の終端を明示する。`ELSE` のバインドは「最も近くまだ閉じていない `IF`」であり、インデントは通用しない。比較の前にやはり型を確認する必要がある：口座ステータスはテキスト、金額は符号付き十進数。

COBOL は `AND` / `OR` で複数の条件を合成した複合条件もサポートしますが、本課ではあえて使いません。ネスティングにより各ルールの優先順がソースに直接出るため、「どの層から先に判定するか」の感覚をここで鍛えるのが狙いです。複合条件はその文法を読み進めてから着手してください。

### 出力テキストの言語について

リポジトリには規約があります：ソースコメントと README 解説は中文ですが、**プログラム実行時に印字される業務テキストは日本語のまま残す。** とはいえ推測する必要はありません。判定に必要な情報はすべて標準出力の `key=value` 行にあり、鍵となるのは `判定=` と `理由=` の 2 値で、和訳は次の節に出ます。

## 完全なサンプルソース

完全なソースは [`lesson.cob`](./lesson.cob)、固定書式で書かれています（第 7 列指示子、Area A は第 8 列から、Area B は第 12 列から、プログラムテキストは第 72 列を超えない）。

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. IF04.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 WS-TRANSACTION-REFERENCE PIC X(12)
          VALUE "TXN-00000001".
       01 WS-ACCOUNT-STATUS PIC X VALUE "A".
       01 WS-TRANSACTION-AMOUNT PIC S9(7)V99
          SIGN IS LEADING SEPARATE CHARACTER VALUE 125.50.
       01 WS-MAXIMUM-AMOUNT PIC 9(7)V99 VALUE 1000.00.
       PROCEDURE DIVISION.
           DISPLAY "取引参照番号="
               WS-TRANSACTION-REFERENCE
           DISPLAY "口座状態=" WS-ACCOUNT-STATUS
           DISPLAY "取引金額=" WS-TRANSACTION-AMOUNT
           DISPLAY "上限金額=" WS-MAXIMUM-AMOUNT
           IF WS-TRANSACTION-AMOUNT <= ZERO
               DISPLAY "判定=REJECTED"
               DISPLAY "理由=AMOUNT_NOT_POSITIVE"
           ELSE
               IF WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT
                   DISPLAY "判定=REJECTED"
                   DISPLAY "理由=AMOUNT_OVER_LIMIT"
               ELSE
                   IF WS-ACCOUNT-STATUS = "A"
                       DISPLAY "判定=ACCEPTED"
                       DISPLAY "理由=WITHIN_RULES"
                   ELSE
                       DISPLAY "判定=REJECTED"
                       DISPLAY "理由=ACCOUNT_INACTIVE"
                   END-IF
               END-IF
           END-IF
           STOP RUN.
```

上記はソースのコメント行を省略しています。ソース内のコメントはルールと契約（金額は正、上限は端点を含む、最初の失敗理由のみ報告）だけを説明し、`DISPLAY` のテキストを逐条復唱するわけではありません。

## データとルール

本課は入力を一切与えません：サンプル取引はプログラム内に固定され、**外部入力なし**、入力フィクスチャも結果ファイルもありません。判定に関わるのは次の 4 つの値だけです。

| フィールド | `PIC` / 格納バイト数 | 初期値 | 役割 |
|---|---|---|---|
| `WS-TRANSACTION-REFERENCE` | `X(12)` / 12 バイト | `TXN-00000001` | 取引識別子、エコーするだけで判定には参加しない |
| `WS-ACCOUNT-STATUS` | `X(1)` / 1 バイト | `A` | 口座ステータス、本課では `A` のみ有効と扱う |
| `WS-TRANSACTION-AMOUNT` | `S9(7)V99`、`SIGN IS LEADING SEPARATE CHARACTER` / 10 バイト | `125.50` | 符号付き金額、下界側から判定に参加 |
| `WS-MAXIMUM-AMOUNT` | `9(7)V99` / 9 バイト | `1000.00` | 単取引金額上限、端点を含む |

金額フィールドの 10 バイト = 独立した前置符号文字 1 個 + 整数部 7 桁 + 小数部 2 桁。`V` は暗示小数点で**格納位置を取らず**、`DISPLAY` 実行時に位置で描画されるだけです。したがって格納は 10 バイト、画面に見える `+0000125.50` は 11 文字です。上記のバイト数は本機で `FUNCTION LENGTH` を用いて実測したもので、以降の課でレコードレイアウトを照合する基準として使えます。本課に通貨フィールドはなく、演示規約として金額は 2 桁小数の「元」とみなし、為替や丸めは扱いません。

ルールと境界方針：

| ルール | 実装条件 | 方針 |
|---|---|---|
| 金額は正 | `WS-TRANSACTION-AMOUNT <= ZERO` → 拒否 | ゼロと負金額は両方拒否。`0.01` から受理 |
| 単取引上限 | `WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT` → 拒否 | 上限は**端点を含む**。`1000.00` は受理、`1000.01` から拒否 |
| 口座ステータス | `WS-ACCOUNT-STATUS = "A"` のとき受理 | 正確に `A` のみ有効。`I`、`a`、スペースその他は同一の拒否理由 |

コードが検査しているのは上の 3 件のみ。**検査していない**：取引参照番号の書式と一意性（本課ではエコーのみ）、ステータスコードの具体的内容（プログラムは `I` が何を意味するか区別しない）、金額上限の出所（演示定数）。前提：`WS-MAXIMUM-AMOUNT` および 3 つのサンプル値は教育用の演示データであり、実業務方針や規制上限を表すものではありません。

## 境界値がどこで分岐するか

まず 1 つ：本課の拒否はすべて業務拒否で、終了コードは依然 `0`、プログラムにはシステム障害ブランチは存在しません。下の表の各行は本機で実際にコンパイル・実行した結果です。

| 金額 | ステータス | どの比較で分岐するか | `判定=` | `理由=` |
|---|---|---|---|---|
| `125.50`（元の初期値） | `A` | 3 条件すべて通過 | `ACCEPTED` | `WITHIN_RULES` |
| `0.00` | `A` | 第 1 層が真 | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| `-0.01` | `A` | 第 1 層が真 | `REJECTED` | `AMOUNT_NOT_POSITIVE` |
| `0.01` | `A` | 下界の直上で、`<= ZERO` は偽 | `ACCEPTED` | `WITHIN_RULES` |
| `1000.00` | `A` | 第 2 層が偽（端点は含まれる） | `ACCEPTED` | `WITHIN_RULES` |
| `1000.01` | `A` | 第 2 層が真 | `REJECTED` | `AMOUNT_OVER_LIMIT` |
| `125.50` | `I` | 第 3 層が偽 | `REJECTED` | `ACCOUNT_INACTIVE` |
| `-5.00` | `I` | 第 1 層が真、第 3 層は**実行されない** | `REJECTED` | `AMOUNT_NOT_POSITIVE` |

どの分岐を決めているか：

| 観測対象 | それを決定する比較 | 結果 |
|---|---|---|
| 下界 | `AMOUNT <= ZERO` | `0.00` と負数は拒否、`0.01` から受理 |
| 上限 | `AMOUNT > MAXIMUM` | 厳密に大きい場合のみ拒否、`1000.00` は含まれる |
| ステータス | `STATUS = "A"` | 正確に `A` のみ。`a`、スペース、`I` はすべて拒否 |
| どの理由が出るか | 3 階層のネスト順 | 最初にヒットした失敗ルールのみ |

## ソース読み方の道筋

データの順に沿って読むほうが、行番号順よりずっと速いです。

1. まず `WORKING-STORAGE` の 4 フィールドを見る：ステータスは `X(1)` テキスト、金額は符号付き数値。これ以降の比較挙動が違うので、そのルーツがここにある。
2. 次に `PROCEDURE DIVISION` 直後の 4 件の `DISPLAY`：判定に参加する入力値をまず印字し、入力と判定を突き合わせやすくする。これら 4 件の間には句点がない、同一文内の並列文であることに注意。
3. 最外層 `IF WS-TRANSACTION-AMOUNT <= ZERO`：この `ELSE` は「金額が正」の場合のみ拾うため、金額自体が誤っていれば、上限とステータスには進まない。
4. 第 2 層 `IF WS-TRANSACTION-AMOUNT > WS-MAXIMUM-AMOUNT`：厳密超を使っていることに注意。端点はここに含めて受理される。
5. 第 3 層 `IF WS-ACCOUNT-STATUS = "A"`：最内層の `ELSE` がステータス拒否。
6. 3 つの `END-IF` を内側から外へ順に閉じ、最後に `STOP RUN.`。ソース中の句点はこの 1 つだけ。

## 発展演習（解答なし）

別シナリオ——たとえば取引種別で——向けの判定を自分で設計してください。ルールの優先順を自分で決め、最初に何のルールを判定するかをドキュメント化し、少なくとも 3 階層のネスト `IF` を書いてください。本課で学んだ構成要素のみを使うこと：独立フィールド宣言、`VALUE`、`IF` / `ELSE` / `END-IF`、関係条件、`DISPLAY`、`STOP RUN`。ソース、選んだルール順とその理由、コンパイル・実行コマンド、いくつかの境界ケースの実際の出力、各ケースでどの層が起動したかの説明を提出してください。

## 実フローの流れ

この判定ロジンを実フローに組み込むと、次のようになります：

1. **金曜午後**、窓口端末またはアプリが送金リクエストをキューに入れ、フロントオフィスが検証ステップへルーティングする。
2. **検証ステップ**。金額、口座の現行ステータス、単取引上限をマスタから取得し、本課の `IF` チェーンが受理／拒否と、拒否時の理由を返す。
3. **受理の場合**、元帳書きステップに進む（本課の範囲外）。拒否の場合、元のチャネルに判定が返り、窓口は表示された理由をその場で説明し、アプリはユーザにメッセージを表示する——どちらも本課の「理由は 1 つだけ」の保証に依存する。
4. **同じ構造**が第 [08](../08_control-flow-practice/README.md) 課で複数取引の集計、第 [26](../26_error-handling/README.md) 課で業務拒否とシステム障害の区別に再利用される。

## もしこのコードが本番に出たら

- **誰が起動するか**：実窓口／アプリフローでは、検証ステップはリクエスト処理サービスから呼び出される——夜間スケジューラではない。同じロジックは夜間バッチにも現れ、各取引が 1 行ずつ検証を通される。
- **誰が出力を見るか**：運用担当はログ（拒否率、優勢な理由）を見、窓口は表示される理由を見る。もし理由の分類を誤れば、すべて下流の処理者が間違ったものを犯人扱いする。
- **最初の月に最も起こりやすい事故**：3 つのチェックを並列の `IF` で書いてしまい、上限超過かつ凍結中の取引が矛盾する 2 つの拒否理由を返し、操作者が判断できなくなる。あるいは「1000 を超えない」を `>=` ではなく `>` と解釈して、1000 円の取引が拒否され始める。

この課が証明しているのは、**「同じ取引でも、演算子の選択やルール順が違えば別の判定になり、報告される理由は 1 つだけで、その理由は優先順に従う」** ということに限られます。実際に受理／拒否したわけではなく、プログラム内の単一取引を確定的な初期値で扱い、入力ファイルもログもなく、すべてのパスで終了コード 0 で終わります。実世界の検証は、データ自体が信頼に足るかも扱わなければなりません。次の層のエラー処理とファイル／DB 入力経路は第 [15](../15_sequential-file-read/README.md) 課と第 [26](../26_error-handling/README.md) 課で扱います。
