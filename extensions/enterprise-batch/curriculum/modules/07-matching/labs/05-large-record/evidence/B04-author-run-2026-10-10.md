# B04 implementation-run evidence (execution-agent; not acceptance)

Date: 2026-10-10. Compiler: `cobc (GnuCOBOL) 3.2.0` on Linux x86-64, Python 3.13.5.

## Reproduction and return codes

- `python3 curriculum/modules/07-matching/labs/05-large-record/scripts/check.py` — RC 0. It
  compiles a probe, checks every one of the 175 catalog leaves using runtime `ADDRESS OF`
  offsets and lengths, validates the 1,778-byte total length, source fixed-format limits,
  student `COURSE_SOURCE`, the streaming independent-oracle guard, the reset lock protocol
  (`output.lock` directory and symlink, plus the check-then-delete race), and the listed
  mutation/failure cases.
- `python3 curriculum/modules/07-matching/labs/05-large-record/scripts/pressure.py` — RC 0.
  Full-chain pressure (see below) over the real `run.sh` chain; every scenario asserts its
  invariants and the CLI is non-zero if any fails.
- `bash curriculum/modules/07-matching/labs/05-large-record/scripts/check.sh` — RC 0. Includes
  the compiler/runtime matrix and fixture/course-package SHA-256 checks.
- `bash curriculum/check.sh` — RC 0. Existing B00–B03 checks, B04, package hashes, and
  fixed-format source check all passed.

## Verified behavior

The permanent B04 check covers normalized text equality; positive and negative packed zero
equality; audit-only changes; invalid domain/null/key/display numeric/date/time/packed
sign/packed digit/range/ABI/version/ASCII/document-mask cases; nullable date/mask/enum/
reason; partial nullable phone groups; duplicate keys; high bytes in COMP; numeric COMP and
scaled COMP-3 changes; both-empty and one-sided input; final business field; student starter
actual compile/run; reset preservation/lock protection; operational and publication failures.
Valid outputs are independently recomputed from input snapshots by the Python byte-level
oracle before rename. The oracle is a verifier, not the matching implementation.

Each `FIELD`/`AUDIT` line now carries the attribution context from `DESIGN.md`:
`FIELD,<run_id>,<layout_version>,<old_seq>,<new_seq>,<redacted_key>,<field_id>,<cobol_name>,<offset>,<length>,<rule>`.
A dedicated regression changes the same field (`B04-HEA-008 REVISION_NO`) on two different
customers to different values and proves each line is uniquely attributable by the redacted
key and the old/new record sequence numbers.

The layout evidence `B04-layout-author.json` contains each catalog ID, actual offset and
length, compiler, and SHA-256 of the catalog, canonical copybook, and COBOL source. The course
copybook is checked byte-identical to
`instructor/modules/07/05-large-record/ENTERPRISE-CUSTOMER-V1.CPY`; package hashes include the
canonical source files.

## Bounded-memory measurement (full runner chain)

The earlier probe measured only the direct COBOL core and left the Python report oracle
untested; the oracle then cached whole input files and built the entire expected report in
memory. Both were fixed:

- `scripts/verify.py` streams both fixed-record inputs one record at a time, emits the
  expected report to a temporary file, and compares it against the COBOL report in 1 MiB
  chunks. Peak memory is one record plus the catalog, independent of record count and report
  size.
- `scripts/check.py` has a permanent guard: 120,000 records (213 MB) must verify under a
  140 MB `ulimit -v` address-space cap.
- `scripts/pressure.py` drives the **real `scripts/run.sh`** (COBOL core + streaming verifier +
  manifest/publish gate), records an exact `wait4` peak for the standalone verifier, 10 ms
  sampled `/proc` `VmHWM`/`VmRSS`, and the sampled scratch-filesystem disk high-water. Every
  scenario asserts `runner_rc == expected_rc`, `published == (rc in {0,4})`, no leaked
  `output.lock`, and a RC-0 standalone verifier when published; otherwise it raises and
  `main()` writes `evidence/B04-pressure-FAILURE.json` and exits non-zero.

`B04-pressure-author.json` results (GnuCOBOL 3.2, Python 3.13.5, Linux x86-64):

|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| matched-million-high-diff (1 field/record changed) | 1,000,000 × 2 | 3,556,000,000 B | 4 | yes | 5,272 KiB | 21,200 KiB | 20,944 KiB | 113,000,308 | 567.2 | 3.86 GB |

Report size grows with the extra per-line attribution context (113 MB for one million diffs)
while verifier RSS stays flat. Scratch disk high-water is sampled `statvfs` used delta; the
scratch root is chosen for free space and was `/var/tmp` in this run.

Failure boundaries in the full chain (both recorded in the JSON):

- verifier failure: a `python3` shim that fails only the verifier makes `run.sh` return RC 12,
  publish nothing and leave no lock (`failure_boundary`).
- oracle scratch exhaustion: a `python3` shim with an 8-block `RLIMIT_FSIZE` makes the oracle
  temp write fail (`OSError: [Errno 27] File too large`); `run.sh` returns RC 12, publishes
  nothing and leaves no lock (`space_exhaustion`).

## Scratch contract

- The scratch root is selected for free space (`B04_PRESSURE_TMP`, then `/var/tmp`, then
  `/tmp`, then the repo parent) and is recorded in `scratch_root`. It is `/var/tmp` — not the
  small `/tmp` tmpfs — whenever enough space is available.
- Every runner and standalone-verifier invocation is given `TMPDIR` pointed at a per-case
  directory under that scratch root, so the oracle temporary file lands on the same recorded
  filesystem. This is recorded per case as `oracle_tmpdir`.
- Each scenario removes its own work tree; `main()` removes the scratch root on exit; course
  fixtures are read-only.

## Limits

This demonstrates bounded memory for the COBOL comparison core, the streaming oracle and the
real runner on the measured workloads (Linux x86-64, GnuCOBOL 3.2). It does not replace the
main agent's independent review/acceptance, and it is not a production capacity claim. The
core binary is removed by `run.sh` before publish, so only its source SHA is retained
(`core_binary_sha256` is the separately compiled probe binary for reference). The
space-exhaustion boundary uses an explicit file-size limit, since a real full filesystem could
not be created without root on the test host.
