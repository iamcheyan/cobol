# 第 03 課：MOVE と COMPUTE —— 金額計算の切捨てと丸め

## 業務の現場

決算日の夜、利息計算バッチは朝 8 時までに 12 万件の預金の当期利息を計算し終え書き終えなければならない。窓口は 9 時に開き、顧客がアプリに残高をひと目見る——それは正しい数字でなければならない。

この帳の各利息は「残高 × 利率」で計算され、結果はほぼ常に小数の長い尻尾を引き、残高は銭単位しかない。だからその場で即座に判断する：小数部は切り捨てるか、繰り上げるか。切り捨ては切捨て、繰り上げは丸め。

デモサンプルではこの利息の真の値が `15.0650`、切捨てで `15.06`、丸めで `15.07`。たった 1 銭と思うかもしれない。しかし 12 万件、全部が同じ方向に傾けば積み上がるのは些細な額ではない。まして期末残高はこの利息を加えて作るので、この 1 銭の差がそのまま残高に持ち込まれる。

実際に夜中に人を叩き起こすのは翌朝の照合だ。コアシステムが自分の基準で再計算し、両者の残高が合わない——たとえ 1 銭でも、照合担当は「だいたい」で済ませられず、バッチ全体が止まり、誰かが 1 銭が落ちた箇所を 1 件ずつ探す。だから「結果をどのフィールドに入れ、そのフィールドが何桁小数を残すか」は数学の問題ではなく、このバッチが時間どおりに出るかの鍵だ。（場面は教学用、金額と決算日は問題を説明するために構成したもので、いかなる機関の実データでもない。）

## なぜ今学ぶか

第 02 課ではすでに残高と金利の `PIC` を書ける。フィールド幅と精度はソースにそのまま置いてある。しかしあの課のフィールドは `DISPLAY` で 1 回初期値を印字しただけで、ずっと誰にも触れられなかった——本当の帳は印字されるものではなく、計算されるもの。

今あなたを止めているのは 3 つの小さなことだ：値を別のフィールドに移す方法、加減乗を含む金額式を書く方法、結果の小数位が受信項目より多いとき、余分な位をどうするか。最後の 1 点は期末残高の桁数を直接決め、銀行の照合でいちばん転びやすい場所だ。

こう思うかもしれない：「値を移す、掛け算をする、他の言語では `a = b` と `a = b * c` で済むのでは？」落とし穴はここにある。Java や Python では `BigDecimal` を別の変数に代入しても数値は変わらないが、COBOL の受信フィールドははっきりした十進目盛を持ち、移した瞬間にその目盛に合わせて再整形される。つまり**「値を移す」という行為そのものが金額を変える可能性があり、プログラムは何も警告しない。** 明示的にルールを書かなければ、「この業務は切捨てか丸めか」と誰にも聞いてくれない。

本課もそこまでしか扱わない。順次実行される代入と算術文だけで、条件（第 04 課）とループ（第 06 課）は導入しない。まず「受信項目の桁位置が結果を決める」という点を踏まえ、そこを足場にして、後から金額の連鎖へ条件とループを積み上げていく。

## この知識項目とは何か、何を解決するか

**この知識項目とは。** 2 つの能力が加わる。`MOVE` は値を別のフィールドへ移し、行き先の `PIC` が移った先でどんな形になるかを決める。`COMPUTE` は右辺の加減乗をまず計算し、結果を左辺の受信項目に入れ、目盛はやはり受信項目が握る。新出用語は 2 つだけ：受信項目の目盛が小数位を決める、`ROUNDED` が余分な小数位をどう処理するか決める。

**業務上の何を解決するか。** 残高・利息・手数料のような金額チェーンを、人手で電卓を叩くのではなくプログラムとして書けるようにすること。より重要なのは「小数位をいくつ残すか、どちらに丸めるか」という業務ルールをコードに残し、レビューでき、修正できるようにすること。業務が初期値を 1 つ変えれば結果は自動で再計算され、ルールはコードから消えない。

**使うべきでない場面・誤用の代償。** 金額の丸めルールを「デフォルト動作」で代用してはならない。`ROUNDED` を書かないことは切捨てを意味するが、それは本ツールチェーンのデフォルトであり、あらゆる業務がそう記帳するわけではない。誤った日を選べばバッチが会計基準と 1 銭ずれる。また、受信項目の整数位が結果を受けきれないときプログラムは警告しない（後述の実測参照）——金額フィールドの容量は業務の上限に合わせて余裕を持つべきで、目の前の 1 件の桁数に合わせるべきではない。

## この課を終えたときに身につくことと限界

この課を終えると、次のことができるようになります。

- `MOVE` で値を別の数値項目に移し、受信項目の小数位がどう残るか（ここでは `15.0650` → `15.06`）を説明できる。
- `COMPUTE` で加減乗を含む金額式を書き、標準出力で各中間値を 1 段ずつ照合できる。
- 「切捨て」（`ROUNDED` を書かない）と「受信項目で丸め」（`ROUNDED` を書く）を区別し、同じ利息がなぜ `15.06` と `15.07` になりえるかを説明できる。
- 2 つのルールが期末残高を `0.01` 異ならせる理由を述べ、業務／会計ルールがその片方を選ばねばならないことを指摘できる。
- 金額フィールドの桁数が足りないときに何が起きるか、この課のサンプルがその境界を引かない理由を言える。

限界：本課は `IF` / `EVALUATE`（第 04、05 課）、ループ（第 06 課）、パラグラフ（第 07 課）、ファイル入力（第 15 課）、エラー処理文（第 26 課）を扱わない。すべての残高と金利はプログラム内のデモ用定数であり、実口座データではなく、いかなる銀行の利息体系も代表しない。オーバーフロー検査も実装していない。

## 知識の分解

### MOVE：移送されるのは「同じ数」ではなく、行き先の PIC で再整形された値

`MOVE source TO target` は `source` の値を `target` に複製し、`source` を変え、演算もしない。しかし行き先フィールドは自分の `PIC` 目盛を持つ：`WS-INTEREST-RAW` は `9(5)V9999`（4 桁小数）、`WS-INTEREST-MOVE` は `9(5)V99`（2 桁小数）。この 2 つで `MOVE` するとき余分な 2 桁は捨てられて `15.06` になり、元の項目は依然 `15.0650`。

Java や Python から来た人が最も仮定しがちなのはここ：`BigDecimal` を別の変数に代入しても数値は普通変わらない。COBOL の受信項目は明確な十進目盛を持ち、移送中にその記述で変換される。だから「値を移す」という行為そのものが金額を変えられる。本番コードでは、移送前後の項目の目盛と業務単位を明記する必要があり、読者にコードから推測させてはいけない。

### COMPUTE：右辺を先に評価し、左辺の受信項目の目盛で格納する

`COMPUTE target = expression` は右辺の式を先に評価し、結果を左辺のデータ項目に格納する。受信項目の `PIC` も同じように何桁残すかを決める。例ではまず取引後残高を計算する：

```cobol
COMPUTE WS-PRE-INTEREST-BALANCE =
    WS-OPENING-BALANCE + WS-DEPOSIT
        - WS-WITHDRAWAL - WS-SERVICE-FEE
```

次に利息 `WS-PRE-INTEREST-BALANCE * WS-PERIOD-RATE` を計算し、中間値を 4 桁小数の `WS-INTEREST-RAW` に書く。入力、中間値、受信項目はすべて明示的な十進 `PIC` で宣言されているので、各ステップはソースで照合でき、浮動小数点近似に依存しない。

もう一点、手を抜かないで：これらの値はフィールドから計算しなければならず、`DISPLAY` リテラルに直接書いてはならない。直書きでは結果を 1 回復唱できるだけ、初期値を変えれば手計算し直し、業務ルールもソースから消える。`COMPUTE` を使えばルールがコードに残り、初期値変更で自動的に新結果が出る（本課の演習はまさにこの構成）。

### 切捨てか丸めか：同じ利息、2 つの業務ルール

GnuCOBOL では、受信項目の小数位が足りない場合、`ROUNDED` を**書かない**ことは `ROUNDED MODE IS TRUNCATION`（切捨て；本課の金額は非負なので、余分な小数位を破棄することに等しい）に等しい。`ROUNDED` を**書く**がモードを書かない場合は `NEAREST-AWAY-FROM-ZERO`（最近傍、ちょうど半のときはゼロから遠い側）に等しい。例題の利息は厳密値 `15.0650`：

| 書き方 | 結果 | 説明 |
|---|---|---|
| `MOVE WS-INTEREST-RAW TO WS-INTEREST-MOVE` | `15.06` | 受信項目が 2 桁小数、第 3・4 桁を捨てる |
| `COMPUTE WS-INTEREST-TRUNC = WS-INTEREST-RAW` | `15.06` | `ROUNDED` なし、同じ切捨て |
| `COMPUTE WS-INTEREST-ROUNDED ROUNDED = WS-INTEREST-RAW` | `15.07` | 第 3 桁が `5`、最近傍で繰上げ |

`ROUNDED` は受信項目の後、等号の前に置く：

```cobol
COMPUTE WS-INTEREST-ROUNDED ROUNDED = WS-INTEREST-RAW
```

どちらを選ぶかはプログラミングの好みではなく、業務と会計の基準だ：切捨て値と丸め値は期末残高を `0.01` 異ならせ、通貨・商品・利息計上方式ごとにルールが異なる。GnuCOBOL のデフォルトモードをあらゆる業務共通のルールと思わないこと、それは財務と商品の担当と合わせるものだ。

### 格納できないとき、プログラムは声を上げない

小数位が落ちるのと同様、整数位も落ちる。本機で独立したプローブで観察した（プローブは [`lesson.cob`](./lesson.cob) に含まれず、本課で学んだ `PIC`、`COMPUTE`、`DISPLAY` のみを使う）：

```sh
mkdir -p /tmp/l03probe && cd /tmp/l03probe
cat > probe.cob <<'EOF'
       IDENTIFICATION DIVISION.
       PROGRAM-ID. PROBE03.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01 WS-BAL PIC 9(7)V99 VALUE 1234567.89.
       01 WS-RATE PIC 9(1)V9(4) VALUE 0.9000.
       01 WS-INT PIC 9(5)V99 VALUE 55.55.
       PROCEDURE DIVISION.
           COMPUTE WS-INT = WS-BAL * WS-RATE.
           DISPLAY "利息=" WS-INT.
           STOP RUN.
EOF
cobc -x -o probe probe.cob && ./probe
```

`1234567.89 × 0.9000 = 1111111.101` を `PIC 9(5)V99` に格納すると実際は `利息=11111.10` と印字され、終了コードは `0`：上位の数字が黙って捨てられ、プログラムは中断もエラー報告もしない。「計算を間違えた」こと自体がエラー信号にならない。だから金額フィールドの容量、オーバーフロー検査、報告方式はプログラムで明示的に決めなければならない。`ON SIZE ERROR` はこの種の条件を捕まえられるが、それはエラー処理に属し、本課では使わず、第 26 課に持ち越す。

## ソース読み方の道筋

### データ宣言

| フィールド | PIC / 初期値 | 用途と目盛 |
|---|---|---|
| `WS-OPENING-BALANCE` | `9(7)V99` / `1000.00` | 期初残高、元、2 桁小数 |
| `WS-DEPOSIT` | `9(7)V99` / `250.55` | 当期預入額 |
| `WS-WITHDRAWAL` | `9(7)V99` / `40.10` | 当期払戻額 |
| `WS-SERVICE-FEE` | `9(5)V99` / `5.25` | 手数料；整数 5 桁、残高フィールドより小さい容量 |
| `WS-PERIOD-RATE` | `9(1)V9(4)` / `0.0125` | 演示金利 1.25%、4 桁小数；日次計算規定なし |
| `WS-PRE-INTEREST-BALANCE` | `9(7)V99` / `ZERO` | 取引後・利息計算前残高 |
| `WS-INTEREST-RAW` | `9(5)V9999` / `ZERO` | 利息中間値、意図的に 4 桁小数を残す |
| `WS-INTEREST-MOVE` | `9(5)V99` / `ZERO` | `MOVE` 後の 2 桁小数結果 |
| `WS-INTEREST-TRUNC` | `9(5)V99` / `ZERO` | `ROUNDED` なしで計算した結果 |
| `WS-INTEREST-ROUNDED` | `9(5)V99` / `ZERO` | `ROUNDED` 付きで計算した結果 |
| `WS-CLOSING-BALANCE` | `9(7)V99` / `ZERO` | 本課の記帳ルール（丸め利息を計上）に従う期末残高 |

### 実行順序と状態変化

1. 第 1 の `COMPUTE`：`1000.00 + 250.55 − 40.10 − 5.25`、`1205.20` を `WS-PRE-INTEREST-BALANCE` に書き込む。
2. 第 2 の `COMPUTE`：`1205.20 × 0.0125 = 15.065`、受信項目は `9(5)V9999`、出力は `15.0650`。
3. `MOVE WS-INTEREST-RAW TO WS-INTEREST-MOVE`：受信項目は 2 桁小数、捨なし、`15.06`。`WS-INTEREST-RAW` は依然 `15.0650`。
4. `COMPUTE WS-INTEREST-TRUNC = WS-INTEREST-RAW`：`ROUNDED` なし、同じ切捨て、`15.06`。
5. `COMPUTE WS-INTEREST-ROUNDED ROUNDED = WS-INTEREST-RAW`：デフォルト `NEAREST-AWAY-FROM-ZERO`、`15.07`。
6. `COMPUTE WS-CLOSING-BALANCE = WS-PRE-INTEREST-BALANCE + WS-INTEREST-ROUNDED`：本課ルールで、`1205.20 + 15.07 = 1220.27`。
7. 11 件の `DISPLAY` がソース順にラベルと値を出力、`STOP RUN` で正常終了。

ステップ 2〜5 は同じ `WS-INTEREST-RAW` から出ているので、3 つの 2 桁小数結果の差は受信項目の違いから来ており、再計算からではない。`DISPLAY` はどのフィールドも変えない。

## 実行と観察

### どこで実行するか

プログラムはファイル、コマンドライン引数、データベースを読まないので、課ディレクトリ内外どこでも結果は同じ。下のコマンドは課ディレクトリ前提：`lesson.cob` も `build/lesson_03` も現在のディレクトリ相対なので、まず `cd lessons/03_move-compute` してから実行する。

### 入力

標準入力、ファイル、データベース入力なし。データは `lesson.cob` の `01` レベル項目の `VALUE` のみ：

- 金額項目は `PIC 9(7)V99` または `9(5)V99`、単位は元、暗示 2 桁小数、最低記帳単位 0.01。
- 利率項目は `PIC 9(1)V9(4)`、`0.0125` は 1.25%、日数規定なし、利息計算前残高に 1 回掛けるだけ。
- 負値、空欄、桁数不足の検証はない——境界は `IF`（第 04 課）、ファイル＆検証（第 15 課以降）、エラー処理（第 26 課）の領分。

### 4 つのコマンドが証明すること

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                    # check: 構文のみ解析、実行ファイル作らず
cobc -x -Wall -o build/lesson_03 lesson.cob      # build: 実行ファイル生成、-Wall でコンパイル時警告
./build/lesson_03                                # run: プログラム実行、stdout が業務結果
echo $?                                          # 直前の実行コマンドの終了コードを確認
rm -rf build                                     # clean: 本課のビルド成果物を削除
```

`-fsyntax-only` 通過は構文経路の OK を示すだけで、振る舞いはコンパイル・実行して初めて検証。`-Wall` はコンパイラにリテラル幅が受信項目を超えるような問題を早期報告させる；本課のソースはその種の警告を出さない。

### 固定書式の注意

ソースは固定書式：第 7 列は指示子（`*` でコメント）、Area A は第 8 列から（`01` レベル宣言と Division 名）、Area B は第 12 列から（`COMPUTE`、`MOVE`、`DISPLAY` など）；有効なプログラムテキストは第 72 列を越えられない。本機で実測済みの落とし穴がある：GnuCOBOL 3.2.0 はこの列位置を**バイト**で数える。各日本語文字は 3 バイト使うので、見た目では短くても第 72 バイトで切られ「文字列終端引用符がありません」のようなエラーを出すことがある。`DISPLAY` テキストを変えるときは、その行が第 72 列に貼り付かないよう注意。本課の最長 `DISPLAY` 行（`MOVE後利息` と `COMPUTE切捨て利息` を含む）は 62 バイト、最長コメント行は 71 バイト、いずれも境界内。

## 実フローの流れ

この金額ロジンを完全な鎖に置くと、次のようになる。

1. **決算日の夜、スケジューラが利息計算バッチを起動する。** バッチは口座マスタから期初残高と金利を取り（実運用ではファイルや DB、本課ではプログラム内定数）、残高と金利を本課の `MOVE` / `COMPUTE` に渡し、取引後残高・利息・期末残高を計算する。
2. **下流はまず利息の決め方を確認する。** 期末残高は口座マスタに書き戻され、翌日は照合プログラムがコアシステム再計算の結果と突き合わせる。丸めルールを誤れば、2 システムの残高は 1 銭ずれる。
3. **同じ一束の金額が後の課で使われる。** 第 04 課以降、これらの金額に条件を付け、取引を受け入れるか拒否するかを判定する。第 15 課以降は金額が実取引ファイルから読まれ、もう定数ではない。第 26 課でオーバーフローと失敗報告を統一的に扱い、第 32 課で金額チェーン全体が口座マスタと照合される。

はっきりさせておくが、本課のこのセグメントはまだ本番投入できるバッチではない：入力ファイルも拒否ロジックもオーバーフロー検査もない。これを単独で夜間に走らせても、あの 1 銭の差がどこから発生したかを示すだけ。

## もしこのコードが本番に出たら

- **誰が起動するか**：決算日の夜間バッチスケジューラが、利息、書き戻し、照合の各ステップを依存順に起動する。終了コードだけを評価し、画面は見ない。
- **誰が出力を見るか**：運用担当は標準出力と標準エラーを見る。会計・照合担当は残高が合っているかを見る。だから「どの行が業務結果で、どの行が環境警告か」をはっきり区別できなければならない。
- **次のシステムは**：計算した期末残高は口座マスタに書き戻され、翌日は照合プログラムがコアシステムの基準と 1 件ずつ突き合わせる——1 銭違っていればバッチ全体が止まる。
- **最初の月に最も起こりやすい事故**：「`ROUNDED` を書かない = 切捨て」を全行共通基準と決め、会計基準と 1 銭ずれる。あるいは金額項目の整数位を目の前の 1 件に合わせて設計し、残高が大きくなったとき上位桁が静かに落ち、プログラムは成功を報告する。

銀行バッチでは、`MOVE` は項目間移送・レイアウト変換・出力準備によく使われ、`COMPUTE` は残高・手数料・利息・制御総額によく使われる。単純に見えても金額正確性の着地点だ：受信項目の小数位が丸めを決め、整数位容量がオーバーフローを決め、業務基準との不一致は残高と基準をずらし、プログラムはエラーを出さないかもしれない。本番投入前に、項目の通貨・整数位・小数位・最大値・負値ルール・丸め位置・超過時ポリシーを固定し、独立した算例または制御総額で照合するべきである。

本課が証明しているのは「同じ利息でもルールが違えば別の結果になり、期末残高は `0.01` ずれる」ことだけで、まだ受容／拒否判断はしていない。分岐は第 04 課から始まり、同じ金額項目で取引を受け入れるかを決める。ファイル入力は第 15 課から始まり、金額が実取引ファイルから来るようにする。オーバーフローと失敗報告は第 26 課で統一され、金額チェーン全体は最終的に第 32 課のプロジェクトで口座マスタと照合される。
