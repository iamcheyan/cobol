# Module 12 System Composition and Dependency Trace (R15)

This document describes the components of an unfamiliar-version system and each component's role in the capstone run. Components are deduplicated by unique path, and their roles are labeled using actual call relationships from `system/lib/common.sh` and `system/jobs/*.sh`.

Classification rules (mutually exclusive, in priority order):

1. **Runtime dependency (run)**: component actually called by the capstone nightly chain and producing capstone artifacts.
2. **Maintenance investigation dependency (maint)**: existing component that must be investigated before modification for the capstone maintenance task (may run or may only be read as part of impact analysis).
3. **Independent teaching reference (ref)**: canonical implementation supplied with the course for reading/comparison; **not** called directly by capstone orchestration.
4. **starter**: learner starting point, intentionally incomplete.
5. **Generated file (generated)**: derived file generated by scripts/tools, identified separately as an output.

## 3. Maintenance investigation dependencies / independent teaching references / starter

- **Maintenance investigation dependencies (maint)**: orchestrated components under `system/` plus the target interface in `maintenance/copybooks/`. Learners must trace their dependencies in `maintenance/impact-investigation.md` first.
- **Independent teaching references (ref)**: Of the 23 canonical `.COB` files under `instructor/`, all except the 3 called by capstone in the table above (reference implementations for modules 01–06 and 08–12, FILEVAL/MATCH/MERGETX/BATCHL3/BATCHL4, module 08 ESQL, etc.) are **not orchestrated by this module**; they are provided for reading only.
- **starter**: `starter/CUSTV2.COB` (incomplete; v2 feed returns RC12 and is not published).
- **Generated files**: fixture seeds, `expected/*` (generated by an independent oracle), `__pycache__/`, etc. are not counted as handwritten implementation.

## 4. Component dependency notes

Capstone composition is determined by actual call relationships. The table above lists runtime dependencies; reference implementations used only for reading, starter code, and generated files are classified separately as described above. Learners can trace each component's responsibilities through the JOB / program / COPY / table relationships.
