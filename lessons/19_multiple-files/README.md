# 第 19 课：同时读取主档与交易——两条输入流，各有各的 EOF

真实批次很少只读一个文件：账户主档和当日交易必须一起被推进，而两者行数往往不同，先读完的那一份不能把另一份也带停。本课同时打开主档和交易两个顺序文件，各自维护文件状态、EOF 标志和记录计数，在主档先到文件尾之后继续把四条交易读完，为第 20 课的按键顺序匹配准备输入推进方式。

## 业务现场

月末最后一个工作日的晚上 22:40，联机交易已经停了（机构、时点、量级都是为教学编的，不是哪家真实机构的真实数据）。你们这套对账流程的第一步很朴素：把**账户主档**和**当日交易**两份文件同时读一遍。主档说的是"这些账户现在长什么样"，交易文件说的是"今天动过哪些户"。真正算账、比对余额是后面的事，眼下你只负责一件事——把两条数据流都完整地推进到底。

这两份文件的行数天生不一样。主档可能几十万行，只要开过户就在里面；当天的交易可能只有十几万笔，今天没动过的账户一条都不会出现。所以"读完了没有"，每一份文件都有自己的答案、自己的时点。完全可能主档才读到一半，交易已经读完了；也完全可能反过来。

新手在这儿最常写出来的东西是：两个文件共用一个"读完了"标志，或者干脆共用一个读取段落。跑起来一切正常——不报错、退出码还是 `0`、最后那行汇总照样打出来。

可你要是把汇总里的两个数字念一遍，就会发现不对：今天明明有 12 万笔交易，汇总上只有 6 万。哪儿也没丢，只是先读完的那一份把另一份也一起带停了，而这次运行"成功"结束了。这种事故不报错、不告警，全靠有人去念那两个计数才能发现——所以本课把两份文件的 EOF、状态和计数从头到尾分开管。

## 为什么现在学

第 15 课你已经能打开一个顺序文件、用 `AT END` 读到文件尾。那时候只有一条流，一个 EOF 标志就够用。

可真实批次很少只让你读一个文件。主档是"参照"，交易是"今天发生的事"，它们得同时在场。于是冒出一个第 15 课没讲过的新问题：**两份文件谁先读完，跟另一份没有关系。**

你可能会想：那我写两段循环，先把主档读完再读交易，不也一样？不一样。只要后面要做的是把两条记录放在一起看（第 20 课干的就是这个），你就必须让两条流同时往前走——主档停在第几条、交易停在第几条，都得由你控制。

还有一个更隐蔽的坑：`AT END` 只认"正常读到文件尾"这一个状态（状态码 `10`）。读取要是因为别的原因失败，状态码不是 `10`，`AT END` 分支根本不会进；你如果只靠它来判断"读完了没有"，程序就会以为还有数据，拿着上一条旧记录继续往下跑——错得一声不响。所以本课不只是"多开一个文件"，还要把 `READ` 之后的状态检查写全。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 一句话：**让两个（或者更多）顺序文件各自独立地往前推进**。每个文件都有自己的一份 `FILE STATUS`、自己的 EOF 标志、自己的记录计数，还有自己那段读取逻辑。循环每转一圈，谁还没读完就读谁；两个都读到尾了，循环才收工。

**它在业务里解决什么问题。** "一份参照数据 + 一份当天发生的数据"是批处理里最常见的输入形态：账户主档配当日交易、商品主档配当日订单、客户资料配当日开户申请。把每个输入各自管起来，换来的是三件事：

- 行数不同不会互相拖累——主档多少行、交易多少行，各算各的；
- 计数是对账里第一个要念的数字——`账户记录数=003 交易记录数=004` 就是"到底读没读全"的凭据；
- 真出问题能说清是**哪个文件、哪个状态码**，而不是笼统一句"读取失败"。

**什么时候不该这么写。** 如果两份文件本来就同进同退、条数一一对应（比如一份是另一份的逐行副本），共用一个循环也不算错。但只要你**不能保证**两边行数一致，就必须把状态、EOF 和计数分开——本课的夹具就是故意做成 3 行对 4 行。要让两条流真正按业务键配成对，还得等[第 20 课](../20_file-matching/README.md)的顺序匹配；本课只把"同时在场"这一步做稳。

## 本课完成后的能力与边界

学完本课后，你可以：

- 在一个程序里声明并 `OPEN INPUT` 两个顺序文件，各自绑定 `FILE STATUS` 字段。
- 给每个输入分别维护 EOF 标志和成功读取计数，并说清为什么不能让它们共用。
- 用一个循环交错推进两条流：一份先到文件尾之后，另一份继续读完。
- 分清正常 EOF（`10`）、打开失败（`35`）、其他读取错误和关闭异常各走哪条路、返回什么码。
- 核对结果：主档三条、交易四条，而且这四条交易都出现在主档 EOF 之后。

边界：程序只读取并回显整行，**不解析字段、不按账户号匹配、不做金额计算、不生成输出文件**；顺序匹配是第 20 课的事。文件格式约定（字段分隔、宽度）由夹具保证，本课不校验。缺失文件、空文件这些边界在本课当作失败或零记录处理，没有重试，也没有恢复手段。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端；本课不依赖数据库或附加工具。
- 本课必须先有输入夹具，而且 `SELECT` 里写的是相对文件名，所以**要从本课目录执行**。
- 语法检查与编译在 `build/` 下生成可执行文件；程序不写任何数据文件。

## 输入文件

| 夹具 | 记录数 | 一行示例 | 说明 |
|---|---:|---|---|
| [`accounts.txt`](./accounts.txt) | 3 | `MASTER\|0001234567\|C0001042\|0001000.00` | 账户主档，行顺序文本 |
| [`transactions.txt`](./transactions.txt) | 4 | `TXN-000001\|D\|0001234567\|125.50` | 当日交易，行顺序文本 |

两者都是行顺序（LINE SEQUENTIAL）文本文件，一个物理行就是一条记录，行内用 `|` 分隔字段；本课不看字段含义，只把整行原样显示出来。两个 `FD` 的记录区都是 `PIC X(100)`，而本课夹具里最长的一行是 34 字节，离上限还远，所以不会出现记录被截断或者两行被拼成一条的情况。

## 两条流怎么一起往前走

程序的骨架其实就一句话：**只要还有没读完的文件，就继续读。**

1. 先开主档。`FILE STATUS` 不是 `00` 就直接报错走人——缺文件在本课算失败，状态是 `35`。
2. 再开交易文件。这一步比第 15 课多做一件事：如果它打不开，得先**把已经打开的主档关掉**再退出，不然资源就漏了。
3. 进循环。每转一圈看谁还没到 EOF：没到就调自己那段读取，到了就跳过。两个读取段落（`1000-READ-ACCOUNT`、`2000-READ-TRANSACTION`）各管一个文件，谁也不碰谁的标志和计数。
4. 读取成功（状态 `00`）只做两件事：把**自己那份**计数加一，把这一整行打出来。主档行以 `账户主档：` 开头，交易行以 `交易：` 开头。
5. 读到文件尾（状态 `10`）只设置**自己那个** EOF 标志。这不是错误，也不加计数——正常读到尾就是这么回事。
6. `READ` 要是返回别的状态，就把"哪个文件、什么状态"打出来，置上 I/O 错误标志，跳出循环，关掉两个文件，以非零码结束。
7. 循环的退出条件：两个 EOF 都是 `Y`，或者出现了 I/O 错误。

`AT END` 那个坑前面提过，这里再说一遍，因为它是本课的重点：**它只覆盖文件状态 `10`**，捕不到其他非零状态。所以两个读取段落都在 `READ` 之后显式检查状态字段——只有这样才分得清"读到尾了"和"读挂了"。

## 文件状态、失败与限制

| 情形 | 观察到的文件状态 | 程序行为 / 返回码 |
|---|---|---|
| 正常读到文件尾 | `10` | 设置该文件 EOF，不计记录数，返回码保持 `0` |
| 输入文件缺失 | `35`（OPEN） | 输出 `... 文件打开失败 STATUS=35`，返回码 `1` |
| 读取中其他非零状态 | 其他状态码 | 输出 `读取...失败 STATUS=xx`，停止读取、关闭文件，返回码 `1` |
| 关闭异常 | 非 `00` | 输出 `关闭时...异常`，返回码 `1` |

- 两个输入都是必需文件：`SELECT` 没写 `OPTIONAL`，缺一个就直接失败。
- 出现 READ 错误时立刻停下，并尝试把两个文件都关掉；本课不做重试，也不能从断点接着读。
- 本课不校验业务日期、不校验记录格式，也不比较两个文件之间的内容——它没有完成文件匹配，这一点别读错。

## 运行与观察

**输入：** 本课目录下的 `accounts.txt` 与 `transactions.txt`；程序按相对路径打开，所以要先 `cd` 到本课目录。

**命令及作用：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                  # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_19 lesson.cob    # 编译并生成可执行文件
./build/lesson_19                              # 运行，读取当前目录下的两个夹具
echo $?                                        # 查看退出码
rm -rf build                                   # 清理生成的可执行文件
```

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，无编译诊断 |
| 标准输出 | 9 行，见下方代码块 |
| 进程退出码 | `0` |
| 生成的业务文件 | 无（本课只读） |

```text
账户与交易文件已打开
账户主档：MASTER|0001234567|C0001042|0001000.00
交易：TXN-000001|D|0001234567|125.50
账户主档：MASTER|0002468101|C0002042|0000020.00
交易：TXN-000002|T|0001234567|0007654321|40.00
账户主档：MASTER|0007654321|C0003042|0000250.75
交易：TXN-000003|D|0002468101|75.00
交易：TXN-000004|T|0007654321|0009999999|20.00
关闭完成 账户记录数=003 交易记录数=004
```

**可独立核算：** 夹具 `accounts.txt` 有 3 行、`transactions.txt` 有 4 行，所以汇总必须是 `账户记录数=003`、`交易记录数=004`，合计 7 条被回显的记录。第 5 行之后主档记录不再出现（主档已 EOF），但交易一直打印到第 4 条——这正是两个 EOF 标志彼此独立的效果。你自己数一遍输出里的行数，就能证明两个计数没有互相干扰。

**证据来源与未验证项：**

- 上面三条命令、9 行输出和退出码，以及 `STATUS=35` 的缺文件路径（缺主档、缺交易各试一次，都是退出码 `1`），都在本工作区实际跑过，与本文一致。
- 两项修改练习已用本课目录下的临时夹具副本复跑，结果与 [`answer.md`](./answer.md) 一致（`003/002` 与 `000/004`，退出码 `0`）。
- **未验证项（照旧挂着）：** 在本工作区运行可执行文件时，标准错误上会多出一行 `Warning: program compiled against libxml 212 using older 209`。这是运行环境的链接库版本警告，不是本程序的业务输出；**为什么没验证**：产生它的组件还没定位，本课核对业务结果也用不到它。
- **也没实测的两条路：** "读取中其他非零状态"和"关闭异常"这两行，是照着源码里的检查分支和 GnuCOBOL 的文件状态语义写出来的，本课没找到稳定的注入办法，所以不当作实测结论。真要把这两条路跑出来，得等[第 26 课](../26_error-handling/README.md)那套错误注入练习。

## 修改练习

两项都在**临时目录里的夹具副本**上做，不要改动仓库内的 `accounts.txt` / `transactions.txt`：

1. 删除副本 `transactions.txt` 的最后两条记录，只留前两条。确认主档仍读完三条，而交易计为两条。
2. 清空副本 `accounts.txt`，保留四条交易。确认空主档在首次 `READ` 就到达 EOF，后续交易仍被逐条读取。

完整题目与预期见 [`exercise.md`](./exercise.md)，参考答案见 [`answer.md`](./answer.md)。

## 举一反三练习

增加一份客户状态文件，与主档和交易文件一起读取。为三个输入各自维护 EOF 和计数；准备三条、两条、一条记录的夹具，确认任意一个流先结束时其他流仍继续推进。设计一个能区分文件名和状态码的读取错误输出格式。不添加账户匹配、排序或数据库访问。题目见 [`exercise.md`](./exercise.md)，本题不提供答案。

## 走一遍真实流程

把本课放回那条月末对账链路里，它是这么一环：

1. 上游把**账户主档**和**当日交易**两份文件放进批处理目录（真实系统在再前面还有一道"文件到齐"检查，本课不涉及）。
2. 你的程序同时打开它们，各自推进，最后报出 `关闭完成 账户记录数=003 交易记录数=004`。这一步保证的是"两条流都在场，而且都读完整了"。
3. 这两个计数是写给值班和对账的人看的（第 27 课把它变成正式日志）。**它们和上游报的笔数对不上，当晚就得查**——本课把规模缩到 3 行对 4 行，就是为了让你能手工数一遍。
4. 两条流都推进完之后，[第 20 课](../20_file-matching/README.md)才把它们按账户号配成对：主档三条、交易四条配完，要满足"匹配数 + 仅主档数 = 主档总数"这类不变量，一条都不能漏。
5. 配对结果再交给[第 16 课](../16_file-writing/README.md)的写出逻辑落成结果文件，[第 22 课](../22_file-processing-practice/README.md)把整条链路串成一个端到端批次。

也就是说，本课不产出任何业务结果，它只是让"两条输入流同时在手"这件事变得可靠。后面所有的对账动作都站在这一步上。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器，通常排在"文件就绪检查"之后。主档或者交易文件缺一个，它第一步就过不去——本课的做法是打印 `STATUS=35` 并以 `1` 退出（正式的错误分类要等第 26 课）。
- **谁看它的输出**：值班的人先看退出码，再看最后那行 `关闭完成 ...` 的两个计数。**计数不对，当晚就要查**，因为程序自己不会替你发现"少了半个文件"。
- **出事谁被叫起来**：某份文件的读取状态既不是 `00` 也不是 `10` 时，程序会打印是哪个文件、哪个状态码，然后非零退出；值班的拿着这一行去判断是哪份输入坏了。
- **下一个系统怎么接**：本课交出去的只是"两条流都读完了"。真正按键配对是[第 20 课](../20_file-matching/README.md)，结果写出是[第 16 课](../16_file-writing/README.md)，错误分流与资源回收是[第 26 课](../26_error-handling/README.md)，日志是[第 27 课](../27_logging/README.md)。
- **第一个月最容易出的事故**：图省事让两个文件共用一个 EOF 标志或一个读取段落。**这种错不报错、退出码还是 0，只是默默少处理一半数据**——它在 7 条夹具上看不出来，只在真实行数差异大的晚上爆发。本课把 3 行对 4 行的差异摆在最前面，就是让你先把这个坑踩一遍。
- **它还没做到的事**：不解析字段（整行照原样回显）、不按账户号匹配、不算金额、不写结果文件；没有重试，也没有断点续读。所以它**不是**一个可以直接上生产的对账批次。
