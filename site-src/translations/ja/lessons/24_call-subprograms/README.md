# 第24課：CALL——金額検証をメインプログラムから切り出し、再利用可能なサブプログラムにする

## 業務の現場

木曜日の午後4時、カスタマーサービスからバッチチームへ問い合わせが届きました。顧客の領収書によると、同じ1,200.00の定期引き落としが、月曜日の口座振替バッチでは**受け入れ**、水曜日の返金バッチでは**拒否**されています。コードを調べると、両方のプログラムに同じ金額上限の判定が複製されていました。3か月前、運用が上限を1000.00から1200.00へ上げたとき、当夜リリースするプログラムだけが変更され、もう一方は忘れられました。**コピー＆ペーストを再利用と考えると、同じルールが2つの版に分かれるのは必然です。**

顧客から問い合わせが続き、照合担当者は2つのバッチ結果を手作業で比較し、どちらを正とするか決めなければなりません。どちらを選んでも、すでに送付した領収書は取り消せません。

（時刻、バッチ、顧客、金額は説明用の架空データです。）

この課では「この金額を記帳してよいか」というルールを各メインプログラムから切り出し、独立してコンパイル・配置でき、複数のバッチから呼び出せるプログラム単位にします。3つの判定を一度だけ実装します。ただしCOBOLの呼び出しインターフェースは**引数を位置で対応付けます**。引数の名前や型はインターフェースに含まれず、コンパイラーも個数を数えません。呼び出し側が引数を省いてもコンパイルが無言で通り、実行時にシグナルで終了することがあります。このワークスペースで確認した終了コードは139でした。誤った呼び出しインターフェースは即時クラッシュを起こし、テストでも見逃しやすい問題です。

## 今学ぶ理由

第23課までの再利用手段は、段落（`PERFORM`、[第7課](../07_paragraphs/README.md)）とCopybook（[第23課](../23_copybooks/README.md)）です。どちらも上の問題は解決できません。

段落は**プログラムの外へ出られません**。`PERFORM 2000-CHECK-AMOUNT` は `LESSON24` の `PROCEDURE DIVISION` 内でだけ有効です。別プログラムで同じ名前を使うと、段落がないというエラーになります。

Copybookは**宣言だけ**です。`COPY` でデータ記述を共通化できますが、複製されるのはフィールドの形であり、判定方法ではありません。`EVALUATE` のロジックをCopybookに置けば、各利用プログラムへ同じコードが展開され、結局それぞれを変更することになります。

「コピーを続けて、変更時に全部直せばよい」と考えるかもしれません。冒頭の事例が答えです。更新漏れは数か月後に顧客問い合わせになります。

不足している機能は**プログラム間呼び出し**です。ロジックに名前とインターフェースを持たせ、データを渡して結果を受け取ります。COBOLでは `CALL` を使います。

## 概念と解決する問題

**概念。** `CALL` はあるプログラム単位から別のプログラム単位へ制御を移します。呼び出された側は `GOBACK` で制御を戻します。データはグローバル変数ではなく、`USING` の後ろにある項目を**位置ごと**に対応付けて渡します。第1実引数は第1LINKAGE引数、第2は第2へ対応します。

- サブプログラムは受け取る引数を `LINKAGE SECTION` に宣言します。これらはサブプログラム内に記憶領域を持たず、呼び出し側項目の別名です。書き込みは呼び出し側のメモリーに反映されます。
- 受け渡し方式を省略すると既定値は `BY REFERENCE` で、**アドレス**を渡します。`MOVE "VALID" TO LK-CHECK-RESULT` は呼び出し側項目を変更します。別個の戻り値ではなく引数経由で結果を返します。

**業務上解決する問題。** 共通ルールの実装を一つに保ちます。上限を一度変更すれば、すべての呼び出し元が次の実行時に新ルールを使います。金額上限、顧客資格、取引コードの判定などに適しています。

**誤用の注意。** `CALL` はインターフェース管理の責任を伴います。呼び出し側の `WS-AMOUNT` / `WS-CHECK-RESULT` とサブプログラム側の `LK-AMOUNT` / `LK-CHECK-RESULT` は名前で結び付きません。コンパイラーは比較しないため、引数順を入れ替えてもコンパイルが通り、実行時に金額を状態として扱うことがあります。引数の個数や幅も検査されない場合があります。後半で実測します。

## 修了後にできることと範囲

- `CALL "PROGRAM-ID" USING ...` で別プログラムへ制御を渡し、`CALL` の次の文から実行が再開することを説明する。
- `LINKAGE SECTION` と `PROCEDURE DIVISION USING` で、呼び出し側の項目を位置対応させる。
- `GOBACK` で戻り、メインの `STOP RUN` が実行単位を終了する理由を説明する。
- メインとサブプログラムを一つの実行ファイルにまとめる方法、またはサブプログラムをモジュールにする方法を使う。
- `VALID`、`ZERO-AMOUNT`、`LIMIT-EXCEEDED` を判定し、8件の件数（`008 = 有効005 + 拒否003`）を確認する。

範囲：既定の `BY REFERENCE` のみを使用します。データ方向、`BY CONTENT` / `BY VALUE`、インターフェースCopybook、ABIリスクは[第25課](../25_using-parameters/README.md)。システムエラーコードは[第26課](../26_error-handling/README.md)。ファイルやデータベース入出力はありません。

## 実行環境

- GnuCOBOL 3.2.0、標準方言（`-std=cobol85` は付けない）、固定形式ソース。
- Linux端末。データベースや追加ツールは不要。
- メインは標準出力に結果を報告し、業務データファイルを読み書きしません。生成物はGit対象外の `build/` に置き、実行後に削除します。

## 2つのファイルと1つのインターフェース契約

| ファイル | 役割 |
|---|---|
| [`lesson.cob`](./lesson.cob) | `PROGRAM-ID. LESSON24`。8件の金額を設定し、`CALL`、状態集計、サマリー表示を行うメインプログラム |
| [`amount_check_24.cob`](./amount_check_24.cob) | `PROGRAM-ID. CHECK-AMOUNT`。3つのルールで判定し、状態を呼び出し側項目へ書き戻すサブプログラム |

呼び出し箇所は1つ、引数は2つです。`USING` の順番が契約で、名前は対応付けに使いません。

| 位置 | 呼び出し側項目 | LINKAGE項目 | PIC | バイト | データ方向 |
|---:|---|---|---|---:|---|
| 1 | `WS-AMOUNT` | `LK-AMOUNT` | `9(7)V99` | 9 | 呼び出し側から渡し、サブプログラムは読む |
| 2 | `WS-CHECK-RESULT` | `LK-CHECK-RESULT` | `X(15)` | 15 | サブプログラムが書き、呼び出し側が読む |

```cobol
           CALL "CHECK-AMOUNT" USING WS-AMOUNT WS-CHECK-RESULT
```

既定の `BY REFERENCE` では、サブプログラムは複製ではなく**呼び出し側項目のアドレス**を受け取ります。第2引数へ `"VALID"` を書くと、呼び出し側の `WS-CHECK-RESULT` がすぐに変わります。

このためインターフェースの誤りは実行時に現れます。このワークスペースでは引数を1つだけ渡しても `cobc -fsyntax-only` と `cobc -x -Wall` はエラーを出さず、終了コード `0` でリンクしました。最初の `CALL` で存在しない第2引数のアドレスを参照し、シグナル終了、終了コード `139`、標準エラー `attempt to reference invalid memory address (signal)` となりました。結果項目を `X(20)` とし、呼び出し側が15バイトだけ渡す場合もコンパイルは通ります。実測範囲は末尾に記載します。

本番ではパラメーター宣言を共有Copybookに置き、呼び出し側と被呼び出し側を同じ宣言でコンパイルします（[第25課](../25_using-parameters/README.md)）。

## 検証ルール：1000.00は有効な境界値

[`amount_check_24.cob`](./amount_check_24.cob) は `EVALUATE TRUE` で上から順に判定します。 検証ルールは [`amount_check_24.cob`](./amount_check_24.cob) に集約されています。

1. 金額がゼロ → `ZERO-AMOUNT`。
2. 金額が1000.00より大きい → `LIMIT-EXCEEDED`。
3. それ以外 → `VALID`。

2番目は**厳密な超過**です。そのため **1000.00自体は有効**で、3番目へ進みます。演習1でこの境界を確認します。

金額項目は符号なしの `PIC 9(7)V99` なので負数を表せません。`V` は暗黙の小数点で、物理幅は9バイトです。

## 手計算で確認できる8件

[`lesson.cob`](./lesson.cob) の `1000-RUN-CHECK-CASES` は8段落を順番に実行し、各金額を共通の `2000-CALL-AMOUNT-CHECK` へ渡します。

| # | 段落 | 金額 | 期待状態 | 理由 |
|---:|---|---:|---|---|
| 1 | `1100` | 125.50 | `VALID` | ゼロではなく1000.00以下 |
| 2 | `1200` | 0.00 | `ZERO-AMOUNT` | ゼロ |
| 3 | `1300` | 1000.00 | `VALID` | 上限より大きくない境界値 |
| 4 | `1400` | 1000.01 | `LIMIT-EXCEEDED` | 1セント超過 |
| 5 | `1500` | 0.01 | `VALID` | 最小の正の金額 |
| 6 | `1600` | 999.99 | `VALID` | 上限の1セント下 |
| 7 | `1700` | 9999999.99 | `LIMIT-EXCEEDED` | `PIC 9(7)V99` の最大値 |
| 8 | `1800` | 500.00 | `VALID` | 範囲内 |

件数の不変条件は `検査8 = 有効5 + 拒否3`、`拒否3 = ゼロ金額1 + 上限超過2` です。3・4件目は上限の両側、2件目は唯一のゼロ金額です。

## 実行と観察

入力ファイルはありません。8件の金額は `lesson.cob` の定数です。

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob amount_check_24.cob                 # 2ソースを構文確認
cobc -x -Wall -o build/lesson_24 lesson.cob amount_check_24.cob   # 一緒にコンパイル・リンク
./build/lesson_24                                                 # 実行
echo $?                                                           # 終了コード
rm -rf build                                                      # 実行ファイルを削除
```

`-fsyntax-only` は構文確認だけです。サブプログラムは実行入口ではないため、`cobc -x` に両ソースを含めます。

| 確認項目 | 期待値 |
|---|---|
| `cobc -fsyntax-only` 終了コード | `0` |
| `cobc -x` 終了コード | `0`、コンパイラー診断なし |
| 標準出力 | 20行 |
| プロセス終了コード | `0` |
| 作成ファイル | `build/lesson_24` のみ |

```text
调用方：开始
调用前 金额=0000125.50
调用返回 状态=VALID
调用前 金额=0000000.00
调用返回 状态=ZERO-AMOUNT
调用前 金额=0001000.00
调用返回 状态=VALID
调用前 金额=0001000.01
调用返回 状态=LIMIT-EXCEEDED
调用前 金额=0000000.01
调用返回 状态=VALID
调用前 金额=0000999.99
调用返回 状态=VALID
调用前 金额=9999999.99
调用返回 状态=LIMIT-EXCEEDED
调用前 金额=0000500.00
调用返回 状态=VALID
调用方：子程序返回后继续
检查总数=008 有效=005 拒绝=003
零金额拒绝数=001 超限拒绝数=002
```

`调用前 金额=` は `CALL` 前の金額、`调用返回 状态=` は結果書き戻し後の状態です。`调用方：子程序返回后继续` は呼び出し元へ戻った証拠で、最後の2行は件数です。表示形式 `PIC 9(7).99` により125.50は `0000125.50` と表示されます。

実行時に標準エラーへ `Warning: program compiled against libxml 212 using older 209` が出ます。リンクライブラリー警告で、業務出力ではありません。

## ソースを読む順序

1. `0000-MAIN` が開始を表示し、`1000-RUN-CHECK-CASES`、呼び出し元の継続表示、`3000-DISPLAY-SUMMARY` を順に実行し、`STOP RUN` します。
2. `1100`～`1800` は金額を `WS-AMOUNT` に移し、`2000-CALL-AMOUNT-CHECK` を実行します。
3. 呼び出し側の段落は `WS-CHECK-RESULT` を空にし、表示項目 `WS-EDITED-AMOUNT` を作り、金額表示後に `CALL` します。戻ったら状態を表示し、件数処理を行います。
4. `2100-COUNT-CHECK-RESULT` は `EVALUATE WS-CHECK-RESULT` で有効・拒否と理由を数えます。未知の状態も拒否です。
5. サブプログラムの `0000-VALIDATE-AMOUNT` は `LK-AMOUNT` を判定し、`LK-CHECK-RESULT` に状態を書いて `GOBACK` します。表示と件数は呼び出し側、ルールはサブプログラムが担当します。
6. `CALL` の次の文から呼び出し元が続き、実行単位はメインの `STOP RUN` で終了します。

呼び出し前に結果項目を空にするのは防御的な取り決めです。将来の分岐が書き忘れても、前回状態を再利用しません。結果項目は15バイト固定で `MOVE "VALID"` が末尾を空白で埋めるため、表示には `FUNCTION TRIM(... TRAILING)` を使います。比較ではCOBOLが空白を補完するため `"VALID"` と一致します。

## 終了コード：業務拒否とシステム障害

`ZERO-AMOUNT` と `LIMIT-EXCEEDED` は**業務拒否**で、件数だけを変えます。8件を処理して `STOP RUN` し、終了コードは `0` です。`GOBACK` は状態コードを返さず、第2引数で結果を戻します。

サブプログラムをコンパイルし忘れる例：

```sh
cobc -x -Wall -o build/lesson_24 lesson.cob   # メインだけ
./build/lesson_24
```

リンクは成功します。リテラル `CALL` は `PROGRAM-ID` で**実行時に**モジュールを探すためです。最初の呼び出しで失敗します。

- 標準出力は2行目 `调用前 金额=0000125.50` の後で停止。
- 標準エラー：`libcob: error: module 'CHECK-AMOUNT' not found`。
- 終了コード：`1`。

業務拒否は `0`、モジュール欠落は `1` です。第26課ではこの区別をエラー処理契約にします。

## サブプログラムを別モジュールとしてコンパイル

モジュール名は `PROGRAM-ID` と一致させ、`CHECK-AMOUNT.so` とします。

```sh
mkdir -p build
cobc -m -Wall -o build/CHECK-AMOUNT.so amount_check_24.cob
cobc -x -Wall -o build/lesson_24 lesson.cob
COB_LIBRARY_PATH=build ./build/lesson_24
rm -rf build
```

この方法の出力と終了コードは一括コンパイルと同じで、この環境ではバイト単位で比較済みです。モジュールを個別に交換・共有できますが、検索パスとファイル名の合意が必要です。[第28課](../28_modular-batch-project/README.md)では再現可能なビルドスクリプトにまとめます。

## 変更練習

元の2ソースから始め、検証ルールがあるサブプログラムも含めて毎回再コンパイルします。

1. 上限を `1000.00` から `1500.00` にし、`1000.01` の結果と件数を確認します。
2. 元のソースから始め、`1200-CHECK-ZERO-AMOUNT` の `ZERO` を `0.01` にし、ゼロ金額ケースがなくなる結果を確認します。

詳細は [`exercise.md`](./exercise.md)、解答例は [`answer.md`](./answer.md)。

## 発展課題

顧客利用状態を検証する第2サブプログラムを作り、`ACTIVE`、`FROZEN`、未知の状態に結果を返します。顧客検証失敗時は金額検証の `CALL` を**実行しない**ようにします。`LINKAGE` と位置対応を設計し、2回目を呼ぶ条件を説明します。`CALL` / `LINKAGE` / `GOBACK` / `EVALUATE` だけを使い、ファイルやDBは追加しません。課題は [`exercise.md`](./exercise.md)。解答はありません。

## 実際の処理フロー

1. **上流：** 夜間バッチが取引ファイルを読みます（[第15課](../15_sequential-file-read/README.md)以降）。結果書き込みは[第16課](../16_file-writing/README.md)です。
2. **この課：** 取引金額を `CHECK-AMOUNT` に渡します。口座振替、返金、手数料計算などから同じモジュールを呼べます。
3. **結果受領後：** 呼び出し側が状態を使い、受け入れ／拒否ファイルへ振り分けます（[第22課](../22_file-processing-practice/README.md)）。
4. **後処理：** 件数はログへ（[第27課](../27_logging/README.md)）、システム障害と業務拒否は別の戻りコードで扱います（[第26課](../26_error-handling/README.md)）。
5. **インターフェース：** この課は位置対応です。[第25課](../25_using-parameters/README.md)はデータ方向を明示して宣言をCopybookにし、[第28課](../28_modular-batch-project/README.md)は複数プログラムを再現可能なビルドにまとめます。

成果物は20行の出力だけではありません。ほかのバッチが `CHECK-AMOUNT` という名前、3つの戻り状態、「第1引数は金額、第2引数は結果」という順序に依存する**インターフェース**も成果物です。

## 本番で使う場合

スケジューラーはメインプログラムを起動し、`CHECK-AMOUNT` モジュールも配備パッケージへ含めます。当番担当者は終了コードと件数を確認してください。**業務拒否は終了コードを変えない**ため、`0` は処理完了を示すだけです。

`module 'CHECK-AMOUNT' not found` は配布漏れ、検索パス誤り、旧版配備などです。引数位置の誤りはデータの無言上書きや実行時クラッシュを起こします。導入初月に起きやすいのは、上限を片方だけ変更すること、引数幅変更後に呼び出し側を再ビルドしないことです。明示的な引数方向とCopybook（[第25課](../25_using-parameters/README.md)）、障害コード（[第26課](../26_error-handling/README.md)）、ログ（[第27課](../27_logging/README.md)）、再現可能なビルド（[第28課](../28_modular-batch-project/README.md)）はこの課にありません。

## 実測と未検証

- **実測（GnuCOBOL 3.2.0標準方言）：** 正常系は標準出力20行、終了コード `0`。メインだけのコンパイルは実行時に終了コード `1` と `libcob: error: module 'CHECK-AMOUNT' not found`。`-m` と `COB_LIBRARY_PATH` の別コンパイル結果は一括コンパイルとバイト単位で一致。引数1つでもコンパイルは `0`、実行は `139`。
- **未検証：** 呼び出し側15バイトに対して結果項目を `X(20)` と宣言した場合、実測ではコンパイル成功、実行 `0`、目立つ異常なしでした。状態文字列が5文字なので範囲を超えません。隣接領域の上書きはレイアウト上の推測で、この課では観測していません。
- **保証しないこと：** コンパイラー・プラットフォーム間のABI互換性は範囲外です。コンパイラー検査に関する説明は確認したGnuCOBOL 3.2.0標準方言に限ります。
