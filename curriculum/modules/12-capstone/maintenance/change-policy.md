# 修正方針：布局 v1/v2、兼容、迁移与回滚

## 1. 布局策略

- **追加**而非改写：企业布局 v2 = v1 的 31 字节 + 区分字段的第 2 位子码。
  第 1–27 字节（含 canonical CUSTOMER v1 前缀与第 27 字节记录状态）保持
  原义，所以"只读前 27 字节"的旧读者不会读到错位数据。
- v1 区分升级规则：`A` → `A1`，`B` → `B1`，`C` → `C1`，`D` → `D1`
  （子码 `1` 表示"v1 基线细分"）。这与模块 07 L4 的映射一致。
- v2 合法码：`[ABCD][0-9]`。其他为 `BADCLASS`（业务拒绝，RC4）。
- 记录状态仍只接受 `A`/`D`，与区分独立校验；其他为 `BADSTATUS`（RC4）。
- layout_version 必须与所声明布局一致（`001`/`002`），不符为
  `BADVERSION`（RC4）。
- 整份文件同名布局；同一文件内 31/32 混排是结构错误（RC8）。

## 2. 兼容策略

| 读者 | 对 v1 文件 | 对 v2 文件 |
|---|---|---|
| v1-only 旧程序 | 正常 | **拒绝**（宽度 32 ≠ 31，RC8 / 未完成者 RC12） |
| v2 程序（本次交付） | 读 31B 并升级为 v2 | 读 32B |
| DB customer.table | — | 统一存 v2（32B） |
| 下游 `customer-day.dat` | 区分列升级为 `A1`..`D1` | 区分列为 v2 码 |

## 3. 迁移步骤

1. 上游先在 MANIFEST 声明 `layout_customer=002`，投递企业布局 v2 文件。
2. 本系统在 JOB002a 按声明布局核对物理宽度；不符即 RC8，不发布。
3. JOB002d 把 v1/v2 统一为 v2，写入 DB `customer.table`（32B）。
4. DB 中既有 31B 行：`capdb.read_customer_records` 自动升级，无需停机脚本；
   若需一次性物理迁移，用同函数重写 `customer.table`。
5. 下游切换到 v2 读取；过渡期可继续用 NIGHTRPT 的 v1 读取路径核对。

## 4. 回滚步骤

- 代码回滚到 v1-only 版本即可读 v1 文件（v2 文件会被拒绝）。
- 数据回滚：把 DB `customer.table` 从 32B 投影回 31B（丢弃第 29 字节子码）。
  **投影会丢失子码**，只在确认下游未使用子码时执行，并保留原始 v2 备份。
- 回滚不改动原始输入夹具，仅改派生数据；回滚后必须重跑当日并重新核对控制总数。
- **canonical CUSTOMER v1 的 27 字节与第 27 字节状态语义不在回滚范围内，
  始终不变。**

## 5. 数据切换与并行验证

- 并行期：新旧版本各跑一次同一 v1 日，比对 `customer-day.dat` 与控制总数一致。
- 切换判据：v1 日、v2 日、跨版本日三类全绿，且事故材料可复现（不改原输入）。
