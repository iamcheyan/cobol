# 第23課：Copybook——レコード定義を一度だけ書く

第17、20、22課の各プログラムには、27バイトの口座マスターレイアウトが個別に複製されていました。この課では `copybooks/ACCOUNT-REC.CPY` に切り出し、2つの独立したプログラムから `COPY` でコンパイル時に同じ宣言を取り込みます。さらにフィールド幅を変更し、影響を受ける利用プログラムを確認します。

## 業務の現場

火曜日の午後3時、基幹システムのインターフェース担当者から新仕様が届きました。**口座番号が10桁から12桁に拡張**され、ほかは変更なしです。

夜間照合処理には、同じ口座レコードを読むプログラムが3つあります。27バイト固定長でマスターを読み書きするもの、口座番号で順次照合するもの、財務向けに残高レポートを出すものです。27バイトのレイアウトは、3人がそれぞれ別の時期に自分のプログラムへ書き写していました。

いま答えるべき問いは「どう変更するか」ではなく、**「何か所を変更する必要があるか」**です。

口座番号が2桁増えると、顧客番号と残高の開始位置が2バイト後ろへ移動します。マスターを読むプログラムを正しく直しても、レポート側は古いオフセットでファイルを切り分けます。残高欄には顧客番号の末尾と残高の先頭が混ざります。エラーにはなりません。固定長ファイルには区切り文字がなく、各フィールドのバイト位置は宣言で決まります。誤った宣言でもファイルは最後まで読み取れ、ログは正常、終了コードは `0` のままです。誤りが気付かれるまで数日かかることもあります。

Copybookは宣言をプログラムから独立したファイルに移し、必要なプログラムがコンパイル時に取り込む仕組みです。同じファイルを使うため、上流の幅変更は**一つの宣言**で行えます。

ただし `COPY` は実行時共有ではありません。コンパイル時にソーステキストを挿入します。変更後に利用プログラムを再ビルドし忘れると、古い実行ファイルが旧レイアウトのまま動きます。ファイルとCopybookが正しくても、古いバイナリーが原因となり、問題はさらに見つけにくくなります。

（機関、日付、金額は説明用の架空例です。）

## 今学ぶ理由

第9課では `01` と `05` で階層レコードを作り、第17課では同じレイアウトを27バイト固定長ファイルにしました。数行の `PIC` を別ファイルへ移すだけで、独立した課が必要でしょうか。

必要です。問題は宣言の書き方ではなく、**誰が使い、誰が保守するか**だからです。宣言は各ソースに閉じています。第2のプログラムが同じレイアウトを使うにはコピーするしかありません。`PIC X(10)` と `PIC X(1)` はどちらも正しい構文で、コンパイラーはオフセットの一致を検査しません。レポートの誤りが指摘されるまで警告もありません。

不足しているのは**共有**です。`COPY "NAME.CPY".` で宣言を取り込み、`-I copybooks` で検索場所を指定します。[第24課](../24_call-subprograms/README.md)では金額検証をサブプログラムへ移し、[第24課](../24_call-subprograms/README.md)でその呼び出し方を学びます。メインとサブプログラムが同じレコードレイアウトを使うため、共通宣言が必要です。

## 概念と解決する問題

**概念。** データ宣言を別ファイルに置きます。慣例上、`.CPY` 拡張子を持つファイルを **Copybook** と呼びます。各プログラムに `COPY "ACCOUNT-REC.CPY".` と書くと、コンパイラーがファイルを探し、内容をその位置へ**そのまま挿入**してコンパイルします。つまり、**同じレイアウトを一度書き、複数プログラムで使う**仕組みです。

**なぜ使うのか。** Copybookがなければ各プログラムに個別宣言を持ちますが、コピー間の一致を保証する規則はありません。幅の誤りも構文上有効で、更新範囲は記憶頼みになります。固定長のオフセットが誤ってもファイルは読み終わり、終了コード `0` のまま金額だけが誤ることがあります。

**業務上の問題。** ホスト連携のフィールド幅が変わったら、夜間バッチの保守担当者は**一度のリリースですべての利用側を更新**します。翌朝の照合担当者が見る口座番号は、プログラムとファイルが合意しているかで決まります。レポート残高の正しさは、マスター読み込み側と同じ宣言を使うかに依存します。Copybookにより「誰がこのレイアウトを書き写したか」を探す作業が、「どのプログラムを再ビルドするか」の確認になります。

**誤解とリスク。** `COPY` はコンパイル時の挿入です。各利用側は個別のコンパイル済み宣言を持つため、一方だけ再ビルドすると別の実行ファイルは旧レイアウトです。Copybookに置くのはレコード、フィールド、引数などの宣言で、処理ロジックは `CALL`（[第24課](../24_call-subprograms/README.md)）の役割です。版管理、変更審査、全利用側への通知、旧新レイアウトの並行運用は本番のリリース手順で整備します。

## 修了後にできることと範囲

- 口座・取引の宣言を `copybooks/ACCOUNT-REC.CPY` と `copybooks/TRANSACTION-REC.CPY` に置き、`WORKING-STORAGE SECTION` で `COPY "NAME.CPY".` を使う。
- `cobc -I copybooks` で検索先を設定し、ファイル不足と連鎖する未定義フィールドエラーを説明する。
- `lesson.cob` と `account_report_23.cob` を別々にコンパイル・実行し、同じ物理 `.CPY` を使うことを確認する。
- 口座レコード27バイト、取引レコード20バイトを測り、第17、20、22課の固定長インターフェースと比べる。
- 幅変更後に再ビルドすべき利用側、コンパイラー警告、外部固定長契約への影響を説明する。

範囲：業務ファイルの読み書きはありません。入力はソース内定数です。サブプログラム呼び出し（第24～25課）、エラー分類（第26課）、ログ（第27課）、ビルドスクリプト（第28課）は扱いません。Copybookの版管理や本番変更手順も範囲外です。

## 実行環境

- GnuCOBOL 3.2.0、標準方言（`-std=cobol85` は**指定しない**）、固定形式ソース。
- Linux端末。DBや追加ツールは不要。
- `-I copybooks` を付け、この課のディレクトリからコンパイルします。パスは作業ディレクトリ基準で、リポジトリールートからは解決されません。
- 実行ファイルはGit対象外の `build/` に置きます。

## 2つのCopybookが共有するもの

### フィールド幅はバイト契約

第17課の口座レコードは口座番号10、顧客番号8、残高9バイト、合計27バイトです。第22課の取引レコードは口座10、タイプ1、金額9バイト、合計20です。これはスタイルではなく**バイト契約**です。交換する両側でフィールド開始位置が一致しなければなりません。

### `COPY` はコンパイル時の挿入で、実行時呼び出しではない

コンパイラーは `COPY "ACCOUNT-REC.CPY".` の位置にファイル内容を挿入します。宣言ファイルは `-I` で指定した場所にコンパイル時必要で、実行時には不要です。取り込み位置（この課では `WORKING-STORAGE SECTION`）に有効なCOBOL宣言を書きます。`CALL` と違い、プログラム単位、引数受け渡し、実行時コストはありません。`COPY` はコンパイル対象の形を変え、`CALL` は実行時の制御先を変えます。

### なぜ個別宣言を続けないのか

演習1では `PIC X(10)` を `PIC X(8)` に狭め、両利用側を再ビルドします。コンパイラーは警告オプション（`-Wall` または `-Wtruncate`）がなければ無言です。レコード幅が変わっても、2プログラムの残高と件数は変わりません。

## 入力とルール

**データ源：** 外部ファイル・引数はありません。`1000-INITIALIZE-RECORDS` は口座 `A000000001`、顧客 `C0001001`、残高 `1000.00` を設定し、続く5段落が取引を順番に作ります。

| 順番 | 段落 | タイプ | 金額 | 結果 | 理由 |
|---:|---|---|---:|---|---|
| 1 | `1100-POST-DEPOSIT` | `D` | 125.50 | 記帳 | 残高に加算 |
| 2 | `1200-POST-WITHDRAWAL` | `C` | 25.25 | 記帳 | 残高1125.50から引き出し |
| 3 | `1300-POST-OVERDRAFT` | `C` | 2000.00 | `INSUFFICIENT` | 2000.00 > 1100.25 |
| 4 | `1400-POST-UNKNOWN-TYPE` | `X` | 1.00 | `BAD_TYPE` | `D` / `C` 以外 |
| 5 | `1500-POST-MISSING-ACCOUNT` | `D` | 1.00 | `NO_ACCOUNT` | `A000000099` と `A000000001` が異なる |

| Copybook | フィールド | PIC | バイト |
|---|---|---|---:|
| `ACCOUNT-REC.CPY` | `WS-ACCOUNT-NUMBER` | `X(10)` | 10 |
| | `WS-CUSTOMER-ID` | `X(8)` | 8 |
| | `WS-ACCOUNT-BALANCE` | `9(7)V99` | 9 |
| `TRANSACTION-REC.CPY` | `WS-TRANSACTION-ACCOUNT` | `X(10)` | 10 |
| | `WS-TRANSACTION-TYPE` | `X` | 1 |
| | `WS-TRANSACTION-AMOUNT` | `9(7)V99` | 9 |

`V` はバイトを使わず、`9(7)V99` は9桁です。口座は `10 + 8 + 9 = 27` バイト、取引は `10 + 1 + 9 = 20` バイトで、[第17課](../17_fixed-length-files/README.md)の口座マスターと第22課の取引行に一致します。 [第17課](../17_fixed-length-files/README.md)と[第22課](../22_file-processing-practice/README.md)のインターフェースを参照してください。

**検査する規則と前提：** プログラムは口座一致、タイプ `D` / `C`、引き出し額が残高以下かを検査します。口座・顧客番号の幅や金額の数字形式は検査せず、上流が保証します。拒否順序も契約の一部です。`2000-POST-TRANSACTION` は口座を**先に**検査し、不一致ならタイプも不正でも `NO_ACCOUNT` を返します。拒否経路は残高を変えません。

## ソースを読む順序

1. `WORKING-STORAGE SECTION` の2つの `COPY` が全データ宣言を供給します。`ACCOUNT-REC.CPY` は `01 WS-ACCOUNT-RECORD` と3つの `05` 項目に展開されます。
2. `1000-INITIALIZE-RECORDS` は口座を初期化して、口座番号を取引領域へ写します。5段落は**同じ**取引領域を上書きして `2000-POST-TRANSACTION` を実行します。5件の独立レコードではありません。
3. `2000-POST-TRANSACTION` → `2100-VALIDATE-AND-POST` → `2200-CHECK-WITHDRAWAL` が判定経路です。口座、タイプ、残高を通過して記帳します。
4. `WS-POST-STATUS` は `X(12)`。短い英数字比較は空白で補われ、表示時だけ `FUNCTION TRIM(... TRAILING)` を使います。
5. `WS-EDITED-AMOUNT` と `WS-EDITED-BALANCE` は表示項目です。`9(7).99` のピリオドは格納されません。レポートの `WS-REPORT-BALANCE` も表示専用です。
6. `account_report_23.cob` は同じ物理 `ACCOUNT-REC.CPY` を使う第2の利用側です。

## 実行と観察

外部入力はありません。課のディレクトリから次を実行します。

```sh
mkdir -p build
cobc -fsyntax-only -I copybooks lesson.cob                 # 構文確認
cobc -fsyntax-only -I copybooks account_report_23.cob      # 第2の利用側
cobc -x -Wall -I copybooks -o build/lesson_23 lesson.cob   # メインをコンパイル
cobc -x -Wall -I copybooks -o build/account_report_23 account_report_23.cob
./build/lesson_23
echo $?
./build/account_report_23
rm -rf build
```

`-fsyntax-only` は実行ファイルを作りません。期待される構文確認・コンパイル・実行終了コードはすべて `0` で、診断はありません。メインは7行、レポートは1行を出力します。

| 確認項目 | 期待値 |
|---|---|
| 2つの `cobc -fsyntax-only` | 終了コード `0`、診断なし |
| 2つの `cobc -x -Wall` | 終了コード `0`、診断なし |
| `./build/lesson_23` 標準出力 | 下記7行 |
| `./build/account_report_23` 標準出力 | 下記1行 |
| 両プロセスの終了コード | `0` |
| 作成ファイル | `build/lesson_23` と `build/account_report_23` のみ |

`lesson_23`：

```text
入账成功 类型=D 金额=0000125.50
入账成功 类型=C 金额=0000025.25
入账拒绝 原因=INSUFFICIENT
入账拒绝 原因=BAD_TYPE
入账拒绝 原因=NO_ACCOUNT
账户号码=A000000001 客户号码=C0001001 余额=0001100.25
成功笔数=002 拒绝笔数=003
```

`account_report_23`：

```text
口座レポート 口座番号=A000000009 顧客番号=C0001009 残高=0000020.00
```

計算確認：`1000.00 + 125.50 = 1125.50`、そこから `25.25` を引いて `1100.25`。3件目は残高不足、`X` は `BAD_TYPE`、未知口座は `NO_ACCOUNT` です。記帳2件、拒否3件、合計5件です。実行時ラベルに中国語と日本語が混在するのはリポジトリー既存の規則です。

実行時、標準エラーに `Warning: program compiled against libxml 212 using older 209` が出ます。リンクライブラリー警告で、業務出力ではありません。`-I copybooks` を省くとCopybook不在に続き、未定義フィールドのエラーが出ます。確認環境のファイル不在メッセージは日本語です。

## 固定形式とバイト確認

固定形式では第7列が指示文字、第8列からArea A、第12列からArea Bです。レベル `05` は第11列開始です。

| 位置規約 | この課での実測 |
|---|---|
| 第7列の指示文字 | `lesson.cob` の1、2、3、8、9、12、16、17、56行が `*` |
| Area A、第8列 | `IDENTIFICATION DIVISION.`、`PROGRAM-ID.`、`WORKING-STORAGE SECTION.`、段落名、レベル`01`は第8列開始 |
| リポジトリー規約：レベル`05`は第11列 | 両 `.CPY` の `05` 項目は第11列、`01` グループは第8列開始 |
| Area Bは第12列から | `MOVE`、`PERFORM`、`IF`、`DISPLAY` は第12列開始。ネストは16、20、24列へ |
| プログラムテキストは第72列以内 | 最長行：`lesson.cob` 65バイト、`account_report_23.cob` 71バイト、2つの `.CPY` は44/47バイト |最長のプログラム行は `lesson.cob` 65バイト、`account_report_23.cob` 71バイト、Copybookは44/47バイトでした。

GnuCOBOL 3.2.0は長いソース行を**バイト単位**で第72列付近に切ります。82バイトの `DISPLAY` 行がマルチバイト文字内で切れると `continuation character expected` と `invalid literal` が出ました。第7列が `*` のコメントは110バイトでも無視されます。標準方言を使い、`-std=cobol85` は指定しません。この課は `FUNCTION TRIM` を使います。

幅変更時は両利用側を再ビルドし、外部固定長契約を確認し、[第28課](../28_modular-batch-project/README.md)の物理的に独立したCopybookも別途同期します。第17、20、22課の27バイト口座・20バイト取引インターフェースと不一致になると位置がずれます。

## 発展課題

月次明細用の第3利用側を作り、同じCopybookを再利用します。残高を符号付きPICにし、レコード幅を測ります。負号を表示する項目を選び、`PIC 9(7).99` では足りない理由を説明します。借方残高を生む記帳ルールへ変更し、2プログラムのコンパイルコマンドと出力全文、27バイト契約への影響を示してください。詳細は [`exercise.md`](./exercise.md)、解答は [`answer.md`](./answer.md) を参照してください。

## 実際の処理フロー

1. **上流：** 基幹システムが仕様に基づき27バイト口座マスターを出力し、第17課が読み書きします。このCopybookは仕様をコード化します。
2. **この課：** `lesson.cob` は記帳、`account_report_23.cob` はレポートに同じ宣言を使います。共有するのは**宣言**であってデータではなく、各実行ファイルは個別にコンパイルされます。
3. **次：** [第24課](../24_call-subprograms/README.md)で `LINKAGE` 経由の受け渡しを行い、[第25課](../25_using-parameters/README.md)で引数宣言も共有します。呼び出しの詳細は[第24課](../24_call-subprograms/README.md)を参照してください。
4. **工程化：** [第28課](../28_modular-batch-project/README.md)はビルドを自動化し、[第32課](../32_bank-reconciliation-project/README.md)は版と内容を検査します。
5. **幅変更時：** Copybook変更、全利用側の特定と再ビルド、外部幅の再合意、独立コピー同期を行います。漏れればエラーなしで誤データになります。

## 本番で使うとしたら

この課の2プログラムは手動実行の教材で、バッチ引数、ログ、ビルドスクリプトはありません。本番ではスケジューラーが終了コードと成果物を確認します。バッチ担当者は記帳／拒否件数、インターフェース担当者は口座幅、照合担当者は明細を確認します。

典型的な障害は、一方だけを再ビルドして別のプログラムが古いオフセットのまま動くことです。どちらもエラーを出しません。Copybookは後続サブプログラムや引数定義から使われる外部インターフェースになるため、幅と順序は版ごとに合意します。この課では版管理、旧新レイアウト対応、変更審査、利用側一覧、上流形式検証は実装しません。関連課は第24～28課と第32課です。

## 検証した範囲と制限

このワークスペースでは両構文確認・ビルドが診断なし、終了コード `0` であること、両プログラムの出力、`-I copybooks` 省略時のエラー、相対パス挙動、`.CPY` の大文字小文字区別を確認しました。`FUNCTION LENGTH` は口座27バイト、取引20バイト、口座番号を狭めた後は25バイトを示しました。

`-Wall` 付きの幅変更では両利用側に `-Wtruncate` が出ますが、終了コードは `0`。警告指定がなければ表示されません。`lesson_23` の口座番号は切り詰められますが、残高と件数は変わりません。[第17課](../17_fixed-length-files/README.md)、[第20課](../20_file-matching/README.md)、[第22課](../22_file-processing-practice/README.md)のプログラムが25バイトレコードをどう扱うか、他環境の動作は未検証です。ルートの `make course-check` は構文を確認しますが実行動作は検査しません。
