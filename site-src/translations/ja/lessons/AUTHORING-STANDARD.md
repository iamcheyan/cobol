# 32課メインカリキュラムの改訂分析と制作基準

> 対象範囲：`lessons/01_*`〜`lessons/32_*` の README、COBOL/Copybook、スクリプト、入力フィクスチャ、`exercise.md`、`answer.md`。本書は次回の各課改訂に向けた実行・検収基準であり、既存教材がすべての条項を満たすことを示すものでも、今回一括改訂を許可するものでもない。

## 1. 目標と現状

プログラミング、Linux、データファイルの基礎を持つ COBOL 初学者が、最終的に銀行の夜間照合バッチを理解して実行できることを目指す。各課では、どの業務課題を解くのか、今の知識ではなぜ足りないのか、コードが何を入力し何を出力するのか、実装済みの保証と本番環境で追加すべき要件は何かを読者が説明できる必要がある。全体の依存関係は [`DIRECTORY.md`](DIRECTORY.md) を参照。

既存教材に業務説明がまったくないわけではないが、導入と深さにばらつきがある。第01〜28課は同じ GnuCOBOL バージョンの文から始まることが多く、第29〜32課は専用ツールチェーンやプロジェクト概要を記す。第02課は PIC とインターフェース契約、第20課はソートキーと順次照合の関係を説明済みだが、読者は本文まで進まないと業務上の動機が分からない。第15課は4件の取引でファイル読み込みと EOF を示し、第28課はモジュール間インターフェースに焦点を当てるためプログラム内の5件を使い、第32課は実ファイル、SQL、再実行、部分失敗の検証を含む。こうした有効な内容を残し、導入を組み直して本当に不足する説明と証拠を補う。

主な確認点：

- `Makefile` の `course-check` は各課の4種類のファイルの存在を確認し、第01課だけをコンパイル・実行する。32課すべての動作検収とは呼べない。
- `01/exercise.md` には「草稿、課の検収待ち」が残り、変更課題は英語の挨拶を求める一方、README と `answer.md` は日本語の挨拶を求めている。各課の README、練習、回答、実際の状態を照合し、古い検収記述をそのまま引き継がない。
- 文書の解説は中国語で、一部のソースコメントと端末出力は日本語、インターフェース表記は英語も使う。各課で中国語話者が主要な出力を説明できるようにする。実行上の約束は、言語統一だけを理由に変更しない。
- 文の動作を繰り返すコメントもある。例えば第15課末尾の EOF フラグと件数、第03課の `ROUNDED` なしの切り捨て説明など。逐語的な説明より業務ルール、例外の理由、復旧境界を残す。
- 第15〜21課には小さなフィクスチャと一部の境界練習があり、第22、32課には入力・出力・失敗・復旧の証拠がよりそろっている。学習段階に応じて複雑さを増し、コード行数では評価しない。

### 第1回改訂の実施状況（2026-10-16）

32課は本基準に沿って各課ごとに改訂・コミット済み。前述の5点の現状を記録する。この節は事実の記録であり、上の審査結論は変更しない。

- `Makefile`：`course-check` は全32課の納品物を確認し、第01〜28課を構文検査、第01課を動作スモークテストする。`course-check-sql` は第29〜32課のプリコンパイル検査と第32課の `check.sh` エンドツーエンドシナリオを対象とする。動作検収の基準は各課 README のコマンドと第32課 `check.sh`。
- 第01課：草稿状態と英語・日本語の挨拶の不一致を解消し、README、exercise、answer を一致させた。
- 言語方針：「README は中国語、実行出力は既存の日本語」を維持し、各課 README に出力ラベルの中国語訳を記載する。
- コメント：第03、15課などの重複または古いコメントを削除・書き換え、各課のコメントを「契約／業務ルール／復旧境界」に沿って整理した。
- フィクスチャと境界：第15〜22、26、30〜32課に空入力、EOF、長すぎる行、ファイル欠落、書き込み失敗、SQL 部分失敗、再実行などの経路を追加した。安定して注入できないケースは未検証と明記した。
- 未参照の `*_ja.cob` 重複ファイル（多くは主ファイルと同一で、一部は DISPLAY ラベルだけ異なる）を該当課から削除した。有用な契約コメントは主ファイルへ移した。

## 2. 基本方針と検収レベル

**分量ではなく、課ごとの能力の積み上げで設計する。** 各課は、中心となる能力、その前提、観察可能な業務処理、後続課へ渡す成果物を明確にする。初期課では概念を切り分けるために小さな値をハードコードしてよい。ファイル、プロジェクト、データベースの段階では、実際のフィクスチャ、ファイル、SQLite を扱い、`DISPLAY` の模擬表示を読み込み・書き込み・SQL 実行と称してはならない。

**次の3段階の約束を区別する。**

| レベル | 最低要件 | これと誤解させないこと |
|---|---|---|
| 教育用デモ（01〜14、一部の単概念課） | コンパイル・実行可能。目標概念と主要な境界が観察できる。ハードコード、制約、未学習内容を明記 | そのまま本番稼働できる業務バッチ |
| 再現可能な業務演習（15〜31） | 添付入力または実モジュール／DBを実際に処理する。契約、状態、出力、終了コード、リセット方法を記載し、課の中心的な境界を検証 | 完全な運用、トランザクション、監査の保証 |
| 総合プロジェクト（08、14、22、28、32。段階に応じて強化） | 学習済み能力を接続する。入力→ルール→出力、件数の不変条件、代表的な失敗と再実行を説明し、結果を独立に検算できる | 複数ファイル／DBの原子性や本番での冪等性が自動的に備わること |

課題に必要な複雑さを選ぶ。有意義な業務分岐、境界入力、状態変化、検算可能な結果を優先する。新しいコードは課の目標を教えるか既習能力を支える場合だけ追加する。「本番らしさ」のために第02課へ未学習のファイル I/O を入れたり、第15課で記帳全体を先取りしたりしない。本番級設計が必要なら後続の総合課に置き、初期課ではリスクと接続先の課を示す。例の業務用語には明確なルールを与え、規制や財務、安全基準に適合すると根拠なく主張しない。

## 3. 各課の改訂前に設計カードを作る

課を改訂する前に、次の項目をその課に合わせて記録する。「企業開発を理解する」のような一般論で空欄を埋めない。

1. **学習上の位置：** 課番号、前提能力、新しい中心概念は1〜2個、後続課／プロジェクトで成果物をどう使うか。
2. **業務タスク：** 誰がどのデータを渡し、どのルールで判断し、結果を誰に渡すか。初期課の模擬データはデモ用と明記。
3. **契約：** 入力元、フィールド幅・単位・文字コード（該当時）、ソート順と一意性の前提、出力ファイル／標準出力／DB変更、正常・異常時の戻りコード。
4. **判断点：** どのフィールド／状態で経路が変わるか。コードが検査する条件と、フィクスチャだけが保証する条件を区別。
5. **観察できる証拠：** 正常値、中心概念に隣接する境界・失敗値、期待出力、独立した計算根拠。
6. **教材の境界：** 未実装の能力と後続の担当課。制限が例の理解に影響するか。
7. **変更一覧：** README、ソース、コメント、練習、回答、フィクスチャ、スクリプト、総目次／課間インターフェースの影響。変更しない項目と理由。

設計カードは課の改訂タスクや納品報告に含めればよく、恒久ファイルを毎課増やす必要はない。まず隣接課と `DIRECTORY.md` を確認し、それから拡張の要否を決める。すでに満たす内容をテンプレートのために重複記載しない。

## 4. README の執筆基準

### 4.1 冒頭の順序

1. タイトル：課番号と具体的なタスク／概念。
2. **一文の導入：**「業務場面＋この課で行う処理＋成果／後続用途」を示す。二文でもよいが、バージョン番号だけで始めない。
3. **今学ぶ理由：** 既習能力で何ができ、どんな具体的な不足に直面し、この知識が何を解決するか。基礎課なら短い業務例でよい。
4. **修了後にできることと境界：** 観察可能な操作を3〜5個挙げ、中心成果と後続に残す能力を示す。「理解する」「習熟する」だけにしない。
5. **実行環境：** GnuCOBOL のバージョン、既定方言／固定形式、OS、追加ツール。DB課では GixSQL／SQLite、対応環境、ビルド入口を明記する。共通事項は総目次へリンクし、固有制限は各課に記す。

例：第15課なら「銀行の日次取引はテキストファイルで届く。この課では取引の原文を1件ずつ読み、ファイル終端とオープン失敗を見分け、後続のフィールド解析と照合の入力処理を作る」と説明する。続けて EOF が業務エラーでない理由と、まだフィールド解析をしないことを書く。例文は書き方の見本にすぎない。実際に改訂するときは、各動詞をコードが裏付けるか確認する。

### 4.2 本文で答える読者の疑問

- **業務と概念：** なぜこの能力が必要か、新しい構文がどう処理するか、前課と何が違うか、既習の方法ではなぜ足りないか。
- **入力とルール：** データの出所、主要フィールドと有効値、金額単位と精度、空値／重複／範囲外／未知コードの方針。入力がない課ではプログラム内定数と明記する。前提、実装済み検査、障害後の動きを区別する。
- **実行と観察：** 課のディレクトリから、または任意の場所から実行する条件。構文検査、ビルド、実行、クリーンアップの違い。期待する stdout、ファイル、DB変更、終了コードを個別に示す。stderr の環境警告を業務出力として扱わない。
- **ソースを読む順序：** データと状態変化に沿って主要段落／フィールドを説明する。分かりにくい COBOL のスコープ、メモリ配置、呼び出し契約、状態コードを説明し、明白な行を逐一言い換えない。
- **実務との接続：** 成果物が後続の銀行照合でどう使われるか、本番で追加の保証が必要かを説明し、具体的な課番号を挙げる。「企業でよく使う」だけで済ませない。
- **練習と参考回答：** README で問題を要約し、`exercise.md`／`answer.md` にリンクする。問題、初期値、期待結果を一致させる。回答のない応用課題は、独力で取り組む範囲を説明する。
- **証拠：** 検証済みコマンドと範囲を現行コードに合わせる。未実行のケースは未検証／既知の制限と明記し、期待結果を実測と偽らない。

課に応じて節名や長さを調整する。01〜14課は概念、状態変化、業務上の動機を中心にする。15〜22課ではファイル形式、物理レコード／EOF、結果ファイルを加える。23〜28課ではモジュール責務と引数契約を加える。29〜32課ではプリコンパイル、SQL状態、DBの変更前後、復旧境界を加える。毎課に同じ「企業実践」段落を貼り付けない。

## 5. COBOLサンプルとプロジェクト基準

### 5.1 データ、状態、境界

- すべてのソースを固定形式に保つ。第7列が指示領域、Area A は第8列から、Area B は第12列から始め、有効なプログラム文字を第72列より後に置かない。厳密な `-std=cobol85` は使わず、既存の `COMP-3`／`FUNCTION TRIM` を含む GnuCOBOL 既定方言を維持する。
- フィールドの `PIC`、`USAGE`、初期値、幅、業務単位を一致させる。識別子と数値、文字数と物理バイト数、暗黙小数と外部表示を区別する。レコード配置を変える場合は、すべての生成元・利用側、Copybook、フィクスチャ、期待値、SQLテーブルを追跡する。
- コードの分岐と文書を一致させる。EOF、未検出、業務拒否、システム障害を混同しない。`FAILED` の表示、フラグ設定、非ゼロコードの返却、オープン済みリソースのクローズは、記載した契約どおりに動くこと。未実装の検査を「自動拒否」と書かない。
- ファイル課では行順レコードと固定長レコードの違い、作業ディレクトリとファイル名、上書き／追記、レコード幅、キーの順序・一意性、長すぎる入力の方針を明記する。DB課では `EXEC SQL` の実際のプリコンパイル手順、SQLCODE 0／100／エラー、接続／カーソルの寿命、ドライバー固有の挙動を示し、SQLiteの挙動を Oracle／PostgreSQL 全般へ拡大解釈しない。
- 総合課では件数と金額の照合を手計算できる根拠を示す。障害後の出力やコミット済みDB状態、復旧方法を正確に記述する。第32課では「SQL失敗時に先行行の更新が残る」境界があり、原子的なコミットと称してはならない。

### 5.2 複雑さを段階的に増やす

| 段階 | 追加できる実業務 | 範囲として抑えること |
|---|---|---|
| 01〜08 言語と制御フロー | 口座番号、残高、取引種別、金額を使う一貫した小さなルール、境界値、明確な受理／拒否理由 | 外部ファイル、完全な財務承認、未学習のテーブル／SQLを早期に強制しない |
| 09〜14 データ構造 | レコード配置、容量上限、ビュー切替、検索の前提、照合結果 | メモリ上の小テーブルを大規模ファイル用索引や本番台帳と呼ばない |
| 15〜22 ファイル処理 | 実フィクスチャ、空ファイル／短長レコード／EOF／孤立キー、結果ファイル | 単概念課はテーマに直接関係する障害に限定し、総合課で全経路をつなぐ |
| 23〜28 モジュール化 | 引数の順序／方向、共有Copybook、ログと業務エラーの分離、再現可能な構築 | すべてのインターフェース課に全外部I/O障害への対応を求めない |
| 29〜32 DBとプロジェクト | 実SQL、データなしとエラー、スナップショット差、再実行、部分失敗の確認 | トランザクション、並行性、移植性を根拠なく約束しない |

分岐やフィールドを追加するなら、フィクスチャ、説明、練習、期待値も合わせて更新する。新たな観察可能な動きがなく、単にコードを長くするだけなら拡張しない。

## 6. ソースコメント基準：業務プログラムの保守者向けに書く

**コメントは「なぜこの処理か、どの前提に基づくか、破ると何が起きるか」を答える。コードは「何をするか」を示す。** 保守者がソースだけを読んでも誤用しないよう、ルールやインターフェースの近くに置く。READMEが概念説明を担うため、教科書全体をコメントに詰め込まない。コードコメントは簡潔な中国語またはプロジェクト既定の業務用語を使う。外部インターフェース／実行出力に既存言語の維持が必要なら、実際の契約を壊して統一せず、READMEで説明する。

コメントに残す内容：

- インターフェース契約と前提：外部レコードのオフセット／単位、上流が保証するキー昇順・一意性、`CALL USING` の引数配置と更新責務など。
- 業務判断：残高不足をバッチ全体の失敗ではなく業務拒否とすること、整数分から換算する前の数値検査、未知取引コードを正常記帳へ流さないことなど。
- 分かりにくい技術制約：`REDEFINES` が同一領域の別ビューであること、`PERFORM` の段落戻り境界、実測済み GixSQL の例外、出力書き込み失敗後に成功と報告できないことなど。
- 復旧と監査の境界：同期前に受理ファイルが出力済みであること、SQL失敗後も更新済み行が残ること、照合件数の不変条件と失敗条件など。

コメントにしない内容：

- 各 `MOVE`、`ADD`、`IF`、`DISPLAY` の逐語的な中国語訳。フィールド名や段落名で分かる動作。
- コードと重複する説明、古い実行結果、実装していない本番保証、READMEからの長い貼り付け。
- テスト用定数を正式な業務方針のように扱うこと、「エラーを確認する」とだけ書いて種類を示さないこと。

コメント例（固定形式、第7列が `*`。フィールドや状態名は実際の対象ソースに合わせる）：

```cobol
      * 上流按账户号升序且去重；逆序会使顺序匹配漏报。
      * 本课将此条件视为输入契约，未在程序中校验。
           PERFORM 2000-MATCH-RECORDS
```

対象課で順序を実行時検査しているなら、2行目を実際の失敗経路に合わせる。そうでなければ、この例をそのまま流用しない。コメントごとに「削除すると業務制約、予期しない挙動、保守上のリスクが失われるか」を問う。失われないなら削除する。有効な日本語コメントは内容を正確に中国語へ移してよいが、翻訳した上で同じ情報を重複させない。プログラムコメント、README、実際のエラー処理を一致させる。

## 7. 練習、回答、フィクスチャ、検収証拠

各課に少なくとも1つ、**回答付きの変更練習**を置く。開始基準、変更場所と制約、再コンパイル／実行コマンド、完全な期待差分と理由を示す。回答はその練習だけに答え、別問題の完了を前提にしない。加えて**回答なしの応用練習**を置く。似た業務場面に置き換え、学習者がフィールドやルール、検証方法を独自に選ぶ。明示的な発展課題でない限り、未学習の仕組みを要求しない。README、exercise、answer の範囲を一致させる。

フィクスチャと期待値は、中心ロジックを独立に検算できるようにする。少量のデータで通常経路と隣接境界を示す。ファイル処理ではバイト幅、改行、順序、レコード数を、金額処理では単位、丸め、保存則を、DB処理ではSQLと変更前後を確認する。入力をその場で変更するか、実行時に何を上書きするか、クリーンなフィクスチャからどう再実行するかを記す。プログラム自身が作った出力だけを正解の根拠にせず、ルールを手計算するか独立した方法で確かめる。

変更範囲に応じて検収シナリオを選び、すべての課に巨大な同一マトリクスを求めない。

| 課の種類 | 最低限実行・観察すること |
|---|---|
| 構文／メモリ基礎 | 課の構文検査、コンパイル、実出力。中心境界値を変更して再実行 |
| ファイル／ソート | 実フィクスチャを実行し、ファイル内容、行／バイト数、RC、テーマに関係するEOF／不正入力／順序境界を検査 |
| モジュール／スクリプト | クリーンな状態から主プログラムを構築・実行し、インターフェース、ログ／出力、失敗状態を確認 |
| SQL／総合 | 実ツールチェーンで実行し、DB照会、出力ファイル、件数、終了コード、宣言済みの障害／再実行を確認 |

`cobc -fsyntax-only` が証明するのは構文経路だけ。`build.sh check` が動作シナリオまで実行するかは課ごとに確認する。ツールチェーン不足、安定した障害注入ができないケース、環境制限は実際に検証できた範囲とともに記す。「合格」を捏造しない。stdout、レコード形式、インターフェースを変えたら利用側、フィクスチャ、回答も照合する。古い問題、リンク、草稿状態、過去の誤った「実測」記述を修正する。

## 9. 後続 goal の実行方法と納品基準

1. **基準を確定する：** 主担当が現状、ツールチェーン、課間レコード／出力契約を調査し、32課のタスクリストを作る。総目次、全体README、共通ビルド／検査入口は一人の統合担当が管理し、並行編集の競合を避ける。既存の拡張課程 [`AUTHORING-STANDARD.md`](../extensions/enterprise-batch/docs/curriculum/AUTHORING-STANDARD.md) は、より厳しい企業向けバッチ演習用である。その障害マトリクスすべてを主線の基礎課へ適用しない。
2. **課ごとに割り当てる：** 1課のディレクトリは1人が設計カード、README、ソース、コメント、練習、回答、フィクスチャ、スクリプトまで完結させ、前提順に検収する。隣接課の調査は並行できる。インターフェースやデータ形式の変更は、統合担当が契約を決めてからまとめて実施する。
3. **課ごとに納品する：**「現状→設計判断→変更ファイル→正常／境界／失敗の実コマンドと結果→未検証項目→課間影響」を報告する。動作に影響しない説明変更を機能変更の検証済み実績のように扱わない。未完成のプレースホルダーを提出しない。
4. **相互レビューする：** 別のレビュアーがREADMEから実行するか重要値を再計算する。業務上の動機、前提、コメントの正確さ、練習の独立性、回答との一致、固定形式を確認する。具体的な誤りがあれば課へ戻して直す。「将来改善する」で代替しない。
5. **段階統合する：** 各段階の完了時に、隣接課の前提、命名、フィールド幅／単位、ディレクトリリンク、課の実行スクリプト、リセット方法を確認し、代表経路を実際に動かす。第29〜32課は対応ツールチェーンを前提とする。欠けている場合は環境上の阻害要因として記録し、モックSQLで合格扱いにしない。
6. **完了条件：** 32課すべてに個別設計と検証証拠がある。影響する利用側、フィクスチャ、回答、総目次、共通入口をそろえる。「草稿／検収待ち」の誤った状態を残さず、教材目標とプログラム動作を一致させる。全体整合性検査、各段階の代表経路、既存の最終プロジェクト `check.sh` が通ってから、カリキュラム全体の完了を宣言する。

### 課別タスクカードのひな形

統合担当が実行者へ渡す際に以下を記入する。未確認の項目は推測で埋めず「調査中」とする。

```text
課番号／ディレクトリ：
前提と後続の接続先：
この課で必ず教える能力（1〜2個）：
現時点で正しい内容と具体的な課題（ファイル位置を記載）：
変更可能なファイル：当該課のディレクトリ。課間契約は統合担当が確定してから変更。
業務入力→ルール→出力／RC：
教材の境界：先取りしない知識、上流前提にすぎない条件。
検収シナリオ：正常、関連境界、該当する障害。期待値と独立計算根拠。
納品：設計カード、変更ファイル、実行コマンドと観察結果、未検証項目、課間影響。
```

同一課のREADME、コード、練習、回答、フィクスチャは同じ実行者が一貫して保守し、統合担当は共有入口と課間契約を扱う。`DIRECTORY.md` の6段階（01〜08、09〜14、15〜22、23〜28、29〜31、32）に沿って進める。段階内で別ディレクトリなら並行できるが、後続課が前課のデータ定義に依存する場合は共通の幅、単位、インターフェース、期待出力を確定してから割り当てる。各課を個別レビューしてから段階完了とする。段階間の契約が変わったら、受け入れ済みの利用側を調べ、影響シナリオを再実行する。

納品報告では次の証拠表を使う。課ごとに恒久レポートを作る必要はない。

| シナリオ | クリーンな入力状態 | 期待する stdout／ファイル／DB／RC | 実際のコマンドと観察結果 | 一致したか、差異の理由 |
|---|---|---|---|---|
| 正常経路 | フィクスチャとリセット方法 | 独立計算した主要値 | 実行記録 | 結論 |
| テーマ境界 | 最小変更とその目的 | 対応する変化と不変条件 | 実行記録 | 結論 |
| 障害経路（該当時） | 再現可能な障害注入 | 失敗状態と残留成果物 | 実行記録または未検証理由 | 結論 |

タスクカードと報告では「文書上の期待」「自分で実行して観察した結果」「コードからの推定」を区別する。文書だけを変更した場合も現行プログラム／フィクスチャとの一致を確認する。動作変更なら影響経路を再実行する。自分でREADMEを言い換えただけで独立レビューの代わりにしない。

各課の納品レビュー項目：

- [ ] 冒頭で業務タスク、知識上の不足、成果を説明し、環境バージョンを実行条件に記す。
- [ ] 目標をソースと実行結果から確認でき、前提を越える概念を追加していない。
- [ ] 入出力、フィールド単位／幅、前提、分岐、エラー、終了コードが実コードと一致する。
- [ ] コメントはルール、契約、技術上の制約を説明し、逐語訳や古い説明を除いている。
- [ ] 固定形式と、影響するCopybook、スクリプト、フィクスチャ、利用側が一致する。
- [ ] 変更練習、応用練習、回答、READMEが一致し、結果を独立に検算できる。
- [ ] 実コンパイル／実行とテーマ境界を検証し、コマンド、観察、未検証範囲を記録した。
- [ ] 隣接課と総目次の関係が正しく、本番保証や実測結果を誇張していない。
- [ ] §10を満たし、業務現場が具体的で自然な口調になっている。稼働準備済みと誤解させない。

## 10. 実務感と自然な語り口（§4〜§6への追加要件）

これまでの改訂で「正確さ」は得られた。コマンド、出力、境界は検算できる。しかし読み味は検収規程に近く、文型がそろい、結論が詰め込まれている一方、「職場で誰が使うのか、使わないと何が起こるのか」が伝わりにくい。硬い事実を変えず、経験のある同僚が手順を教えるように書く。

### 10.1 各課で必ず答える4つの問い

順に説明し、冒頭2画面を読むだけで答えが分かるようにする。

1. **この知識は何か。** まず新たにできることを平易に述べ、その後に用語を出す。「この課でX構文を導入する」と書き始めない。
2. **なぜ必要なのか。** 使わなければ何が書けないか、どう間違えるかを具体化する。「同じ処理を12万回コピーする羽目になる」「3件目の金額に文字が混ざり、バッチ全体が失敗する」など。
3. **実業務では何を解決するか。** 銀行、保険、証券、決済、製造の誰が、いつ必要とするかを示す。なければその人が何を手作業し、どんなリスクを負うかを書く。
4. **使うべきでない場面、誤用の結果は何か。** 構文エラーより業務上の誤用の方が高くつく。

### 10.2 各課の冒頭に「業務現場」を置く

- 具体的な場面を2〜4段落で描く。誰が何時に、どのシステムを、どの程度の量と締切で扱い、失敗すると何が起きるか。細部を入れる（「午前8時までに12万件を処理」「9時の窓口開始を待つ顧客」など）。
- 場面はその課の知識が解決できる内容にする。話を逸らさず、「規制要件を満たした」と誇張しない。
- 場面は**教育用デモ**である。組織名、金額、日付を出すとき、実在組織の実データと誤解させない。

### 10.3 規程文ではなく同僚に話すように

- 「こう考えるかもしれない」「まずループを書き始めないで」「ここが一番はまりやすい」「これで午後をつぶす人を見たことがある」のような表現や、二人称を使ってよい。
- 公文書調の「本課では〜する」「当該フィールドは〜しなければならない」「目的とする」「総括すると」「不足は3点」を避ける。「必須／すべき」を連ねず、手順を抜くと起きることを直接書く。
- **32課それぞれの文章にする。** 業務ストーリーは課の知識に根ざし、同じテンプレートを使い回さない（例えば全課を「銀行の夜間バッチでは……」で始めない）。同じ段階で関連させても、文章は別にする。
- 文は短く、一文一段落でもよい。技術的な密度は必要なデータとコードに置き、形容詞を重ねない。

### 10.4 口語化しても失ってはならない事実

- コマンド、期待stdout／ファイル内容、バイト数、終了コード、ファイル状態コードはコードと実測に一致させる。変えるのは言い方であり、結論ではない。
- 未検証項目は引き続き明記し、なぜ検証できなかったかを書く。
- 新しい業務説明から、新たな技術保証（特に本番稼働可能という含意）を導かない。

### 10.5 構成の調整

- §4.1の導入順と§4.2の必須質問は維持し、この節の要件を重ねる。
- 業務現場は「今学ぶ理由」の前または中に置く。「この知識は何か」「何を解決するか」をすぐ見つけられるようにする。
- 「企業における位置づけ」を「このコードを本番に入れたらどうなるか」へ具体化する。誰がスケジュールし、誰がログを見て、障害時に誰が呼ばれ、次のシステムがどう受け取るか、最初の月に何が起きやすいかを書く。
- 各課に「実際の流れをたどる」節を設ける。成果物をエンドツーエンドの連鎖に置き、受け手と、その処理を担う後続課のソースを示す。

### 10.6 反例から正例へ

反例（業務現場がなく、公文書調）：

> 本課では `PERFORM VARYING` を導入し、「1件の処理」をループにまとめ、反復範囲と件数を独立に検算できるようにする。課題は「繰り返し」である。実際のバッチでは N 件の取引に同じ処理を行い、N は実行時に決まる。

正例（構文に入る前に現場を示す）：

> 処理するのは3件ではなく12万件だ。しかも件数が分かるのは朝7時になってから。
> 同じコードを12万回コピーするだろうか。もちろんしない。バッチでは同じ処理を実行時に決まるN回繰り返すことがよくある。COBOLなら `PERFORM VARYING` を使い、1件目から始めて、処理のたびに番号を増やし、上限を越えたら終了する。
> 簡単そうに見えるが、事故は境界に集中する。上限の1件は処理するのか。0件の日に余計な1周が起きないか。この課で両方を確かめよう。
