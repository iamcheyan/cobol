# 第22課：総合演習——整列・検証・照合・結果出力

この課で一つの小さなバッチを完成させます。未整列の取引ファイルと整列済み口座マスターを受け取り、**受け入れ、拒否、マスターのみの一覧、制御件数**を出力します。4つの成果物は互いに整合していなければなりません。新しい構文はなく、第15～21課の要素を一つの処理に接続します。途中で失敗した場合にディレクトリへ何が残るかも扱います。

## 業務の現場

金曜夜、日次バッチが照合処理へ進みます。上流の2つのジョブが作業ディレクトリへファイルを置きました。口座マスターは日中にホストから抽出され、口座番号順です。取引ファイルは窓口とモバイルバンキングの1日分で、入力順のまま**未整列**です。すべての取引に対応する口座がマスターにある保証もありません。

処理後の成果物は画面ではなく、次の人やシステムへ渡します。

- 受け入れ明細は次の記帳ジョブへ。
- 拒否明細は運用担当へ。翌朝、顧客が未記帳の理由を尋ねたら、窓口担当者はこのファイルを調べます。
- マスターのみの口座は照合担当へ。口座は存在するが当日取引がなかった一覧です。
- 制御件数は上流ジョブの報告件数と照合します。

「プログラムが終了した」と「バッチを引き渡せる」は別です。引き渡せるとは、**全レコードの行き先が説明でき、全マスターレコードが一度ずつ処理され、件数が整合する**ことです。

2つの結果ファイルは `OPEN OUTPUT` で開くため、**実行ごとに以前の内容を上書きします**。マスター読み込みやディスク書き込みで途中失敗すると、ディレクトリに残るのは**部分的な新結果**です。以前の結果でも完全な新結果でもありません。ロールバックはありません。引き渡す前に件数と行数を照合してください。

（機関、口座、金額、日付、時刻は説明用の架空データです。）

## 今学ぶ理由

ファイル読み込み、整列、キー照合、結果ファイル出力は個別に練習しました。まだ行っていないのは、**一回の実行内ですべてをつなぐこと**です。

前のフィクスチャは各概念を切り分けていました。第21課は未整列入力、第20課は両側が整列済み、第16課はすでに分類済みの結果を扱いました。実際のバッチでは、未整列レコード、マスターにない口座、不正な取引コード、金額中の英字、取引のないマスター口座が一度に混在します。

一回の実行で全部を分類し、各結果の証拠を残し、**「このレコードはどこへ行ったか」「一件も漏らしていないか」**に答えます。拒否理由とファイル行が前者を、件数不変条件が後者を示します。構文を覚えるだけでなく、バッチを引き渡せる状態にする練習です。

## 概念と解決する問題

新しい構文はありません。既習の処理を決まった順に並べます。取引を口座番号で整列し、マスターと順次照合し、一致したレコードを検証して2つのファイルへ振り分け、最後に件数を表示します。マージスキャンの規則は同じです。キーが等しければ一致し、小さいキー側を先へ進めます。

**すべてのレコードに行き先が必要です。** 次の2つの式で確認します。

- `受け入れ件数 + 拒否件数 = 入力取引件数`。取引は受け入れか拒否のどちらか一方です。
- `照合済みマスター件数 + マスターのみ件数 = マスターレコード件数`。各マスターレコードを一度処理し、取引がないものをマスターのみとします。

電卓で誰でも確認できます。漏れの有無を尋ねられたら、ログを探す代わりに件数を示せます。

**失敗時の出力状態を把握します。** 出力ファイルは置き換えモードで開き、実行中に書き込みます。途中失敗では旧結果が失われ、不完全な新結果が残ります。終了コード `0` だけでは引き渡し確認にならず、件数と行数も照合します。

**失敗や誤用の注意点：**

- このプログラムは記帳しません。**分類と出力**だけを行い、残高更新や借貸ルールを適用しません。
- マスターの昇順と口座番号の一意性が前提ですが、**このプログラムはどちらも検査しません**。順序逆転や重複キーは静かな誤照合につながります。
- 2ファイルへの書き込みは**原子的な引き渡し**ではありません。`OPEN OUTPUT` や `WRITE` の失敗で部分出力が残ることがあります。

## 修了後にできることと範囲

- `SORT` と `INPUT PROCEDURE` / `RELEASE` で未整列取引を整列し、登録前に幅を確認する。
- マージスキャンで各取引を受け入れ、マスターなし拒否、不正項目拒否へ分類し、残ったマスターをマスターのみとして記録する。
- `accepted.txt` と `rejected.txt` を作り、行と幅を照合する。
- `受け入れ + 拒否 = 入力取引` と `照合済みマスター + マスターのみ = マスター` で漏れを検出する。
- `OPEN OUTPUT` が旧結果を置き換えること、整列・照合の前提、未実装の会計統制を説明する。

範囲：**分類と出力**のみです。残高集計、借貸ルール、2ファイルの原子的引き渡しはありません。マスターは昇順かつ一意である必要がありますが、プログラムは検査しません。同一口座の複数取引は未対応です。バッチID、再実行、原子的出力、金額ルールは第26～32課で扱います。

## 実行環境

- GnuCOBOL 3.2.0、標準方言（`-std=cobol85` は付けない）、固定形式ソース。
- Linux端末。データベースや追加ツールは不要。
- `SELECT` は相対パスです。**現在の作業ディレクトリ**から `transactions-unsorted.txt` と `accounts.txt` を読み、`accepted.txt` と `rejected.txt` を書きます。
- 2つの出力は `OPEN OUTPUT` で毎回置換します。入力を `build/` に複製してそこで実行し、ソースディレクトリを避けます。`build/` はGit対象外です。

## 入出力レコード

| ファイル | フィールド順 | フィールド幅 | レコード幅 |
|---|---|---:|---:|
| `transactions-unsorted.txt`（入力） | 口座、タイプ、金額数字 | 10 + 1 + 9 | 20 |
| `accounts.txt`（入力） | 口座、顧客、残高数字 | 10 + 8 + 9 | 27 |
| `accepted.txt`（出力） | 口座、顧客、タイプ、金額数字 | 10 + 8 + 1 + 9 | 28 |
| `rejected.txt`（出力） | 口座、理由、タイプ、金額数字 | 10 + 10 + 1 + 9 | 30 |

9桁は `PIC 9(7)V99` を表し、`V` は物理文字を使いません。`000012550` は `125.50` です。1行が1レコードで、改行はFD幅に含まれません。

マスターは `A000000001`、`A000000003`、`A000000005`、`A000000007`、`A000000009` の順です。取引は意図的に未整列です。フィクスチャには有効な一致、マスターなし、不正タイプ、数字以外を含む金額、取引のないマスター口座が含まれます。

拒否理由は10文字です。`NO_ACCOUNT`、`BAD_TYPE__`（アンダースコアで10文字に補完）、`BAD_AMOUNT`。**項目検証より先にマスターを調べます。** マスターにない取引は、タイプや金額も誤っていても `NO_ACCOUNT` です。口座がなければ項目検証に意味がないため、この順序は意図的です。

## 1回の実行で各レコードが進む先

1. メインプログラムは `SORT ... ON ASCENDING KEY SD-TRANSACTION-ACCOUNT` を呼び、整列と分類を一つの流れにします。
2. `1000-LOAD-TRANSACTIONS` が取引入力を開き、各行の実幅を測定します。20文字の行だけ `RELEASE` します。短い行や長い行があればバッチを停止します。
3. `2000-RECONCILE-TRANSACTIONS` がマスターと2つの結果ファイルを開き、最初のマスター行を読みます。
4. 出力手続きは整列済み取引を1件ずつ `RETURN` します。マスターキーが小さければそのマスターは取引なしなので、マスターのみとして数え、次を読みます。キー一致なら検証へ進みます。取引キーが小さい場合、またはマスターを読み終えた場合は、対応マスターなしです。
5. 一致した取引はタイプが `D` / `C`、金額がすべて数字である必要があります。有効行は `accepted.txt`、無効行は理由付きで `rejected.txt` に書きます。
6. 取引処理後、未照合のマスターをマスターのみとして数えます。ファイルを閉じて件数を表示します。整列、読み込み、書き込み、クローズの失敗は非ゼロ戻りコードになります。

## 件数の不変条件：「漏れはないか」を2式で確認

フィクスチャは取引6件、マスター5件です。

| 不変条件 | この例 | 意味 |
|---|---|---|
| `受け入れ件数 + 拒否件数 = 入力件数` | `3 + 3 = 6` | 各取引に行き先が一つある |
| `照合済みマスター件数 + マスターのみ件数 = マスター件数` | `4 + 1 = 5` | 各マスター行を一度処理。照合済み = 入力 − マスターなし拒否 = `6 − 2` |

件数だけでは不十分です。`accepted.txt` は3行、`rejected.txt` も3行であることを確認します。標準出力と2ファイルをまとめて照合してください。集計値だけでは、どの行が欠けたか分かりません。

## エラーと境界

- 取引行は20文字、マスター行は27文字でなければなりません。不一致は非ゼロ終了でバッチを中断し、推測読み込みはしません。
- タイプは大文字 `D` / `C` のみ、金額欄はすべて数字です。
- `OPEN` / `READ` / `WRITE` / `CLOSE` 状態と `SORT` / `RELEASE` / `RETURN` の結果を確認します。EOF状態 `10` は正常終了です。
- 権限やディスク不足で `OPEN OUTPUT` や書き込みに失敗することがあります。**失敗バッチは引き渡し成功ではありません。** 部分結果が残る可能性があります。
- マスターの順序と一意キーは上流が保証します。プログラムは検査せず、同一口座の複数取引にも未対応です。
- 件数項目は3桁で、この小規模例は999件までです。本番規模に応じて幅を再設計します。
- 残高集計、2ファイルの原子性、重複キー方針、ロールバック、バッチID、出力方針はこの課の対象外です。

## 実行して確認する

**入力：** この課の `transactions-unsorted.txt`（6行）と `accounts.txt`（5行）。`build/` へ複製し、そこで実行して結果ファイルを作ります。

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                    # 構文確認のみ
cobc -x -Wall -o build/lesson_22 lesson.cob      # build/ にコンパイル
cp accounts.txt transactions-unsorted.txt build/ # 入力を複製
(cd build && ./lesson_22)                        # そこで実行、結果も同じ場所へ
echo $?                                          # 終了コード確認
rm -rf build                                     # 実行ファイル・複製・結果を削除
```

期待結果：

| 確認項目 | 期待値 |
|---|---|
| `cobc -fsyntax-only` 終了コード | `0` |
| `cobc -x` 終了コード | `0`、コンパイラー診断なし |
| 標準出力 | 下記10行 |
| プロセス終了コード | `0` |
| 作成ファイル | `build/accepted.txt`（3行）、`build/rejected.txt`（3行） |

期待値：構文確認とコンパイルは診断なし、終了コード `0`。標準出力10行、プロセス終了コード `0`。`build/accepted.txt` と `build/rejected.txt` は各3行です。

```text
ACCEPTED 账号=A000000001
ACCEPTED 账号=A000000003
被拒绝 账号=A000000004 REASON=NO_ACCOUNT
ACCEPTED 账号=A000000005
被拒绝 账号=A000000006 REASON=NO_ACCOUNT
被拒绝 账号=A000000007 REASON=BAD_AMOUNT
MASTER_ONLY账户 账号=A000000009
输入记录数=006 排序记录数=006
接受记录数=003
拒绝记录数=003 MASTER_ONLY账户记录数=001
```

`accepted.txt`（3行、各28文字、改行を含め87バイト）：

```text
A000000001C0001001D000012550
A000000003C0001003C000000200
A000000005C0001005D000004000
```

`rejected.txt`（3行、各30文字、改行を含め93バイト）：

```text
A000000004NO_ACCOUNTD000007500
A000000006NO_ACCOUNTX000000100
A000000007BAD_AMOUNTD00000X001
```

`ACCEPTED` と `被拒绝` は同じマージスキャン中に出力するため、口座番号順に混在します。最後の3行が件数です。整列後の取引口座は `001, 003, 004, 005, 006, 007`。`001`、`003`、`005` は有効一致、`004` と `006` は `NO_ACCOUNT`、`007` は金額中の `X` により `BAD_AMOUNT`。マスター `009` はマスターのみです。`3 + 3 = 6`、`4 + 1 = 5` を確認します。

`入力記録数=006 排序記録数=006` は6件すべてが幅検査を通り、ソートへ渡った証拠です。不一致なら `RELEASE` 時点の行幅を調べます。

実行ラベルは英語と中国語が混在します。`ACCEPTED` は受け入れ、`被拒绝` は拒否、`账号` は口座、`REASON=` は拒否理由、`MASTER_ONLY账户` はマスターのみです。残りは各件数です。

この環境では標準エラーに `Warning: program compiled against libxml 212 using older 209` が出ます。リンクライブラリー警告で、業務出力ではありません。原因コンポーネントは特定されていません。

## 変更練習

**フィクスチャ複製**を `build/` に置いて使い、リポジトリーの元ファイルは変更しないでください。結果ファイルは上書きされるため、各実行を新しい複製から始めます。

1. 取引口座 `A000000004` をマスターにある `A000000009` に変更し、他フィールドは保ちます。受け入れファイルへ入り、マスターのみ件数がゼロになり、両ファイルが期待どおりか確認します。
2. 元のフィクスチャから始め、`A000000007` の金額 `00000X001` を `000000001` に変更します。拒否から受け入れへ変わり、マスター行は引き続き照合されることを確認します。

詳細は [`exercise.md`](./exercise.md)、解答例は [`answer.md`](./answer.md)。

## 発展課題

同じ口座に有効な2件目の取引を追加します。一つのマスターレコードで複数取引を処理できる照合ルールを設計し、出力順、残高変化、拒否方針を定めます。同一口座の連続取引、口座欠落、マスターEOF、不正金額をテストします。現行プログラムがどこでマスターを消費し、状態遷移をどう変えるか説明します。全件を `OCCURS` に入れず、実行後の受け入れ・拒否ファイルを提出してください。課題は [`exercise.md`](./exercise.md)。解答はありません。

## 実際の処理フロー

1. **上流：** 取引とマスターは作業ディレクトリに置かれます。読み込みは[第15課](../15_sequential-file-read/README.md)、固定レコードのバイト位置は[第17課](../17_fixed-length-files/README.md)、CSV境界は[第18課](../18_csv-processing/README.md)です。この課はファイルが配置済みであることを前提とします。
2. **この段階：** 取引を整列（[第21課](../21_sort/README.md)）、マスターと昇順キーでマージ（[第20課](../20_file-matching/README.md)）、検証して出力し、件数を報告します。成果物は2つの結果ファイル、マスターのみ一覧、4つの件数です。
3. **拒否明細：** この課は `rejected.txt` を作ります。ファイル書き込みは[第16課](../16_file-writing/README.md)、業務拒否とシステム障害の分離は[第26課](../26_error-handling/README.md)を参照。
4. **ログ：** 現状の件数は画面にしか出ません。[第27課](../27_logging/README.md)で後から調べられるログに記録します。
5. **次の段階：** DBへの結果反映と再実行可能なバッチは[第29課](../29_embedded-sql/README.md)と[第32課](../32_bank-reconciliation-project/README.md)です。

この段階の防護線は `受け入れ + 拒否 = 入力` と `照合済みマスター + マスターのみ = マスター` です。

## 本番でこのコードを使うとしたら

- **スケジューラー：** 2入力の準備完了後、下流の記帳前に起動します。画面ではなく終了コードと生成ファイルを確認します。
- **出力確認者：** 当番担当者は終了コードと受け入れ／拒否／マスターのみの件数、運用担当は翌朝 `rejected.txt`、照合担当は上流件数との一致を確認します。不一致はその夜に調査します。
- **障害対応：** 件数不一致なら照合・検証分岐、部分ファイルならディスク・権限・出力状態を調べます。ロールバックはありません。
- **後続：** `accepted.txt` は記帳、`rejected.txt` は運用確認、マスターのみ一覧は照合、件数はログへ渡します。幅と理由コードはインターフェース契約です。
- **起こりやすい事故：** 行幅不一致で停止、マスター有無より先に項目検証して理由を誤る、終了コード `0` だけを見て行数確認を省き部分出力を渡す、の3つです。
- **未実装：** 残高集計、借貸規則、マスター整列・一意性検査、同一口座複数取引、バッチID、再実行方針、原子的出力、ロールバック、ログです。これらは[第26課](../26_error-handling/README.md)、[第27課](../27_logging/README.md)、第29～32課で補います。

この課が示すのは、フィクスチャ上で読み込み・整列・照合・出力がつながり、件数が整合し、手計算で確認できることです。**本番用会計バッチや原子的引き渡しを保証するものではありません。**
