# 第 08 课：综合练习——把前七课的零件接成一条迷你交易批次

前七课你手里已经攒了一把零件：字段、`MOVE`/`COMPUTE`、`IF`、`EVALUATE`、`PERFORM` 循环、命名段落。这一课不加新零件，只干一件事——把它们接成一条"进来一笔、判一笔、过一笔、记一笔"的处理链，并且让这条链自己报出"一共几笔、收了几笔、拒了几笔"。真实批次里的余额就是这么一笔一笔滚出来的，所以"接得对不对、查得出来吗"就是这份代码能不能交付的分界线。

## 业务现场

凌晨 1 点，日终批次开始跑。白天柜面和手机银行产生的交易，已经被上游按发生顺序排好，等着夜里一笔一笔过账。程序要做的事听起来很朴素：从头往下走，能过账的改余额，不能过账的记下原因，最后报个总数。

但顺序这件事不讲情面。第 3 笔是一张 1500.00 的取款单，它能不能取出来，取决于第 1、2 笔有没有被接受——余额是滚出来的，不是查出来的。这就是为什么这一课不能像前面几课那样"只看一笔"：**前面一笔的结果，是后面一笔的前提。**

我见过的夜间批次事故，很少是某一句话写错。更多是这种情况：跑完了，日志报的总数跟明细差一笔——可没人说得清丢的是哪一笔。所以有经验的组长上线前只问一句话：**"每一笔都有交代吗？"** 你要是能当场拿两个数回答他——"处理 5 笔 = 接受 2 笔 + 拒绝 3 笔"，这一批就过了；答不上来，就得从头翻。

下面场景里的机构、金额、时点都是为教学编的演示材料，不是某家真实机构的真实数据。本课也还没有文件输入，五笔交易写死在程序里（真实文件从[第 15 课](../15_sequential-file-read/README.md)开始）。

## 为什么现在学

你可能会想：`IF` 我写过，`EVALUATE` 我写过，`PERFORM` 我也跑过，五笔交易照着前几课拼一拼不就出来了？这一课是不是纯粹复习？

不是。前面每一课的练习都只让你盯一小段逻辑：判断一笔金额、给一个交易码分类、跑三轮循环。真实批次不给你这种待遇——它是一整串，而且**前一笔的执行结果会改掉后一笔的前提**。

举个具体的。第 3 笔取款能不能过，取决于跑它的时候余额是多少；而余额是第 1、2 笔算出来的。你要是把"余额够不够"的判断挪到"扣余额"后面，或者哪条拒绝路径顺手也改了余额，第 3、4、5 笔的结果会一起歪掉。这种事编译器不拦你，五笔样例也可能看不出差别——但它会让早上 9 点柜面开门时客户看到的余额是错的。

还有一类更隐蔽的坑：分支多起来以后，计数很容易加漏或者加重。余额更新和计数更新必须成对出现在同一条路径上——接受就加接受数、拒绝就加拒绝数，一笔只能落进一边。落不进去或者落进两边，程序不会报错，但月底对账时这笔账就说不清了。

所以这一课用五笔固定样例，把"接起来"最容易踩的四处摆给你看：执行顺序、拒绝不改状态、一笔一个去向、最后计数闭环。

## 这个知识点是什么，它解决什么问题

**这个知识点是什么。** 说白了，这一课不给你新语法。它要你把已经会的六件事接起来：用字段存状态（期初余额、当前余额、交易码、金额、三个计数）、用 `COMPUTE` 改余额、用 `IF` 判金额正负和余额够不够、用 `EVALUATE` 认交易码、用 `PERFORM VARYING` 一笔一笔往下走、用命名段落把流程分成初始化／处理／汇总几块。接完之后再挂上一句能自证清白的话——**计数不变量**：`処理件数 = 承認件数 + 拒否件数`。

**它在业务里解决什么问题。** 它把"每句话都对"升级成"整体能对账"：

- **执行顺序**：余额顺序累积，所以顺序本身就是业务规则，不能随手调整。
- **状态隔离**：拒绝路径只加拒绝计数，绝不碰余额——一笔失败不能污染后面的计算。
- **去向唯一**：一笔交易只能记入接受或拒绝其中一边，不能漏、不能重。
- **可核对**：最后用三个计数把它们锁在一起，任何人拿计算器就能验。

**什么时候该警惕、用错会怎样。** 别把"五笔样例跑通"当成"账务逻辑正确"。样例跑通只说明这一组输入走通了，边界照样可能是错的——比如取款金额**恰好等于**余额时，到底算过还是不过？这题本课练习会让你亲自跑一遍。也别把计数器当装饰：它存在的意义就是让人一句话确认"没漏账"；如果计数摆在那里却没人核对关系，它比没有还危险，因为那会让人以为自己查过了。

## 本课完成后的能力与边界

学完本课后，你可以：

- 用 `WORKING-STORAGE` 字段保存期初余额、当前余额、交易码、带符号金额和三种计数。
- 用 `PERFORM VARYING` 依序处理五笔固定样例，并说清循环的起止边界。
- 用 `EVALUATE` 按交易码选择存款、取款或未知代码路径，用嵌套 `IF` 校验正金额与可用余额。
- 逐笔追踪每笔交易对共享余额和计数的影响，并用计数不变量 `処理件数 = 承認件数 + 拒否件数` 核对有没有漏账。
- 把初始化、样例装载、交易处理和汇总组织成可调用的命名段落。

边界：样例数据直接写在 `2100-LOAD-SAMPLE` 里，程序不读终端、文件或数据库；没有持久化状态，重复运行结果完全相同。生产账务需要的文件状态、审计、并发和重启策略不在本课范围内，见第 15 课以后与[第 26 课](../26_error-handling/README.md)。

## 运行环境

- GnuCOBOL 3.2.0，默认方言（不加 `-std=cobol85`），源文件为固定格式。
- Linux 终端；本课不依赖数据库或附加工具。
- 无输入夹具、无输出数据文件；编译产物写在 `build/`，可以直接删掉重来。

## 五笔样例和判定规则

程序从 `1000.00` 开始，按样例编号处理五笔固定交易：

| 编号 | 代码 | 金额 | 处理规则 | 余额变化 |
|---|---|---:|---|---:|
| 001 | `D` | 125.50 | 正数存款，接受 | 1000.00 → 1125.50 |
| 002 | `W` | 40.10 | 正数取款且余额足够，接受 | 1125.50 → 1085.40 |
| 003 | `W` | 1500.00 | 金额大于当前余额，拒绝 | 不变 |
| 004 | `D` | -5.00 | 存款金额不是正数，拒绝 | 不变 |
| 005 | `X` | 25.00 | 未知代码，拒绝 | 不变 |

这三笔拒绝各有各的理由（余额不足、金额非正、代码不认识），output 里也是三个不同的理由代码——**拒绝也要说清为什么**，不然回查的人只能靠猜。

计数不变量：`処理件数 = 承認件数 + 拒否件数`，本课为 `5 = 2 + 3`。

再交代一遍边界：这是用来练控制流程的批次，五笔样例是写在程序里的固定数据（演示数据），不是从外部文件读到的真实交易。程序也没有实现生产账务需要的持久化、审计、并发或重启规则。

## 程序里谁管什么

完整源码见 [`lesson.cob`](./lesson.cob)。它用独立字段保存期初余额、当前余额、交易码、带独立符号的金额、样例序号以及三种计数。金额统一两个小数位，存储和计算行为以本平台的 GnuCOBOL 实测为准。

| 段落 | 职责 | 关键语句 |
|---|---|---|
| `0000-MAIN` | 按顺序调用初始化、批次处理和汇总 | `PERFORM`、`STOP RUN` |
| `1000-INITIALIZE` | 设置当前余额并清零计数 | `MOVE` |
| `2000-PROCESS-BATCH` | 从 1 循环到最后一个样例，装载并处理每笔交易 | `PERFORM VARYING`、段落 `PERFORM` |
| `2100-LOAD-SAMPLE` | 将序号映射为交易码和金额 | `EVALUATE`、`MOVE` |
| `2200-CLASSIFY-AND-POST` | 按代码验证交易并更新余额或拒绝计数 | `EVALUATE`、嵌套 `IF`、`COMPUTE` |
| `9000-REPORT` | 输出处理数、结果数和最终余额 | `DISPLAY` |

这六个段落**共用同一组 `WORKING-STORAGE` 字段**——这就是它们能"接力"的原因，也是本课要小心的地方：任何一段改了余额，后面所有段落看到的都是改过的值。处理每一笔时，外层循环先调用装载段落，再调用分类处理段落，最后把处理计数加一。被 `PERFORM` 调用的段落执行完，控制权回到调用点，循环接着走下一笔。

顺带提一句 `2100-LOAD-SAMPLE` 的 `WHEN OTHER`：它是给"序号超出样例范围"兜底的。本课上界是 5、样例也是 5，兜底分支用不上；但只要有人把上界改了而忘了加样例，它会替你接住，而不是让程序拿着上一笔的残值继续算——第 06 课已经让你踩过这个坑。

## 一笔一笔看它怎么走

1. 主段落先执行 `1000-INITIALIZE`：当前余额设为期初余额，三个计数清零，然后打印批次开始和期初余额。
2. `PERFORM VARYING` 把序号从 1 递增到 5。上界比较写的是 `WS-SAMPLE-INDEX > WS-LAST-SAMPLE`，所以序号 5 那一笔也会被处理（这就是第 06 课的"严格大于"边界）。
3. `2100-LOAD-SAMPLE` 用 `EVALUATE` 按序号装入代码和金额，并打印这笔的原文。
4. `2200-CLASSIFY-AND-POST` 先按代码选路：`D` 存款、`W` 取款、其他一律进 `WHEN OTHER`。
5. 存款只有金额大于零才加进余额并增加接受数；金额非正就进拒绝计数。
6. 取款是两层判断：先看金额大于零，再看金额小于或等于当前余额。两个都满足才扣款——**恰好相等也允许**，余额会变成零；否则按余额不足拒绝。
7. 未知代码增加拒绝计数，理由记为 `UNKNOWN_TRANSACTION_CODE`。
8. 每笔处理完，外层循环恰好加一次处理计数——加在循环体里，不在任何分支里，所以不会漏加也不会重复加。
9. 循环结束后主段落调用 `9000-REPORT`：五笔里两笔接受、三笔拒绝，最终余额 `1085.40`。

交易处理次序是业务规则的一部分：每笔已接受的交易都会影响后面取款的可用余额。拒绝路径不修改余额。

## 运行与观察

程序不读终端、文件、命令行参数或数据库，也不生成数据文件，所以在哪个目录跑结果都一样。下面按本课目录说明。

**输入：** 无外部输入。五笔样例是 `2100-LOAD-SAMPLE` 里的程序内固定数据。

**命令及作用：**

```sh
mkdir -p build
cobc -fsyntax-only lesson.cob                  # 只做语法检查，不生成可执行文件
cobc -x -Wall -o build/lesson_08 lesson.cob    # 编译并生成可执行文件
./build/lesson_08                              # 运行程序，输出写到标准输出
echo $?                                        # 查看退出码
rm -rf build                                   # 清理生成的可执行文件
```

**预期结果：**

| 观察项 | 预期值 |
|---|---|
| `cobc -fsyntax-only` 退出码 | `0` |
| `cobc -x` 退出码 | `0`，无编译诊断 |
| 标准输出 | 16 行，见下方代码块 |
| 进程退出码 | `0` |

```text
バッチ=START
期首残高=0001000.00
レコード=001 符号=D 金額=+00125.50
結果=ACCEPTED 理由=DEPOSIT
レコード=002 符号=W 金額=+00040.10
結果=ACCEPTED 理由=WITHDRAWAL
レコード=003 符号=W 金額=+01500.00
結果=REJECTED 理由=INSUFFICIENT_FUNDS
レコード=004 符号=D 金額=-00005.00
結果=REJECTED 理由=AMOUNT_NOT_POSITIVE
レコード=005 符号=X 金額=+00025.00
結果=REJECTED 理由=UNKNOWN_TRANSACTION_CODE
処理件数=005
承認件数=002
拒否件数=003
最終残高=0001085.40
```

**别光看最后一行，自己口算一遍：** `1000.00 + 125.50 = 1125.50`，`1125.50 - 40.10 = 1085.40`；后面三笔全进拒绝，一分钱都不动余额。然后核对数目：5 笔进、5 笔出，`2 + 3 = 5`。这两步都能在纸上算完——如果哪天上线前你算不出来，就是这段逻辑还没接对。

**输出字段对照（日文输出 → 含义）：** `バッチ=START` = 批次开始；`期首残高` = 期初余额；`レコード` = 样例序号；`符号` = 交易码；`金額` = 交易金额；`結果` = 接受/拒绝；`理由` = 判定理由代码；`処理件数` / `承認件数` / `拒否件数` = 处理/接受/拒绝件数；`最終残高` = 最终余额。

金额的前导零和正负号来自字段 `PIC` 和 `SIGN IS LEADING SEPARATE CHARACTER` 的显示格式；`V` 只是隐含的小数点位置，显示时省略。余额字段是 `PIC 9(7)V99`，所以 `1085.40` 显示成 `0001085.40`。

**未验证项（照旧挂着）：** 在本工作区运行可执行文件时，标准错误上会多出一行 `Warning: program compiled against libxml 212 using older 209`。这是运行环境的链接库版本警告，不是本程序打印的业务内容；**为什么没验证**：产生它的组件还没定位，本课也不需要它就能核对业务结果。真正的输出在标准输出，退出码是 `0`。

## 修改练习

两项修改各自从原始 [`lesson.cob`](./lesson.cob) 开始，**不要叠加**；每次都要看完整输出，别只盯最后一行余额。

1. 把 `WS-OPENING-BALANCE` 的初值从 `1000.00` 改成 `2000.00`，编译运行，记录 `処理件数`、`承認件数`、`拒否件数` 和 `最終残高`。做完想一想：翻盘的其实只有第 003 笔——期初一改，后面取款能用的余额就跟着变，这就是"顺序累积"的直白后果。
2. 把样例 003 的取款额从 `1500.00` 改成 `1085.40`，编译运行，确认"金额恰好等于处理到该笔时的余额"到底走接受还是拒绝，并记下最终余额和两个结果计数。这是本课最该亲手跑一次的边界。

完整题目与预期见 [`exercise.md`](./exercise.md)，参考答案见 [`answer.md`](./answer.md)。

## 举一反三练习

扩展批次，让它能处理第六笔固定交易：自己挑交易码和金额，说清它应该被接受还是拒绝，并逐笔写出余额变化和最终的三项计数。要求至少包含一次"取款金额恰好等于当前余额"的边界，并确认 `処理件数` 只按实际处理的交易数增加。别只改数据忘了同步最后样例序号和装载逻辑。仍然用固定样例，不要引入文件、表格或数据库。题目见 [`exercise.md`](./exercise.md)，本题不提供答案。

## 走一遍真实流程

把本课这条链放进那个凌晨 1 点的批次，它前后是这样接的：

1. **上游送数据进来。** 本课的数据写死在程序里；真实批次里它来自文件——[第 15 课](../15_sequential-file-read/README.md)你第一次亲手打开文件读交易，[第 17](../17_fixed-length-files/README.md)/[18 课](../18_csv-processing/README.md)处理定长记录和 CSV。
2. **本课这一环。** 一笔一笔判定：能过账的改余额，不能过账的带理由挑出来。这一环的产物就是"接受/拒绝 + 理由 + 三个计数"。
3. **拒绝的那部分要单独送出去。** 拒绝明细写成文件是[第 16 课](../16_file-writing/README.md)的活；以后接电话问"我昨天那笔为什么没到账"的人，查的就是那个文件。
4. **数字要留痕。** 批次开始/结束和拒绝明细写进日志是[第 27 课](../27_logging/README.md)；区分"业务拒绝"和"系统故障"（什么时候该报警、什么时候只是拒一笔）是[第 26 课](../26_error-handling/README.md)。
5. **最后汇总。** 余额和状态要落进数据库，是[第 29 课](../29_embedded-sql/README.md)往后的事；整条夜链串成一个能对账的项目，是[第 32 课](../32_bank-reconciliation-project/README.md)。

同一条链上，"计数对不上"这件事必须有一句能查的话——本课这句就是 `処理件数 = 承認件数 + 拒否件数`。

## 这份代码进了生产会怎样

- **谁调度它**：夜间批处理调度器，通常排在"文件就绪检查"之后、日终汇总之前。它不看你屏幕，只看退出码。
- **谁看它的输出**：值班的人先看退出码，再看三个计数。数不对，当晚就得查，不能等到早上柜面开门。
- **下一个系统怎么接**：在真实系统里，这一环决定余额往哪儿走，紧接着的报表和客户查询都基于它；本课只把结果打在屏幕上，还没有交给任何下游。
- **第一个月最容易出的事故**：不是语法错误，而是"接错线"——某条拒绝路径碰了余额、计数加漏或加重、或者把判断顺序调换导致后续交易全歪。这类错在五笔样例上可能只差一点点，到了几万笔就是一笔说不清的账。
- **它还没做的事**：读文件、校验记录、写结果文件、区分业务拒绝与系统故障、持久化和重跑。它也没有账户授权、并发控制和重复请求检测。这些分别从第 15、16、26、29 课开始补。

把话说清楚：本课证明的是"内存里的顺序规则接对了、计数能闭环、结果能手算核对"，**不是**"这是一套已验证的账务系统"。
