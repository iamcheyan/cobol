# 第 31 課：データ同期——ファイルスナップショットとデータベーススナップショットは何が違うのか

銀行は夜間に口座変更を固定長スナップショットファイルとして出力し、システムのプライマリデータベース（本課では SQLite）には口座の基準スナップショットが保存されています。本課では実際にバッチを動かし、ファイルのスナップショットを 1 行ずつ読み、口座の主キーで `ACCOUNT_SNAPSHOT` を検索し、各ファイルレコードを `MATCH` / `CHANGED` / `FILE_ONLY` に分類して `RECON_RESULT` に書き込みます。不一致のレコードは `differences.txt` にも出力します。件数の不変条件、再実行時の挙動、失敗後に残る状態についても説明します。

## 業務現場

朝 8 時、業務部門の担当者が数字の合わない 2 つの表を持ってきて、いつも同じ質問をします。

> **「両方の数字が違うのはなぜですか？」**

一方は上流システムが出力した口座ファイル、もう一方はシステムのプライマリデータベースにある口座スナップショットです。「一致しません」というだけでは答えになりません。相手が知りたいのは、次の 3 つのどれなのかです。ファイルにはあるがデータベースにはない、両方にあるが金額または顧客番号が違う、データベースにはあるがファイルにはまったく記載がない。最初の 2 種類は上流データの修正が必要です。3 つ目は、上流で一部のデータを出力し忘れた可能性があります。必要な対応はまったく異なるため、「合いません」とひとまとめにしても何も伝わりません。

そのため照合プログラムには 2 つの仕事があります。1 つ目は、ファイルの各レコードを 3 種類のいずれかに分類し、口座番号から追跡できるよう結果テーブルに記録すること。2 つ目は、不一致を別の差異一覧に保存し、業務部門や運用担当者が調査できるようにすることです。一覧を作るだけで問題が解決するわけではありませんが、これがなければ 2 つの表を開いて 1 行ずつ見比べることになります。

もう 1 つ、先に明言しておくべき事実があります。このバッチは**原子的ではありません**。SQL が途中で失敗しても、それ以前の `INSERT` はすでに反映されており、自動では取り消されません。初期状態に戻すには、先頭からバッチを再実行します（`./build.sh run` がデータベースを削除して再作成し、期初残高から再計算します）。これはロールバックではありません。本課ではこの境界を実際に確かめ、再実行後に何が残るかを説明します。受け入れ確認では、障害が起きてから話すのではなく、コードを書いた人が先に説明しておくべき内容です。

## なぜ今これを学ぶか

検索して比べるだけなら、難しくないのではと思うかもしれません。

1 件を検索する方法はすでに学びました。第 29 課では `SELECT ... INTO` で SQLite から主キーを指定して 1 行取得し、第 30 課ではカーソルを使って口座テーブル全体を 1 行ずつ読みました。しかし、この 2 つを組み合わせると新たに 3 つの問題が出てきます。

1. **不一致にはどんな種類があり、それぞれどこへ出すのか。** ファイルにあってデータベースにない、両方にあるが値が異なる、データベースにあるがファイルにない。この 3 種類をすべて「エラー」と呼ぶことはできず、出力先も異なります。判定結果を記録する状態フィールドが必要です。
2. **1 件も漏らしていないと、どう確認するのか。** 夜間バッチの翌朝に、誰かが数字を照合します。「処理件数、3 分類それぞれの件数、差異ファイルの行数」が互いに計算で確かめられる必要があります。これが本課の件数不変条件です。
3. **処理に失敗したらどうするのか。** 挿入が途中で失敗した場合、それ以前に書いたデータは有効なのでしょうか。これは構文の問題ではなく、復旧境界の問題です。

第 20 課では、2 つのファイルを昇順に並べ、ポインターを進めながら照合する方法を学びました。そのときは両側ともファイルでした。本課では一方がファイル、もう一方がデータベースであり、主キー検索を行います。そのため、ファイル自体がソート済みかどうかはプログラムの正しさに影響しません。これが第 20 課との最も大きな違いです。

## この知識項目とは何か、どんな問題を解決するのか

**この知識項目とは。** 簡単に言うと、「ファイルの 1 レコードとデータベースの 1 口座を一緒に見る」ことです。固定幅スナップショット行から口座番号、顧客番号、金額を切り出し、口座番号を使ってデータベースを主キー検索します。行が見つかれば顧客番号と金額を比較し、見つからなければファイル側のみと判定します。判定結果を状態フィールドに入れ、結果テーブルに 1 行書き込みます。

**業務上どんな問題を解決するのか。** 「両方の数字が違うのはなぜか」という問いを、指し示すことができ、集計もできる 3 種類の結果に変えます。具体的には、次の 3 つの効果があります。

- 業務部門や運用担当者は、口座番号から「このレコードがどうなったか」を調べられます。バッチを再実行して推測する必要はありません。
- 3 分類の集計を合計するとファイル行数に一致するため、1 件の漏れもその夜のうちに見つけられます。
- 不一致一覧を別ファイルに出すので、上流への照会にそのまま使えます。

**使うべきでない場面と、誤用したときの問題。** 本課が行うのは**片方向**の照合です。ファイルを起点にし、ファイルの各行からデータベースを検索します。データベースにはあるもののファイルにはない口座は、本課では**確認も出力もしません**（`DB_ONLY` 分類はありません）。両側全体を照合する用途に使うと、3 つ目の不一致が何も出ないまま見落とされます。これは本課が意図的に残している範囲外です。補うには第 30 課のカーソルで逆方向にも走査します。もう 1 つの注意点は単位です。ファイルの金額は「分（フェン）」、データベースの金額は「元（ユアン）」です。比較前に単位を変換してください。文字列のまま比較すると、`00100.00` と `100` は異なるものと判定され、差異一覧が誤った不一致だらけになります。

## 本課を終えた後にできることと、その範囲

本課を終えると、次のことができるようになります。

- 27 バイトの固定長スナップショットから口座番号（10）、顧客番号（8）、金額（分、9）を切り出し、比較前に分をデータベースの元に換算する理由を説明できる。
- `EVALUATE SQLCODE` を使って 3 種類の結果を分けられる。`0` は口座が見つかり `MATCH` / `CHANGED` を判定したこと、`100` はファイル側のみ（`FILE_ONLY`）であること、その他の値はシステム障害として処理を中止し、0 以外の終了コードを返すことを示す。
- ファイルレコードごとに 1 行を `RECON_RESULT` に書き、`CHANGED` / `FILE_ONLY` を `differences.txt` に追加し、件数不変条件を使って「ファイル行数 = 結果テーブル行数 = 3 分類の合計」を確認できる。
- 再実行時の挙動を説明し再現できる。`./build.sh run` はデータベースを再作成するため繰り返し実行できる。一方、同じデータベースに実行ファイルを直接再実行すると主キー競合により終了コード `1` で終了する。
- 本課で**行わない**ことを説明できる。データベースのみの口座を走査しない（`DB_ONLY` 分類なし）、`ACCOUNT_SNAPSHOT` を変更しない、口座残高を更新しない、トランザクションとロールバックを実装しない。

範囲：本課は**片方向**の照合（ファイル → データベース）です。`RECON_RESULT` に記録するのはファイル側の状態であり、口座マスタを更新するものではありません。サンプルデータベースはローカル SQLite ファイルで、実際の SQL エンジンとファイルを使いますが、Oracle / PostgreSQL / DB2 のトランザクション動作や並行実行時の挙動を示すものでは**ありません**。ツールチェーンの検証環境は x86-64 Linux + GixSQL v1.0.20b のみです。

## 入力とルール

### ファイル側スナップショット：`snapshot.txt`

| 列 | フィールド | 幅 | 説明 |
|---|---|---:|---|
| 1–10 | 口座番号 | 10 | `ACCOUNT_SNAPSHOT.ACCOUNT_NO` に対応 |
| 11–18 | 顧客番号 | 8 | `CUSTOMER_ID` に対応 |
| 19–27 | 金額（銭） | 9 | 小数点を含まない値：`0000125075` = `1250.75` |

各行は区切り文字のない 1 レコードです。`FD` のレコード幅は 27 バイトで、改行は幅に含みません。プログラムは**行長を検証しない**ため、長さによって挙動が異なります。

- ちょうど 27 バイト：通常どおり処理します。
- 27 バイト未満：GnuCOBOL が空白で補い、第 19～27 列は空白になります。金額フィールドが数値でなくなるため、システム障害として処理を中止します（終了コード `1`）。空行も同様で、口座番号の表示は空白になります。
- 27 バイトを超える：`READ` がファイル状態 `06` を返し、システム障害として処理を中止します（終了コード `1`）。

金額フィールドは数字でなければなりません。数字以外が含まれる場合、業務上の拒否として扱わず、状態 `1` でバッチを失敗させます。入力不正であって、業務判断ではないためです。キーの昇順は**レビュー上の前提にすぎません**（検索はデータベースの主キーを使うため、順序に依存しません）。キーの一意性は上流が保証し、プログラムは重複チェックをしません。重複キーは結果テーブルへの書き込み時に主キー制約で止まります（「失敗、残留状態、復旧境界」を参照）。

### データベースのテーブルとキー（`schema.sql`）

```sql
CREATE TABLE ACCOUNT_SNAPSHOT (      -- 基准快照，来源表
    ACCOUNT_NO  TEXT PRIMARY KEY,    -- 主键：每个账号最多查到一行
    CUSTOMER_ID TEXT NOT NULL,
    BALANCE     NUMERIC NOT NULL     -- 单位：元
);
CREATE TABLE RECON_RESULT (          -- 核对结果，按文件键写回
    ACCOUNT_NO    TEXT PRIMARY KEY,  -- 每个文件键最多一行，重复即冲突
    FILE_STATUS   TEXT NOT NULL,
    FILE_CUSTOMER TEXT NOT NULL,
    FILE_BALANCE  NUMERIC NOT NULL
);
```

デモ用データベースは `run` のたびに再作成されます。`ACCOUNT_SNAPSHOT` は常に 2 行から始まります。`A000000001` / `C0001001` / `1250.75` と `A000000002` / `C0001002` / `875.00` です。`RECON_RESULT` は空の状態から始まります。フィクスチャにはビルド時の件数上限が 1 つあります。カウンターは `PIC 9(3)` なので、この小さなフィクスチャで扱えるのは最大 999 行です。

![各ファイル行は MATCH・CHANGED・FILE_ONLY のいずれか 1 つに必ず入る（相互排他かつ網羅）。DB にしか無い口座はこの課では検出しない、意図的な境界](assets/reconcile-classes.svg)


| 条件 | 判定 | カウント | `differences.txt` に書くか |
|---|---|---|---|
| `SQLCODE = 0`、顧客番号と金額が両方一致 | `MATCH` | 一致 | いいえ |
| `SQLCODE = 0`、顧客番号または金額の少なくとも一方が異なる | `CHANGED` | 変更 | はい |
| `SQLCODE = 100`（一致する口座なし） | `FILE_ONLY` | ファイルのみ | はい |
| その他の `SQLCODE` | システム障害、失敗フラグを設定 | — | — |

金額の比較は**数値比較**です。ファイル側の分を 100 で割って元に換算し、`BALANCE` と比較します。文字列比較はしません。顧客番号は 8 バイト固定長文字列として比較します。データベースのみの口座（`ACCOUNT_SNAPSHOT` にはあるがファイルにはない口座）は、**比較せず、出力もありません**。これは本課で明確に定めた範囲であり、実装漏れではありません。

注意点は 3 つあります。`FILE_STATUS` は 10 文字の固定長フィールドで、末尾に空白が付いた状態で保存されます（`MATCH     `）。`FILE_BALANCE` は数値列であり、SQLite の NUMERIC 親和性により `100.00` は `100` として保存されます（値は変わらず、表示形式だけが変わります）。ファイル側の金額 `000010000`（分）は結果テーブルでは `100`（元）になります。

## 件数不変条件と再実行時の挙動

本課のフィクスチャはファイル 3 行、`ACCOUNT_SNAPSHOT` 2 行です。

| 不変条件 | 本課での計算 | 意味 |
|---|---|---|
| ファイル行数 = `RECON_RESULT` 行数 | `3 = 3` | ファイルの各レコードに結果行が 1 行ずつ残り、重複も漏れもない |
| `一致 + 変更 + ファイルのみ` = ファイル行数 | `1 + 1 + 1 = 3` | 3 分類は互いに重ならず、全件を網羅する |
| `differences.txt` の行数 = `変更 + ファイルのみ` | `2 = 1 + 1` | 差異ファイルの行数と分類件数が一致する |
| データベースのみの口座数 = `ACCOUNT_SNAPSHOT` 行数 −（`一致 + 変更`） | `2 − 2 = 0` | 本課は `DB_ONLY` を検出しない。今回のフィクスチャには該当口座がない |

4 つ目は本課の**範囲外項目**であり、達成項目ではありません。`ACCOUNT_SNAPSHOT` に `A000000099` を追加して再実行しても、標準出力と差異ファイルはベースラインと完全に同じで、結果テーブルも 3 行のままです。その口座はどの出力にも現れません（実測。次節参照）。検出するには第 30 課のカーソルで逆方向に走査する必要があります。「発展演習」を参照してください。

**再実行時の挙動：**

- `./build.sh run` は実行のたびに `build/lesson31.db` を削除し、`schema.sql` で再作成します。同じフィクスチャで繰り返せば、標準出力と差異ファイルは行単位で同じになります。`OPEN OUTPUT` は `differences.txt` を切り詰めて作り直すため、前回の行が蓄積されません。
- データベースを再作成せず、**同じ**データベースに実行ファイルを直接再実行すると、冪等ではありません。最初のレコードの `INSERT` が `RECON_RESULT` の主キーと競合します。バッチは `エラー=挿入 SQLSTATE=HY000`、`集計 行数=001` を出して終了コード `1` で終了します。初回実行の結果 3 行は**データベースに残ったまま**であり、今回の実行で `differences.txt` は 0 バイトに切り詰められます。

**原子性について（正確に理解すること）：** プログラムには `COMMIT`、`ROLLBACK`、バッチ ID、復旧マーカーがありません。GixSQL は SQL 文を 1 つずつ実行するため、失敗時には**それ以前の文がすでに反映されています**。表の「部分反映」がその証拠です。バッチの終了コードは `1` ですが、今回新たに挿入された 2 行がデータベースに残っています。したがって、本課を原子的なコミットとして説明したり、失敗すれば自動でロールバックされると断言したりしてはいけません。

失敗後に使える復旧方法は 2 つだけで、いずれも外部操作が必要です。`./build.sh run` を再実行してデータベースを削除・再作成し、きれいなフィクスチャに戻すか、運用手順で `RECON_RESULT` を明示的に空にします。実際のバッチにはトランザクション境界、バッチ識別子、再入可能な設計が必要です。これらは第 32 課の総合課題の範囲であり、本課では実装しません。

## ソースコードを読む順序

「データと状態がどう変わるか」の順に読みます。2 つのデータの流れが合流する箇所が要点です。

1. **`FILE-CONTROL` / `FILE SECTION`**：`SNAPSHOT-FILE`（読み取り、27 バイト、`LINE SEQUENTIAL`）と `DIFFERENCE-FILE`（書き込み、80 バイト）は、それぞれ `FILE STATUS` フィールドに結び付いています。以降の各 I/O 操作はこの値で成功を判定します。
2. **`MAIN-PROCEDURE`**：入力 → 差異ファイル → データベースの順で開きます。どこかで失敗すると、後続の業務処理を飛ばします。クローズ時は実際に開いたリソースだけを閉じます。最後に**切断前に件数を表示**し、切断の失敗も失敗フラグに反映します。
3. **`3000-RECONCILE-ROW`**：`SNAPSHOT-RECORD(1:10)`、`(11:8)`、`(19:9)` がファイル側フィールドの切り出し位置です。`FUNCTION NUMVAL(...) / 100` が分から元への換算で、数字以外は `エラー=不正残高` の分岐に進みます。
4. **`3100-LOOKUP-ACCOUNT`**：まずホスト変数をクリアします（`SQLCODE 100` のとき、ドライバーは受け取り項目を書き換えないため）。次に `:WS-ACCOUNT` を `WHERE` 条件にした `SELECT ... INTO` を実行します。`EVALUATE SQLCODE` の `0 / 100 / OTHER` が 3 つの業務経路です。
5. **`4000-WRITE-RESULT`**：データベースへの書き込み箇所は `INSERT INTO RECON_RESULT` です。挿入が成功した後にだけ、表示行と差異行を組み立てます。ファイルへの書き込み箇所は `IF WS-STATUS NOT = "MATCH"` の後にある `WRITE DIFFERENCE-RECORD` です。
6. **`9000-DISCONNECT-DATABASE`**：`CONNECT RESET` の後に `SQLCODE` を確認し、失敗時には `STOP RUN RETURNING 1` を実行します。

2 つの流れは `3100` で合流します。ファイル側の項目は `3000` で分割し、データベース側の列は `SELECT ... INTO` で取得し、`3100` の `IF WS-CUSTOMER = WS-DB-CUSTOMER AND WS-BALANCE = WS-DB-BALANCE` で比較します。

## 実際の業務フローをたどる

このバッチを照合処理全体の中に置いてみます。

1. 上流システムは夜間に当日の口座を `snapshot.txt` に出力し、共有ディレクトリに置きます。本課ではそのファイルを読みます。固定長形式と行境界は第 17 課の内容です。
2. システムのプライマリデータベースにある `ACCOUNT_SNAPSHOT` は「基準バージョン」です。第 29 課では接続方法と `SELECT ... INTO` による 1 行の取得を、第 30 課ではカーソルによるテーブル全体の走査を学びました。
3. 本課のプログラムは両側を合わせ、各行を判定して `RECON_RESULT` に書き込み、不一致を `differences.txt` に取り出します。
4. 差異ファイルは業務部門や上流に渡して調査に使い、`RECON_RESULT` は口座番号から状態を追跡する場所になります。
5. データベースにだけある口座も検出するには、逆方向にカーソル走査を追加します。第 30 課のカーソルと本課の判定ロジックを組み合わせれば実現できます。
6. トランザクション境界、バッチ識別子、再実行設計を備えた一連のプロジェクトにする方法は、第 32 課の総合課題を参照してください。

差異ファイルがあれば、手作業での照合を大幅に減らせます。なければ業務部門が 2 つの表を開き、1 行ずつ確認することになります。見栄えの良さではなく、口座番号から各レコードをすぐに特定できることが価値です。

## このコードが本番に入ったら

- **誰がスケジュールするか：** 通常は、ファイル準備確認と上流の出力処理の後に夜間バッチスケジューラーが起動します。
- **誰が出力を見るか：** 当直担当者がまず終了コードを確認し、次に集計行の件数を見ます。3 つの件数が合わなければ、その夜のうちに調査が必要です。
- **後続システムはどう受け取るか：** `differences.txt` は業務部門または上流システムに渡し、下流のレポートや手動検索では `RECON_RESULT` を参照します。
- **最初の 1 か月に起きやすい障害：** 金額が数字でないときに「処理を続ける」ように変更してしまう（本課の実装は正しく中止しますが、実際のプログラムでは誤って改変されることがあります）、または分から元への換算を忘れ、すべての行が `CHANGED` と判定されることです。差異一覧が不要な行で埋まり、業務部門は 1 日かけても確認しきれません。
- **まだ実装していないこと：** データベースのみの口座、重複キーとキー形式の検証、トランザクションまたは再入可能な再実行設計、バッチ ID と監査情報、差異ファイルの引き渡しと保管方針は、本課では明確に未実装です。ファイル照合は第 20 課、エラーの振り分けは第 26 課、カーソルは第 30 課、全体課題は第 32 課で扱います。

本課は、この照合フローにおける**最小の実行可能版**です。実ファイル、実際の SQLite、実際の SQL を使い、結果テーブルと差異ファイルをレコード単位で照合でき、失敗経路も観察できます。動作することと、本番投入できることは別です。
